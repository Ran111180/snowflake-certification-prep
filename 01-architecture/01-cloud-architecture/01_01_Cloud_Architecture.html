1. Architecture Overview

What Makes Snowflake Unique?

Snowflake is a cloud-native, SaaS data platform built from scratch for the cloud. Unlike traditional databases that were retrofitted for cloud deployment, Snowflake was designed with three fundamental principles:

Key Architecture Principles:
  1. Multi-Cluster Shared Data - Multiple compute clusters share a single copy of data
  2. Separation of Concerns - Storage, Compute, and Services are independent layers
  3. Cloud-Agnostic Design - Runs identically on AWS, Azure, and GCP

USE SCHEMA CERT_STUDY_DB.ARCHITECTURE;

-- Create a table and load data to see micro-partitions
CREATE OR REPLACE TABLE sample_data AS
SELECT 
  SEQ4() AS id,
  UNIFORM(1, 1000, RANDOM()) AS amount,
  DATEADD(day, UNIFORM(1, 365, RANDOM()), '2024-01-01')::DATE AS order_date,
  ARRAY_CONSTRUCT('Electronics','Clothing','Food','Books','Sports')

-- Check table storage metrics (micro-partitions!)
SELECT 
  TABLE_NAME,
  ROW_COUNT,
  BYTES,
  BYTES / (1024*1024) AS size_mb,
  CLUSTERING_KEY
FROM INFORMATION_SCHEMA.TABLES
WHERE TABLE_SCHEMA = 'ARCHITECTURE' AND TABLE_NAME = 'SAMPLE_DATA';

-- See micro-partition details
SELECT SYSTEM$CLUSTERING_INFORMATION('sample_data');

-- Query result cache demonstration

Script 5: Resource Monitor (Cost Control)

-- Create a resource monitor to track credit usage
-- (Requires ACCOUNTADMIN role)

CREATE OR REPLACE RESOURCE MONITOR cert_study_monitor
  WITH CREDIT_QUOTA = 10
  FREQUENCY = MONTHLY
  START_TIMESTAMP = IMMEDIATELY

6. Interview & Certification Q&A

Q1: What is Snowflake's architecture called and why?

A: Multi-Cluster Shared Data Architecture. "Shared Data" because all compute clusters access the same centralized data in cloud object storage. "Multi-Cluster" because multiple independent virtual warehouses can operate simultaneously without resource contention. This hybrid approach combines benefits of shared-disk (single data copy, no data movement) and shared-nothing (independent scaling, no contention).

Q2: What are the three main layers of Snowflake? Explain each.

A:

  1. Storage Layer - Stores data in a proprietary columnar format as immutable micro-partitions (50-500 MB) in cloud object storage (S3/Blob/GCS). Data is always compressed and encrypted (AES-256).
  2. Compute Layer - Virtual warehouses (MPP clusters) that execute queries. Warehouses are independent, can be resized, and scale independently of storage. They have local SSD cache.
  3. Cloud Services Layer - The "brain" handling authentication, query optimization, metadata, transaction management, and result caching. Runs 24/7, shared across accounts in a region.
Q3: How do micro-partitions work?

A: When data is loaded, Snowflake automatically divides it into micro-partitions of 50-500 MB (compressed). Each partition stores data in columnar format and is immutable. Snowflake maintains metadata (min/max values, NULL count, distinct values) for each column in each partition. This enables partition pruning - where the query optimizer skips partitions that can't contain relevant data based on WHERE clause predicates.

Q4: What's the difference between scaling UP vs scaling OUT?

A:

  • Scale UP = Increase warehouse size (XS to S to M...). Better for complex queries that need more compute power. Each size doubles nodes and credits.
  • Scale OUT = Multi-cluster warehouse (add more clusters of the same size). Better for handling concurrency (many users/queries simultaneously). Requires Enterprise edition.
Q5: Does Snowflake require capacity planning?

A: No. Unlike traditional databases, Snowflake requires minimal capacity planning because:

  • Storage automatically expands (cloud object storage is virtually unlimited)
  • Compute can be instantly resized or scaled out
  • No indexes to maintain or partitions to manually manage
  • Auto-suspend/resume handles idle periods
However, users should plan warehouse sizes for different workloads and set resource monitors for cost control.

Q6: What happens when a warehouse is suspended?

A: When a warehouse is suspended: it stops consuming credits, its local SSD cache is dropped, and running queries finish (or are canceled depending on settings). When it resumes, it starts fresh with an empty cache. The warehouse auto-resumes when a query is submitted (if AUTO_RESUME = TRUE).

Q7: What is the result cache and when is it used?

A: The result cache is in the Cloud Services layer and stores query results for 24 hours. It's used when:

  • Same query text is submitted by the same role
  • Underlying data hasn't changed
  • Same role context (same database/schema/warehouse isn't required)
Result cache queries consume NO warehouse credits - they're served directly from Cloud Services. The cache persists even if the warehouse is suspended.

Q8: What's the difference between Snowflake editions?

A: Key differences:

  • Standard: Basic features, 1 day Time Travel, no multi-cluster, no masking policies
  • Enterprise: Multi-cluster warehouses, data masking, row access policies, 90 days Time Travel, materialized views, search optimization
  • Business Critical: Everything in Enterprise + enhanced security (PrivateLink, Tri-Secret Secure, HIPAA/PCI compliance, failover/failback)
  • VPS: Completely isolated environment - dedicated metadata store, separate compute infrastructure

Q9: Can multiple virtual warehouses access the same data simultaneously?

A: Yes! This is a core benefit of the architecture. Multiple warehouses can read the same data concurrently without any contention because they access shared immutable data in object storage. A warehouse executing a heavy ETL job won't impact a warehouse serving BI dashboards. Write operations use MVCC (Multi-Version Concurrency Control) to handle concurrent reads and writes.

Q10: How is Snowflake different from a data lake or a traditional data warehouse?

A: Snowflake is positioned as a Data Cloud / Data Platform that combines benefits of both:

  • Like a data warehouse: ACID transactions, SQL interface, schemas, security, governance
  • Like a data lake: Semi-structured data support (JSON, Avro, Parquet), separation of storage and compute, near-unlimited storage, schema-on-read capability
  • Beyond both: Data sharing, marketplace, Snowpark (Python/Java/Scala), Cortex AI, Iceberg tables for open format support
