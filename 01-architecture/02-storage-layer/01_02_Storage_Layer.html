1. Micro-Partitions - The Foundation

What Are Micro-Partitions?

Micro-partitions are Snowflake's fundamental unit of data storage. When data is written to Snowflake, it's automatically organized into these small, immutable files.

Core Properties of Micro-Partitions:
  • Size: 50-500 MB of uncompressed data (typically 10-20 MB after compression)
  • Format: Proprietary columnar format (NOT Parquet/ORC)
  • Immutable: Once written, never modified - updates create NEW partitions
  • Automatic: Snowflake handles all partitioning - no manual intervention
  • Contiguous: Rows in a partition are stored contiguously by insertion order

How Data is Organized Within a Micro-Partition

  MICRO-PARTITION #1 (50-500 MB uncompressed)
  +--------------------------------------------------+
  |  HEADER (metadata about this partition)           |
  +--------------------------------------------------+
  |  Column A data  [compressed, encoded]            |
  |  Column B data  [compressed, encoded]            |
  |  Column C data  [compressed, encoded]            |
  |  ...                                             |
  +--------------------------------------------------+
  |  Column statistics (min, max, count, nulls)      |
  +--------------------------------------------------+
  
  Key: Each column stored SEPARATELY within the partition
       Allows reading only needed columns (columnar benefit)

Partition Assignment: Natural Clustering

Data is assigned to micro-partitions based on insertion order. This means:

  • Data loaded together ends up in the same or adjacent partitions
  • If data is loaded chronologically (e.g., daily logs), dates are naturally clustered
  • This "natural clustering" often provides good pruning without explicit clustering keys
Exam Tip: Snowflake does NOT use traditional partitioning (like Hive). You cannot specify partition columns at table creation. Micro-partitioning is always automatic. You CAN define CLUSTER BY to RE-ORGANIZE existing data for better pruning.

Compression in Snowflake

Snowflake applies multiple compression techniques per column:

TechniqueBest ForHow It Works
Dictionary EncodingLow-cardinality columns (status, category)Stores unique values once, references by ID
Run-Length Encoding (RLE)Sorted/clustered columns with repeatsStores value + count of consecutive repeats
Bit PackingIntegers with limited rangeUses minimum bits needed per value
Delta EncodingSequential/timestamp dataStores differences between values
LZ4/ZSTDGeneral-purposeBlock compression after encoding
Key Facts for Exam:
  • Compression is automatic - Snowflake chooses the best algorithm per column
  • Typical compression ratio: 3x-5x (sometimes 10x+)
  • Storage billing is based on compressed data size
  • You CANNOT choose or disable compression

What Metadata Does Snowflake Store?

For EVERY micro-partition, Snowflake's Cloud Services layer maintains:

Max ValueMaximum value in that columnRange-based pruning
NULL CountNumber of NULLsIS NULL / IS NOT NULL optimization
Distinct CountApproximate distinct valuesJoin optimization
Number of RowsTotal rows in partitionCOUNT(*) without scanning

How Partition Pruning Works

  Table: ORDERS (10 million rows, 100 micro-partitions)
  Query: SELECT * FROM orders WHERE order_date = '2024-06-15'

  Step 1: Cloud Services checks metadata for each partition:
    - Partition #1: order_date min='2024-01-01', max='2024-01-31' --> SKIP!
    - Partition #2: order_date min='2024-02-01', max='2024-02-28' --> SKIP!
    ...
    - Partition #47: order_date min='2024-06-01', max='2024-06-30' --> SCAN!
    ...
    - Partition #100: order_date min='2024-12-01', max='2024-12-31' --> SKIP!

  Result: Only 1-2 partitions scanned instead of 100!
  This is "partition pruning" - the most important optimization in Snowflake.
Exam Tip: Pruning happens in the Cloud Services layer (not the warehouse). It's FREE - no compute credits consumed for pruning decisions. The better your data is clustered, the more effective pruning becomes.

4. Data Lifecycle in Storage

The Immutability Model

  INSERT 3 rows:
    Creates Partition P1 [row1, row2, row3]

  UPDATE row2:
    P1 is NOT modified
    Creates new Partition P2 [row1, row2_updated, row3]
    P1 is marked for Time Travel (still accessible)

  DELETE row3:
    P2 is NOT modified  
    Creates new Partition P3 [row1, row2_updated]
    P2 is marked for Time Travel

  Timeline: P1 --> P2 --> P3 (current)
            ^       ^
            |       |--- accessible via Time Travel
            |--- accessible via Time Travel

Storage Lifecycle States

StateDurationAccessible ByBilled?
Active/CurrentUntil changedNormal queriesYes
Time Travel0-90 days (configurable)AT/BEFORE queries, UNDROPYes
Fail-safe7 days (after Time Travel)Snowflake support ONLYYes
PurgedAfter Fail-safeGone foreverNo
 
  Data Written --> [Active] --> Data Changed --> [Time Travel: 0-90 days] --> [Fail-safe: 7 days] --> Purged
                                                 (user accessible)            (Snowflake only)

  Total retention for Permanent table (Enterprise):
  Active + Up to 90 days Time Travel + 7 days Fail-safe = up to 97 days of old data stored

  Transient table: Time Travel (0-1 day) + NO Fail-safe
  Temporary table: Time Travel (0-1 day) + NO Fail-safe + dropped at session end
Storage Cost Impact: A table with 100 GB active data, 90-day Time Travel, and many DML operations could store significantly more than 100 GB total. Each UPDATE/DELETE creates new partitions while old ones remain in Time Travel. Monitor with TABLE_STORAGE_METRICS.

Script 4: Storage Metrics Deep Dive

-- Comprehensive storage view for all tables
SELECT 
  TABLE_NAME,
  ACTIVE_BYTES / (1024*1024) AS active_mb,
  TIME_TRAVEL_BYTES / (1024*1024) AS time_travel_mb,
  FAILSAFE_BYTES / (1024*1024) AS failsafe_mb,
  RETAINED_FOR_CLONE_BYTES / (1024*1024) AS clone_retained_mb,
  (ACTIVE_BYTES + TIME_TRAVEL_BYTES + FAILSAFE_BYTES) / (1024*1024) AS total_billed_mb
FROM TABLE(INFORMATION_SCHEMA.TABLE_STORAGE_METRICS())
WHERE TABLE_CATALOG = 'CERT_STUDY_DB' 
  AND TABLE_SCHEMA = 'ARCHITECTURE'
  AND ACTIVE_BYTES > 0
ORDER BY total_billed_mb DESC;

SELECT * FROM SNOWFLAKE.ACCOUNT_USAGE.STORAGE_USAGE

-- Create a larger table to demonstrate clustering
CREATE OR REPLACE TABLE clustering_demo AS

  UNIFORM(1, 100, RANDOM()) AS customer_id,

7. Interview & Certification Q&A

Q1: What is a micro-partition and how is it different from traditional partitioning?

A: A micro-partition is Snowflake's proprietary storage unit (50-500 MB uncompressed). Key differences from traditional partitioning:

  • Traditional: User defines partition columns (e.g., PARTITION BY date). Snowflake: Automatic, based on insertion order.
  • Traditional: Partitions can be very large. Snowflake: Always small (50-500 MB) for parallelism.
  • Traditional: User manages partition maintenance. Snowflake: Fully managed.
  • Traditional: Mutable (in-place updates). Snowflake: Immutable (COW - Copy-On-Write).

Q2: Why does Snowflake use columnar storage? When might row-based be better?

A: Columnar storage benefits for analytics:

  • Only reads columns referenced in query (I/O reduction)
  • Same-type data compresses much better (3-10x compression)
  • SIMD and vectorized operations on homogeneous data
  • Better cache utilization for analytical scans
Row-based would be better for: single-row lookups by primary key, OLTP workloads with many small inserts/updates, queries that always SELECT *. That's why Snowflake also offers Hybrid Tables (row-based) for OLTP-like workloads.

Q3: Explain partition pruning. How does it differ from indexing?

A: Partition pruning uses min/max metadata per column per partition to eliminate partitions that cannot contain matching data. Differences from indexing:

  • No user management: Pruning metadata is automatic; indexes must be created/maintained
  • No storage overhead: Metadata is small; indexes can be as large as the data
  • Granularity: Pruning is partition-level; indexes can be row-level
  • Write overhead: Pruning metadata has minimal write cost; indexes slow down writes
  • Effectiveness: Pruning works best on range filters on clustered columns; indexes work on point lookups
Snowflake has NO traditional indexes. It relies on pruning + Search Optimization Service for point lookups.

Q4: What happens to storage when you UPDATE a row in Snowflake?

A: Due to immutability:

  1. The partition containing the modified row is NOT changed
  2. A NEW partition is created with the updated data
  3. The old partition moves to Time Travel state
  4. The old partition is billed as Time Travel storage for the retention period
  5. After Time Travel expires, it moves to Fail-safe (7 days, permanent tables only)
  6. After Fail-safe, it's purged and storage is freed
This means frequent UPDATEs on large tables can significantly increase storage usage.

Q6: How does zero-copy cloning work with storage?

A: When you clone a table:

  • NO data is physically copied - clone references same micro-partitions
  • Initial storage cost of clone = 0 (shares all partitions with source)
  • When either table is modified, only the CHANGED partitions diverge
  • Storage grows only for diverged partitions
  • Dropping the source doesn't affect clone (partitions remain as long as referenced)
This enables instant database/schema/table cloning for dev/test environments.

Q7: How does Snowflake achieve its compression ratios?

A: Multiple layers of compression:

  1. Columnar organization: Same data type stored together = better patterns
  2. Encoding: Dictionary (low cardinality), RLE (sorted data), Delta (timestamps), Bit-packing (small integers)
  3. Block compression: LZ4 or ZSTD applied after encoding
  4. Automatic selection: Snowflake's optimizer picks best combination per column per partition
Result: Typical 3-5x compression. Highly repetitive data (status columns) can see 10-50x.

Q8: When should you define a clustering key?

A: Define clustering keys when:

  • Table is large (multi-TB) AND queries consistently filter on specific columns
  • Query Profile shows poor pruning (scanning most partitions)
  • Data is loaded in an order different from how it's queried
  • Clustering depth is high (poor natural clustering on filter columns)
Do NOT cluster when: table is small (<1 GB), queries don't have consistent filters, or data is already naturally well-clustered by the filter column.

Q9: Can you store unstructured data in Snowflake's storage layer?

A: Semi-structured data (JSON, XML, Avro, Parquet, ORC) is stored natively in VARIANT columns within micro-partitions. Snowflake optimizes this by detecting repeated keys and storing them columnar-like when possible. For truly unstructured files (PDFs, images, videos), you store them in Snowflake stages (internal or external) - they're in cloud object storage but managed by Snowflake. Directory tables let you catalog staged files.

Q10: What is the Snowflake Search Optimization Service?

A: Search Optimization Service (SOS) is an add-on that creates persistent data structures (like auxiliary indexes) to speed up:

  • Point lookups (WHERE id = 12345)
  • Substring searches (WHERE col LIKE '%pattern%')
  • Selective filters on high-cardinality columns
  • VARIANT field access and GEO functions
It supplements partition pruning. Requires Enterprise edition. Has additional storage and compute costs for maintenance.
