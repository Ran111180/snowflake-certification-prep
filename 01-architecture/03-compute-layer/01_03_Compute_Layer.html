1. Virtual Warehouse Fundamentals

What Is a Virtual Warehouse?

A virtual warehouse is an MPP (Massively Parallel Processing) compute cluster provisioned from cloud resources (EC2/Azure VMs/GCE) that executes SQL queries and DML operations. Key facts:

  • Users NEVER see or manage the underlying VMs/nodes
  • Each warehouse is an independent cluster - no shared resources between warehouses
  • A warehouse can run multiple queries concurrently
  • Warehouses ONLY consume credits when running (not suspended)
  • Minimum billing increment: 60 seconds (1 second after the first minute)

  • Each size UP = 2x credits, 2x nodes

Result Cache Deep Dive

  CONDITIONS FOR RESULT CACHE HIT:
  +--------------------------------------------------+
  | 1. Exact same query text (whitespace matters!)   |
  | 2. Same role executing the query                 |
  | 3. Underlying data NOT changed since last run    |
  | 4. Query doesn't use non-deterministic functions |
  |    (CURRENT_TIMESTAMP, RANDOM, UUID_STRING...)   |
  | 5. Result cache not explicitly disabled          |
  | 6. Within 24-hour window                         |
  +--------------------------------------------------+

  RESULT: Query returns instantly, 0 credits consumed
  (served entirely from Cloud Services layer)
Exam Tip: Result cache does NOT require a running warehouse. Even if warehouse is suspended, cached results are returned. The cache persists for 24 hours, refreshing the timer on each access (up to 31 days max).

Local Disk Cache (Warehouse Cache)

  HOW IT WORKS:
  - When a warehouse scans data, it caches raw micro-partition data on local SSD
  - Subsequent queries needing same partitions read from SSD (faster than S3/Blob)
  - Cache is per-warehouse, per-node
  - LOST when warehouse suspends (SSD wiped)

  IMPLICATIONS:
  - Keep AUTO_SUSPEND reasonable (not too aggressive for repeated queries)
  - First query after resume = "cold cache" = slower
  - Larger warehouse = more SSD = more cache capacity
Common Pitfall: Setting AUTO_SUSPEND = 0 (immediately) means the warehouse suspends after every query, wiping the local cache. Set it to at least 60-300 seconds for interactive workloads to benefit from cache warm-up.

Concurrency & Queuing

  MAX_CONCURRENCY_LEVEL (default: 8)
  - Maximum queries a single cluster processes concurrently
  - When exceeded: queries enter the QUEUE

  STATEMENT_QUEUED_TIMEOUT_IN_SECONDS (default: 0 = no limit)
  - How long a query waits in queue before being canceled
  - Set this to avoid infinite waiting

  STATEMENT_TIMEOUT_IN_SECONDS (default: 172800 = 48 hours)
  - Max execution time for a single query
  - After this, query is automatically canceled

Resource Monitors

Resource monitors track credit consumption and can send notifications or suspend warehouses:

  CREATE RESOURCE MONITOR monthly_monitor
    WITH CREDIT_QUOTA = 1000
    FREQUENCY = MONTHLY
    START_TIMESTAMP = IMMEDIATELY
    TRIGGERS
      ON 50 PERCENT DO NOTIFY          -- Email at 50%
      ON 75 PERCENT DO NOTIFY          -- Email at 75%
      ON 90 PERCENT DO SUSPEND         -- Suspend running queries finish
      ON 100 PERCENT DO SUSPEND_IMMEDIATE;  -- Kill all queries immediately

Script 3: Monitor Warehouse Performance

-- Query execution breakdown
SELECT 
  warehouse_name,
  COUNT(*) AS query_count,
  AVG(total_elapsed_time)/1000 AS avg_elapsed_sec,
  AVG(queued_overload_time)/1000 AS avg_queue_sec,
  SUM(bytes_scanned)/(1024*1024*1024) AS total_gb_scanned
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY
WHERE start_time > DATEADD('hour', -24, CURRENT_TIMESTAMP())
  AND warehouse_name IS NOT NULL
GROUP BY warehouse_name
ORDER BY query_count DESC;

  warehouse_name,
  SUM(credits_used) AS total_credits,

8. Interview & Certification Q&A

Q1: What is a Virtual Warehouse and how does it relate to actual servers?

A: A virtual warehouse is a named, configurable compute cluster. Under the hood, Snowflake provisions cloud VMs (EC2 instances on AWS, etc.) into an MPP cluster. Users never see or manage these VMs. The warehouse abstracts all infrastructure - you just specify a size (XS-6XL) and Snowflake handles provisioning, scaling, and decommissioning. When suspended, VMs are released. When resumed, new VMs are provisioned (typically in seconds).

Q2: Explain the three types of caching in Snowflake.

A:

  1. Result Cache (Cloud Services): Stores complete query results for 24h. Hit requires same query text + same role + unchanged data. No credits consumed. Persists across warehouse suspend/resume.
  2. Local Disk Cache (Warehouse SSD): Caches raw micro-partition data on warehouse nodes' SSDs. Faster than reading from S3/Blob. Lost on warehouse suspend. Per-warehouse, not shared.
  3. Remote Disk Cache: Intermediate layer in cloud storage. More persistent than local SSD but slower. Shared across warehouses for frequently accessed data.

Q3: A user reports queries are slow and getting queued. What do you check?

A: Troubleshooting steps:

  1. Check queuing: Query Profile > see if queries are in QUEUED state (concurrency issue)
  2. If queuing: Scale OUT (increase MAX_CLUSTER_COUNT) or increase MAX_CONCURRENCY_LEVEL
  3. If slow but not queued: Scale UP (bigger warehouse size) or check query optimization (pruning, clustering)
  4. Check spilling: Query Profile > if "Bytes Spilled to Local/Remote" is high, warehouse is too small
  5. Check workload isolation: Maybe ETL is competing with BI - separate warehouses
  6. Check resource monitor: Warehouse might be suspended by quota limit

Q4: What is "spilling" and what does it indicate?

A: Spilling occurs when a query's intermediate results exceed the warehouse's memory:

  • Spill to Local Disk: Data written to warehouse node SSDs. Moderate performance impact.
  • Spill to Remote Storage: Data written to cloud storage (S3/Blob). Severe performance impact.
Solutions: Increase warehouse size (more memory), optimize query to reduce intermediate results (better filters, smaller JOINs), use Snowpark-optimized warehouses for memory-intensive workloads.

Q5: How does billing work for warehouses?

A:

  • Billed in credits per second (minimum 60-second charge on startup)
  • After first 60 seconds, billing is per-second
  • Credits = warehouse_size_credits x running_time_in_hours
  • Multi-cluster: credits = size x number_of_active_clusters x time
  • Suspended warehouse = $0 (no credits consumed)
  • Cloud Services: separate billing, free if < 10% of daily compute
  • Credit price depends on edition and contract ($2-4 per credit typical)

Q6: Standard vs Economy scaling policy - when to use which?

A:

  • Standard: Adds cluster as soon as ANY query queues. Fastest response time. Use for SLA-driven workloads where queuing is unacceptable (real-time dashboards, user-facing apps).
  • Economy: Only adds cluster if it will be busy for at least 6 minutes. Saves money by tolerating short queue bursts. Use for batch workloads, internal analytics where brief delays are acceptable.
Standard scales up faster but costs more. Economy is ~20-30% cheaper but queries may queue briefly.

Q7: Can you resize a warehouse while queries are running?

A: Yes! Resizing is non-disruptive:

  • Scale UP: New nodes added. Currently running queries continue on old nodes. New queries use the larger cluster.
  • Scale DOWN: Nodes marked for removal. Once running queries on those nodes finish, nodes are released. New queries only go to remaining nodes.
This allows dynamic right-sizing without interrupting users.

Q8: What's the difference between suspending and dropping a warehouse?

A:

  • SUSPEND: Stops compute, releases nodes, local cache wiped. Warehouse still exists as a named object with all settings preserved. Can be resumed instantly. No credits while suspended.
  • DROP: Permanently removes the warehouse definition. All settings lost. Must recreate from scratch. Can UNDROP within Time Travel period.

Q9: What are Snowpark-optimized warehouses and when should you use them?

A: Snowpark-optimized warehouses have 16x more memory per node. Use them for:

  • ML model training with large datasets in memory
  • Python UDFs/UDTFs that hold large state
  • Operations that spill to disk on standard warehouses
  • Large DataFrames in Snowpark
They cost more credits per hour but avoid expensive spilling. Created with WAREHOUSE_TYPE = 'SNOWPARK-OPTIMIZED'.
