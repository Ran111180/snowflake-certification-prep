1. Cloud Services Layer Overview

The "Brain" of Snowflake

The Cloud Services layer is a collection of services that coordinate activities across Snowflake. It runs 24/7, is shared across all accounts in a region, and is highly available (no single point of failure).

4. Transaction Management

ACID Properties in Snowflake

PropertyHow Snowflake Implements It
AtomicityStatements are atomic. Multi-statement transactions supported. Failure = rollback all.
ConsistencyConstraints (NOT NULL, UNIQUE*) enforced. Data always in valid state after transaction.
IsolationREAD COMMITTED isolation level (default and only level). MVCC prevents dirty reads.
DurabilityCommitted data persisted in cloud object storage with replication.

MVCC (Multi-Version Concurrency Control)

  HOW MVCC WORKS IN SNOWFLAKE:

  Time T1: Transaction A starts reading TABLE_X
            (sees snapshot at T1 - version V1)

  Time T2: Transaction B updates TABLE_X
            (creates new micro-partitions - version V2)
            Transaction B commits

  Time T3: Transaction A is STILL reading TABLE_X
            (still sees V1 - consistent snapshot!)
            No dirty reads, no phantom reads within the statement

  Key: Readers never block writers. Writers never block readers.
       This is possible because micro-partitions are IMMUTABLE.
       Old versions exist simultaneously with new versions.
Key Transaction Facts:
  • Default isolation: READ COMMITTED (only level available)
  • Readers don't block writers and vice versa (MVCC)
  • DDL statements are auto-committed (can't be rolled back)
  • DML within BEGIN...COMMIT/ROLLBACK is transactional
  • Default: each DML statement is its own auto-commit transaction
  • AUTOCOMMIT parameter controls this behavior
  • Deadlocks: handled automatically with timeout (statement blocked too long = abort)

Locking in Snowflake

OperationLock TypeBlocks Other
SELECT (read)None (uses MVCC snapshot)Nothing blocked
INSERTTable-level write intentOther DML on same table queued
UPDATE/DELETE/MERGETable-level write lockOther DML on same table queued
DDL (ALTER, DROP)Object-level exclusiveAll access blocked briefly
Important: Snowflake uses table-level locking for DML (not row-level). This means concurrent UPDATEs to the SAME table will queue. Different tables can be updated simultaneously without blocking. This is a common interview question!

6. Cloud Services Billing

The 10% Rule

  CLOUD SERVICES BILLING:

  Daily Calculation:
  +--------------------------------------------+
  | Cloud Services credits consumed today: 5   |
  | Warehouse compute credits today: 100       |
  | 10% threshold: 100 x 0.10 = 10            |
  |                                            |
  | 5 < 10, so Cloud Services = FREE today     |
  +--------------------------------------------+

  Another day:
  +--------------------------------------------+
  | Cloud Services credits consumed: 15        |
  | Warehouse compute credits: 100             |
  | 10% threshold: 100 x 0.10 = 10            |
  |                                            |
  | 15 > 10, so you pay: 15 - 10 = 5 credits  |
  +--------------------------------------------+

  When Cloud Services might exceed 10%:
  - Many small, fast queries (lots of parsing/optimization)
  - Heavy use of CLONE operations
  - Frequent SHOW/DESCRIBE commands at scale
  - Replication sync operations
  - Partner tools polling metadata heavily
Exam Fact: In practice, ~95% of customers NEVER pay extra for Cloud Services. The 10% threshold is generous for typical workloads. The most common cause of Cloud Services overage is external tools making excessive metadata calls.

  query_type,

Script 4: Transaction Behavior

-- Auto-commit behavior (default)
CREATE OR REPLACE TABLE CERT_STUDY_DB.ARCHITECTURE.txn_demo (id INT, val VARCHAR);

-- Each statement is auto-committed:
INSERT INTO CERT_STUDY_DB.ARCHITECTURE.txn_demo VALUES (1, 'auto-committed');

-- Explicit transaction
BEGIN;
  INSERT INTO CERT_STUDY_DB.ARCHITECTURE.txn_demo VALUES (2, 'in transaction');
  INSERT INTO CERT_STUDY_DB.ARCHITECTURE.txn_demo VALUES (3, 'also in transaction');
COMMIT;

-- Rollback example
BEGIN;
  INSERT INTO CERT_STUDY_DB.ARCHITECTURE.txn_demo VALUES (4, 'will be rolled back');
  -- Oops, mistake!
ROLLBACK;

-- Check results - only IDs 1, 2, 3 exist (4 was rolled back)
SELECT * FROM CERT_STUDY_DB.ARCHITECTURE.txn_demo ORDER BY id;

Script 5: Cloud Services Credit Monitoring

-- Check Cloud Services usage vs Compute
SELECT 
  DATE_TRUNC('day', start_time) AS day,
  SUM(credits_used_compute) AS compute_credits,
  SUM(credits_used_cloud_services) AS cs_credits,
  ROUND(SUM(credits_used_cloud_services) / NULLIF(SUM(credits_used_compute), 0) * 100, 2) 
    AS cs_pct_of_compute
FROM SNOWFLAKE.ACCOUNT_USAGE.WAREHOUSE_METERING_HISTORY
WHERE start_time > DATEADD('day', -7, CURRENT_TIMESTAMP())
GROUP BY day
ORDER BY day DESC;

8. Interview & Certification Q&A

Q1: What services does the Cloud Services layer provide?

A: The Cloud Services layer handles:

  1. Authentication & Security: Login, MFA, SSO, OAuth, key-pair auth, network policies
  2. Access Control: RBAC privilege enforcement, data masking, row access policies
  3. Query Processing: Parsing, compiling, optimizing SQL (cost-based optimizer)
  4. Metadata Management: Object catalog, partition statistics, table profiles
  5. Infrastructure Management: Warehouse provisioning, scaling, health monitoring
  6. Result Cache: 24-hour query result caching
  7. Transaction Management: ACID enforcement, MVCC, locking
It's always running, highly available, and shared across accounts in a region.

Q2: How does Snowflake's query optimizer work without indexes?

A: Snowflake uses a cost-based optimizer (CBO) that relies on:

  • Micro-partition metadata: Min/max values for partition pruning
  • Table statistics: Row counts, byte sizes, cardinality estimates
  • Column statistics: Distinct values, NULL ratios for join optimization
  • Historical patterns: Previous execution data to inform decisions
The optimizer chooses join types (hash/broadcast/merge), join order, aggregate strategies, and parallelism levels. Users CANNOT provide hints - Snowflake handles it all. This "zero-tuning" philosophy means no DBA intervention needed for most workloads.

Q3: What's the difference between INFORMATION_SCHEMA and ACCOUNT_USAGE?

A:

  • INFORMATION_SCHEMA: Real-time, scoped to current database, limited history (7 days-6 months), available to any role with database access
  • ACCOUNT_USAGE: Up to 3-hour latency, account-wide scope, 365-day history, includes dropped objects, requires ACCOUNTADMIN (or explicit grant)
Use INFORMATION_SCHEMA for real-time operational checks. Use ACCOUNT_USAGE for historical analysis, compliance auditing, and cost management.

Q4: Explain MVCC in Snowflake. How does it handle concurrent reads and writes?

A: MVCC (Multi-Version Concurrency Control) works because micro-partitions are immutable:

  • When a transaction starts, it gets a snapshot timestamp
  • All reads within that transaction see data as it existed at that timestamp
  • Writes create NEW micro-partitions (old ones aren't modified)
  • Multiple versions coexist - each reader sees its consistent snapshot
  • Result: Readers never block writers. Writers never block readers.
This is why Time Travel is possible - old partition versions are retained. The isolation level is READ COMMITTED (the only level supported).

Q5: Does Snowflake support row-level locking?

A: No. Snowflake uses table-level locking for DML operations. This means:

  • Two concurrent UPDATEs on the same table will serialize (second waits)
  • A SELECT never blocks and is never blocked (MVCC)
  • DDL operations briefly lock the object exclusively
  • Lock timeout: configurable via LOCK_TIMEOUT parameter (default: indefinite wait)
This is a deliberate design choice - Snowflake is optimized for analytics (large scans) not OLTP (many small row-level updates). For OLTP needs, use Hybrid Tables which DO support row-level locking.

Q6: When would Cloud Services billing exceed the 10% free threshold?

A: Cloud Services might exceed 10% when:

  • External tools (BI, ETL) make excessive metadata API calls
  • Very high frequency of small queries (each needs parse/optimize)
  • Heavy CLONE operations (metadata-intensive)
  • Frequent replication/failover sync
  • Many SHOW/DESCRIBE commands in automated scripts
  • Warehouse is suspended but Cloud Services still processing (unusual workload pattern)
Solution: Batch metadata calls, reduce polling frequency, use result cache effectively.

Q7: What operations can you perform without a running warehouse?

A: All Cloud Services operations, including:

  • DDL: CREATE, ALTER, DROP, UNDROP (any object)
  • Metadata: SHOW, DESCRIBE, LIST stages
  • Security: GRANT, REVOKE, CREATE ROLE/USER
  • Result cache hits (previously computed query results)
  • Some COUNT(*) queries (answered from metadata alone)
  • Session management: USE, SET parameters
  • Account management: Resource monitors, replication setup
Anything that needs to SCAN data requires a warehouse (SELECT with data access, DML, COPY INTO).

Q8: How does Snowflake handle automatic query optimization without DBA tuning?

A: Snowflake's "zero-tuning" approach includes:

  1. Automatic statistics: Partition metadata maintained on every write
  2. No indexes to create: Pruning + Search Optimization handle lookups
  3. No partition management: Micro-partitions auto-created and maintained
  4. Adaptive query execution: Runtime adjustments based on actual data
  5. Automatic clustering: Background re-organization when clustering key defined
  6. Result caching: Automatic 24h cache for repeated queries
The only tuning users typically do: warehouse sizing, clustering keys for large tables, and query restructuring for complex queries.
