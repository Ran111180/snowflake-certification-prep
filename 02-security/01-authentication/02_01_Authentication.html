Key-Pair Authentication (Detail)

  SETUP PROCESS:
  
  1. Generate key pair (client-side):
     $ openssl genrsa 2048 | openssl pkcs8 -topk8 -inform PEM -out rsa_key.p8 -nocrypt
     $ openssl rsa -in rsa_key.p8 -pubout -out rsa_key.pub

  2. Assign public key to user (Snowflake):
     ALTER USER service_user SET RSA_PUBLIC_KEY = 'MIIBIjANBgkq...';

  3. Connect using private key (client):
     # Python example
     conn = snowflake.connector.connect(
         account='xy12345',
         user='service_user',
         private_key_file='/path/to/rsa_key.p8'
     )

  SECURITY:
  - Private key NEVER sent to Snowflake
  - Can rotate keys (RSA_PUBLIC_KEY_2 for seamless rotation)
  - Supports encrypted private keys (passphrase protected)
  - Recommended for ALL service accounts / automated processes
Key-Pair Key Facts:
  • Minimum key size: 2048 bits
  • Maximum: 2 public keys assigned simultaneously (for rotation)
  • Properties: RSA_PUBLIC_KEY and RSA_PUBLIC_KEY_2
  • Works with: Python connector, JDBC, ODBC, Snowpark, SnowSQL
  • Does NOT work with: Snowsight web UI (browser login)

Exam Tip: MFA in Snowflake:
  • Uses Duo Security (not Google Authenticator natively)
  • Can be enforced for all users via authentication policy
  • Applies to password-based login only (not key-pair, not OAuth)
  • ACCOUNTADMIN should ALWAYS have MFA enabled
  • MFA token caching reduces repeated prompts during a session

SSO Key Facts:
  • Protocol: SAML 2.0 (not OIDC for native SSO)
  • Supported IdPs: Okta, Azure AD (Entra ID), ADFS, OneLogin, Ping, custom SAML 2.0
  • User must exist in Snowflake (auto-provisioning via SCIM optional)
  • SP-initiated (user starts at Snowflake) and IdP-initiated (user starts at IdP) both supported
  • Created using CREATE SECURITY INTEGRATION TYPE = SAML2

5. OAuth

OAuth Types in Snowflake

TypeUse CaseToken Issuer
Snowflake OAuthCustom apps that redirect users to Snowflake loginSnowflake (built-in authorization server)
External OAuthEnterprise apps already using an OAuth providerExternal (Okta, Azure AD, PingFederate, custom)

Snowflake OAuth Flow

  1. App redirects user to Snowflake authorization endpoint
  2. User logs in to Snowflake (with password + MFA if configured)
  3. User consents to grant app access
  4. Snowflake returns authorization code to app
  5. App exchanges code for access token + refresh token
  6. App uses access token to call Snowflake APIs
  7. When access token expires, app uses refresh token to get new one
  
  -- Create Snowflake OAuth integration
  CREATE SECURITY INTEGRATION my_oauth_app
    TYPE = OAUTH
    ENABLED = TRUE
    OAUTH_CLIENT = CUSTOM
    OAUTH_CLIENT_TYPE = 'CONFIDENTIAL'
    OAUTH_REDIRECT_URI = 'https://myapp.com/callback'
    OAUTH_ISSUE_REFRESH_TOKENS = TRUE
    OAUTH_REFRESH_TOKEN_VALIDITY = 86400;  -- 24 hours

  -- External OAuth integration
  CREATE SECURITY INTEGRATION ext_oauth
    TYPE = EXTERNAL_OAUTH
    ENABLED = TRUE
    EXTERNAL_OAUTH_TYPE = AZURE
    EXTERNAL_OAUTH_ISSUER = 'https://login.microsoftonline.com/...'
    EXTERNAL_OAUTH_TOKEN_USER_MAPPING_CLAIM = 'upn'
    EXTERNAL_OAUTH_SNOWFLAKE_USER_MAPPING_ATTRIBUTE = 'login_name'
    EXTERNAL_OAUTH_JWS_KEYS_URL = 'https://login.microsoftonline.com/.../discovery/v2.0/keys';

6. Authentication Policies

NEW Feature (2025-2026)

What Are Authentication Policies?

Authentication policies let you enforce which authentication methods are allowed for users connecting to your account. They provide centralized control over login security.

  -- Create an authentication policy
  CREATE AUTHENTICATION POLICY strict_auth_policy
    AUTHENTICATION_METHODS = ('SAML', 'KEYPAIR')  -- Only SSO and key-pair allowed
    MFA_AUTHENTICATION_METHODS = ('SAML')         -- MFA required for SAML
    CLIENT_TYPES = ('SNOWFLAKE_UI', 'DRIVERS')    -- Allowed client types
    SECURITY_INTEGRATIONS = ('my_sso_integration') -- Which SSO integrations allowed
    COMMENT = 'Strict policy - no password-only auth';

  -- Apply to entire account
  ALTER ACCOUNT SET AUTHENTICATION POLICY = strict_auth_policy;

  -- Apply to specific user
  ALTER USER service_user SET AUTHENTICATION POLICY = keypair_only_policy;

Authentication Policy Parameters

ParameterOptionsPurpose
AUTHENTICATION_METHODSALL, PASSWORD, SAML, OAUTH, KEYPAIRWhich methods can be used to log in
MFA_AUTHENTICATION_METHODSALL, SAML, PASSWORDWhich methods require MFA
CLIENT_TYPESALL, SNOWFLAKE_UI, DRIVERS, SNOWSQLWhich client types are allowed
SECURITY_INTEGRATIONSALL, or list of integrationsWhich SSO/OAuth integrations can be used
Important: Authentication policies are powerful but dangerous if misconfigured. Setting AUTHENTICATION_METHODS = ('KEYPAIR') at the account level would lock out all users who don't have key-pair configured - including ACCOUNTADMIN! Always test on individual users first.

  first_authentication_factor,
  second_authentication_factor,
  COUNT(*) AS login_count,
  COUNT(DISTINCT user_name) AS unique_users

  AND event_timestamp > DATEADD('day', -7, CURRENT_TIMESTAMP())

ORDER BY login_count DESC;

8. Interview & Certification Q&A

Q1: What authentication methods does Snowflake support?

A:

  1. Username/Password: Basic, stored in Snowflake. Can enforce password policies (min length, complexity, rotation).
  2. Key-Pair (RSA): 2048+ bit RSA keys. Private key on client, public key registered in Snowflake. Best for service accounts.
  3. Multi-Factor (MFA): Duo Security - push or TOTP. Add-on to password auth.
  4. Federated SSO (SAML 2.0): Delegate auth to IdP (Okta, Azure AD). Users don't need Snowflake passwords.
  5. OAuth 2.0: Token-based. Snowflake OAuth (built-in) or External OAuth (enterprise IdP).
  6. PAT (Programmatic Access Token): Pre-generated tokens for automation with configurable expiry.

Q2: What's the difference between Snowflake OAuth and External OAuth?

A:

  • Snowflake OAuth: Snowflake acts as both authorization server and resource server. User authenticates directly with Snowflake. Simpler setup. Good for custom apps.
  • External OAuth: External IdP (Okta, Azure AD, PingFederate) issues tokens. Snowflake validates tokens against the IdP. Better for enterprises already using OAuth infrastructure. Supports token user mapping (map OAuth claims to Snowflake users).

Q3: How does key-pair authentication improve security?

A:

  • Private key never transmitted to Snowflake (asymmetric cryptography)
  • No password to steal, phish, or brute-force
  • Supports key rotation with 2 simultaneous public keys (RSA_PUBLIC_KEY + RSA_PUBLIC_KEY_2)
  • Private key can be encrypted with passphrase for defense-in-depth
  • Combined with network policies = very strong authentication
  • Recommended for ALL service accounts and CI/CD integrations

Q4: Can you enforce MFA for all users?

A: Yes, using an authentication policy: 

CREATE AUTHENTICATION POLICY enforce_mfa
  MFA_AUTHENTICATION_METHODS = ('PASSWORD')
  COMMENT = 'Require MFA for all password logins';
ALTER ACCOUNT SET AUTHENTICATION POLICY = enforce_mfa;
This ensures any user logging in with a password must complete MFA. Key-pair and OAuth users are not prompted for MFA (they already have strong auth). Best practice: Enforce MFA at minimum for all ACCOUNTADMIN users.

Q5: What happens if a user's session token expires?

A: Snowflake sessions have configurable timeouts:

  • Session idle timeout: Default 4 hours (240 min). User must re-authenticate.
  • Master token expiry: Long-lived (~14 days) for refresh purposes
  • Session policies: Can override defaults (e.g., SESSION_IDLE_TIMEOUT_MINS = 30)
  • On expiry, the driver/connector typically auto-refreshes using the master token
  • If master token expires, full re-authentication required

Q6: How does SCIM provisioning work with Snowflake?

A: SCIM (System for Cross-domain Identity Management) automates user/group sync:

  • IdP (Okta, Azure AD) pushes user create/update/delete to Snowflake
  • Snowflake auto-creates users when added in IdP
  • Snowflake auto-deactivates users when removed from IdP groups
  • Groups in IdP map to roles in Snowflake
  • Configured via: CREATE SECURITY INTEGRATION TYPE = SCIM
  • Eliminates manual user provisioning - reduces security risk of orphaned accounts

Q7: A company wants to prevent password-only logins for production accounts. How?

A: Multiple approaches:

  1. Authentication Policy: AUTHENTICATION_METHODS = ('SAML', 'KEYPAIR', 'OAUTH') - blocks password login entirely
  2. Enforce MFA: Allow passwords but require MFA always
  3. Remove passwords: Create users with TYPE = SERVICE and only key-pair configured
  4. Network policy + SSO: Restrict network access to VPN + require SSO from that VPN
Authentication policies are the cleanest solution as they provide declarative, account-wide or per-user enforcement.

Q8: What is the ACCOUNTADMIN role's recommended auth setup?

A: ACCOUNTADMIN is the most powerful role - security best practices:

  • MFA MUST be enabled for all ACCOUNTADMIN users
  • Should have at least 2 users with ACCOUNTADMIN (avoid single point of failure)
  • Should NOT be the default role for any user (only USE ROLE when needed)
  • Monitor login attempts via LOGIN_HISTORY
  • Consider: separate ACCOUNTADMIN users for break-glass scenarios only
  • Network policy restricting ACCOUNTADMIN to trusted IPs
