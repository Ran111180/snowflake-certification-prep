1. RBAC (Role-Based Access Control) Overview

How Access Control Works in Snowflake

Snowflake uses a combination of two models:

ModelDescriptionKey Concept
DAC (Discretionary Access Control)Object owner controls access to their objectsEach object has an owner role that grants access
RBAC (Role-Based Access Control)Privileges assigned to roles, roles assigned to usersUsers don't get direct privileges - always through roles
 
  THE ACCESS CONTROL MODEL:

  +--------+     assigned to     +--------+     granted     +-------------+
  |  USER  | -----------------> |  ROLE  | -------------> | PRIVILEGE   |
  +--------+                    +--------+                 | on OBJECT   |
                                     |                     +-------------+
                                     | (role hierarchy)
                                     v
                                +--------+
                                | PARENT |  (inherits all privileges of child roles)
                                |  ROLE  |
                                +--------+

  KEY RULES:
  - Users are granted ROLES (not direct privileges)
  - Roles are granted PRIVILEGES on objects
  - Roles form a hierarchy (parent inherits child's privileges)
  - Every object has an OWNER (role that created it)
  - A user can have a PRIMARY ROLE + SECONDARY ROLES in a session
Critical Concepts:
  • Securable Object: Any entity access can be granted on (database, schema, table, view, warehouse, etc.)
  • Role: An entity privileges are granted TO, and that users are assigned TO
  • Privilege: A specific permission (SELECT, INSERT, USAGE, CREATE, etc.)
  • Users NEVER get privileges directly - always through a role

System Roles Explained

RolePurposeKey PrivilegesBest Practice
ACCOUNTADMIN Top-level role, combines SYSADMIN + SECURITYADMIN ALL privileges on the account. Can manage billing, resource monitors, reader accounts. Use sparingly! Assign to 2+ users. Enable MFA. Never use as default role.
SECURITYADMIN Manage security: users, roles, grants MANAGE GRANTS (can grant/revoke any privilege). CREATE USER, CREATE ROLE. Use for user/role administration. Delegated security management.
USERADMIN Create and manage users and roles only CREATE USER, CREATE ROLE. Cannot grant privileges on objects. Subset of SECURITYADMIN for user provisioning.
SYSADMIN Manage all objects (databases, schemas, tables, warehouses) CREATE DATABASE, CREATE WAREHOUSE. Inherits all custom role privileges. Recommended owner of all databases/warehouses. Custom roles should be granted TO SYSADMIN.
PUBLIC Default role granted to every user automatically Only privileges explicitly granted. Minimal by default. Don't grant sensitive access to PUBLIC (it's everyone!).
Exam Tip - Role Inheritance:
  • ACCOUNTADMIN = SECURITYADMIN + SYSADMIN combined (inherits both)
  • SECURITYADMIN inherits USERADMIN (so it can do everything USERADMIN can)
  • SYSADMIN should inherit ALL custom roles (best practice)
  • ACCOUNTADMIN inherits EVERYTHING (all system + custom roles via SYSADMIN)
  • PUBLIC is auto-granted to every user (base role)

GRANT Syntax

-- Grant privilege on object to role
GRANT SELECT ON TABLE mydb.myschema.mytable TO ROLE analyst_role;

-- Grant multiple privileges
GRANT SELECT, INSERT ON TABLE mytable TO ROLE etl_role;

-- Grant on ALL tables in schema
GRANT SELECT ON ALL TABLES IN SCHEMA mydb.myschema TO ROLE analyst_role;

-- Grant on FUTURE tables (auto-applied to new objects)
GRANT SELECT ON FUTURE TABLES IN SCHEMA mydb.myschema TO ROLE analyst_role;

-- Grant warehouse usage
GRANT USAGE ON WAREHOUSE compute_wh TO ROLE analyst_role;

-- Grant role to user
GRANT ROLE analyst_role TO USER john;

-- Grant role to another role (hierarchy)
GRANT ROLE analyst_role TO ROLE sysadmin;  -- Best practice!

-- Revoke
REVOKE SELECT ON TABLE mytable FROM ROLE analyst_role;
FUTURE Grants - Critical for Exam:
  • GRANT ... ON FUTURE TABLES IN SCHEMA - applies to objects created AFTER the grant
  • Does NOT apply to existing objects (use ON ALL TABLES for those)
  • Common pattern: Grant on ALL existing + Grant on FUTURE = complete coverage
  • FUTURE grants at database level apply to ALL schemas in that database

Key Privileges Explained

PrivilegeWhat It AllowsCommon Gotcha
USAGE (Database)Enter the database (required to see schemas)Without USAGE on DB, can't access anything inside
USAGE (Schema)Enter the schema (required to see objects)Need BOTH db USAGE + schema USAGE to reach tables
USAGE (Warehouse)Use the warehouse to run queriesUSAGE alone allows running queries but not resizing

MODIFY (Warehouse)Change warehouse properties (size, etc.)Most powerful WH privilege besides OWNERSHIP
OWNERSHIPFull control. Can grant others access.Only one role can own an object at a time
The Access Chain (Common Exam Question):

To SELECT from a table, a role needs ALL of these:

  1. USAGE on the warehouse
  2. USAGE on the database
  3. USAGE on the schema
  4. SELECT on the table

Missing ANY one of these = access denied!

Important for Sharing & Modern Design

-- Create a database role
CREATE DATABASE ROLE sales_db.reader_role;

-- Grant privileges to database role
GRANT USAGE ON SCHEMA sales_db.public TO DATABASE ROLE sales_db.reader_role;
GRANT SELECT ON ALL TABLES IN SCHEMA sales_db.public TO DATABASE ROLE sales_db.reader_role;

-- Grant database role to an account role
GRANT DATABASE ROLE sales_db.reader_role TO ROLE analyst_role;

-- Key benefit: Database roles travel with shares!
-- When you share a database, the consumer gets the database roles too.
Why Database Roles Matter:
  • Enable fine-grained access control within shared databases
  • Consumers of shared data can use provider-defined database roles
  • Simplify privilege management for large databases
  • Recommended for all new database designs

6. Ownership

How Ownership Works

  RULES OF OWNERSHIP:
  
  1. Every securable object has exactly ONE owner (a role)
  2. The role that CREATES an object becomes its owner
  3. Owner has full control (all privileges + can grant to others)
  4. Ownership can be transferred:
     GRANT OWNERSHIP ON TABLE mytable TO ROLE new_owner;
  5. Only the owner (or ACCOUNTADMIN/SECURITYADMIN) can drop an object
  6. SECURITYADMIN with MANAGE GRANTS can grant on objects it doesn't own

Ownership Transfer

-- Transfer single object
GRANT OWNERSHIP ON TABLE mydb.myschema.mytable 
  TO ROLE new_owner_role 
  REVOKE CURRENT GRANTS;  -- or COPY CURRENT GRANTS

-- Transfer all tables in a schema
GRANT OWNERSHIP ON ALL TABLES IN SCHEMA mydb.myschema
  TO ROLE new_owner_role
  REVOKE CURRENT GRANTS;

-- Transfer future objects
GRANT OWNERSHIP ON FUTURE TABLES IN SCHEMA mydb.myschema
  TO ROLE new_owner_role;
REVOKE vs COPY CURRENT GRANTS on transfer:
  • REVOKE CURRENT GRANTS: All existing grants removed. New owner starts fresh.
  • COPY CURRENT GRANTS: Existing grants preserved. New owner inherits same access structure.

7. Hands-On SQL Scripts

Script 1: Explore Current Role Hierarchy

-- Show all roles in the account
SHOW ROLES;

-- Show role hierarchy (who is granted to whom)
SELECT 
  grantee_name AS child_role,
  name AS parent_role,
  granted_by
FROM SNOWFLAKE.ACCOUNT_USAGE.GRANTS_TO_ROLES
WHERE granted_on = 'ROLE'
  AND privilege = 'USAGE'
  AND deleted_on IS NULL
ORDER BY parent_role, child_role;

-- Show grants TO your current role
SHOW GRANTS TO ROLE ACCOUNTADMIN;

-- Show grants ON a specific object
SHOW GRANTS ON DATABASE CERT_STUDY_DB;

Script 2: Create a Role Hierarchy

USE ROLE ACCOUNTADMIN;

-- Create access roles (lowest level - hold privileges)
CREATE ROLE IF NOT EXISTS CERT_READ_ROLE
  COMMENT = 'Read access to cert study objects';
CREATE ROLE IF NOT EXISTS CERT_WRITE_ROLE
  COMMENT = 'Write access to cert study objects';

-- Create functional role (assigned to users)
CREATE ROLE IF NOT EXISTS CERT_ANALYST_ROLE
  COMMENT = 'Analyst functional role';

-- Build hierarchy
GRANT ROLE CERT_READ_ROLE TO ROLE CERT_ANALYST_ROLE;   -- analyst gets read
GRANT ROLE CERT_ANALYST_ROLE TO ROLE SYSADMIN;         -- SYSADMIN inherits all

-- Grant privileges to access roles
GRANT USAGE ON DATABASE CERT_STUDY_DB TO ROLE CERT_READ_ROLE;
GRANT USAGE ON SCHEMA CERT_STUDY_DB.ARCHITECTURE TO ROLE CERT_READ_ROLE;
GRANT SELECT ON ALL TABLES IN SCHEMA CERT_STUDY_DB.ARCHITECTURE TO ROLE CERT_READ_ROLE;
GRANT SELECT ON FUTURE TABLES IN SCHEMA CERT_STUDY_DB.ARCHITECTURE TO ROLE CERT_READ_ROLE;

-- Grant warehouse usage
GRANT USAGE ON WAREHOUSE COMPUTE_WH TO ROLE CERT_READ_ROLE;

-- Test: Switch to the analyst role
USE ROLE CERT_ANALYST_ROLE;
SELECT COUNT(*) FROM CERT_STUDY_DB.ARCHITECTURE.SAMPLE_DATA;  -- Should work!

-- Switch back
USE ROLE ACCOUNTADMIN;

8. Interview & Certification Q&A

Q1: Explain RBAC in Snowflake. How do users get access to objects?

A: Snowflake uses Role-Based Access Control. The chain is:

  1. PRIVILEGES are granted ON objects TO roles
  2. ROLES are granted TO users (or other roles)
  3. Users NEVER get privileges directly - always through roles
  4. Roles form a hierarchy - parent roles inherit all child role privileges
To access a table: User activates a role --> role must have USAGE on warehouse + USAGE on database + USAGE on schema + SELECT on table.

Q2: What are the system-defined roles and their purposes?

A:

  • ACCOUNTADMIN: Top-level. Combines SYSADMIN + SECURITYADMIN. Manages billing, reader accounts, failover.
  • SECURITYADMIN: Manages users, roles, and grants (has MANAGE GRANTS global privilege).
  • USERADMIN: Can only create users and roles (subset of SECURITYADMIN).
  • SYSADMIN: Creates and manages databases, warehouses, schemas. Should own all data objects.
  • PUBLIC: Automatically granted to every user. Minimal privileges only.

Q3: What's the difference between GRANT ON ALL vs GRANT ON FUTURE?

A:

  • ON ALL TABLES: Applies to all EXISTING tables at the time of execution. Does NOT affect tables created later.
  • ON FUTURE TABLES: Applies ONLY to tables created AFTER the grant. Does NOT affect existing tables.
  • Best practice: Use BOTH together for complete coverage: 
    GRANT SELECT ON ALL TABLES IN SCHEMA myschema TO ROLE reader;
GRANT SELECT ON FUTURE TABLES IN SCHEMA myschema TO ROLE reader;

Q4: Why should custom roles always be granted to SYSADMIN?

A: If a custom role is NOT granted to SYSADMIN (and by extension ACCOUNTADMIN), then objects owned by that custom role become "orphaned" - not accessible by SYSADMIN or ACCOUNTADMIN through normal role hierarchy. This creates governance issues:

  • ACCOUNTADMIN can't manage those objects through normal means
  • If the only user with that role is deleted, objects become inaccessible
  • Best practice: GRANT ROLE custom_role TO ROLE SYSADMIN; immediately after creation

Q5: What is the MANAGE GRANTS privilege and who has it?

A: MANAGE GRANTS is a global privilege that allows a role to grant or revoke privileges on ANY object, even objects it doesn't own. By default:

  • SECURITYADMIN has MANAGE GRANTS
  • ACCOUNTADMIN inherits it (through SECURITYADMIN)
  • It's the reason SECURITYADMIN can administer access to objects it doesn't own
  • Can be granted to custom roles for delegated security administration

Q6: Explain the access chain needed to query a table.

A: A role needs this complete chain (all 4 required):

  1. USAGE on Warehouse (to have compute resources)
  2. USAGE on Database (to enter the database)
  3. USAGE on Schema (to see objects in schema)
  4. SELECT on Table/View (to read data)
Missing any one results in an error. USAGE is like having a "key to the door" - it doesn't grant data access, just the ability to enter that level.

Q7: What are database roles and how do they differ from account roles?

A: Database roles are scoped to a single database:

  • Can only grant privileges on objects WITHIN their database
  • Created with CREATE DATABASE ROLE db_name.role_name
  • Key advantage: travel with data shares - consumers get the database role and its privileges
  • Account roles are account-wide and can't be shared
  • Database roles are granted TO account roles (not the reverse)

Q8: A user can see a database but gets "Object does not exist" on a table. Why?

A: The user's active role has USAGE on the database but is missing one of:

  • USAGE on the schema (most common cause) - they can see the DB but not the schema contents
  • SELECT on the table - they can see the schema but not query the table
Note: "Object does not exist" is deliberately vague (not "permission denied") to avoid information leakage. The user can't tell if the object truly doesn't exist or they lack access. This is a security feature.

Q9: Design an RBAC structure for a company with analysts, engineers, and data scientists.

A: 

-- Access roles (privileges)
CERT_RAW_READ    -- SELECT on raw/staging schemas
CERT_CURATED_READ -- SELECT on curated/marts schemas
CERT_RAW_WRITE   -- INSERT/UPDATE on staging
CERT_ML_ACCESS   -- Access to ML schemas + stages

-- Functional roles (assigned to users)
DATA_ENGINEER  -- gets RAW_READ + RAW_WRITE + CURATED_READ
DATA_ANALYST   -- gets CURATED_READ only
DATA_SCIENTIST -- gets CURATED_READ + ML_ACCESS

-- Hierarchy: All functional roles --> SYSADMIN --> ACCOUNTADMIN

Q10: What are secondary roles and how do they help?

A: Secondary roles allow a session to use privileges from multiple roles simultaneously:

  • Primary role: The main role for the session (objects created are owned by this role)
  • Secondary roles: Additional roles whose privileges are ALSO available
  • Set with: USE SECONDARY ROLES ALL; or DEFAULT_SECONDARY_ROLES = ('ALL')
  • Benefit: User doesn't need to switch roles to access objects owned by different roles
  • Without secondary roles: Must USE ROLE to switch, loses context of previous role
