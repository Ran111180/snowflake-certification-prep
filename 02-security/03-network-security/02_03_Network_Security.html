2. Network Policies

How Network Policies Work

  EVALUATION ORDER:

  1. Check BLOCKED_IP_LIST first
     - If client IP matches BLOCKED --> DENY (even if also in ALLOWED)
  
  2. Check ALLOWED_IP_LIST
     - If list is non-empty: client IP MUST match --> else DENY
     - If list is empty: all IPs allowed (unless blocked)

  SPECIAL CASE: 0.0.0.0/0
     - In ALLOWED_IP_LIST: allows ALL IPs (but BLOCKED still takes priority)
     - This is useful when you want to block specific IPs but allow everything else

Network Policy Levels

LevelApplied WithScopePriority
Account-levelALTER ACCOUNT SET NETWORK_POLICY = ...All users in accountLowest (default for all)
User-levelALTER USER SET NETWORK_POLICY = ...Specific user onlyHighest (overrides account)
Security IntegrationOn OAuth/SAML integrationUsers authenticating via that integrationIntegration-specific
Exam Tip - Priority: User-level policy overrides account-level policy. If a user has their own network policy, the account-level policy is ignored for that user. This allows exceptions (e.g., a service account that needs to connect from anywhere while other users are restricted).

Network Policy Syntax

-- Create a restrictive policy (only office IPs allowed)
CREATE NETWORK POLICY office_only_policy
  ALLOWED_IP_LIST = ('203.0.113.0/24', '198.51.100.0/24')
  BLOCKED_IP_LIST = ('203.0.113.99')  -- Block specific IP within range
  COMMENT = 'Only allow office network ranges';

-- Apply to entire account
ALTER ACCOUNT SET NETWORK_POLICY = office_only_policy;

-- Apply to specific user (overrides account policy)
ALTER USER service_user SET NETWORK_POLICY = service_policy;

-- Remove/unset
ALTER ACCOUNT UNSET NETWORK_POLICY;
ALTER USER service_user UNSET NETWORK_POLICY;

-- View current policies
SHOW NETWORK POLICIES;
DESCRIBE NETWORK POLICY office_only_policy;
DANGER: If you set a network policy that blocks YOUR OWN IP, you'll be locked out! Always:
  1. Include your current IP in ALLOWED_IP_LIST before applying
  2. Test with user-level policy on a test user FIRST
  3. Keep a backup user without network policy restrictions
  4. Snowflake support can remove account-level policies if you're locked out

3. Private Connectivity

Business Critical+ Only

What Is Private Connectivity?

Private connectivity routes traffic between your network and Snowflake through the cloud provider's private backbone - never traversing the public internet.

CloudTechnologyHow It Works
AWSAWS PrivateLinkVPC Endpoint connects to Snowflake's VPC privately
AzureAzure Private LinkPrivate Endpoint in your VNet connects to Snowflake
GCPPrivate Service ConnectPSC endpoint connects to Snowflake's service attachment
 
  WITHOUT PRIVATE CONNECTIVITY:
  Your VPC/VNet --> Internet Gateway --> Public Internet --> Snowflake

  WITH PRIVATE CONNECTIVITY (e.g., AWS PrivateLink):
  Your VPC --> VPC Endpoint --> AWS Private Network --> Snowflake VPC
  (Traffic NEVER leaves the AWS backbone)

Private Connectivity Benefits

  • Security: Traffic never traverses public internet
  • Compliance: Required by many regulated industries (HIPAA, PCI, FedRAMP)
  • Performance: Lower latency, more consistent bandwidth
  • Simplified networking: No need for complex VPN setups

Setup Overview

  STEPS FOR AWS PrivateLink:
  1. Enable PrivateLink on Snowflake account (by Snowflake - org admin request)
  2. Get Snowflake's AWS service name for PrivateLink
     SELECT SYSTEM$GET_PRIVATELINK_CONFIG();
  3. Create VPC Endpoint in YOUR AWS account pointing to Snowflake's service
  4. Update DNS to resolve Snowflake URL to private endpoint IP
  5. Connect using privatelink URL: account.region.privatelink.snowflakecomputing.com
  
  NOTE: Can block public access entirely with:
  ALTER ACCOUNT SET ALLOW_CLIENT_MFA_CACHING = TRUE;
  -- Combined with network policy blocking non-private IPs
Private Connectivity Key Facts:
  • Requires Business Critical edition or higher
  • Additional cost for the private connectivity service
  • Must be enabled by Snowflake (submit request through support/org admin)
  • URL changes: <account>.<region>.privatelink.snowflakecomputing.com
  • Can run alongside public access (or block public with network policy)
  • Client-side VPC endpoint costs are on the customer

4. Network Rules

NEW Feature (2025-2026)

What Are Network Rules?

Network rules are a more flexible, modern replacement for the IP lists in network policies. They support additional identifier types beyond simple IP addresses.

FeatureLegacy Network PolicyNetwork Rules (New)
IP addressesYes (CIDR notation)Yes
VPC/VNet identifiersNoYes (VPCE IDs, Private Endpoint IDs)
Host namesNoYes (for egress control)
ReusabilityIP lists embedded in policyRules are reusable objects (reference in multiple policies)
Egress controlNo (ingress only)Yes (control what Snowflake can reach out to)
 
-- Create a network rule for office IPs
CREATE NETWORK RULE office_ips_rule
  TYPE = IPV4
  MODE = INGRESS
  VALUE_LIST = ('203.0.113.0/24', '198.51.100.0/24')
  COMMENT = 'Office IP ranges';

-- Create a network rule for AWS PrivateLink endpoints
CREATE NETWORK RULE privatelink_rule
  TYPE = AWSVPCEID
  MODE = INGRESS
  VALUE_LIST = ('vpce-0a1b2c3d4e5f6g7h8')
  COMMENT = 'VPC Endpoint for private access';

-- Create a network rule for egress (External Access Integration)
CREATE NETWORK RULE external_api_rule
  TYPE = HOST_PORT
  MODE = EGRESS
  VALUE_LIST = ('api.example.com:443', 'hooks.slack.com:443')
  COMMENT = 'Allow Snowflake to reach these external APIs';

-- Use network rules in a network policy
CREATE NETWORK POLICY modern_policy
  ALLOWED_NETWORK_RULE_LIST = ('office_ips_rule', 'privatelink_rule')
  BLOCKED_NETWORK_RULE_LIST = ()
  COMMENT = 'Policy using network rules';

External Access Integrations

Network rules also enable External Access Integrations - allowing UDFs/procedures to call external APIs:

-- Create external access integration (allows UDF to call external API)
CREATE EXTERNAL ACCESS INTEGRATION my_api_integration
  ALLOWED_NETWORK_RULES = ('external_api_rule')
  ENABLED = TRUE
  COMMENT = 'Allow access to example API';

-- Use in a UDF
CREATE FUNCTION call_api(input VARCHAR)
  RETURNS VARCHAR
  LANGUAGE PYTHON
  RUNTIME_VERSION = '3.11'
  EXTERNAL_ACCESS_INTEGRATIONS = (my_api_integration)
  HANDLER = 'main'
  ...
Network Rules Key Points:
  • More flexible than legacy IP-only network policies
  • Support VPC endpoint IDs (better for private connectivity)
  • Reusable across multiple policies
  • Enable egress control (what Snowflake UDFs/procedures can connect to)
  • Used in External Access Integrations for UDF/procedure network access

6. Interview & Certification Q&A

Q1: What is a network policy and how does it control access?

A: A network policy restricts which IP addresses can connect to Snowflake:

  • ALLOWED_IP_LIST: Only these IPs can connect (whitelist). If non-empty, all other IPs are blocked.
  • BLOCKED_IP_LIST: These IPs are always blocked (blacklist). Takes priority over allowed list.
  • Evaluation: BLOCKED checked first (deny) --> then ALLOWED checked (must match if list non-empty)
  • Can be applied at account level (all users) or user level (specific user, overrides account)

Q2: What happens if both account-level and user-level network policies exist?

A: User-level policy completely overrides account-level policy for that user. The account policy is NOT checked at all. This allows:

  • Service accounts to have broader access while human users are restricted
  • Exceptions for specific users who work from different locations
  • Testing new policies on individual users before account-wide deployment

Q3: What is AWS PrivateLink and when should you use it?

A: AWS PrivateLink creates a private connection between your VPC and Snowflake's VPC through AWS's internal network:

  • When to use: Regulated industries (HIPAA, PCI), security-sensitive data, compliance requirements that prohibit internet transit
  • Requirements: Business Critical edition, Snowflake enablement, customer VPC endpoint
  • Benefits: Traffic never leaves AWS backbone, lower latency, better security posture
  • Cost: Additional Snowflake charge + AWS VPC endpoint charges

Q4: What's the difference between network policies and network rules?

A:

  • Network Policies (legacy): Contain IP lists directly (ALLOWED_IP_LIST, BLOCKED_IP_LIST). IP addresses only. Ingress only.
  • Network Rules (modern): Reusable objects that define network identifiers. Support IPs, VPC endpoint IDs, and hostnames. Support both ingress AND egress. Referenced by policies via ALLOWED_NETWORK_RULE_LIST.
Network rules are the recommended modern approach. They also enable External Access Integrations for UDF/procedure egress control.

Q5: Can Snowflake UDFs call external APIs? How is this secured?

A: Yes, through External Access Integrations:

  1. Create a Network Rule (TYPE=HOST_PORT, MODE=EGRESS) specifying allowed endpoints
  2. Create an External Access Integration referencing the network rule
  3. Reference the integration in the UDF/procedure creation
This ensures UDFs can ONLY reach approved external endpoints - preventing data exfiltration through arbitrary network calls. By default, UDFs have NO network access.

Q6: A company needs to ensure Snowflake is ONLY accessible from their corporate VPN. How?

A: Multiple approaches depending on requirements:

  1. Network Policy: Set ALLOWED_IP_LIST to VPN exit IP ranges only. Simplest approach.
  2. Private Connectivity + Network Policy: Set up PrivateLink AND block all public IPs. Most secure - traffic never touches internet.
  3. Network Rules + VPC Endpoint: Use AWSVPCEID rule type to only allow traffic from specific VPC endpoints.
Recommendation: PrivateLink + network policy blocking public access for highest security. Requires Business Critical edition.

Q7: What port does Snowflake use and can it be changed?

A: Snowflake exclusively uses port 443 (HTTPS). This cannot be changed. Benefits:

  • Simplifies firewall rules (just allow outbound 443)
  • Works through most corporate proxies and firewalls
  • TLS 1.2+ is always enforced
  • No need to open special database ports (1433, 5432, etc.)

Q8: What is SYSTEM$GET_PRIVATELINK_CONFIG() used for?

A: This system function returns the configuration information needed to set up PrivateLink on the client side:

  • Snowflake's AWS service name for PrivateLink
  • The privatelink account URL to use for connections
  • OCSP endpoint for certificate validation
You give this info to your network team to create the VPC endpoint in your AWS account.
