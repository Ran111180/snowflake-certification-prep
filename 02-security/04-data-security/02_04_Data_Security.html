Tri-Secret Secure

Business Critical+ Only

  STANDARD ENCRYPTION:
  Data encrypted with Snowflake-managed keys only
  Customer trusts Snowflake entirely

  TRI-SECRET SECURE:
  Composite master key = Snowflake key + Customer key (from cloud KMS)
  
  Customer provides key via:
  - AWS KMS (Key Management Service)
  - Azure Key Vault
  - GCP Cloud KMS

  BENEFIT: Customer can REVOKE their key --> Snowflake CANNOT read the data
  This gives customers ultimate control even over Snowflake employees.
Encryption Key Facts:
  • ALL data always encrypted at rest (AES-256) and in transit (TLS 1.2+)
  • Cannot be disabled - encryption is mandatory
  • Key rotation: automatic, annual
  • Periodic re-keying: Snowflake re-encrypts old data with new keys
  • Tri-Secret Secure: Business Critical+ only; customer holds part of the key

2. Dynamic Data Masking

Enterprise+ Only

What Is Dynamic Data Masking?

Column-level security that masks sensitive data at query time based on the user's role. Data is stored unmasked but appears masked to unauthorized roles.

  TABLE: CUSTOMERS
  +----+----------+------------------+-----------+
  | ID | NAME     | EMAIL            | SSN       |
  +----+----------+------------------+-----------+
  | 1  | Alice    | alice@corp.com   | 123-45-6789 |
  | 2  | Bob      | bob@corp.com     | 987-65-4321 |

  ROLE: ADMIN (unmask privilege)     ROLE: ANALYST (no unmask)
  +----+--------+----------------+   +----+--------+------------+
  | 1  | Alice  | alice@corp.com |   | 1  | Alice  | ***@***.com|
  | 2  | Bob    | bob@corp.com   |   | 2  | Bob    | ***@***.com|
  +----+--------+----------------+   +----+--------+------------+

  Same query, same table, different results based on ROLE!

Masking Policy Syntax

-- Create a masking policy for email
CREATE OR REPLACE MASKING POLICY email_mask AS
  (val STRING) RETURNS STRING ->
  CASE
    WHEN CURRENT_ROLE() IN ('ADMIN_ROLE', 'HR_ROLE') THEN val
    ELSE REGEXP_REPLACE(val, '.+@', '***@')
  END;

-- Apply to a column
ALTER TABLE customers MODIFY COLUMN email 
  SET MASKING POLICY email_mask;

-- Create a masking policy for SSN (full mask)
CREATE OR REPLACE MASKING POLICY ssn_mask AS
  (val STRING) RETURNS STRING ->
  CASE
    WHEN CURRENT_ROLE() IN ('HR_ROLE') THEN val
    WHEN CURRENT_ROLE() IN ('ANALYST_ROLE') THEN 'XXX-XX-' || SUBSTR(val, 8)
    ELSE '***-**-****'
  END;

-- Conditional masking (based on another column)
CREATE OR REPLACE MASKING POLICY conditional_mask AS
  (val STRING, country STRING) RETURNS STRING ->
  CASE
    WHEN country = 'US' AND CURRENT_ROLE() NOT IN ('COMPLIANCE') THEN '***'
    ELSE val
  END;

-- Unset masking policy
ALTER TABLE customers MODIFY COLUMN email UNSET MASKING POLICY;
Exam Tips - Masking Policies:
  • Enterprise edition or higher required
  • Applied at the column level (not row, not table)
  • Policy return type MUST match column data type
  • Evaluated at query time (dynamic, not physical masking)
  • Data is stored UNMASKED - policy just controls what's shown
  • One masking policy per column (cannot stack multiple)
  • Can use CURRENT_ROLE(), IS_ROLE_IN_SESSION(), system functions in conditions
  • Works with views, clones, and data sharing

3. Row Access Policies

Enterprise+ Only

What Are Row Access Policies?

Row-level security that filters which ROWS a user can see based on their role or attributes. Like an invisible WHERE clause automatically applied.

  TABLE: SALES_DATA
  +----+--------+---------+--------+
  | ID | REGION | REVENUE | REP    |
  +----+--------+---------+--------+
  | 1  | EAST   | 50000   | Alice  |
  | 2  | WEST   | 75000   | Bob    |
  | 3  | EAST   | 30000   | Carol  |
  | 4  | NORTH  | 45000   | Dave   |

  ROLE: EAST_MANAGER sees:         ROLE: ADMIN sees:
  +----+------+---------+-------+  +----+-------+---------+------+
  | 1  | EAST | 50000   | Alice |  | 1  | EAST  | 50000   | Alice|
  | 3  | EAST | 30000   | Carol |  | 2  | WEST  | 75000   | Bob  |
                                   | 3  | EAST  | 30000   | Carol|
                                   | 4  | NORTH | 45000   | Dave |

Row Access Policy Syntax

-- Create a mapping table (which role sees which region)
CREATE TABLE region_access (role_name VARCHAR, region VARCHAR);
INSERT INTO region_access VALUES 
  ('EAST_MANAGER', 'EAST'),
  ('WEST_MANAGER', 'WEST'),
  ('ADMIN_ROLE', 'EAST'), ('ADMIN_ROLE', 'WEST'), ('ADMIN_ROLE', 'NORTH');

-- Create row access policy
CREATE OR REPLACE ROW ACCESS POLICY region_policy AS
  (region_val VARCHAR) RETURNS BOOLEAN ->
  CURRENT_ROLE() = 'ADMIN_ROLE'
  OR EXISTS (
    SELECT 1 FROM region_access 
    WHERE role_name = CURRENT_ROLE() 
      AND region = region_val
  );

-- Apply to table
ALTER TABLE sales_data ADD ROW ACCESS POLICY region_policy ON (region);

-- Remove
ALTER TABLE sales_data DROP ROW ACCESS POLICY region_policy;
Row Access Policy Key Facts:
  • Returns BOOLEAN: TRUE = row visible, FALSE = row filtered out
  • Applied to tables/views - acts like invisible WHERE clause
  • ONE row access policy per table (but policy can reference multiple columns)
  • Evaluated BEFORE any user-specified WHERE clause
  • Cannot be bypassed (even table owner sees filtered results unless policy allows)
  • Use mapping tables for flexible role-to-data assignments
  • Enterprise edition required

4. Object Tagging & Data Classification

Object Tags

Tags are key-value metadata attached to Snowflake objects for governance, cost tracking, and policy management.

-- Create a tag
CREATE TAG sensitivity_level ALLOWED_VALUES = ('PUBLIC', 'INTERNAL', 'CONFIDENTIAL', 'RESTRICTED');
CREATE TAG cost_center;
CREATE TAG data_owner;

-- Apply tags to objects
ALTER TABLE customers SET TAG sensitivity_level = 'CONFIDENTIAL';
ALTER TABLE customers MODIFY COLUMN ssn SET TAG sensitivity_level = 'RESTRICTED';
ALTER WAREHOUSE compute_wh SET TAG cost_center = 'ENGINEERING';

-- Query tags
SELECT * FROM TABLE(INFORMATION_SCHEMA.TAG_REFERENCES('customers', 'TABLE'));

-- Tag-based masking policies (apply policy to all tagged columns!)
ALTER TAG sensitivity_level SET MASKING POLICY ssn_mask;
-- Now ANY column tagged 'RESTRICTED' automatically gets the masking policy!

Data Classification

Snowflake can automatically detect and classify sensitive data:

-- Classify a table (auto-detect PII, PHI, etc.)
SELECT * FROM TABLE(
  SNOWFLAKE.CORE.CLASSIFY('my_table', {'auto_tag': true})
);

-- Classification categories detected:
-- IDENTIFIER: SSN, email, phone, credit card
-- QUASI_IDENTIFIER: name, address, date of birth
-- SENSITIVE: salary, medical records
-- SYSTEM: internal IDs, timestamps

-- View classification results
SELECT * FROM TABLE(
  INFORMATION_SCHEMA.TAG_REFERENCES_ALL_COLUMNS('my_table', 'TABLE')
);
Tag-Based Policies (Powerful Feature):

Instead of applying a masking policy column-by-column, you can attach it to a TAG. Then every column with that tag automatically gets the policy. This scales across thousands of columns/tables.

Projection Policy (Prevents Column Selection)

-- Prevent non-admins from seeing SSN column at all
CREATE PROJECTION POLICY hide_sensitive AS () RETURNS PROJECTION_CONSTRAINT ->
  CASE
    WHEN CURRENT_ROLE() IN ('ADMIN_ROLE') THEN PROJECTION_CONSTRAINT(ALLOW => true)
    ELSE PROJECTION_CONSTRAINT(ALLOW => false)
  END;

ALTER TABLE customers MODIFY COLUMN ssn SET PROJECTION POLICY hide_sensitive;
-- Non-admins can't even SELECT ssn (not just masked - completely hidden)

Aggregation Policy (k-Anonymity)

-- Require queries to aggregate at least 5 rows
CREATE AGGREGATION POLICY min_group_size AS () RETURNS AGGREGATION_CONSTRAINT ->
  AGGREGATION_CONSTRAINT(MIN_GROUP_SIZE => 5);

ALTER TABLE patients SET AGGREGATION POLICY min_group_size;
-- Queries must GROUP BY with groups of 5+ rows, or they fail
-- Prevents re-identification of individuals

7. Interview & Certification Q&A

Q1: How does encryption work in Snowflake? Can it be disabled?

A: Snowflake uses end-to-end encryption that CANNOT be disabled:

  • At rest: AES-256 encryption for all data in micro-partitions
  • In transit: TLS 1.2+ for all network communication
  • Key management: Hierarchical model (root > account > table > file keys)
  • Key rotation: Automatic annual rotation + periodic re-keying of data
  • Tri-Secret Secure: Optional (Business Critical+) - customer provides part of the key
Customers never manage encryption keys unless using Tri-Secret Secure.

Q2: What's the difference between masking policies and row access policies?

Q3: Explain Tri-Secret Secure. Why would a company use it?

A: Tri-Secret Secure uses a composite master key made from BOTH a Snowflake-managed key AND a customer-managed key (stored in cloud KMS):

  • How: Customer creates a key in AWS KMS/Azure Key Vault/GCP Cloud KMS. Snowflake uses this + its own key to create a composite key.
  • Why: Customer can REVOKE their key at any time, making data unreadable - even by Snowflake employees. Provides ultimate control.
  • Use cases: Highly regulated industries (banking, healthcare, government), compliance requirements that demand customer key control, zero-trust with cloud providers.
  • Requires: Business Critical edition or higher.

Q4: How do tag-based masking policies work?

A: Instead of applying a masking policy to each column individually:

  1. Create a tag (e.g., sensitivity = 'RESTRICTED')
  2. Attach the masking policy to the TAG: ALTER TAG sensitivity SET MASKING POLICY my_mask
  3. Tag columns that need masking: ALTER TABLE t MODIFY COLUMN ssn SET TAG sensitivity = 'RESTRICTED'
  4. Any column with that tag value AUTOMATICALLY gets the masking policy
Benefits: Scales to thousands of columns, consistent policy enforcement, easier governance.

Q5: What is data classification in Snowflake?

A: Data classification automatically scans table data and metadata to identify sensitive information:

  • Detects PII: emails, SSNs, phone numbers, credit cards, names
  • Categories: IDENTIFIER, QUASI_IDENTIFIER, SENSITIVE
  • Uses both column names AND data patterns for detection
  • Can auto-tag columns with system tags (SNOWFLAKE.CORE.SEMANTIC_CATEGORY, PRIVACY_CATEGORY)
  • Helps identify what needs masking/protection
  • Called via: SYSTEM$CLASSIFY() or SNOWFLAKE.CORE.CLASSIFY()

Q6: Can a table owner bypass masking and row access policies?

A: No! This is a key security feature:

  • Masking policies and row access policies are enforced for ALL roles, including the table owner
  • Even ACCOUNTADMIN sees masked data unless the policy explicitly allows it
  • The policy body determines who sees what (using CURRENT_ROLE() etc.)
  • Only the policy OWNER can modify the policy, and the MASKING_ADMIN or equivalent role sets them
  • This prevents privilege escalation through ownership

Q7: What are the new projection and aggregation policies?

A:

  • Projection Policy: Controls whether a column can appear in query results AT ALL. Unlike masking (shows masked value), projection completely hides the column. Query with that column fails or returns null.
  • Aggregation Policy: Enforces minimum group size (k-anonymity). Queries must aggregate enough rows to prevent individual identification. E.g., MIN_GROUP_SIZE=5 means any GROUP BY must have 5+ rows per group.
  • Join Policy: Controls which tables can be joined together, preventing correlation attacks (joining PII with external data).

Q8: Design a data security strategy for a healthcare company storing patient records.

A:

  1. Encryption: Tri-Secret Secure (Business Critical) for HIPAA compliance
  2. Network: PrivateLink + restrictive network policy (no public internet access)
  3. Column masking: SSN, DOB, phone masked for all non-clinical roles
  4. Row access: Doctors see only their patients; nurses see their department only
  5. Classification: Auto-classify to discover PHI in all tables
  6. Tags: Tag all PHI columns, apply tag-based masking at scale
  7. Aggregation: Research role requires k-anonymity (min group size 10)
  8. Audit: Access history tracking on all patient tables
