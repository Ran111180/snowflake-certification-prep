2. Access History

What Does ACCESS_HISTORY Track?

Records which columns and objects were read (SELECT) and written (INSERT/UPDATE/DELETE/COPY) by each query.

  ACCESS_HISTORY captures:
  +------------------------------------------------------------+
  | QUERY_ID         | Which query accessed data               |
  | QUERY_START_TIME | When                                    |
  | USER_NAME        | Who ran the query                       |
  | ROLE_NAME        | Which role was active                   |
  | DIRECT_OBJECTS   | Tables/views directly referenced in SQL |
  | BASE_OBJECTS     | Underlying base tables (through views)  |
  | OBJECTS_MODIFIED | Tables written to (DML targets)         |
  | COLUMNS_READ     | Specific columns accessed               |
  +------------------------------------------------------------+

  KEY INSIGHT: Even if user queries a VIEW, ACCESS_HISTORY records
  the BASE TABLES underneath. This provides true data lineage!

Why Access History Matters

Use CaseHow Access History Helps
Compliance auditing (GDPR, HIPAA)Prove who accessed patient/customer data
Security investigationTrace data exfiltration or unauthorized access
Data lifecycle managementFind unused tables (no access in 90 days = archive?)
Impact analysisBefore changing a table, see who uses it
Cost attributionWhich teams/users query which data
Access History Key Facts:
  • Available in Enterprise edition and above
  • Records both read (SELECT) and write (DML) operations
  • Tracks access through views down to base tables
  • Column-level granularity (which specific columns were read)
  • 365-day retention in ACCOUNT_USAGE
  • Latency: up to 3 hours

3. Object Dependencies

What Are Object Dependencies?

Dependencies track relationships between objects - which views depend on which tables, which functions call which tables, etc.

  DEPENDENCY CHAIN EXAMPLE:

  BASE TABLE: raw.customers
       |
       +--> VIEW: analytics.customer_summary (depends on raw.customers)
       |         |
       |         +--> DASHBOARD (queries customer_summary)
       |
       +--> PROCEDURE: etl.transform_customers (reads raw.customers)
       |
       +--> FUNCTION: get_customer_name (accesses raw.customers)

  If you DROP or ALTER raw.customers --> all dependents may break!
  OBJECT_DEPENDENCIES tells you what will be affected.
  
-- Query object dependencies
SELECT 
  referencing_object_name,
  referencing_object_type,
  referenced_object_name, 
  referenced_object_type,
  dependency_type
FROM SNOWFLAKE.ACCOUNT_USAGE.OBJECT_DEPENDENCIES
WHERE referenced_database = 'CERT_STUDY_DB'
ORDER BY referenced_object_name;

4. Data Lineage

Column-Level Lineage

Snowflake tracks how data flows from source columns to target columns through transformations.

  SOURCE TABLE             TRANSFORMATION           TARGET TABLE
  orders.customer_id  -->  JOIN + GROUP BY  -->  summary.customer_id
  orders.amount       -->  SUM()           -->  summary.total_revenue
  orders.order_date   -->  DATE_TRUNC()    -->  summary.order_month

  LINEAGE tells you: "summary.total_revenue comes from orders.amount via SUM()"

Lineage via ACCESS_HISTORY

-- The OBJECTS_MODIFIED field in ACCESS_HISTORY shows write lineage:
-- Query: INSERT INTO target SELECT col1, SUM(col2) FROM source GROUP BY col1
-- ACCESS_HISTORY records:
--   base_objects_accessed: source.col1, source.col2
--   objects_modified: target (columns: col1, sum_col2)
-- This creates a lineage link: source --> target

GET_LINEAGE Function

-- Trace lineage for a specific object (Enterprise+)
SELECT *
FROM TABLE(SNOWFLAKE.CORE.GET_LINEAGE(
  'CERT_STUDY_DB.ARCHITECTURE.SAMPLE_DATA',  -- object name
  'TABLE',                                     -- object type
  'DOWNSTREAM'                                 -- direction: UPSTREAM or DOWNSTREAM
));

6. Hands-On SQL Scripts

Script 1: Access History Analysis

-- Who accessed what in the last 24 hours?
SELECT 
  query_start_time,
  user_name,
  role_name,
  direct_objects_accessed,
  base_objects_accessed,
  objects_modified
FROM SNOWFLAKE.ACCOUNT_USAGE.ACCESS_HISTORY
WHERE query_start_time > DATEADD('hour', -24, CURRENT_TIMESTAMP())
ORDER BY query_start_time DESC
LIMIT 20;

Script 2: Find Unused Tables

-- Tables not accessed in the last 30 days (candidates for archival)
SELECT t.table_catalog, t.table_schema, t.table_name,
       t.row_count, t.bytes,
       MAX(ah.query_start_time) AS last_accessed
FROM SNOWFLAKE.ACCOUNT_USAGE.TABLES t
LEFT JOIN SNOWFLAKE.ACCOUNT_USAGE.ACCESS_HISTORY ah
  ON ARRAY_CONTAINS(t.table_name::VARIANT, ah.base_objects_accessed)
WHERE t.deleted IS NULL
  AND t.table_catalog = 'CERT_STUDY_DB'
GROUP BY 1, 2, 3, 4, 5
HAVING last_accessed IS NULL 
   OR last_accessed < DATEADD('day', -30, CURRENT_TIMESTAMP())
ORDER BY t.bytes DESC;

Script 3: Query History for Governance

-- Query patterns by user (who runs what type of queries)
SELECT 
  user_name,
  query_type,
  COUNT(*) AS query_count,
  ROUND(SUM(total_elapsed_time) / 1000, 1) AS total_seconds,
  ROUND(SUM(credits_used_cloud_services), 4) AS cs_credits
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY
WHERE start_time > DATEADD('day', -7, CURRENT_TIMESTAMP())
GROUP BY user_name, query_type
ORDER BY query_count DESC
LIMIT 20;

-- Find long-running queries (performance governance)
SELECT query_id, user_name, role_name,
       SUBSTR(query_text, 1, 100) AS query_preview,
       total_elapsed_time / 1000 AS elapsed_sec,
       bytes_scanned / (1024*1024*1024) AS gb_scanned
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY
WHERE start_time > DATEADD('day', -7, CURRENT_TIMESTAMP())
  AND total_elapsed_time > 30000  -- > 30 seconds
ORDER BY total_elapsed_time DESC
LIMIT 10;

Script 6: Login & Security Audit

-- Failed logins (potential brute force)
SELECT 
  DATE_TRUNC('hour', event_timestamp) AS hour,
  user_name,
  COUNT(*) AS failed_attempts,
  ARRAY_AGG(DISTINCT client_ip) AS source_ips
FROM SNOWFLAKE.ACCOUNT_USAGE.LOGIN_HISTORY
WHERE is_success = 'NO'
  AND event_timestamp > DATEADD('day', -7, CURRENT_TIMESTAMP())
GROUP BY hour, user_name
HAVING failed_attempts > 3
ORDER BY hour DESC;

-- Users without MFA (security risk)
SELECT name, login_name, has_mfa, ext_authn_duo,
       default_role, last_success_login
FROM SNOWFLAKE.ACCOUNT_USAGE.USERS
WHERE deleted_on IS NULL
  AND has_mfa = false
  AND disabled = false;

7. Interview & Certification Q&A

Q1: What is ACCESS_HISTORY and why is it important for governance?

A: ACCESS_HISTORY is an ACCOUNT_USAGE view that records which objects and columns were read/written by each query:

  • Tracks column-level access (not just table-level)
  • Resolves through views to base tables (true lineage)
  • Records both reads (SELECT) and writes (INSERT/UPDATE/DELETE)
  • 365-day retention for compliance auditing
  • Critical for GDPR (right to know who accessed personal data), HIPAA, SOX
  • Enterprise edition required

Q2: How can you determine if a table is safe to drop?

A: Use multiple governance tools:

  1. OBJECT_DEPENDENCIES: Check if any views/functions reference the table
  2. ACCESS_HISTORY: Check when it was last queried (no access in 90+ days?)
  3. QUERY_HISTORY: Search for queries referencing the table name
  4. GET_LINEAGE: Check downstream dependencies
  5. Tags: Check if it's tagged as critical/production
If no dependencies, no recent access, and no critical tags - safe to archive or drop (with Time Travel as safety net).

Q3: What's the difference between INFORMATION_SCHEMA and ACCOUNT_USAGE for governance?

A:

INFORMATION_SCHEMAACCOUNT_USAGE
ScopeCurrent databaseEntire account
LatencyReal-time45 min - 3 hours

Dropped objectsNot shownIncluded (with deleted timestamp)
AccessAny role with DB accessACCOUNTADMIN or granted
Governance useOperational checksAudit, compliance, historical analysis
For governance/compliance, ACCOUNT_USAGE is preferred (365-day history, account-wide, includes dropped objects).

Q4: What is Snowflake Horizon?

A: Snowflake Horizon is the unified data governance solution built into Snowflake. It's not a separate product - it's the collection of governance features organized into pillars:

  • Discover: Search, catalog, classify, tag, lineage
  • Protect: Masking, row access, encryption, policies
  • Comply: Access history, audit logs, data retention
  • Secure: Trust Center, network policies, authentication
  • Access: RBAC, sharing, Marketplace, database roles
Everything is built-in (no separate deployment). Available capabilities vary by edition.

Q5: What is the Trust Center?

A: Trust Center is Snowflake's security posture management tool:

  • Scanners: Automated checks that detect security misconfigurations
  • CIS Benchmark scanner: Checks against industry security standards
  • Security Essentials: Basic hygiene (MFA enrollment, network policies, etc.)
  • Threat Intelligence: Detects suspicious patterns (unusual logins, bulk exports)
  • Findings: Prioritized list with severity and remediation steps
Accessible in Snowsight under Admin > Security > Trust Center.

Q6: How does data lineage work in Snowflake?

A: Snowflake automatically tracks data lineage at column level:

  • Write lineage: When INSERT/CTAS/COPY writes data, ACCESS_HISTORY records the source columns and target columns
  • Read lineage: When SELECT reads through views, base objects are recorded
  • GET_LINEAGE function: Traces upstream (where data came from) or downstream (where data goes)
  • Works across: tables, views, stages, streams, tasks, dynamic tables
  • Available in Enterprise+ edition
Use cases: Impact analysis before schema changes, compliance tracking, data quality root cause.

Q7: A compliance officer needs to prove that only authorized users accessed patient records in the last year. How?

A: Query ACCESS_HISTORY combined with role information: 

SELECT ah.query_start_time, ah.user_name, ah.role_name,
       ah.direct_objects_accessed, ah.base_objects_accessed
FROM SNOWFLAKE.ACCOUNT_USAGE.ACCESS_HISTORY ah
WHERE ARRAY_CONTAINS('PATIENT_RECORDS'::VARIANT, ah.base_objects_accessed)
  AND ah.query_start_time > DATEADD('year', -1, CURRENT_TIMESTAMP())
ORDER BY ah.query_start_time;
Then cross-reference with authorized roles to identify any unauthorized access. This satisfies HIPAA audit requirements.

Q8: How would you set up a governance framework for a new Snowflake deployment?

A: Phased approach:

  1. Foundation: RBAC hierarchy (functional + access roles), network policies, MFA for admins
  2. Classification: Run SYSTEM$CLASSIFY on all tables, apply sensitivity tags
  3. Protection: Masking policies on tagged sensitive columns (tag-based for scale)
  4. Row security: Row access policies for multi-tenant or regional data
  5. Monitoring: Dashboard on ACCESS_HISTORY, LOGIN_HISTORY, QUERY_HISTORY
  6. Alerting: Alerts on failed logins, unusual access patterns, policy violations
  7. Trust Center: Enable all scanners, remediate findings
  8. Review: Quarterly access reviews using ACCESS_HISTORY + role grants
