1. Query Profile

What Is the Query Profile?

The Query Profile is a visual execution plan (DAG) showing how Snowflake processed a query. It's the #1 tool for performance diagnosis.

  QUERY PROFILE DAG (Directed Acyclic Graph):

  [TableScan: orders]  [TableScan: customers]
         |                      |
         v                      v
  [Filter: date > X]    [Filter: region = Y]
         |                      |
         +----------+-----------+
                    |
                    v
            [HashJoin: id = cust_id]
                    |
                    v
            [Aggregate: SUM, COUNT]
                    |
                    v
            [Sort: revenue DESC]
                    |
                    v
              [Result: LIMIT 100]

Key Metrics in Query Profile

MetricWhat It ShowsRed Flag Threshold
Partitions Scanned / TotalHow many micro-partitions were read vs skippedScanned > 50% of total = poor pruning
Bytes ScannedAmount of data read from storageMuch larger than result size = inefficient
% Scanned from CacheData served from local SSD vs remote storage0% on repeated query = cold cache
Spillage to Local DiskMemory overflow written to warehouse SSDAny spill > 0 = warehouse may be too small
Spillage to RemoteMemory overflow to cloud storageANY remote spill = definitely scale up
Exploding JoinsOutput rows >> input rows from a join10x output/input = likely bad join key
Queued TimeTime waiting for warehouse resources> 0 = concurrency issue (scale out)
Exam Tip - Performance Diagnosis Flow:
  1. Query slow? Check Query Profile first
  2. High partitions scanned? --> Add clustering key
  3. Spilling to disk? --> Increase warehouse size
  4. Queuing? --> Multi-cluster warehouse (scale out)
  5. Exploding joins? --> Fix join condition or data model
  6. Repeated same query? --> Leverage result cache

2. Partition Pruning

How Pruning Works (Recap + Performance Focus)

  GOOD PRUNING (well-clustered data):
  Query: WHERE order_date = '2024-06-15'
  Total partitions: 1000
  Partitions scanned: 3  (99.7% pruned!)
  
  BAD PRUNING (poorly clustered):
  Query: WHERE customer_id = 12345
  Total partitions: 1000
  Partitions scanned: 980  (only 2% pruned!)
  
  WHY? Data was loaded chronologically, so order_date is naturally clustered.
  But customer_id is scattered across ALL partitions.

What Enables Good Pruning?

FactorGood PruningPoor Pruning
Filter columnMatches data's clustering orderColumn values scattered across partitions
Filter typeEquality, range (BETWEEN, <, >)LIKE '%pattern%', functions on column
Data loadingOrdered/sequential loads (time-series)Random/shuffled bulk loads
Clustering keyDefined on filter columnsNo clustering key, or wrong columns
Pruning Killers (Functions on Columns): 
-- BAD: Function prevents pruning
WHERE YEAR(order_date) = 2024          -- wraps column in function!
WHERE UPPER(customer_name) = 'ALICE'   -- function blocks pruning

-- GOOD: Direct comparison enables pruning  
WHERE order_date >= '2024-01-01' AND order_date < '2025-01-01'
WHERE customer_name = 'Alice'

3. Clustering Keys

When to Use Clustering Keys

Use Clustering WhenDon't Cluster When
Table is large (multi-GB to TB)Table is small (< 1 GB)
Queries consistently filter on specific columnsQueries use different columns every time
Clustering depth is high (poor natural clustering)Natural clustering is already good (depth ~1-2)
Pruning ratio is bad in Query ProfilePruning already eliminates 90%+ partitions

Clustering Key Design

-- Check current clustering quality
SELECT SYSTEM$CLUSTERING_INFORMATION('my_table', '(date_col, category_col)');

-- Returns JSON with:
-- "average_depth": 5.2      (lower = better, 1 = perfect)
-- "average_overlaps": 3.1   (lower = better)
-- "total_partition_count": 200

-- Add clustering key
ALTER TABLE my_table CLUSTER BY (date_col, region);

-- Best practices for column choice:
-- 1. Columns used in WHERE/JOIN most often
-- 2. Date/timestamp columns first (range queries)
-- 3. Low-to-medium cardinality second (region, category)
-- 4. Max 3-4 columns in clustering key
-- 5. High cardinality columns (user_id) = usually bad choice

-- Remove clustering key (stops reclustering charges)
ALTER TABLE my_table DROP CLUSTERING KEY;
Automatic Clustering Service:
  • Once you define a clustering key, Snowflake AUTOMATICALLY re-clusters data in background
  • Uses serverless compute (not your warehouse) - separate billing
  • Runs when data changes significantly degrade clustering
  • Credit cost depends on table size and change frequency
  • Can be monitored: SHOW TABLES shows automatic_clustering = ON/OFF

4. Search Optimization Service (SOS)

Enterprise+ Only

What Does SOS Do?

Creates auxiliary data structures (like search indexes) for queries that partition pruning handles poorly:

Query PatternPruning AloneWith SOS
WHERE id = 12345 (point lookup)Scans many partitionsJumps directly to correct partition
WHERE col LIKE '%pattern%'Full scanUses search access path
WHERE variant:key = 'value'Scans all partitionsIndexes VARIANT paths
WHERE ST_CONTAINS(geo, point)Full scanSpatial indexing
WHERE col IN (val1, val2, ...100 values)Some pruningEfficient multi-point lookup
 
-- Enable SOS on a table
ALTER TABLE my_table ADD SEARCH OPTIMIZATION;

-- Enable on specific columns only (more cost-effective)
ALTER TABLE my_table ADD SEARCH OPTIMIZATION 
  ON EQUALITY(id, email)
  ON SUBSTRING(name)
  ON GEO(location);

-- Check status
SHOW TABLES LIKE 'my_table';  -- search_optimization = ON
DESCRIBE SEARCH OPTIMIZATION ON my_table;

-- Remove SOS
ALTER TABLE my_table DROP SEARCH OPTIMIZATION;
SOS Key Facts:
  • Enterprise edition required
  • Additional serverless compute cost for maintenance
  • Additional storage cost for search structures
  • Best for: point lookups on high-cardinality columns, LIKE substring searches, VARIANT field access
  • NOT needed for: range queries on clustered columns (pruning handles those)
  • Supplements clustering - doesn't replace it

5. Query Acceleration Service (QAS)

Enterprise+ Only

What Is QAS?

QAS offloads portions of a query to additional serverless compute resources, accelerating queries that benefit from more parallelism.

  WITHOUT QAS:                          WITH QAS:
  +------------------+                  +------------------+
  |  Your Warehouse  |                  |  Your Warehouse  |
  |  [processing..] |                  |  [processing..] |
  |  [processing..] |                  +------------------+
  |  [waiting..]    |                          +
  +------------------+                  +------------------+
                                        | QAS Serverless   |
  Query takes 60 seconds               | [accelerating..] |
                                        +------------------+
                                        
                                        Query takes 15 seconds!

Best Queries for QAS

Good CandidatesPoor Candidates
Large scans with selective filters (scan + filter pattern)Small quick queries (overhead not worth it)
Queries with many OR/IN conditionsQueries limited by single-node operations
Aggregations over large datasetsComplex multi-join queries (not parallelizable)
Queries that unevenly distribute workQueries that already max out warehouse
 
-- Enable QAS on a warehouse
ALTER WAREHOUSE my_wh SET 
  ENABLE_QUERY_ACCELERATION = TRUE
  QUERY_ACCELERATION_MAX_SCALE_FACTOR = 8;  -- up to 8x additional compute

-- Check eligible queries
SELECT query_id, eligible_query_acceleration_time
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_ACCELERATION_ELIGIBLE
WHERE start_time > DATEADD('day', -7, CURRENT_TIMESTAMP())
  AND eligible_query_acceleration_time > 0
ORDER BY eligible_query_acceleration_time DESC;

6. Caching Strategies (Performance Focus)

  CACHE HIERARCHY (checked in this order):

  1. RESULT CACHE (Cloud Services)
     - Full query result stored for 24h
     - Conditions: same query + same role + unchanged data
     - Cost: $0 (no warehouse needed)
     - Best for: repeated dashboard queries, scheduled reports

  2. LOCAL DISK CACHE (Warehouse SSD)
     - Raw partition data cached on node
     - Conditions: warehouse running + same partitions accessed
     - Cost: warehouse must stay running (credits)
     - Best for: iterative analysis on same dataset

  3. REMOTE DISK CACHE
     - Cloud storage warm cache layer  
     - Conditions: data recently accessed by any warehouse
     - Cost: included in storage/compute
     - Best for: frequently accessed hot data

  TUNING ACTIONS:
  - For dashboards: rely on result cache (run queries periodically to keep warm)
  - For interactive: set AUTO_SUSPEND high enough to keep SSD cache (120-600s)
  - For batch ETL: set AUTO_SUSPEND low (no reuse benefit)

Materialized Views as Performance Tool

-- Create materialized view for expensive aggregation (Enterprise+)
CREATE MATERIALIZED VIEW daily_sales_mv AS
  SELECT order_date, region, SUM(amount) AS total_sales, COUNT(*) AS order_count
  FROM orders
  GROUP BY order_date, region;

-- Queries automatically use the MV when it matches:
SELECT region, SUM(amount) FROM orders WHERE order_date > '2024-01-01' GROUP BY region;
-- Optimizer may rewrite to use daily_sales_mv instead of scanning orders!

-- Key facts:
-- Enterprise+ only
-- Maintained automatically (serverless)
-- Limited to: SELECT, JOIN, GROUP BY, WHERE (no UNION, subquery, HAVING)
-- Optimizer decides when to use it (transparent to user)

Script 3: Warehouse Performance Monitoring

-- Queries that spilled (need bigger warehouse)
SELECT query_id, 
       SUBSTR(query_text, 1, 80) AS query,
       warehouse_size,
       bytes_spilled_to_local_storage / (1024*1024*1024) AS gb_spilled_local,
       bytes_spilled_to_remote_storage / (1024*1024*1024) AS gb_spilled_remote,
       total_elapsed_time / 1000 AS seconds
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY
WHERE start_time > DATEADD('day', -7, CURRENT_TIMESTAMP())
  AND (bytes_spilled_to_local_storage > 0 OR bytes_spilled_to_remote_storage > 0)
ORDER BY bytes_spilled_to_remote_storage DESC
LIMIT 10;

-- Queries that were queued (need multi-cluster or separate warehouse)
SELECT query_id,
       SUBSTR(query_text, 1, 80) AS query,
       warehouse_name,
       queued_overload_time / 1000 AS queue_seconds
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY
WHERE start_time > DATEADD('day', -7, CURRENT_TIMESTAMP())
  AND queued_overload_time > 0
ORDER BY queued_overload_time DESC
LIMIT 10;

Script 4: Cache Effectiveness

-- How effective is caching across the account?
SELECT 
  DATE_TRUNC('day', start_time) AS day,
  COUNT(*) AS total_queries,
  SUM(CASE WHEN bytes_scanned = 0 AND rows_produced > 0 THEN 1 ELSE 0 END) AS result_cache_hits,
  ROUND(result_cache_hits / total_queries * 100, 1) AS cache_hit_pct,
  ROUND(AVG(percentage_scanned_from_cache), 1) AS avg_pct_from_disk_cache
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY
WHERE start_time > DATEADD('day', -7, CURRENT_TIMESTAMP())
  AND query_type = 'SELECT'
  AND warehouse_name IS NOT NULL
GROUP BY day
ORDER BY day DESC;

9. Interview & Certification Q&A

Q1: A query is slow. Walk me through how you'd diagnose it.

A:

  1. Query Profile: Open the visual DAG. Look at the most expensive operator node.
  2. Partitions: Check scanned vs total. If ratio is high --> clustering issue.
  3. Spilling: Any spill to local/remote? --> Warehouse too small, scale UP.
  4. Queuing: Was query queued? --> Concurrency issue, scale OUT or separate warehouse.
  5. Joins: Is there an "exploding" join (output >> input)? --> Fix join logic.
  6. Pruning: Is a function wrapping the filter column? --> Rewrite query.
  7. Data volume: Is the query scanning too much data? --> Add better WHERE filters.

Q2: What's the difference between clustering keys and indexes?

A: Snowflake has NO traditional indexes. Clustering keys reorganize how data is physically stored:

Traditional IndexSnowflake Clustering Key
StorageSeparate data structure (B-tree)Reorganizes actual data placement
MaintenanceManual (REBUILD, REORGANIZE)Automatic (serverless background)
Write penaltyEvery INSERT updates indexBackground reclustering as needed
Point lookupEfficient (B-tree traversal)Good if well-clustered, else use SOS
Range queriesEfficient with clustered indexExcellent (pruning eliminates partitions)
CreationCREATE INDEX (user decides)ALTER TABLE CLUSTER BY (user decides columns)

Q3: When would you use SOS vs clustering vs QAS?

A:

  • Clustering: Range queries on specific columns (dates, categories). Best when queries consistently filter on 1-3 columns. Reorganizes data.
  • SOS (Search Optimization): Point lookups on high-cardinality columns (ID=X), substring searches (LIKE '%X%'), VARIANT field access. Adds search structures WITHOUT reorganizing data.
  • QAS (Query Acceleration): Queries that benefit from MORE parallelism - large scans, many OR conditions, uneven work distribution. Adds temporary serverless compute to your warehouse.
They complement each other: Clustering = data organization, SOS = lookup speed, QAS = compute scaling.

Q4: How do you decide warehouse size for a workload?

A: Start small, measure, and scale:

  1. Start with X-Small or Small
  2. Run representative queries
  3. Check Query Profile for spilling:
    • No spill = size is adequate
    • Spill to local = might benefit from 1 size up
    • Spill to remote = definitely need larger warehouse
  4. Doubling warehouse size doesn't guarantee 2x speed (Amdahl's law)
  5. For concurrency: prefer multi-cluster (scale out) over larger single cluster

Q5: What queries does the result cache NOT work for?

A: Result cache miss when:

  • Underlying data changed since last execution
  • Query uses non-deterministic functions: CURRENT_TIMESTAMP(), RANDOM(), UUID_STRING(), CURRENT_DATE()
  • Different role than original execution
  • Different query text (even whitespace changes)
  • Explicitly disabled: ALTER SESSION SET USE_CACHED_RESULT = FALSE
  • Past 24-hour window (or 31 days if repeatedly accessed)

Q6: What is the Query Acceleration Service and how is it billed?

A: QAS offloads query processing to additional serverless compute:

  • Billing: Serverless credits (separate from warehouse). Only charged when QAS actually accelerates a query.
  • Scale factor: QUERY_ACCELERATION_MAX_SCALE_FACTOR controls maximum additional compute (1-100, default 8 = up to 8x warehouse size)
  • Automatic: Optimizer decides per-query whether QAS helps. Not all queries benefit.
  • No impact on other queries: QAS resources are isolated, don't take from warehouse pool

Q7: A table has 100TB and queries filter on user_id (1 billion unique values). Best optimization?

A: Search Optimization Service (SOS) - because:

  • user_id is high-cardinality (1B values) - bad candidate for clustering key
  • Point lookups (WHERE user_id = X) benefit from SOS search structures
  • Clustering on user_id would create too many overlapping partitions
  • SOS creates efficient lookup paths without rearranging data
If queries ALSO filter on date range: CLUSTER BY (date_col) + SOS ON EQUALITY(user_id) = best combo.
