    rows_loaded_last_batch = :rows_count,
    rows_loaded_total = rows_loaded_total + :rows_count,
    updated_at = CURRENT_TIMESTAMP()
WHERE pipeline_id = :pipeline_id;

3. Failure Handling & Recovery

When Snowpipe Fails

  DIAGNOSIS STEPS:

  1. CHECK PIPE STATUS:
     SELECT SYSTEM$PIPE_STATUS('my_pipe');
     -- Returns: executionState, pendingFileCount, lastForwardedTimestamp

  2. CHECK COPY HISTORY (for Snowpipe):
     SELECT file_name, stage_location, status, 
            first_error_message, first_error_line_number,
            row_count, row_parsed, error_count
     FROM SNOWFLAKE.ACCOUNT_USAGE.COPY_HISTORY
     WHERE pipe_name = 'MY_PIPE'
       AND last_load_time > DATEADD('hour', -6, CURRENT_TIMESTAMP())
       AND status != 'LOADED'
     ORDER BY last_load_time DESC;

  3. CHECK PIPE USAGE HISTORY:
     SELECT * FROM SNOWFLAKE.ACCOUNT_USAGE.PIPE_USAGE_HISTORY
     WHERE pipe_name = 'MY_PIPE'
     ORDER BY start_time DESC LIMIT 20;

  4. COMMON SNOWPIPE FAILURES:
     +-------------------------------+--------------------------------+
     | Error                         | Fix                            |
     +-------------------------------+--------------------------------+
     | LOAD_FAILED (data type)       | Fix source data or add ON_ERROR|
     | PARTIALLY_LOADED              | Check specific rows with errors|
     | FILE_NOT_FOUND                | File deleted before Snowpipe   |
     | INSUFFICIENT_PRIVILEGES       | Grant USAGE on stage/pipe      |
     | QUEUE_FULL                    | Pipe overwhelmed, check lag    |
     +-------------------------------+--------------------------------+

  5. RECOVERY:
     -- Re-process failed files
     ALTER PIPE my_pipe REFRESH PREFIX = 'failed_path/';
     
     -- Or load manually with FORCE
     COPY INTO target FROM @stage/failed_file.json
       FILE_FORMAT = (TYPE = JSON) 
       FORCE = TRUE ON_ERROR = 'CONTINUE';

COPY INTO Failure Diagnosis

-- Get detailed errors from last failed COPY
SELECT * FROM TABLE(VALIDATE(my_table, JOB_ID => '_last'));

-- Returns per-row errors:
-- ERROR, FILE, LINE, CHARACTER, COLUMN, REJECTED_RECORD

-- Pattern: Load to error table for analysis
CREATE TABLE load_errors AS
SELECT 
  $1 AS raw_line,
  METADATA$FILENAME AS file_name,
  METADATA$FILE_ROW_NUMBER AS row_num,
  CURRENT_TIMESTAMP() AS error_time
FROM @my_stage/problem_file.csv
WHERE TRY_CAST($3 AS NUMBER) IS NULL;  -- Find non-numeric values in col3

4. Schema Evolution & Data Type Changes

Scenario: New Columns Appear in Source Files

  STRATEGY 1: VARIANT RAW LAYER (Recommended)
  -----------------------------------------------
  Load ALL data into a VARIANT column. Schema changes don't break the pipeline.
  
  CREATE TABLE raw_orders (
    raw_payload VARIANT,
    _loaded_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP(),
    _source_file VARCHAR DEFAULT METADATA$FILENAME
  );
  
  -- Always succeeds regardless of schema changes!
  COPY INTO raw_orders (raw_payload, _source_file) 
  FROM (SELECT PARSE_JSON($1), METADATA$FILENAME FROM @stage/)
  FILE_FORMAT = (TYPE = CSV FIELD_DELIMITER = NONE);
  
  -- Or for JSON directly:
  COPY INTO raw_orders (raw_payload) FROM @stage/ FILE_FORMAT = (TYPE = JSON);
  
  -- Downstream: Extract typed columns (handles missing cols gracefully)
  CREATE OR REPLACE VIEW staged_orders AS
  SELECT 
    raw_payload:order_id::INT AS order_id,
    raw_payload:customer_id::INT AS customer_id,
    raw_payload:amount::DECIMAL(10,2) AS amount,
    raw_payload:order_date::DATE AS order_date,
    raw_payload:new_column::VARCHAR AS new_column,  -- NULL if missing (no error!)
    _loaded_at
  FROM raw_orders;


  STRATEGY 2: SCHEMA EVOLUTION (Auto-add columns)
  -----------------------------------------------
  ALTER TABLE orders SET ENABLE_SCHEMA_EVOLUTION = TRUE;
  
  -- Now COPY INTO will AUTO-ADD columns that appear in Parquet/Avro files
  COPY INTO orders FROM @stage/
    FILE_FORMAT = (TYPE = PARQUET)
    MATCH_BY_COLUMN_NAME = CASE_INSENSITIVE;
  -- New columns in Parquet? Automatically added to table!
  

  STRATEGY 3: DETECT AND ALERT
  -----------------------------------------------
  -- Compare file schema vs table schema before loading
  SELECT column_name, data_type 
  FROM TABLE(INFER_SCHEMA(
    LOCATION => '@stage/new_file.parquet',
    FILE_FORMAT => 'parquet_format'
  ));
  -- Compare with INFORMATION_SCHEMA.COLUMNS and alert on diff

Scenario: Data Type Changes from Source

  PROBLEM: Source suddenly sends "amount" as STRING instead of NUMBER

  SOLUTIONS:
  
  1. TRY_CAST in transformation layer:
     SELECT 
       TRY_CAST(raw:amount AS DECIMAL(10,2)) AS amount,
       CASE WHEN TRY_CAST(raw:amount AS DECIMAL(10,2)) IS NULL 
            THEN 'INVALID_AMOUNT' END AS dq_flag
     FROM raw_table;

  2. Data Quality checks BEFORE loading to curated:
     -- Count invalid records
     SELECT COUNT(*) AS invalid_amounts
     FROM raw_table
     WHERE TRY_CAST(raw:amount AS NUMBER) IS NULL
       AND raw:amount IS NOT NULL;
     
     -- If > threshold, HALT pipeline and alert

  3. ON_ERROR handling in COPY:
     COPY INTO target FROM @stage
       ON_ERROR = 'SKIP_FILE_3%';  -- Skip file if > 3% errors
     -- Combine with monitoring to alert on skipped files

5. Deduplication & Idempotency

Scenario: Kafka Delivers Duplicate Messages (At-Least-Once)

  WHY DUPLICATES HAPPEN:
  - Kafka at-least-once delivery (consumer reprocessing)
  - Snowpipe re-processing after transient failure
  - Manual COPY with FORCE = TRUE
  - Source system retries sending same record

  DEDUP STRATEGIES:

  STRATEGY 1: DEDUP IN STAGING (Most Common)
  -------------------------------------------
  -- Use ROW_NUMBER to keep only latest per business key
  CREATE OR REPLACE VIEW deduped_orders AS
  SELECT * FROM (
    SELECT *,
      ROW_NUMBER() OVER (
        PARTITION BY order_id 
        ORDER BY _loaded_at DESC  -- Keep most recent
      ) AS rn
    FROM raw_orders
  )
  WHERE rn = 1;


  STRATEGY 2: MERGE WITH DEDUP (Idempotent Load)
  -------------------------------------------
  -- MERGE is naturally idempotent - re-running produces same result
  MERGE INTO curated.orders AS target
  USING (
    SELECT * FROM (
      SELECT *, ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY event_ts DESC) AS rn
      FROM staging.orders_stream
    ) WHERE rn = 1
  ) AS source
  ON target.order_id = source.order_id
  WHEN MATCHED AND source.event_ts > target.updated_at THEN
    UPDATE SET amount = source.amount, updated_at = source.event_ts
  WHEN NOT MATCHED THEN
    INSERT (order_id, amount, created_at, updated_at)
    VALUES (source.order_id, source.amount, source.event_ts, source.event_ts);


  STRATEGY 3: QUALIFY CLAUSE (Snowflake-specific, elegant)
  -------------------------------------------
  INSERT INTO curated.orders
  SELECT order_id, amount, event_ts
  FROM raw.orders
  QUALIFY ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY event_ts DESC) = 1;

6. SCD1 & SCD2 Implementation

SCD Type 1 (Overwrite - No History)

-- SCD1: Simply overwrite with latest values
-- Use case: Correct errors, update current state (e.g., customer email)

MERGE INTO dim_customer AS target
USING staging_customer AS source
ON target.customer_id = source.customer_id
WHEN MATCHED AND (
  target.email != source.email OR
  target.phone != source.phone OR
  target.address != source.address
) THEN UPDATE SET
  email = source.email,
  phone = source.phone,
  address = source.address,
  updated_at = CURRENT_TIMESTAMP()
WHEN NOT MATCHED THEN INSERT 
  (customer_id, name, email, phone, address, created_at, updated_at)
  VALUES (source.customer_id, source.name, source.email, source.phone, 
          source.address, CURRENT_TIMESTAMP(), CURRENT_TIMESTAMP());

SCD Type 2 (Full History - Track All Changes)

-- SCD2 Dimension Table Structure
CREATE TABLE dim_customer_scd2 (
  dim_key INT AUTOINCREMENT,          -- Surrogate key
  customer_id INT,                     -- Business key (natural key)
  name VARCHAR,
  email VARCHAR,
  address VARCHAR,
  effective_from TIMESTAMP_NTZ,        -- When this version became active
  effective_to TIMESTAMP_NTZ,          -- When this version was superseded (NULL = current)
  is_current BOOLEAN DEFAULT TRUE,     -- Quick filter for current records
  record_hash VARCHAR,                 -- Hash of tracked columns for change detection
  created_at TIMESTAMP_NTZ DEFAULT CURRENT_TIMESTAMP()
);

-- SCD2 MERGE Pattern (close old record + insert new)
MERGE INTO dim_customer_scd2 AS target
USING (
  SELECT 
    customer_id, name, email, address,
    MD5(CONCAT(name, '|', email, '|', address)) AS record_hash
  FROM staging_customer
) AS source
ON target.customer_id = source.customer_id 
   AND target.is_current = TRUE
WHEN MATCHED AND target.record_hash != source.record_hash THEN
  -- Close the old record
  UPDATE SET 
    effective_to = CURRENT_TIMESTAMP(),
    is_current = FALSE
WHEN NOT MATCHED THEN
  -- New customer
  INSERT (customer_id, name, email, address, effective_from, effective_to, is_current, record_hash)
  VALUES (source.customer_id, source.name, source.email, source.address, 
          CURRENT_TIMESTAMP(), NULL, TRUE, source.record_hash);

-- IMPORTANT: After MERGE, insert new versions for changed records
INSERT INTO dim_customer_scd2 (customer_id, name, email, address, effective_from, is_current, record_hash)
SELECT s.customer_id, s.name, s.email, s.address, CURRENT_TIMESTAMP(), TRUE,
       MD5(CONCAT(s.name, '|', s.email, '|', s.address))
FROM staging_customer s
JOIN dim_customer_scd2 t 
  ON s.customer_id = t.customer_id 
  AND t.is_current = FALSE 
  AND t.effective_to = (SELECT MAX(effective_to) FROM dim_customer_scd2 WHERE customer_id = s.customer_id)
WHERE NOT EXISTS (
  SELECT 1 FROM dim_customer_scd2 
  WHERE customer_id = s.customer_id AND is_current = TRUE
);

SCD2 with Streams (Automated)

-- Use Streams to detect changes automatically
CREATE STREAM customer_changes ON TABLE staging.customers;

-- Task runs MERGE on schedule using stream data
CREATE TASK scd2_customer_task
  WAREHOUSE = ETL_WH
  SCHEDULE = 'USING CRON 0 * * * * UTC'  -- Every hour
  WHEN SYSTEM$STREAM_HAS_DATA('customer_changes')
AS
  -- Execute SCD2 MERGE using stream data
  MERGE INTO dim_customer_scd2 ...
  USING customer_changes ...;
SCD2 Best Practices in Snowflake:
  • Use MD5/SHA hash of tracked columns for efficient change detection
  • Use Streams to capture CDC from staging tables
  • Use Tasks with WHEN condition to only run when changes exist
  • Include is_current flag for easy filtering of latest records
  • Consider Dynamic Tables for simpler declarative approach (Snowflake manages refresh)

8. Monitoring & Alerting

-- ALERT: Pipeline hasn't loaded data in expected SLA
CREATE ALERT pipeline_stale_alert
  WAREHOUSE = COMPUTE_WH
  SCHEDULE = 'USING CRON 0/15 * * * * UTC'  -- Check every 15 min
  IF (EXISTS (
    SELECT 1 FROM pipeline_control
    WHERE status = 'SUCCESS'
      AND DATEDIFF('minute', last_successful_load, CURRENT_TIMESTAMP()) > sla_minutes
  ))
  THEN
    CALL SYSTEM$SEND_EMAIL(
      'alert_integration', 
      'data-team@company.com',
      'Pipeline SLA Breach',
      'One or more pipelines are stale. Check pipeline_control table.'

-- ALERT: Snowpipe failures

      AND status = 'LOAD_FAILED'
      AND last_load_time > DATEADD('minute', -15, CURRENT_TIMESTAMP())
  ))
  THEN
    CALL SYSTEM$SEND_EMAIL(...);

-- Data Quality monitoring view
CREATE VIEW dq_monitoring AS
SELECT 
  'NULL_CHECK' AS check_type,
  'orders.customer_id' AS column_name,
  COUNT(*) AS violations,
  CURRENT_TIMESTAMP() AS check_time
FROM curated.orders WHERE customer_id IS NULL
UNION ALL
SELECT 'RANGE_CHECK', 'orders.amount', COUNT(*), CURRENT_TIMESTAMP()
FROM curated.orders WHERE amount < 0 OR amount > 1000000;

9. Interview Scenario Questions

Q1: "You receive duplicate records from Kafka. The same order_id arrives 3 times. How do you handle it?"

A: Multi-layer approach:

  1. Accept duplicates in raw: Never reject data at ingestion - append everything with _loaded_at timestamp
  2. Dedup in staging: Use QUALIFY ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY event_timestamp DESC) = 1
  3. MERGE to curated: MERGE is naturally idempotent - re-running produces same result
  4. Monitor: Track duplicate rate in DQ dashboard. If spike, investigate source.
Key principle: Idempotent pipelines - running the same pipeline twice produces the same result.

Q2: "A new column appears in the Kafka message. What happens to your pipeline?"

A: Depends on raw layer design:

  • If loading to VARIANT column: Nothing breaks! New field automatically captured in VARIANT. Downstream views just need updating to expose the new column.
  • If loading to typed columns: Pipeline may fail or ignore the new field depending on connector config. This is why VARIANT raw layer is recommended.
Best practice: Raw layer always uses VARIANT. Schema enforcement happens in staging/curated layers where you control the mapping.

Q3: "Data types changed in source (amount was INT, now STRING). Your pipeline breaks. How do you fix it AND prevent it?"

A:

  • Immediate fix: Use TRY_CAST in transformation: TRY_CAST(raw:amount AS NUMBER) returns NULL instead of error
  • Root cause: If raw is VARIANT, COPY doesn't break. The issue is in transformation layer.
  • Prevention:
    1. Always use TRY_CAST/TRY_TO_NUMBER/TRY_TO_DATE in transformations
    2. Data quality checks before promoting to curated layer
    3. Schema contracts with source teams (API versioning)
    4. INFER_SCHEMA on new files before loading to detect changes
    5. Alerts when DQ check failure rate exceeds threshold

Q4: "Design a pipeline that implements SCD2 for a customer dimension with 10M records and 50K daily updates."

A: 

Architecture:
1. Source CDC --> Kafka --> Snowpipe Streaming --> RAW.CUSTOMERS (VARIANT)
2. Stream on RAW.CUSTOMERS captures new/changed records
3. Task (hourly) runs MERGE:
   - Hash compare (MD5 of tracked columns) to detect actual changes
   - Close old record (is_current=FALSE, effective_to=NOW)
   - Insert new version (is_current=TRUE, effective_from=NOW)
4. Clustering key on dim_customer_scd2: (customer_id, is_current)
   - Optimizes both current-state queries and history lookups

Performance considerations:
- 50K daily changes on 10M table = 0.5% change rate (manageable)
- MERGE is efficient with clustering on business key
- Hash comparison avoids unnecessary updates (same data = no change)
- Hourly cadence balances freshness vs compute cost

Q5: "Snowpipe stopped loading files 2 hours ago. Walk me through troubleshooting."

A:

  1. SELECT SYSTEM$PIPE_STATUS('my_pipe') - Check if pipe is RUNNING or STALLED
  2. Check COPY_HISTORY for recent failures: WHERE pipe_name='...' AND status != 'LOADED'
  3. Check if files are arriving in stage: LIST @stage - are new files there?
  4. Check cloud event notifications: Is SQS/Event Grid still connected?
  5. Check for privilege changes: Does the pipe's role still have stage access?
  6. Check if pipe was paused: SHOW PIPES - look at state
  7. If queue is building up but not processing: Check for lock contention on target table
  8. Recovery: ALTER PIPE my_pipe REFRESH to reprocess pending files

Q6: "Should we use ADF or Prefect for our Snowflake pipelines? We're an Azure shop."

A: It depends on complexity:

  • Use ADF if: Pipelines are primarily data movement (copy from Azure SQL/Blob to Snowflake), team has ADF expertise, you need visual pipeline designer, integration with Azure DevOps
  • Use Prefect/Airflow if: Complex Python transformations, ML pipelines, need fine-grained retry/error handling, multi-cloud or hybrid, team prefers code-over-GUI
  • Use Snowflake Tasks if: All logic is SQL within Snowflake, simple DAGs, don't want external infrastructure
  • Hybrid approach (recommended): ADF for cross-system data movement + Snowflake Tasks for in-database transformations. Or: dbt for transforms + ADF for orchestration.

Q7: "How do you ensure data quality in a streaming pipeline?"

A: Layered DQ approach:

  1. Ingestion: Accept everything (don't reject at gate). Log metadata (_source, _loaded_at, _file_name)
  2. Staging: Apply DQ rules:
    • NULL checks on required fields
    • Range validation (amount > 0, date not in future)
    • Format validation (email regex, phone format)
    • Referential integrity (customer_id exists in dim_customer)
  3. Quarantine: Failed records go to quarantine table (not dropped!)
  4. Promotion: Only clean records move to curated layer
  5. Monitoring: DQ metrics dashboard (error rate, null rate by column, trend)
  6. Alerting: Alert if error rate exceeds threshold (e.g., >2% failures)
