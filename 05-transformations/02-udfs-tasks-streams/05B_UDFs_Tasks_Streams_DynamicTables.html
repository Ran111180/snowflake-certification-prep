1. User-Defined Functions (UDFs)

UDF Types

TypeLanguageReturnsUse Case
Scalar UDFSQL, Python, Java, Scala, JavaScriptSingle value per rowTransform individual values
UDTF (Table Function)SQL, Python, Java, Scala, JavaScriptMultiple rows (table)Generate/expand rows
UDAF (Aggregate)Python, JavaSingle value per groupCustom aggregation logic
 
-- SQL Scalar UDF
CREATE OR REPLACE FUNCTION mask_email(email VARCHAR)
  RETURNS VARCHAR
  AS $$
    REGEXP_REPLACE(email, '.+@', '***@')
  $$;

-- Python Scalar UDF
CREATE OR REPLACE FUNCTION sentiment_score(text VARCHAR)
  RETURNS FLOAT
  LANGUAGE PYTHON
  RUNTIME_VERSION = '3.11'
  HANDLER = 'analyze'
AS $$
def analyze(text):
    positive = ['good','great','excellent','love']
    negative = ['bad','terrible','hate','awful']
    words = text.lower().split()
    score = sum(1 for w in words if w in positive) - sum(1 for w in words if w in negative)
    return score / max(len(words), 1)
$$;

-- SQL UDTF (Table Function)
CREATE OR REPLACE FUNCTION generate_date_range(start_date DATE, end_date DATE)
  RETURNS TABLE (dt DATE)
  AS $$
    SELECT DATEADD(day, SEQ4(), start_date)::DATE AS dt
    FROM TABLE(GENERATOR(ROWCOUNT => DATEDIFF('day', start_date, end_date) + 1))
  $$;

-- Call UDTF
SELECT * FROM TABLE(generate_date_range('2024-01-01', '2024-01-07'));

-- Python UDTF (returns table)
CREATE OR REPLACE FUNCTION split_tags(tags VARCHAR)
  RETURNS TABLE (tag VARCHAR)
  LANGUAGE PYTHON
  RUNTIME_VERSION = '3.11'
  HANDLER = 'SplitTags'
AS $$
class SplitTags:
    def process(self, tags):
        if tags:
            for tag in tags.split(','):
                yield (tag.strip(),)
$$;
UDF Key Facts:
  • UDFs are called in SELECT (like built-in functions)
  • Cannot perform DML (INSERT/UPDATE/DELETE) - use procedures for that
  • Scalar UDFs: one input row → one output value
  • UDTFs: one input row → zero or more output rows
  • Python UDFs run in a sandboxed environment (limited packages)
  • SQL UDFs are generally fastest (inlined by optimizer)
  • Secure UDFs: CREATE SECURE FUNCTION - hides definition from non-owners

-- Snowflake Scripting Procedure (SQL)
CREATE OR REPLACE PROCEDURE refresh_summary()
  RETURNS VARCHAR
  LANGUAGE SQL
  EXECUTE AS CALLER
AS
$$
BEGIN
  TRUNCATE TABLE curated.daily_summary;
  INSERT INTO curated.daily_summary
    SELECT order_date, category, SUM(amount), COUNT(*)
    FROM raw.orders
    GROUP BY order_date, category;
  RETURN 'Summary refreshed: ' || SQLROWCOUNT || ' rows';
END;
$$;

-- Python Stored Procedure
CREATE OR REPLACE PROCEDURE load_and_transform(source_table VARCHAR)
  RETURNS VARCHAR
  LANGUAGE PYTHON
  RUNTIME_VERSION = '3.11'
  PACKAGES = ('snowflake-snowpark-python')
  HANDLER = 'run'
AS $$
def run(session, source_table):
    df = session.table(source_table)
    result = df.group_by("category").agg({"amount": "sum"})
    result.write.save_as_table("curated.category_totals", mode="overwrite")
    return f"Processed {df.count()} rows"
$$;

-- Call procedures
CALL refresh_summary();
CALL load_and_transform('raw.orders');

Caller's Rights vs Owner's Rights

-- CALLER'S RIGHTS (default): Runs with privileges of the user who calls it
CREATE PROCEDURE my_proc() ... EXECUTE AS CALLER;
-- Use when: Procedure should respect the caller's access

-- OWNER'S RIGHTS: Runs with privileges of the role that owns the procedure
CREATE PROCEDURE admin_proc() ... EXECUTE AS OWNER;
-- Use when: Procedure needs elevated access the caller doesn't have
-- Example: Allow analysts to call a proc that truncates/loads tables they can't directly modify

3. Streams (Change Data Capture)

What Are Streams?

Streams capture row-level changes (inserts, updates, deletes) on a table since the last time the stream was consumed.

  HOW STREAMS WORK:

  TABLE: orders (source)
  +----+--------+-------+
  | 1  | Alice  | 100   |  <-- existing
  | 2  | Bob    | 200   |  <-- existing
  +----+--------+-------+
       |
       | CREATE STREAM orders_stream ON TABLE orders;
       v
  Time passes... changes happen:
    INSERT (3, Carol, 300)
    UPDATE id=1 SET amount=150
    DELETE id=2
       |
       v
  STREAM: orders_stream (captures changes)
  +----+--------+-------+---------------------+---------------------+-------------------+
  | ID | NAME   | AMT   | METADATA$ACTION     | METADATA$ISUPDATE   | METADATA$ROW_ID   |
  +----+--------+-------+---------------------+---------------------+-------------------+
  | 3  | Carol  | 300   | INSERT              | FALSE               | abc123            |
  | 1  | Alice  | 150   | INSERT              | TRUE                | def456 (new ver)  |
  | 1  | Alice  | 100   | DELETE              | TRUE                | def456 (old ver)  |
  | 2  | Bob    | 200   | DELETE              | FALSE               | ghi789            |
  +----+--------+-------+---------------------+---------------------+-------------------+

  KEY COLUMNS:
  - METADATA$ACTION: INSERT or DELETE
  - METADATA$ISUPDATE: TRUE if this row is part of an UPDATE (shows as DELETE old + INSERT new)
  - METADATA$ROW_ID: Unique row identifier

Stream Types

TypeCapturesUse Case
Standard (default)INSERT, UPDATE, DELETEFull CDC, SCD2 dimensions
Append-OnlyINSERT onlyLog tables, event streams (no updates expected)
Insert-OnlyINSERT only (for external tables/directory tables)New files arriving in stage
 
-- Create streams
CREATE STREAM orders_stream ON TABLE raw.orders;                     -- Standard
CREATE STREAM events_stream ON TABLE raw.events APPEND_ONLY = TRUE;  -- Append-only
CREATE STREAM files_stream ON STAGE @my_stage;                        -- Directory table

-- Consume stream (reading it advances the offset)
INSERT INTO curated.orders_changes
SELECT *, CURRENT_TIMESTAMP() AS processed_at
FROM orders_stream;  -- After this, stream is "consumed" (empty until new changes)

-- Check if stream has data
SELECT SYSTEM$STREAM_HAS_DATA('orders_stream');  -- TRUE/FALSE
Stream Critical Facts:
  • Stream is consumed (advanced) when used in a DML statement (INSERT, MERGE, etc.)
  • Just SELECTing from a stream does NOT consume it
  • A stream becomes stale if the source table's retention period passes without consumption
  • Stale stream = data loss! Set adequate DATA_RETENTION_TIME on source table
  • Multiple streams on the same table are independent (each tracks separately)

4. Tasks (Scheduling)

What Are Tasks?

Tasks schedule SQL execution on a CRON schedule or when triggered by stream data.

-- Simple scheduled task
CREATE TASK hourly_refresh
  WAREHOUSE = COMPUTE_WH
  SCHEDULE = 'USING CRON 0 * * * * UTC'  -- Every hour
AS
  INSERT INTO curated.hourly_summary
  SELECT DATE_TRUNC('hour', CURRENT_TIMESTAMP()), COUNT(*) FROM raw.events;

-- Stream-triggered task (runs ONLY when stream has data)
CREATE TASK process_orders
  WAREHOUSE = ETL_WH
  SCHEDULE = '1 MINUTE'  -- Check every minute
  WHEN SYSTEM$STREAM_HAS_DATA('orders_stream')
AS
  MERGE INTO curated.orders AS t
  USING orders_stream AS s ON t.id = s.id
  WHEN MATCHED AND s.METADATA$ACTION = 'DELETE' AND s.METADATA$ISUPDATE = FALSE
    THEN DELETE
  WHEN MATCHED AND s.METADATA$ISUPDATE = TRUE
    THEN UPDATE SET t.amount = s.amount, t.updated_at = CURRENT_TIMESTAMP()
  WHEN NOT MATCHED AND s.METADATA$ACTION = 'INSERT'
    THEN INSERT (id, name, amount, created_at) VALUES (s.id, s.name, s.amount, CURRENT_TIMESTAMP());

-- Serverless task (no warehouse - Snowflake manages compute)
CREATE TASK serverless_task
  USER_TASK_MANAGED_INITIAL_WAREHOUSE_SIZE = 'XSMALL'
  SCHEDULE = '5 MINUTE'
AS
  CALL my_procedure();

-- IMPORTANT: Tasks are created SUSPENDED! Must resume:
ALTER TASK hourly_refresh RESUME;
ALTER TASK process_orders RESUME;

Task DAGs (Graphs)

  TASK DAG (Directed Acyclic Graph):

  [Root Task: extract]  (has SCHEDULE)
         |
    +----+----+
    |         |
  [transform_a]  [transform_b]  (AFTER extract)
    |         |
    +----+----+
         |
  [load_summary]  (AFTER transform_a AND transform_b)

  -- Root task (has schedule)
  CREATE TASK extract WAREHOUSE = WH SCHEDULE = '1 HOUR' AS ...;

  -- Child tasks (triggered by parent completion)
  CREATE TASK transform_a WAREHOUSE = WH AFTER extract AS ...;
  CREATE TASK transform_b WAREHOUSE = WH AFTER extract AS ...;

  -- Grandchild (waits for BOTH parents)
  CREATE TASK load_summary WAREHOUSE = WH AFTER transform_a, transform_b AS ...;

  -- Resume entire DAG (start from root)
  ALTER TASK extract RESUME;
  -- Children auto-resume when parent is resumed (if previously resumed)
Tasks Key Facts:
  • Tasks are created SUSPENDED - must ALTER TASK ... RESUME
  • Only ROOT tasks have a SCHEDULE; child tasks use AFTER
  • WHEN clause: only run if condition is true (e.g., stream has data)
  • Serverless tasks: no warehouse needed (managed compute)
  • CRON format: minute hour day-of-month month day-of-week
  • Minimum schedule: 1 minute
  • Task history: TASK_HISTORY() table function

5. Dynamic Tables

Key Modern Feature (replaces Streams+Tasks for many use cases)

What Are Dynamic Tables?

Dynamic Tables are declarative, auto-refreshing tables defined by a SQL query. Snowflake automatically keeps them up-to-date - no streams, tasks, or MERGE logic needed.

  STREAMS + TASKS (Imperative):          DYNAMIC TABLES (Declarative):
  
  1. CREATE STREAM                       1. CREATE DYNAMIC TABLE ... AS SELECT ...
  2. CREATE TASK with MERGE logic        2. Done! Snowflake handles the rest.
  3. Handle edge cases (stale streams)
  4. Monitor task failures
  5. Manage task dependencies

  DYNAMIC TABLE = "Materialized view that auto-refreshes incrementally"
  
-- Create a dynamic table (auto-refreshes every 1 minute)
CREATE OR REPLACE DYNAMIC TABLE curated.order_summary
  TARGET_LAG = '1 minute'  -- Freshness SLA: data is at most 1 min stale
  WAREHOUSE = COMPUTE_WH
AS
  SELECT 
    DATE_TRUNC('hour', order_date) AS hour,
    category,
    SUM(amount) AS total_revenue,
    COUNT(*) AS order_count
  FROM raw.orders
  GROUP BY hour, category;

-- That's it! Snowflake automatically:
-- - Detects changes in raw.orders
-- - Incrementally refreshes curated.order_summary
-- - Maintains the 1-minute freshness target

-- Dynamic Table pipeline (chained)
CREATE DYNAMIC TABLE bronze.cleaned_orders
  TARGET_LAG = '1 minute' WAREHOUSE = WH
AS SELECT * FROM raw.orders WHERE amount > 0;

CREATE DYNAMIC TABLE silver.enriched_orders
  TARGET_LAG = '5 minutes' WAREHOUSE = WH
AS SELECT o.*, c.name AS customer_name
   FROM bronze.cleaned_orders o
   JOIN dim.customers c ON o.customer_id = c.id;

CREATE DYNAMIC TABLE gold.daily_revenue
  TARGET_LAG = '10 minutes' WAREHOUSE = WH
AS SELECT order_date, SUM(amount) AS revenue
   FROM silver.enriched_orders GROUP BY order_date;

When to Use What:
  • Dynamic Tables: Your pipeline is SELECT-based transforms (90% of use cases). Simplest, least code.
  • Streams + Tasks: You need MERGE (SCD2), conditional logic, multi-step imperative operations.
  • Materialized Views: Simple single-table aggregations, real-time freshness, Enterprise edition.

$$

7. Interview & Certification Q&A

Q1: What's the difference between UDFs and Stored Procedures?

A: Key differences:

  • UDF: Called in SELECT, returns value(s), cannot do DML/DDL, used for transformation
  • Procedure: Called with CALL, can do DML/DDL/transaction control, used for pipeline logic
  • UDF runs per row (scalar) or generates rows (UDTF). Procedure runs once.
  • UDF is functional (no side effects). Procedure is imperative (changes state).

Q2: What are Streams and how do they track changes?

A: Streams capture CDC (change data capture) on a table:

  • Track INSERT, UPDATE (as DELETE old + INSERT new), DELETE operations
  • Provide metadata columns: METADATA$ACTION, METADATA$ISUPDATE, METADATA$ROW_ID
  • Stream advances (consumed) when data is used in DML - just SELECT doesn't advance it
  • Can become stale if not consumed within table's retention period (data loss!)
  • Types: Standard (all changes), Append-only (INSERTs only)

Q3: Explain Dynamic Tables. When would you use them vs Streams+Tasks?

A:

  • Dynamic Tables: Declarative - define the desired result as a SELECT. Snowflake auto-detects source changes, auto-refreshes incrementally, manages dependencies. No MERGE, no stream management.
  • Use Dynamic Tables when: Pipeline is SELECT-based (GROUP BY, JOIN, filter). 90% of ETL fits this.
  • Use Streams+Tasks when: Need MERGE (SCD2), conditional branching, multi-statement procedures, complex error handling, or non-SQL logic.
Dynamic Tables are the modern default - only reach for Streams+Tasks when DT can't express the logic.

Q4: What is TARGET_LAG in Dynamic Tables?

A: TARGET_LAG is the freshness SLA:

  • It tells Snowflake: "This table's data should be at most X minutes behind its sources"
  • Snowflake decides WHEN and HOW to refresh to meet this target
  • Shorter lag = more frequent refreshes = more compute cost
  • Options: time-based ('1 minute', '1 hour') or DOWNSTREAM (refresh only when downstream DTs need it)
  • Snowflake may refresh MORE frequently than needed (proactive) or batch changes

Q5: A stream becomes stale. What happened and how do you prevent it?

A:

  • What happened: The stream wasn't consumed (used in DML) before the source table's Time Travel retention expired. The change records are gone.
  • Impact: Stream becomes stale - can't read from it. Must recreate.
  • Prevention:
    1. Set adequate DATA_RETENTION_TIME on source table (e.g., 14 days)
    2. Ensure tasks consuming streams run frequently enough
    3. Monitor with STALE_AFTER column in SHOW STREAMS
    4. Set alerts for stream staleness approaching retention period
  • Recovery: Recreate stream + do a full reload from source to target.

Q6: How do Task DAGs work?

A:

  • Only the root task has a SCHEDULE (CRON or interval)
  • Child tasks use AFTER parent_task to define dependencies
  • A child with multiple parents runs only when ALL parents succeed
  • Tasks are created SUSPENDED - must RESUME root to start the DAG
  • If a task fails: downstream tasks don't run (unless configured otherwise)
  • Finalizer tasks: Run regardless of success/failure (cleanup logic)
  • Max 1000 tasks per DAG

Q7: Owner's rights vs Caller's rights - when to use which?

A:

  • Caller's rights (EXECUTE AS CALLER): Default. Procedure runs with the CALLER's privileges. Use when the user should only access what they're already allowed to see. Safer, follows least privilege.
  • Owner's rights (EXECUTE AS OWNER): Procedure runs with the OWNER role's privileges. Use when you want to grant controlled access to operations the caller can't do directly (e.g., truncate + reload a table, access admin schemas).
  • Example: An analyst calls a proc that loads data into a table they can't write to directly - owner's rights enables this without granting INSERT to the analyst.

Q8: Design a real-time pipeline: Kafka events → cleaned/enriched data → dashboard-ready summary.

A: Using Dynamic Tables (modern approach): 

-- Layer 1: Raw (Kafka Connector loads here)
TABLE raw.events (payload VARIANT, _loaded_at TIMESTAMP)

-- Layer 2: Cleaned (Dynamic Table, 1 min lag)
CREATE DYNAMIC TABLE silver.clean_events TARGET_LAG = '1 minute' ...
AS SELECT payload:event_id::INT, payload:type::VARCHAR, 
          TRY_CAST(payload:amount AS NUMBER) AS amount, ...
   FROM raw.events WHERE payload:event_id IS NOT NULL;

-- Layer 3: Enriched (Dynamic Table, 5 min lag)
CREATE DYNAMIC TABLE silver.enriched_events TARGET_LAG = '5 minutes' ...
AS SELECT e.*, c.segment FROM silver.clean_events e 
   JOIN dim.customers c ON e.customer_id = c.id;

-- Layer 4: Summary (Dynamic Table, 10 min lag)
CREATE DYNAMIC TABLE gold.hourly_summary TARGET_LAG = '10 minutes' ...
AS SELECT DATE_TRUNC('hour', event_time) AS hour, segment,
          SUM(amount), COUNT(*) FROM silver.enriched_events GROUP BY 1,2;
No tasks, no streams, no MERGE - Snowflake manages everything!
