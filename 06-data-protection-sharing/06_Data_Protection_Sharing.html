1. Time Travel

What Is Time Travel?

Access historical data (past versions) at any point within the retention period. Enables querying, cloning, and restoring data as it existed in the past.

  TIMELINE:
  
  Data written ──────────[ACTIVE DATA]──────────> Current
                              |
                    Data modified/deleted
                              |
                              v
                   [TIME TRAVEL WINDOW: 0-90 days]
                   (User accessible via AT/BEFORE)
                              |
                              v
                   [FAIL-SAFE: 7 days]
                   (Snowflake support only)
                              |
                              v
                   [PURGED - Gone forever]

Time Travel Retention by Object Type

Object TypeStandard EditionEnterprise+Default
Permanent Table0-1 days0-90 days1 day
Transient Table0-1 days0-1 days1 day
Temporary Table0-1 days0-1 days1 day
Database/Schema0-1 days0-90 days1 day

Accessing Historical Data

-- AT a specific timestamp
SELECT * FROM my_table AT(TIMESTAMP => '2024-06-15 10:30:00'::TIMESTAMP);

-- AT an offset (seconds ago)
SELECT * FROM my_table AT(OFFSET => -3600);  -- 1 hour ago

-- BEFORE a specific query (undo what a query did)
SELECT * FROM my_table BEFORE(STATEMENT => '01a1b2c3-...');  -- Query ID

-- Compare current vs historical
SELECT 
  a.id, a.amount AS current_amount, b.amount AS yesterday_amount,
  a.amount - b.amount AS change
FROM my_table a
JOIN my_table AT(OFFSET => -86400) b ON a.id = b.id
WHERE a.amount != b.amount;

UNDROP (Restore Dropped Objects)

-- Drop and restore table
DROP TABLE important_data;
UNDROP TABLE important_data;  -- Recovered!

-- Drop and restore schema
DROP SCHEMA analytics;
UNDROP SCHEMA analytics;

-- Drop and restore database
DROP DATABASE prod_db;
UNDROP DATABASE prod_db;

-- IMPORTANT: UNDROP only works within Time Travel retention period!
-- After retention expires + fail-safe = gone forever
Exam Tips - Time Travel:
  • Standard edition: MAX 1 day Time Travel (even for permanent tables)
  • Enterprise+: Up to 90 days for permanent tables/schemas/databases
  • Transient/Temporary: ALWAYS max 1 day (regardless of edition)
  • Parameter: DATA_RETENTION_TIME_IN_DAYS
  • Setting to 0: Disables Time Travel (no historical access, no UNDROP)
  • Time Travel data COSTS STORAGE (old partitions retained)
  • UNDROP works for tables, schemas, AND databases

Key Distinction: Fail-safe is NOT a backup system you can use directly. It's Snowflake's last-resort disaster recovery. If you need user-accessible recovery, use Time Travel. Fail-safe only exists for permanent objects and requires contacting Snowflake support.

3. Zero-Copy Cloning

How Cloning Works

  BEFORE CLONE:                     AFTER CLONE:
  
  Original Table                    Original Table     Clone Table
  [Partition A]                     [Partition A] <--- [Points to same A]
  [Partition B]                     [Partition B] <--- [Points to same B]
  [Partition C]                     [Partition C] <--- [Points to same C]
  
  Storage used: 3 partitions        Storage used: STILL 3 partitions (shared!)
                                    Clone cost: $0 additional storage!

  AFTER MODIFYING CLONE:
  
  Original Table     Clone Table
  [Partition A] <--- [Points to same A]  (unchanged - still shared)
  [Partition B]      [NEW Partition B']  (clone modified B - diverged)
  [Partition C] <--- [Points to same C]  (unchanged - still shared)
  
  Storage used: 4 partitions (3 original + 1 new B')
  Only DIVERGED partitions cost extra storage!
  
-- Clone a table
CREATE TABLE orders_dev CLONE orders;

-- Clone with Time Travel (clone as it was yesterday)
CREATE TABLE orders_snapshot CLONE orders AT(OFFSET => -86400);

-- Clone entire schema
CREATE SCHEMA dev_schema CLONE prod_schema;

-- Clone entire database
CREATE DATABASE dev_db CLONE prod_db;

-- Clone at a point in time
CREATE DATABASE recovery_db CLONE prod_db 
  BEFORE(TIMESTAMP => '2024-06-15 09:00:00'::TIMESTAMP);

What Gets Cloned

Included in CloneNOT Included in Clone
Table data (zero-copy)Privileges/grants (must re-grant)
Table structure & metadataLoad history (COPY dedup metadata)
Clustering keysStreams on the table
Stage definitions (named stages)Pipes
Constraints (NOT NULL, etc.)Tasks
Child objects (if cloning schema/db)External stage data (just metadata)
Cloning Key Facts:
  • Instant operation (metadata-only, no data copy)
  • Zero additional storage UNTIL data diverges
  • Works on: tables, schemas, databases, stages
  • Can clone with Time Travel (point-in-time clone)
  • Grants are NOT cloned - must be re-applied
  • Clone is independent - modifying either doesn't affect the other
  • Common uses: dev/test environments, backup snapshots, experimentation

4. Data Sharing

Secure Data Sharing (Zero-Copy)

  PROVIDER ACCOUNT                           CONSUMER ACCOUNT
  +--------------------+                     +--------------------+
  | Database: PROD_DB  |                     | Shared Database    |
  | Table: ORDERS      |---[SHARE]---------->| (Read-only)        |
  | View: SECURE_VIEW  |   No data copy!     | Can query directly!|
  +--------------------+                     +--------------------+

  KEY PRINCIPLES:
  - Data STAYS in provider's account (no copy, no movement)
  - Consumer gets READ-ONLY access (cannot modify provider's data)
  - Real-time (consumer always sees latest data)
  - Provider controls what's shared (tables, secure views, UDFs)
  - No ETL, no file transfers, no replication
  - Works within same region/cloud OR cross-region (with replication)

Creating a Share

-- PROVIDER SIDE:
-- 1. Create a share
CREATE SHARE orders_share COMMENT = 'Orders data for partners';

-- 2. Grant objects to the share
GRANT USAGE ON DATABASE prod_db TO SHARE orders_share;
GRANT USAGE ON SCHEMA prod_db.public TO SHARE orders_share;
GRANT SELECT ON TABLE prod_db.public.orders TO SHARE orders_share;
-- Or share a secure view (recommended for filtering):
GRANT SELECT ON VIEW prod_db.public.secure_orders_view TO SHARE orders_share;

-- 3. Add consumer accounts
ALTER SHARE orders_share ADD ACCOUNTS = consumer_account_locator;

-- CONSUMER SIDE:
-- 4. Create database from share
CREATE DATABASE partner_orders FROM SHARE provider_org.provider_acct.orders_share;

-- 5. Query shared data (read-only)
SELECT * FROM partner_orders.public.orders;

Sharing Objects & Secure Views

-- Secure View: Hide underlying query logic from consumer
CREATE OR REPLACE SECURE VIEW orders_for_partner AS
SELECT order_id, product, amount, order_date
FROM orders
WHERE partner_id = 'PARTNER_A'  -- Filter: partner sees only their data
  AND order_date > DATEADD('year', -2, CURRENT_DATE());
-- Consumer can't see the WHERE clause (SECURE hides it)

-- Share the secure view
GRANT SELECT ON VIEW orders_for_partner TO SHARE my_share;

Reader Accounts

-- Reader Account: For consumers WITHOUT their own Snowflake account
-- Provider creates and manages the reader account

CREATE MANAGED ACCOUNT partner_reader
  ADMIN_NAME = 'partner_admin'
  ADMIN_PASSWORD = 'TempPass123!'
  TYPE = READER;

-- Share data with reader account
ALTER SHARE my_share ADD ACCOUNTS = partner_reader;

-- Provider pays for reader account compute!
-- (Reader can only read shared data, not load their own)

5. Replication & Failover

Database Replication

  PRIMARY ACCOUNT (us-east-1)         SECONDARY ACCOUNT (eu-west-1)
  +--------------------+               +--------------------+
  | Database: PROD_DB  |--[REPLICATE]-->| Database: PROD_DB  |
  | (Read-Write)       |               | (Read-Only replica)|
  +--------------------+               +--------------------+
  
  -- Enable replication on primary
  ALTER DATABASE prod_db ENABLE REPLICATION TO ACCOUNTS org.account2;
  
  -- Create replica on secondary
  CREATE DATABASE prod_db AS REPLICA OF org.account1.prod_db;
  
  -- Refresh replica (manual or scheduled)
  ALTER DATABASE prod_db REFRESH;

Failover & Failback

Business Critical+ Only

  NORMAL OPERATION:                  AFTER FAILOVER:
  Primary (us-east-1): READ-WRITE   Primary (us-east-1): READ-ONLY
  Secondary (eu-west-1): READ-ONLY  Secondary (eu-west-1): READ-WRITE (promoted!)
  
  -- Failover: Promote secondary to primary
  ALTER DATABASE prod_db PRIMARY;  -- Run on secondary account
  
  -- Failback: After primary is healthy, reverse the process
  ALTER DATABASE prod_db PRIMARY;  -- Run on original primary

Replication Groups (Account-Level)

-- Replicate multiple objects together (databases, shares, parameters)
CREATE REPLICATION GROUP my_rg
  OBJECT_TYPES = DATABASES, SHARES, ROLES
  ALLOWED_DATABASES = prod_db, analytics_db
  ALLOWED_SHARES = orders_share
  ALLOWED_ACCOUNTS = org.secondary_account
  REPLICATION_SCHEDULE = '10 MINUTE';
Replication & Sharing Key Facts:
  • Data Sharing: Same region = instant, zero-copy. Cross-region = requires replication.
  • Replication: Copies data to another region/cloud (has cost + lag).
  • Failover: Business Critical+ only. Promotes replica to primary.
  • Reader Accounts: Provider pays for compute. Consumer can only read shared data.
  • Secure Views: Recommended for sharing (hide logic, filter data per consumer).
  • Marketplace: Discover and consume third-party data without ETL.

7. Interview & Certification Q&A

Q1: Explain Time Travel in Snowflake. How does it work under the hood?

A: Time Travel works because of micro-partition immutability:

  • When data is modified, old partitions are NOT deleted - they're retained for the retention period
  • Snowflake tracks which partitions were active at each point in time
  • AT/BEFORE queries reconstruct the table state using historical partition versions
  • After retention expires: partitions move to Fail-safe (7 days, Snowflake-only access)
  • After Fail-safe: partitions are purged (storage freed)
All retention-period data is billed as storage (active + time travel + fail-safe).

Q2: What's the difference between Time Travel and Fail-Safe?

A:

  • Time Travel: User-accessible (AT, BEFORE, UNDROP). Configurable (0-90 days). For intentional recovery and auditing.
  • Fail-Safe: Snowflake-support-only. Fixed 7 days. For catastrophic disaster recovery. Starts AFTER Time Travel ends.
  • Total protection for permanent table (Enterprise): Up to 90 days TT + 7 days FS = 97 days
  • Transient tables: Max 1 day TT + NO fail-safe = less protection, less cost

Q3: How does zero-copy cloning work? Is it truly free?

A:

  • Mechanism: Clone creates metadata pointers to existing micro-partitions (no physical copy)
  • Initial cost: Zero additional storage (shares all partitions with source)
  • After modifications: Only CHANGED partitions create new storage. Unchanged partitions remain shared.
  • Independence: Clone and source are fully independent after creation. Changes to one don't affect the other.
  • Not free long-term: As clone diverges, storage grows. But initial creation is instant and free.

Q4: How does Snowflake Data Sharing work? Is data copied?

A: No data is copied!

  • Provider creates a SHARE object and grants access to specific tables/views
  • Consumer creates a database FROM the share (read-only)
  • Consumer queries execute against the provider's data directly
  • Consumer uses their OWN warehouse (their compute costs, not provider's)
  • Always up-to-date (no ETL, no sync, no lag)
  • Works within same region. Cross-region requires replication first.

Q5: What is a Reader Account?

A: A managed Snowflake account for consumers who don't have their own Snowflake subscription:

  • Created BY the provider using CREATE MANAGED ACCOUNT
  • Provider PAYS for the reader's compute costs
  • Reader can ONLY access data shared with them (cannot load their own data)
  • Limited functionality compared to full Snowflake account
  • Use case: Share data with partners/customers who aren't Snowflake customers

Q6: Why use Secure Views for sharing instead of base tables?

A:

  • Row filtering: Show each consumer only their relevant data (WHERE partner_id = ...)
  • Column restriction: Exclude sensitive columns from the view
  • Logic hiding: SECURE keyword prevents consumers from seeing the view definition (no SHOW CREATE VIEW)
  • Aggregation: Share summarized data instead of raw records
  • Consistent interface: Can change underlying tables without breaking consumer access
Best practice: Always share Secure Views, never raw tables directly.

Q8: An employee accidentally runs DELETE FROM production_table (no WHERE). How do you recover?

A: Multiple recovery options:

  1. UNDROP (if table was dropped): UNDROP TABLE production_table;
  2. Clone from Time Travel: CREATE TABLE production_table_recovery CLONE production_table BEFORE(STATEMENT => 'query_id_of_delete');
  3. Re-insert from Time Travel: INSERT INTO production_table SELECT * FROM production_table BEFORE(STATEMENT => 'delete_query_id');
  4. SWAP: Clone to recovery → swap with damaged table: 
    CREATE TABLE recovery CLONE production_table AT(OFFSET => -300);
ALTER TABLE recovery SWAP WITH production_table;
Prevention: Use row-level RBAC, separate roles for DDL vs DML, resource monitors.
