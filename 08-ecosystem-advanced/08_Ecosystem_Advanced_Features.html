1. Apache Iceberg Tables

What Are Iceberg Tables in Snowflake?

Apache Iceberg is an open table format. Snowflake supports Iceberg tables, allowing interoperability with other engines (Spark, Trino, Flink) while still using Snowflake's query engine.

  TWO MODES OF ICEBERG IN SNOWFLAKE:

  MODE 1: SNOWFLAKE-MANAGED (Recommended)
  +--------------------+
  | Snowflake manages: |
  | - Data files       |  (Parquet in customer's cloud storage)
  | - Metadata         |  (Iceberg metadata in Snowflake + external)
  | - Full DML support |  (INSERT, UPDATE, DELETE, MERGE)
  | - Full Snowflake   |
  |   features         |  (Clustering, Time Travel, etc.)
  +--------------------+
  Storage: YOUR external volume (S3/Azure/GCS)
  Query: From Snowflake AND external engines!

  MODE 2: CATALOG-LINKED (External Catalog)
  +--------------------+
  | External manages:  |
  | - AWS Glue Catalog |  or Polaris/Unity Catalog
  | - Read-mostly from |
  |   Snowflake        |
  +--------------------+
  Use when: Another system (Spark) is primary writer
  
-- Create External Volume (where Iceberg data physically lives)
CREATE EXTERNAL VOLUME my_iceberg_volume
  STORAGE_LOCATIONS = (
    (
      NAME = 'my-s3-location'
      STORAGE_BASE_URL = 's3://my-bucket/iceberg-data/'
      STORAGE_PROVIDER = 'S3'
      STORAGE_AWS_ROLE_ARN = 'arn:aws:iam::123456:role/snowflake-iceberg'
    )
  );

-- Create Snowflake-managed Iceberg table
CREATE ICEBERG TABLE sales_iceberg (
  order_id INT,
  customer_id INT,
  amount DECIMAL(10,2),
  order_date DATE
)
  CATALOG = 'SNOWFLAKE'
  EXTERNAL_VOLUME = 'my_iceberg_volume'
  BASE_LOCATION = 'sales/';

-- Full DML works!
INSERT INTO sales_iceberg VALUES (1, 100, 99.99, '2024-06-15');
UPDATE sales_iceberg SET amount = 109.99 WHERE order_id = 1;

-- Catalog-linked (read from external catalog)
CREATE ICEBERG TABLE external_sales
  CATALOG = 'GLUE'
  CATALOG_TABLE_NAME = 'sales'
  EXTERNAL_VOLUME = 'my_volume';
Iceberg Key Facts for Interview:
  • Open format: Data stored as Parquet files with Iceberg metadata - readable by any Iceberg-compatible engine
  • Snowflake-managed: Full DML, Time Travel, clustering - Snowflake writes Iceberg format directly
  • External catalog: Read data managed by Spark/Glue/Polaris - limited DML
  • External Volume: Required - data physically in YOUR cloud storage (not Snowflake-internal)
  • Use case: Multi-engine architectures, data lakehouse patterns, avoiding vendor lock-in
  • Interop: Same data queryable from Snowflake + Spark + Trino + Flink simultaneously

3. Snowpark Container Services (SPCS)

What Is SPCS?

Run containerized applications (Docker) directly within Snowflake's infrastructure. Full OCI container support with GPU access.

  TRADITIONAL:                        SPCS:
  Run containers on:                  Run containers IN Snowflake:
  - AWS ECS/EKS                       - Compute pools (Snowflake-managed)
  - Azure AKS                         - Data stays in Snowflake
  - GCP GKE                           - Full governance applies
  - Self-managed K8s                  - GPU support for ML
  
  Must move data OUT to              Data accessed directly via
  container infrastructure           Snowflake internal network

  SPCS ARCHITECTURE:
  +------------------------------------------+
  | COMPUTE POOL (GPU or CPU nodes)          |
  |------------------------------------------|
  | +------------------+  +---------------+  |
  | | Service A        |  | Service B     |  |
  | | (REST API)       |  | (ML Model)    |  |
  | | Container Image  |  | Container Img |  |
  | +------------------+  +---------------+  |
  +------------------------------------------+
           |                     |
           v                     v
  +------------------------------------------+
  | Snowflake Data (tables, stages, etc.)   |
  | Accessed via Snowpark/SQL internally    |
  +------------------------------------------+
  
-- Create compute pool
CREATE COMPUTE POOL my_gpu_pool
  MIN_NODES = 1
  MAX_NODES = 3
  INSTANCE_FAMILY = GPU_NV_S;  -- NVIDIA GPU instances

-- Create image repository (store Docker images)
CREATE IMAGE REPOSITORY my_repo;

-- Push Docker image (from local)
-- docker tag my-app:latest .registry.snowflakecomputing.com/db/schema/my_repo/my-app:latest
-- docker push .registry.snowflakecomputing.com/db/schema/my_repo/my-app:latest

-- Create service
CREATE SERVICE my_ml_service
  IN COMPUTE POOL my_gpu_pool
  FROM SPECIFICATION $$
  spec:
    containers:
    - name: model-server
      image: /db/schema/my_repo/my-app:latest
      env:
        MODEL_PATH: /models/latest
      resources:
        requests:
          nvidia.com/gpu: 1
    endpoints:
    - name: predict
      port: 8080
      public: true
  $$;

-- Call the service
SELECT my_ml_service!PREDICT(input_data) FROM my_table;

6. Interview & Certification Q&A

Q1: What are Iceberg Tables and why would a company use them?

A: Iceberg Tables store data in Apache Iceberg open format (Parquet data files + Iceberg metadata):

  • Interoperability: Same data queryable from Snowflake, Spark, Trino, Flink, Presto without copying
  • No vendor lock-in: Data in open format on YOUR storage (S3/Azure/GCS)
  • Data lakehouse: Combine data lake openness with Snowflake's performance and governance
  • Snowflake-managed mode: Full DML + Time Travel + clustering (Snowflake writes Iceberg format natively)
  • Migration path: Gradually move Spark workloads to Snowflake without big-bang migration

Q2: What are Native Apps and how do they differ from Data Sharing?

Native Apps are for building data products; sharing is for giving data access.

Q3: What is SPCS and when would you use it vs standard Snowflake?

A: Use SPCS when standard SQL/UDFs aren't sufficient:

  • Custom ML models: PyTorch/TensorFlow models requiring GPU inference
  • Arbitrary languages: Go, Rust, C++ processing not supported as UDFs
  • Stateful services: REST APIs, long-running processes, web apps
  • Large models: LLM hosting, computer vision models needing GPU memory
  • Third-party tools: Run OSS tools (dbt, Airflow workers) inside Snowflake
Use standard Snowflake (SQL/Snowpark/UDFs) when: transformations are expressible in SQL/Python, no GPU needed, stateless processing suffices.

Q4: How does Snowflake fit into a modern data lakehouse architecture?

A: Snowflake bridges data warehouse + data lake:

  • Warehouse capabilities: ACID transactions, SQL, security, governance, performance
  • Lake capabilities: Iceberg tables (open format), external tables (query S3 files), semi-structured support (VARIANT)
  • Open ecosystem: Iceberg interop with Spark/Trino, Snowpark Connect for PySpark compatibility
  • Lakehouse pattern: Store in Iceberg (open), query from Snowflake (performant), also accessible from Spark (flexibility)
Snowflake is no longer "just a warehouse" - it's a data platform that supports open formats while adding enterprise capabilities.

Q5: What is a Data Clean Room and how is it implemented in Snowflake?

A:

  • Concept: Secure environment where two parties can analyze combined data WITHOUT exposing raw records to each other
  • Implementation: Built on Secure Data Sharing + approved query templates + aggregation requirements
  • Controls: Only pre-approved queries run, minimum group sizes enforced, no raw-row export
  • Use cases: Ad measurement (match ad exposure to purchases), healthcare research (combine datasets without exposing PHI), financial compliance
  • How it works: Both parties share data into the clean room. Analysis runs on combined data. Only aggregated results are returned.

Q7: You're designing a platform for 5 teams with different data needs. What Snowflake features do you use?

A: Modern multi-team architecture:

  1. Databases per domain: RAW_DB, STAGING_DB, ANALYTICS_DB, ML_DB (separation of concerns)
  2. RBAC: Functional roles per team (DATA_ENGINEER, ANALYST, DATA_SCIENTIST) + access roles per schema
  3. Warehouses per workload: ETL_WH (Medium), BI_WH (Small, multi-cluster), ML_WH (Snowpark-optimized)
  4. Dynamic Tables: For declarative ETL pipelines (staging → curated → marts)
  5. Data Sharing: Internal shares between teams for governed cross-domain access
  6. Tags + Masking: Classify sensitive data, auto-mask for unauthorized roles
  7. Resource Monitors: Per-team credit quotas to prevent overspend
  8. Cortex AI: Semantic views for analyst self-service; ML functions for data science team
  9. Git Integration: Version-controlled SQL + dbt for deployment pipeline
