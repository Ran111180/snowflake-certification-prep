1. Streams + Tasks (CDC Pattern)

The #1 exam pattern: Streams capture changes (INSERT/UPDATE/DELETE) on a table. Tasks consume the stream on a schedule. Together = Snowflake-native CDC without Kafka/Debezium.

How Streams Work

ConceptDetail
What it tracksDML changes (INSERT, UPDATE, DELETE) on a table
Metadata columnsMETADATA$ACTION, METADATA$ISUPDATE, METADATA$ROW_ID
ConsumptionOnce a DML reads from stream in a transaction, those rows are "consumed" (removed from stream)
TypesStandard (default), Append-only, Insert-only
CostZero additional cost (uses Time Travel metadata)
StalenessStream goes stale if not consumed within data retention period

Stream Types

TypeTracksUse Case

Complete Pattern: Stream + Task

-- 1. Create stream on source table
CREATE OR REPLACE STREAM orders_stream
  ON TABLE raw.orders;

-- 2. Create task that triggers ONLY when stream has data
CREATE OR REPLACE TASK process_new_orders
  WAREHOUSE = transform_wh
  SCHEDULE = '1 MINUTE'
  WHEN SYSTEM$STREAM_HAS_DATA('orders_stream')
AS
  MERGE INTO silver.orders t
  USING orders_stream s
  ON t.order_id = s.order_id
  WHEN MATCHED AND s.METADATA$ACTION = 'INSERT' AND s.METADATA$ISUPDATE = TRUE
    THEN UPDATE SET t.amount = s.amount, t.updated_at = CURRENT_TIMESTAMP()
  WHEN NOT MATCHED AND s.METADATA$ACTION = 'INSERT'
    THEN INSERT (order_id, amount, created_at)
         VALUES (s.order_id, s.amount, CURRENT_TIMESTAMP())
  WHEN MATCHED AND s.METADATA$ACTION = 'DELETE'
    THEN DELETE;

-- 3. Resume
ALTER TASK process_new_orders RESUME;
How WHEN works:
- Task still has a SCHEDULE (checks every 1 minute)
- Every minute, Snowflake evaluates SYSTEM$STREAM_HAS_DATA
- If FALSE (no new data) → task is SKIPPED (no compute cost)
- If TRUE → task body executes
- The schedule check itself is FREE (cloud services layer)
Exam Traps:
- WHEN clause does NOT eliminate the SCHEDULE - you still need one
- A stream with no data returns 0 rows but still "exists" - it's not stale
- Stream staleness = data retention expired without consumption → stream becomes unusable
- Consuming a stream is TRANSACTIONAL - if the DML fails/rolls back, stream data is NOT consumed

3. Task Graph CONFIG & Return Values

Passing Configuration to Task Graphs

-- Root task with CONFIG (parameters passed to entire DAG)
CREATE OR REPLACE TASK root_task
  WAREHOUSE = wh
  SCHEDULE = 'USING CRON 0 6 * * * UTC'
  CONFIG = '{"environment": "prod", "batch_size": 10000}'
AS
  CALL load_data();

-- Inside the procedure, read CONFIG:
CREATE OR REPLACE PROCEDURE load_data()
RETURNS STRING LANGUAGE SQL
AS
DECLARE
  v_config VARIANT;
  v_env STRING;
BEGIN
  v_config := PARSE_JSON(SYSTEM$GET_TASK_GRAPH_CONFIG());
  v_env := :v_config:environment::STRING;
  -- Use v_env in logic...
  RETURN 'Loaded for ' || :v_env;
END;

Return Values Between Tasks

-- Parent task: SET return value
CREATE TASK parent_task
  WAREHOUSE = wh
  SCHEDULE = '60 MINUTE'
AS
  CALL SYSTEM$SET_RETURN_VALUE('{"rows_loaded": 5000, "status": "ok"}');

-- Child task: GET predecessor's return value
CREATE TASK child_task
  WAREHOUSE = wh
  AFTER parent_task
AS
BEGIN
  LET parent_result VARCHAR := SYSTEM$GET_PREDECESSOR_RETURN_VALUE('parent_task');
  LET rows_loaded INT := PARSE_JSON(:parent_result):rows_loaded::INT;
  -- Use rows_loaded in logic...
END;
Key Points:
- CONFIG is set on the ROOT task, available to all tasks in the DAG
- SYSTEM$SET_RETURN_VALUE stores a string (use JSON for structured data)
- SYSTEM$GET_PREDECESSOR_RETURN_VALUE reads a specific predecessor's output
- Return values are visible in TASK_HISTORY.return_value column

4. Finalizer Tasks

-- Finalizer: runs AFTER the entire DAG completes (success OR failure)
CREATE OR REPLACE TASK cleanup_task
  WAREHOUSE = wh
  FINALIZE = root_task
AS
  CALL send_completion_notification();

-- Finalizer that checks for failures and alerts
CREATE OR REPLACE PROCEDURE send_completion_notification()
RETURNS STRING LANGUAGE SQL
AS
BEGIN
  -- Check if any task in the graph failed
  LET v_graph_status STRING := SYSTEM$GET_TASK_GRAPH_STATUS();
  -- Send appropriate notification
  IF (PARSE_JSON(:v_graph_status):status::STRING = 'FAILED') THEN
    CALL SYSTEM$SEND_EMAIL('email_int', 'oncall@company.com', 'PIPELINE FAILED', 'Check task history');
  ELSE
    CALL SYSTEM$SEND_EMAIL('email_int', 'team@company.com', 'Pipeline OK', 'All steps succeeded');
  END IF;
  RETURN :v_graph_status;
END;

5. Error Handling & Auto-Suspend

SUSPEND_TASK_AFTER_NUM_FAILURES

-- Auto-suspend after 3 consecutive failures (default is 10)
CREATE OR REPLACE TASK my_task
  WAREHOUSE = wh
  SCHEDULE = '5 MINUTE'
  SUSPEND_TASK_AFTER_NUM_FAILURES = 3
AS
  CALL my_procedure();

-- Check why a task was suspended
SHOW TASKS LIKE 'MY_TASK';
-- Look at 'last_suspended_reason' column
-- Values: USER_SUSPENDED, TASK_FAILURE_THRESHOLD_EXCEEDED

ERROR_INTEGRATION (Auto-Alert on Failure)

-- Automatically notify when task fails (no code needed!)
CREATE OR REPLACE TASK critical_pipeline
  WAREHOUSE = wh
  SCHEDULE = '60 MINUTE'
  ERROR_INTEGRATION = my_email_int
  SUSPEND_TASK_AFTER_NUM_FAILURES = 5
AS
  CALL run_critical_etl();

-- When the task FAILS, Snowflake automatically sends an error email
-- to the integration's DEFAULT_RECIPIENTS
-- Subject: "Snowflake task CRITICAL_PIPELINE has failed"
-- Body: includes error message, scheduled time, task name
Error handling strategy:
1. SUSPEND_TASK_AFTER_NUM_FAILURES = prevent runaway costs
2. ERROR_INTEGRATION = auto-alert on failure (no code!)
3. Finalizer task = custom logic on success OR failure
4. Inside procedure: TRY/CATCH with EXCEPTION handling

EXECUTE AS USERTask runs as if a specific user triggered itUseful for audit trails
Common Gotcha: You create a task as DATA_ENGINEER role. The procedure calls SYSTEM$SEND_EMAIL. Even if YOUR user has ACCOUNTADMIN, the task runs as DATA_ENGINEER. DATA_ENGINEER needs USAGE on the integration - not your user, not your other roles.

Fix: GRANT USAGE ON INTEGRATION email_int TO ROLE DATA_ENGINEER;

7. Task Cost Calculation

-- Credits consumed by task runs (via warehouse metering)
SELECT
  warehouse_name,
  DATE_TRUNC('day', start_time) AS day,
  SUM(credits_used) AS total_credits,
  COUNT(*) AS run_count
FROM SNOWFLAKE.ACCOUNT_USAGE.WAREHOUSE_METERING_HISTORY
WHERE warehouse_name = 'TASK_WH'
  AND start_time > DATEADD('day', -30, CURRENT_DATE())
GROUP BY 1, 2
ORDER BY day DESC;

-- Serverless task cost (different view)
SELECT
  task_name,
  DATE_TRUNC('day', start_time) AS day,
  SUM(credits_used) AS total_credits
FROM SNOWFLAKE.ACCOUNT_USAGE.SERVERLESS_TASK_HISTORY
WHERE start_time > DATEADD('day', -30, CURRENT_DATE())
GROUP BY 1, 2
ORDER BY day DESC;

-- Correlate task runs with warehouse cost
SELECT
  th.name AS task_name,
  th.scheduled_time,
  DATEDIFF('second', th.query_start_time, th.completed_time) AS runtime_sec,
  -- XS warehouse = 1 credit/hour = 0.000278 credits/second
  ROUND(DATEDIFF('second', th.query_start_time, th.completed_time) * 0.000278, 6) AS est_credits
FROM SNOWFLAKE.ACCOUNT_USAGE.TASK_HISTORY th
WHERE th.name = 'BIWEEKLY_REFRESH_TASK'
  AND th.state = 'SUCCEEDED'
ORDER BY th.scheduled_time DESC
LIMIT 10;
Cost Rules:
- User-managed tasks: Standard warehouse credit rate (XS = 1 credit/hr)
- Serverless tasks: 1.5x multiplier on compute
- WHEN condition check (cloud services): FREE
- Warehouse auto-resume: 60-second minimum billing even for 5-second task
- Best practice: Group small tasks into one procedure to avoid repeated warehouse startup

  WAREHOUSE = wh
  SCHEDULE = '5 MINUTE'
  ALLOW_OVERLAPPING_EXECUTION = FALSE  -- default
AS ...;

  WAREHOUSE = wh
  SCHEDULE = '1 MINUTE'
  ALLOW_OVERLAPPING_EXECUTION = TRUE
AS ...;
PolicyBehaviorWhen to Use
FALSE (default)If previous run still running, next run is SKIPPEDMost cases - prevents resource pile-up
TRUEMultiple runs can execute simultaneouslyIndependent batches that don't conflict (rare)
What happens with NO_OVERLAP:
- Schedule = 5 min, task takes 7 min
- Run 1 starts at 00:00, finishes at 00:07
- Run 2 (scheduled 00:05) → SKIPPED (run 1 still active)
- Run 3 starts at 00:10 normally
- Check TASK_HISTORY: skipped run shows state = SKIPPED

11. Exam Q&A (Part 2)

Q: A stream goes stale. What happens to the task with WHEN SYSTEM$STREAM_HAS_DATA?
A: The WHEN condition will return an error. The stream must be recreated. Staleness occurs when the stream isn't consumed within the table's data retention period.
Q: What's the cost of a WHEN condition check when the stream is empty?
A: FREE. The condition check runs in the cloud services layer. You only pay when the task body actually executes.
Q: Serverless task costs 1.5x. When is it CHEAPER than a warehouse?
A: When tasks are short (< 60 sec) and infrequent. A warehouse has 60-second minimum billing on resume. If your task takes 5 seconds, you pay for 60 sec anyway. Serverless bills per-second with no minimum.
Q: Can a finalizer task have child tasks?
A: NO. A finalizer is always the terminal node. It cannot be a predecessor to anything.
Q: You clone a database. Do tasks run on the clone?
A: NO. Tasks are NOT included in clone operations. Must recreate manually.
Q: A task runs as DATA_ENGINEER role but needs to read from another database owned by ANALYTICS role. What do you do?
A: Grant SELECT on the source tables to DATA_ENGINEER role. Tasks run with owner's rights - the owner role needs all necessary privileges.
Q: How does SYSTEM$GET_PREDECESSOR_RETURN_VALUE work with multiple predecessors (fan-in)?
A: Pass the predecessor task name as argument: SYSTEM$GET_PREDECESSOR_RETURN_VALUE('task_a'). Each predecessor's value is accessed independently.
Q: Task has SUSPEND_TASK_AFTER_NUM_FAILURES = 3. It fails 3 times then you fix the bug. What next?
A: The task auto-suspended. You must ALTER TASK ... RESUME manually after fixing. The failure counter resets on next successful run.
Q: What's the difference between ERROR_INTEGRATION and a finalizer task for error alerting?
A: ERROR_INTEGRATION = automatic email on any task failure (zero code, basic alert). Finalizer = custom logic (can check which step failed, send rich notifications, do cleanup). Use both together for production.
Q: An append-only stream is created on a table. Someone UPDATEs a row. Does the stream capture it?
A: NO. Append-only streams only capture INSERTs. Updates and deletes are invisible to it.
