1. Task Fundamentals

What is a Task? A Snowflake object that executes a single SQL statement or stored procedure on a schedule or triggered by data (stream).
FeatureDetail
ExecutionSingle SQL statement OR CALL procedure
ScheduleCRON expression OR fixed interval (e.g., 5 MINUTE)
TriggerWHEN clause (typically SYSTEM$STREAM_HAS_DATA)
ComputeUser-managed warehouse OR serverless
Default stateSUSPENDED (must explicitly RESUME)
DAG supportYes - parent/child task chains
Max tree depth1000 tasks per DAG
OverlapDefault: NO_OVERLAP (skips if previous still running)

What Tasks CANNOT Do (Limitations)

Know these for the exam - common trick questions!
#LimitationWorkaround
1Cannot run multiple SQL statements directly - only ONE statement per taskUse a stored procedure (CALL) to wrap multiple statements
2Cannot pass parameters at runtime - no input arguments like a procedureUse CONFIG or session variables, or read from a control table
3No built-in retry on failure - failed tasks don't auto-retryBuild retry logic in stored procedure, or use error integration + alerting
4No conditional branching in DAG - all children of a parent always runAdd WHEN condition on each child task, or use IF/ELSE inside procedure
5Cannot run interactively - no UI feedback, no RESULT_SCAN accessLog results to a table for later inspection
6Minimum schedule is 1 minute - cannot run more frequentlyUse Snowpipe Streaming or Dynamic Tables for sub-minute latency
7Cannot send email directly - task itself has no email capabilityCall SYSTEM$SEND_EMAIL inside a stored procedure
8No file/stage operations directly - can't PUT/GET filesUse COPY INTO in the SQL statement, or call a procedure
9Cannot be owned by ACCOUNTADMIN in best practice - tasks should be owned by functional rolesGrant EXECUTE TASK to a lower role, let that role own tasks
10Cannot access other accounts' data - no cross-account queriesUse data sharing to bring data into your account first
11WHEN condition limited - only boolean SQL expressions (no subqueries in some contexts)Use SYSTEM$STREAM_HAS_DATA or simple boolean expressions
12No dynamic scheduling - cannot change schedule based on data/conditionsUse a meta-task that ALTER TASKs programmatically via procedure
13Serverless tasks have size limits - max XXLARGE equivalentUse user-managed warehouse for very large workloads
14Cannot be cloned individually - tasks are not cloned with database/schema CLONERecreate tasks manually in the cloned environment
15No Time Travel on task objects - dropped task cannot be UNDROP'dKeep task DDL in version control (Git)
Interview Question: "Why use a stored procedure with a task instead of just SQL?"
Answer: Tasks only support ONE SQL statement. For multi-step ETL (multiple CREATE/INSERT, error handling, variable logic, email notifications), you MUST wrap in a stored procedure and CALL it from the task.

2. Complete Syntax Reference

CREATE TASK

CREATE [ OR REPLACE ] TASK [ IF NOT EXISTS ] task_name
  WAREHOUSE = wh_name              -- OR omit for serverless
  [ SCHEDULE = 'cron_or_interval' ]
  [ AFTER predecessor_task ]       -- child task (no SCHEDULE)
  [ WHEN condition ]               -- boolean expression
  [ ALLOW_OVERLAPPING_EXECUTION = TRUE | FALSE ]
  [ SUSPEND_TASK_AFTER_NUM_FAILURES = n ]
  [ ERROR_INTEGRATION = notification_integration ]
  [ COMMENT = 'description' ]
AS
  sql_statement | CALL procedure_name();

ALTER TASK

-- Suspend/Resume
ALTER TASK task_name SUSPEND;
ALTER TASK task_name RESUME;

-- Change schedule
ALTER TASK task_name SET SCHEDULE = 'USING CRON 0 6 * * * UTC';

-- Change warehouse
ALTER TASK task_name SET WAREHOUSE = new_wh;

-- Remove schedule (convert to child task)
ALTER TASK task_name UNSET SCHEDULE;

-- Add predecessor
ALTER TASK child_task ADD AFTER parent_task;

-- Remove predecessor
ALTER TASK child_task REMOVE AFTER parent_task;

Other Commands

DROP TASK task_name;
SHOW TASKS [ IN SCHEMA schema_name ];
DESCRIBE TASK task_name;
EXECUTE TASK task_name;  -- manual trigger (does not need RESUME)

3. Scheduling (CRON)

CRON Format

SCHEDULE = 'USING CRON minute hour day_of_month month day_of_week timezone'

-- Examples:
'USING CRON 0 6 * * * America/New_York'       -- Daily 6 AM ET
'USING CRON 0 0 1,15 * * Asia/Kolkata'        -- 1st & 15th midnight IST
'USING CRON */5 * * * * UTC'                   -- Every 5 minutes
'USING CRON 0 9 * * MON-FRI UTC'              -- Weekdays 9 AM
'USING CRON 0 0 L * * UTC'                    -- Last day of month

Fixed Interval

SCHEDULE = '5 MINUTE'     -- Every 5 minutes
SCHEDULE = '1 HOUR'       -- Every hour
SCHEDULE = '1440 MINUTE'  -- Every day (legacy, prefer CRON)
Exam Trap: Fixed interval is measured from the START of the last run, not from completion. If a task takes 3 min and interval is 5 min, next run starts 5 min after previous START (not 5 min after it finishes).

4. Task DAGs (Chaining)

-- Root task (has SCHEDULE)
CREATE TASK root_task
  WAREHOUSE = wh
  SCHEDULE = 'USING CRON 0 6 * * * UTC'
AS ...;

-- Child task (has AFTER, no SCHEDULE)
CREATE TASK child_step_1
  WAREHOUSE = wh
  AFTER root_task
AS ...;

-- Grandchild
CREATE TASK child_step_2
  WAREHOUSE = wh
  AFTER child_step_1
AS ...;

-- RESUME order: children FIRST, then root LAST
ALTER TASK child_step_2 RESUME;
ALTER TASK child_step_1 RESUME;
ALTER TASK root_task RESUME;

-- SUSPEND order: root FIRST, then children
ALTER TASK root_task SUSPEND;
ALTER TASK child_step_1 SUSPEND;
ALTER TASK child_step_2 SUSPEND;
Key Rules:
- Only the ROOT task has a SCHEDULE
- Child tasks use AFTER (no schedule)
- Resume from leaf to root; Suspend from root to leaf
- A child can have multiple predecessors (fan-in)
- A parent can have multiple children (fan-out)

Finalizer Tasks

-- Runs regardless of success/failure (cleanup)
CREATE TASK cleanup_task
  WAREHOUSE = wh
  FINALIZE = root_task
AS
  CALL cleanup_procedure();

6. Monitoring & History

-- View task run history
SELECT name, state, scheduled_time, completed_time,
       return_value, error_code, error_message
FROM TABLE(INFORMATION_SCHEMA.TASK_HISTORY(
  TASK_NAME => 'MY_TASK',
  SCHEDULED_TIME_RANGE_START => DATEADD('hour', -24, CURRENT_TIMESTAMP())
))
ORDER BY scheduled_time DESC;

-- Account-level history (all tasks)
SELECT *
FROM SNOWFLAKE.ACCOUNT_USAGE.TASK_HISTORY
WHERE scheduled_time > DATEADD('day', -7, CURRENT_DATE())

7. Stored Procedures with Tasks

CREATE OR REPLACE PROCEDURE my_schema.refresh_reports()
RETURNS STRING
LANGUAGE SQL
AS
DECLARE
  v_count INT;
  v_msg STRING DEFAULT '';
BEGIN
  -- Execute transforms
  CREATE OR REPLACE TABLE gold.report AS SELECT ...;

  -- Get row count into variable
  SELECT COUNT(*) INTO :v_count FROM gold.report;

  -- String concatenation
  v_msg := 'Refreshed ' || :v_count || ' rows';

  RETURN :v_msg;
END;

-- Call from a task
CREATE TASK my_task
  WAREHOUSE = wh
  SCHEDULE = '60 MINUTE'
AS
  CALL my_schema.refresh_reports();
Key SQL Scripting Rules:
- Variables need : prefix inside SQL statements: SELECT ... INTO :v_count
- Assignment uses := in code blocks: v_msg := 'hello';
- DECLARE block for variables, LET for inline declaration
- RETURN ends execution and returns value

Key Facts

Create Integration

-- Only ACCOUNTADMIN can create notification integrations
USE ROLE ACCOUNTADMIN;

CREATE NOTIFICATION INTEGRATION my_email_int
  TYPE = EMAIL
  ENABLED = TRUE
  ALLOWED_RECIPIENTS = ('user@company.com', 'team@company.com')
  DEFAULT_RECIPIENTS = ('user@company.com')
  DEFAULT_SUBJECT = 'Snowflake Pipeline Alert'
  COMMENT = 'Email alerts for data pipelines';

-- Grant to functional role
GRANT USAGE ON INTEGRATION my_email_int TO ROLE data_engineer;

ALTER Integration

-- Add more recipients
ALTER NOTIFICATION INTEGRATION my_email_int
  SET ALLOWED_RECIPIENTS = ('user@company.com', 'manager@company.com', 'oncall@company.com');

-- Change default subject
ALTER NOTIFICATION INTEGRATION my_email_int
  SET DEFAULT_SUBJECT = 'Data Pipeline Notification';

-- Disable temporarily
ALTER NOTIFICATION INTEGRATION my_email_int SET ENABLED = FALSE;

-- Describe / inspect
DESCRIBE NOTIFICATION INTEGRATION my_email_int;
SHOW NOTIFICATION INTEGRATIONS;

Send Email (SYSTEM$SEND_EMAIL)

-- Syntax:
CALL SYSTEM$SEND_EMAIL(
  'integration_name',       -- notification integration
  'recipient1,recipient2',  -- comma-separated (must be in ALLOWED_RECIPIENTS)
  'Subject Line',           -- subject (cannot be empty)
  'Body content',           -- body (cannot be empty)
  'text/html'               -- OPTIONAL: MIME type (default: text/plain)
);

-- Plain text example
CALL SYSTEM$SEND_EMAIL(
  'my_email_int',
  'user@company.com',
  'Pipeline Complete',
  'All tables refreshed successfully at ' || CURRENT_TIMESTAMP()::STRING
);

-- HTML email example
CALL SYSTEM$SEND_EMAIL(
  'my_email_int',
  'user@company.com',
  'Report Ready',
  '<html><body><h1 style="color:green">Success</h1><p>6 tables refreshed</p></body></html>',
  'text/html'
);
Common Errors:
- Integration does not exist or not authorized = Role needs USAGE grant on the integration
- Recipient not in allowed list = Email not in ALLOWED_RECIPIENTS property
- Empty subject/body = Both are required, cannot be empty strings
Exam & Interview Points:
- Sender is ALWAYS no-reply@snowflake.net - cannot customize
- No attachments - use GET_PRESIGNED_URL(@stage, 'file', expiry_seconds) for file links
- Stored procedure with owner's rights: the OWNER role needs USAGE on integration, not the caller
- Integration is an ACCOUNT-level object (not database/schema level)
- HTML is NOT validated - malformed HTML will still send (just render poorly)

9. Dynamic Tables vs Tasks

FactorTaskDynamic Table
Schedule controlYou decide exactly whenSnowflake decides (TARGET_LAG)
LogicAny SQL, procedures, multi-stepSingle SELECT only
Cost modelPay only when runningContinuous monitoring cost
Best forFixed schedules, complex logicNear-real-time, simple transforms
CREATE OR REPLACESupportedNot applicable (declarative)
OrchestrationManual (DAGs, procedures)Automatic (dependency resolution)
MaintenanceYou manage retries, alertingSnowflake handles it
Decision Rule:
- Data changes frequently + simple SELECT + need freshness = Dynamic Table
- Fixed schedule + complex logic + cost-sensitive = Task
- Need email notifications or multi-step = Task + Stored Procedure

10. Exam Tips & Tricky Questions

Q: A task is created but never runs. What's wrong?
A: Most common reasons: (1) Task is SUSPENDED (must ALTER TASK ... RESUME), (2) Role doesn't have EXECUTE TASK privilege, (3) Warehouse is suspended and AUTO_RESUME = FALSE.
Q: Which role creates notification integrations?
A: ACCOUNTADMIN (integration is account-level object). Other roles need USAGE grant.
Q: Can a child task have a SCHEDULE?
A: NO. A child task (one with AFTER) cannot have a SCHEDULE. Only root tasks have schedules.
Q: What happens if a task takes longer than its interval?
A: With default ALLOW_OVERLAPPING_EXECUTION = FALSE, the next run is SKIPPED. It does NOT queue.
Q: EXECUTE TASK command - does it require the task to be RESUMED?
A: NO. EXECUTE TASK runs a task immediately regardless of its state (even if suspended). It's for manual/testing triggers.
Q: What's the difference between EXECUTE TASK and EXECUTE MANAGED TASK?
A: EXECUTE TASK = user-managed warehouse tasks. EXECUTE MANAGED TASK = serverless tasks (Snowflake picks compute automatically).
Q: Can a task call a stored procedure?
A: YES. Use AS CALL my_procedure() in the task definition.
Q: How to trigger a task only when a stream has new data?
A: Use WHEN clause: WHEN SYSTEM$STREAM_HAS_DATA('my_stream'). Task still needs a schedule but only executes the body when condition is TRUE.
Q: What is SUSPEND_TASK_AFTER_NUM_FAILURES?
A: Auto-suspends a task after N consecutive failures. Default: 10. Prevents runaway errors from burning credits.
Q: Which role should create roles - ACCOUNTADMIN or SECURITYADMIN?
A: SECURITYADMIN. It's purpose-built for role/grant management. ACCOUNTADMIN works but violates least privilege.
