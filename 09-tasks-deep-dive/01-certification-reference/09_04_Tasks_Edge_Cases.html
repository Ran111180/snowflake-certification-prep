1. Task DDL Impact

DDL OperationTask StateScheduleHistory
CREATE OR REPLACE TASK SUSPENDED — always starts suspended New schedule applies Old history preserved in ACCOUNT_USAGE
ALTER TASK ... SUSPEND SUSPENDED — stops scheduling Preserved but inactive Preserved — shows when suspended
ALTER TASK ... RESUME STARTED — begins scheduling Active from next scheduled time New runs added to history
DROP TASK GONE Gone History in ACCOUNT_USAGE for 365 days
ALTER TASK ... SET SCHEDULE Must be SUSPENDED first! New schedule from next resume Preserved
ALTER TASK ... SET WAREHOUSE Must be SUSPENDED first! Unchanged Preserved
ALTER TASK ... MODIFY WHEN Must be SUSPENDED first! Unchanged Preserved
Critical Rule: ALL tasks start as SUSPENDED after creation. You MUST explicitly ALTER TASK ... RESUME. For DAGs, resume children FIRST, then the root task — otherwise the root fires before children are ready.

The Resume Order Rule (DAGs)

-- CORRECT order: Resume leaf → middle → root
ALTER TASK child_task_c RESUME;
ALTER TASK child_task_b RESUME;
ALTER TASK child_task_a RESUME;
ALTER TASK root_task RESUME;  -- Last!

-- WRONG order: Root first
ALTER TASK root_task RESUME;  -- Fires immediately!
ALTER TASK child_task_a RESUME;  -- Too late, root already ran
-- Result: Root ran but children were suspended → children skipped

-- SUSPEND order: Opposite — root first, then children
ALTER TASK root_task SUSPEND;  -- Stop scheduling first
ALTER TASK child_task_a SUSPEND;
ALTER TASK child_task_b SUSPEND;

2. DAG / Task Graph Edge Cases

ScenarioWhat HappensRisk
Predecessor task FAILS All downstream tasks are SKIPPED for that run. They don't execute. Data gap — downstream tables not updated
Predecessor task SKIPPED (WHEN condition false) Downstream tasks still RUN! SKIPPED ≠ FAILED. Successors execute normally. Unexpected execution — successors may process empty data
Circular dependency (A→B→A) Snowflake prevents this at creation time. Error: "Circular dependency detected." Blocked — can't create
Root task execution overlaps with previous run Snowflake SKIPS the new run. Tasks don't run concurrently with themselves. Missed execution — schedule fires but skip occurs
Child task takes longer than root schedule interval Next root run waits until entire DAG completes. If it can't, next run is skipped. Schedule drift
ALLOW_OVERLAPPING_EXECUTION = TRUE Multiple instances of the same DAG can run concurrently. Dangerous for stateful operations. Race conditions — possible duplicates or conflicts
Finalizer task Runs AFTER all tasks complete (success or failure). Used for cleanup/alerting. Safety net
DAG with 100+ tasks Limit: 1000 tasks per DAG. But deep chains add latency (sequential scheduling overhead). Performance — keep DAGs wide, not deep
Root task has AFTER clause ERROR. Root tasks define SCHEDULE, not AFTER. Only child tasks use AFTER. Blocked
Multiple root tasks in one schema Allowed. Each root task is an independent DAG. They don't interact. Normal
Key Distinction: FAILED predecessor → downstream SKIPPED. But WHEN condition evaluates to FALSE (SKIPPED) → downstream still RUNS. This is a common exam trap.

Predecessor Failure Behavior

-- DAG: root_task → task_a → task_b → task_c

-- If task_a FAILS:
-- task_b: SKIPPED (predecessor failed)
-- task_c: SKIPPED (predecessor chain broken)
-- Finalizer task (if any): RUNS (always runs)

-- If task_a is SKIPPED (WHEN = FALSE):
-- task_b: RUNS (skipped ≠ failed)
-- task_c: RUNS
-- This is the #1 exam trap for task DAGs!

3. Scheduling & Execution Edge Cases

ScenarioWhat Happens
SCHEDULE = '1 MINUTE' but SQL takes 5 minutes Next scheduled run at minute 2, 3, 4 are all SKIPPED (task still running). Runs again at minute 6.
CRON schedule: timezone DST change Task follows the specified timezone. During DST spring-forward: one run is skipped. Fall-back: one extra run.
WHEN clause + SCHEDULE together Task wakes at SCHEDULE interval, evaluates WHEN. If false, task is SKIPPED (not failed). Successors still run.
WHEN clause uses SYSTEM$STREAM_HAS_DATA If stream is empty, WHEN=FALSE, task is skipped. No compute charged for the skip (serverless tasks).
EXECUTE TASK (manual trigger) Runs the task immediately, ignoring schedule and WHEN clause. Counts as a normal execution. Triggers children.
EXECUTE TASK on a child task ERROR. Only root tasks can be manually triggered. Child tasks require predecessor completion.
Task AUTO_SUSPENDED (SUSPEND_TASK_AFTER_NUM_FAILURES) After N consecutive failures, Snowflake auto-suspends the task. Default: no auto-suspend (unlimited retries).
Warehouse suspended/dropped while task runs Current run fails. Task retries on next schedule. If warehouse doesn't exist: fails every time until fixed.
Task schedule: '60 MINUTES' vs CRON '0 * * * *' INTERVAL: 60 min from last completion. CRON: exactly at :00 every hour regardless of last run. CRON is wall-clock aligned.
SCHEDULE = '1 MINUTE' (minimum) 1 minute is the minimum interval for user-managed tasks. Serverless tasks: also 1 minute minimum.
INTERVAL vs CRON:
INTERVAL = relative (from last completion). If a run takes 3 min, next run starts at completion + interval.
CRON = absolute (wall clock). Runs at fixed times regardless of previous execution duration.

4. Ownership, Permissions & Warehouse Edge Cases

ScenarioWhat HappensFix
Task owner role dropped Task becomes orphaned. Still exists but can't run (no role to execute as). GRANT OWNERSHIP to a new role
Warehouse privilege revoked from task owner Task fails every scheduled run with "insufficient privileges". Grant USAGE on warehouse back to owner role
EXECUTE TASK privilege not granted ACCOUNTADMIN owns task but developer can't manually trigger it. GRANT EXECUTE TASK ON ACCOUNT TO ROLE developer_role;
Task references table it doesn't have access to Task fails at runtime with access error. Scheduling still fires normally. Grant SELECT/INSERT on required tables to task owner role
OWNERSHIP transferred while task is STARTED Task automatically SUSPENDED during transfer. Must be manually resumed by new owner. New owner must RESUME the task
Serverless task: no warehouse needed Serverless tasks use Snowflake-managed compute. No warehouse required or used. Set USER_TASK_MANAGED_INITIAL_WAREHOUSE_SIZE instead of WAREHOUSE
Warehouse auto-suspended during task execution Won't happen — warehouse stays active while a query is running. Auto-suspend applies only after idle. Not a real problem
Multiple tasks sharing one warehouse All tasks compete for the same warehouse resources. Queries queue if warehouse is maxed. Separate warehouses for critical vs non-critical tasks
Exam Alert: When task OWNERSHIP is transferred, the task is automatically SUSPENDED. The new owner must explicitly resume it. This is a security feature to prevent unauthorized execution under new roles.

5. Serverless Tasks Edge Cases

Serverless vs User-Managed Tasks

Serverless tasks use Snowflake-managed compute (no warehouse). They auto-scale but have different limits and billing model.

AspectServerless TaskUser-Managed Task
Warehouse None needed (Snowflake-managed) Must specify WAREHOUSE
Sizing USER_TASK_MANAGED_INITIAL_WAREHOUSE_SIZE (auto-adjusts) Fixed warehouse size
Cold start Yes — first run after idle may have startup delay Depends on warehouse suspend/resume
Cost model Per-second compute × 1.5x serverless multiplier Warehouse credit consumption
Max concurrent Limited by account-level serverless credit quota Limited by warehouse concurrency
WHEN clause evaluation FREE — no compute charged for WHEN=FALSE Warehouse starts just to evaluate WHEN
EXECUTE TASK Supported — runs on serverless compute Supported — runs on specified warehouse
Require privilege EXECUTE MANAGED TASK on account EXECUTE TASK on account + USAGE on warehouse
Cost Advantage of Serverless + WHEN clause: If a task checks SYSTEM$STREAM_HAS_DATA and the stream is empty, serverless tasks charge NOTHING. User-managed tasks would still start the warehouse (and incur 60s minimum credit) just to evaluate the condition.

6. Streams + Tasks Interaction Edge Cases

ScenarioWhat Happens
Task fails AFTER reading stream SAFE. Stream offset only advances on successful COMMIT. Failed task = rollback = stream data preserved for retry.
Stream goes stale while task is suspended Task resumes, tries to read stream, gets error "stream is stale". Task execution fails.
WHEN SYSTEM$STREAM_HAS_DATA but stream is stale WHEN evaluation itself may fail or return FALSE. Task might not fire at all, hiding the staleness problem.
Two tasks reading same stream Race condition. First task to commit consumes the data. Second task sees empty stream.
Task processes stream but INSERT fails (target full/permissions) Transaction rolls back. Stream data preserved. But task may keep failing until root cause fixed.
Stream + Task + MERGE: source row updated 5 times between runs Stream shows only the NET CHANGE (final state). MERGE sees one row, not 5. This is correct behavior.
ALLOW_OVERLAPPING_EXECUTION + Stream Dangerous. Two concurrent task instances both try to consume same stream. One succeeds, other gets empty result.

7. Recovery Playbook

Scenario A: Task Auto-Suspended After Repeated Failures

-- 1. Check what happened
SELECT *
FROM TABLE(INFORMATION_SCHEMA.TASK_HISTORY(
  TASK_NAME => 'my_task',
  SCHEDULED_TIME_RANGE_START => DATEADD(days, -7, CURRENT_TIMESTAMP())
))
WHERE STATE = 'FAILED'
ORDER BY SCHEDULED_TIME DESC
LIMIT 10;

-- 2. Read the error message from ERROR_MESSAGE column
-- Common causes: permission revoked, table dropped, warehouse unavailable

-- 3. Fix the root cause (grant permissions, recreate table, etc.)

-- 4. Resume the task
ALTER TASK my_task RESUME;

-- 5. Verify it runs successfully
EXECUTE TASK my_task;  -- Manual test run

Scenario B: DAG Child Task Keeps Failing (Blocking Pipeline)

-- 1. Identify the failing child
SELECT TASK_NAME, STATE, ERROR_MESSAGE, SCHEDULED_TIME
FROM TABLE(INFORMATION_SCHEMA.TASK_HISTORY())
WHERE ROOT_TASK_ID = (SELECT TASK_ID FROM INFORMATION_SCHEMA.TASKS
                      WHERE TASK_NAME = 'root_task')
  AND STATE = 'FAILED'
ORDER BY SCHEDULED_TIME DESC LIMIT 10;

-- 2. Suspend the entire DAG (root first)
ALTER TASK root_task SUSPEND;

-- 3. Fix the child task
ALTER TASK failing_child SUSPEND;
ALTER TASK failing_child SET AS = 'fixed SQL statement here';

-- 4. Resume in correct order (children first, root last)
ALTER TASK failing_child RESUME;
ALTER TASK root_task RESUME;

-- 5. Test manually
EXECUTE TASK root_task;

Scenario C: Task Running But Producing Wrong Results

-- 1. Suspend immediately to stop further damage
ALTER TASK my_task SUSPEND;

-- 2. Check when it started going wrong
SELECT SCHEDULED_TIME, STATE, RETURN_VALUE
FROM TABLE(INFORMATION_SCHEMA.TASK_HISTORY(TASK_NAME => 'my_task'))
ORDER BY SCHEDULED_TIME DESC LIMIT 20;

-- 3. Time Travel the target table to before the bad runs
CREATE TABLE target_table_fixed CLONE target_table
  AT(TIMESTAMP => '2026-08-14 10:00:00'::TIMESTAMP_LTZ);

-- 4. Swap tables
ALTER TABLE target_table RENAME TO target_table_bad;
ALTER TABLE target_table_fixed RENAME TO target_table;

-- 5. Fix the task SQL, recreate stream if needed
ALTER TASK my_task SUSPEND;
ALTER TASK my_task SET AS = 'corrected SQL';
-- If stream was consumed during bad runs, may need to recreate:
-- CREATE OR REPLACE STREAM my_stream ON TABLE source
--   AT(TIMESTAMP => '2026-08-14 10:00:00'::TIMESTAMP_LTZ);

-- 6. Resume
ALTER TASK my_task RESUME;

Scenario D: Ownership Transfer Gone Wrong

-- Task was transferred and auto-suspended. New owner didn't know.

-- 1. Find suspended tasks owned by a role
SHOW TASKS IN SCHEMA my_db.my_schema;
-- Look for state = 'suspended' with the new owner role

-- 2. As new owner, verify the task is safe to run
SELECT GET_DDL('TASK', 'my_task');  -- Review what it does

-- 3. Ensure the new owner has all required privileges
-- (warehouse usage, table access, etc.)

-- 4. Resume
ALTER TASK my_task RESUME;

Scenario E: Schedule Drift (Tasks Running Behind)

-- Task set to '5 MINUTE' but actual runs are 20 min apart

-- 1. Check execution duration
SELECT TASK_NAME,
       SCHEDULED_TIME,
       COMPLETED_TIME,
       DATEDIFF(second, QUERY_START_TIME, COMPLETED_TIME) AS duration_sec
FROM TABLE(INFORMATION_SCHEMA.TASK_HISTORY(TASK_NAME => 'my_task'))
ORDER BY SCHEDULED_TIME DESC LIMIT 10;

-- 2. If duration > schedule interval: runs are being skipped
-- Options:
-- a) Optimize the SQL (reduce runtime)
-- b) Use a larger warehouse
-- c) Increase the schedule interval to match reality
-- d) Switch to serverless (auto-scales compute)

ALTER TASK my_task SUSPEND;
ALTER TASK my_task SET
  USER_TASK_MANAGED_INITIAL_WAREHOUSE_SIZE = 'MEDIUM';  -- Serverless, bigger compute
ALTER TASK my_task UNSET WAREHOUSE;  -- Remove warehouse = becomes serverless
ALTER TASK my_task RESUME;

8. Exam Scenario Questions

ScenarioCorrect Answer
"A root task's predecessor fails. What happens to downstream tasks?" All downstream tasks are SKIPPED for that run. They don't execute. A finalizer (if configured) still runs.
"A task's WHEN clause evaluates to FALSE. Do successor tasks run?" YES. SKIPPED (WHEN=false) ≠ FAILED. Successor tasks STILL execute. Only FAILED predecessors block successors.
"A task is created. Does it start running immediately?" NO. All tasks start SUSPENDED. Must explicitly ALTER TASK ... RESUME to activate.
"Task OWNERSHIP is transferred to a new role. What's the task state after transfer?" SUSPENDED. Ownership transfer auto-suspends the task. New owner must resume it.
"Can you run EXECUTE TASK on a child task in a DAG?" NO. Only the ROOT task can be manually executed. Child tasks can only be triggered by predecessor completion.
"A task runs every 5 minutes but takes 8 minutes to complete. What happens?" Scheduled runs at minutes 5 and 10 are SKIPPED (task still running). Next run starts after completion (minute 8+).
"What privilege is needed to create serverless tasks?" EXECUTE MANAGED TASK ON ACCOUNT (not EXECUTE TASK, which is for user-managed warehouse tasks).
"A serverless task's WHEN clause evaluates to FALSE. Is there a compute charge?" NO. Serverless tasks don't charge for WHEN evaluation. User-managed tasks DO start the warehouse to evaluate.
"What is the minimum task schedule interval?" 1 minute. Both CRON (using '*/1 * * * *') and INTERVAL ('1 MINUTE') support 1-minute minimum.
"How do you resume a DAG correctly?" Resume CHILDREN first, then ROOT last. If root resumes first, it fires before children are active = children skipped.
Top 3 Exam Traps for Tasks:
  1. SKIPPED (WHEN=false) vs FAILED — only FAILED blocks successors
  2. All tasks start SUSPENDED — must explicitly RESUME
  3. Ownership transfer auto-suspends — new owner must RESUME
