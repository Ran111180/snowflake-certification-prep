Fundamentals (Q1-Q10)

Q1Basics
What compute resource does Snowpipe use to load data?
  • A) The virtual warehouse specified in the pipe definition
  • B) The user's default warehouse
  • C) Snowflake-supplied compute (serverless)
  • D) The warehouse associated with the target table
Snowpipe uses Snowflake-managed serverless compute. It does NOT use any user warehouse. This is a key billing and architecture difference from bulk COPY INTO.
Q2Metadata
How long does Snowpipe retain file load metadata to prevent duplicate loading?
  • A) 7 days
  • B) 14 days
  • C) 30 days
  • D) 64 days
Snowpipe retains load metadata for 14 days. After 14 days, if the same file is still on the stage and a new notification arrives, it WILL be reloaded (causing duplicates).
Q3CREATE OR REPLACE
What happens when you run CREATE OR REPLACE PIPE on an existing pipe?
  • A) The pipe is paused and the definition is updated
  • B) The pipe is updated in-place with no data impact
  • C) The load history (metadata) is purged, risking duplicate loads
  • D) An error is thrown because pipes cannot be replaced
CREATE OR REPLACE drops and recreates the pipe, purging all load metadata. Previously loaded files will be loaded again if still on the stage, causing duplicates.
Q4Latency
What is the typical latency for data to be queryable after a file arrives with auto-ingest?
  • A) Milliseconds
  • B) About 1 minute
  • C) 5-10 minutes
  • D) Depends on warehouse size
Snowpipe typically loads data within about 1 minute of the file notification. It does not depend on warehouse size since Snowpipe uses its own serverless compute.
Q5Billing
How is Snowpipe billed?
  • A) Per hour of active pipe time
  • B) Per file loaded (compute time for each file)
  • C) Per warehouse credit-second while loading
  • D) Flat monthly fee per pipe
Snowpipe billing is based on the serverless compute time used to load each file. Approximately 0.06 credits per 1000 files, but actual cost depends on file size and complexity.
Q6Auto-Ingest
Which stage type supports AUTO_INGEST for Snowpipe?
  • A) User stage (@~)
  • B) Table stage (@%table)
  • C) Named internal stage
  • D) Named external stage
AUTO_INGEST only works with external stages because it requires cloud event notifications (S3 events, Azure Event Grid, GCS Pub/Sub). Internal stages have no notification mechanism.
Q7PATTERN
How does PATTERN matching in Snowpipe differ from bulk COPY INTO?
  • A) Snowpipe doesn't support PATTERN
  • B) Snowpipe trims the stage URL before applying regex; bulk COPY applies to full path
  • C) Both behave identically
  • D) Bulk COPY trims the URL; Snowpipe applies to full path
In Snowpipe, the stage URL is trimmed from the file path BEFORE the regex pattern is applied. In bulk COPY INTO, the pattern matches against the full path. This can cause patterns that work in COPY to fail in Snowpipe.
Q8Transaction
How does Snowpipe handle transactions when loading multiple files?
  • A) All files in one transaction (atomic)
  • B) Each file is a separate micro-transaction
  • C) Files are grouped into batches of 10
  • D) Transaction depends on ON_ERROR setting
Each file loaded by Snowpipe is its own micro-transaction. If one file fails, others are not affected. This differs from bulk COPY INTO where all files can be in a single transaction.
Q9Basics
What does a Snowpipe object contain?
  • A) A COPY INTO statement that defines how to load data
  • B) A warehouse reference and schedule
  • C) A stream definition and merge logic
  • D) A SELECT statement for data transformation
A pipe object encapsulates a COPY INTO statement that defines the source stage, target table, file format, and error handling. It does not contain a warehouse reference or schedule.
Q10Operations
What is the purpose of ALTER PIPE REFRESH?
  • A) Restart the pipe after an error
  • B) Force Snowpipe to scan the stage and queue files for loading
  • C) Clear the pipe's load history
  • D) Update the pipe's COPY INTO definition
ALTER PIPE REFRESH instructs Snowpipe to scan the stage for files and queue them for loading. Used for backfill (files that arrived before the pipe existed) or when notifications were missed.

Auto-Ingest & Cloud (Q11-Q20)

Q11AWS
For AWS auto-ingest, what notification mechanism does Snowflake use?
  • A) S3 Event Notification to SNS topic
  • B) S3 Event Notification to SQS queue (Snowflake-managed)
  • C) CloudWatch Events to Lambda
  • D) S3 Event Notification to Kinesis stream
Snowflake uses a Snowflake-managed SQS queue. You configure S3 bucket events to send notifications TO this queue. The SQS ARN is found in the notification_channel column of SHOW PIPES.
Q12AWS
Where do you find the SQS queue ARN for configuring S3 event notifications?
  • A) AWS SQS console
  • B) SHOW PIPES output (notification_channel column)
  • C) DESCRIBE INTEGRATION output
  • D) Snowflake account settings
After creating a pipe with AUTO_INGEST=TRUE, run SHOW PIPES. The notification_channel column contains the Snowflake-managed SQS ARN to configure in S3 bucket event notifications.
Q13Azure
For Azure auto-ingest, what notification mechanism is used?
  • A) Azure Functions with HTTP trigger
  • B) Event Grid to Storage Queue
  • C) Service Bus Topic subscription
  • D) Azure Monitor Alert rule
Azure auto-ingest uses Event Grid subscriptions that route blob storage events to a Storage Queue that Snowflake polls. Requires a notification integration in Snowflake.
Q14GCS
For GCS auto-ingest, what notification mechanism is used?
  • A) GCS to Pub/Sub subscription
  • B) Cloud Functions HTTP callback
  • C) Eventarc to Cloud Run
  • D) GCS to Cloud Scheduler
GCS auto-ingest uses GCS notifications to a Pub/Sub topic, and Snowflake subscribes via a notification integration.
Q15Integration
What Snowflake object is required for auto-ingest on Azure/GCS (but NOT AWS)?
  • A) Storage Integration
  • B) Notification Integration
  • C) Security Integration
  • D) API Integration
Azure and GCS require a notification integration. AWS uses a Snowflake-managed SQS queue directly and doesn't need a separate notification integration for auto-ingest.
Q16Setup
Correct order to set up auto-ingest Snowpipe on AWS?
  • A) Create pipe, Create stage, Configure S3 events
  • B) Create storage integration, Create stage, Create pipe, Configure S3 events
  • C) Configure S3 events, Create stage, Create pipe
  • D) Create pipe, Configure S3 events, Create stage
Correct order: 1) Storage integration, 2) External stage, 3) Pipe with AUTO_INGEST=TRUE, 4) Get SQS ARN from SHOW PIPES, 5) Configure S3 events to that SQS.
Q17Internal
How can you trigger Snowpipe to load files from an internal stage?
  • A) AUTO_INGEST = TRUE
  • B) Snowpipe REST API (insertFiles) or ALTER PIPE REFRESH
  • C) Happens automatically when files are PUT
  • D) EXECUTE PIPE command
Internal stages don't support AUTO_INGEST. You must trigger manually via REST API (insertFiles) or ALTER PIPE REFRESH.
Q18Status
What does SYSTEM$PIPE_STATUS return for a paused pipe?
  • A) An error because pipe is inactive
  • B) JSON with executionState = "PAUSED"
  • C) NULL
  • D) Status of last successful load
SYSTEM$PIPE_STATUS returns JSON with executionState ("RUNNING", "PAUSED", or "STOPPED_FEATURE_DISABLED"), pendingFileCount, lastIngestedTimestamp, and lastIngestedFilePath.
Q19Notifications
Who creates and manages the SQS queue used for Snowpipe auto-ingest on AWS?
  • A) The customer creates it in their AWS account
  • B) Snowflake creates and manages it automatically
  • C) Both customer and Snowflake co-manage it
  • D) Created by the storage integration
The SQS queue is created and managed entirely by Snowflake. The customer only configures their S3 bucket to send events to this Snowflake-managed SQS queue.
Q20ERROR_INTEGRATION
What is the purpose of ERROR_INTEGRATION in a pipe?
  • A) Retries failed file loads automatically
  • B) Sends notifications when files fail to load
  • C) Routes error records to a dead-letter table
  • D) Transforms error messages before logging
ERROR_INTEGRATION sends push notifications (SNS, Event Grid, Pub/Sub) when loads fail. It only alerts - it does not retry or route data.

Streaming & Kafka (Q21-Q30)

Q21Streaming
Key difference between Snowpipe and Snowpipe Streaming?
  • A) Streaming uses a warehouse; Snowpipe does not
  • B) Snowpipe is file-based; Streaming is row-based (no files/stages needed)
  • C) Streaming requires Kafka; Snowpipe does not
  • D) They are the same service
Snowpipe (classic) loads FILES from stages. Snowpipe Streaming inserts ROWS directly via SDK without files or stages. Streaming has seconds latency vs ~1 minute for file-based.
Q22Streaming
Typical data availability latency for Snowpipe Streaming?
  • A) ~1 minute
  • B) ~5 minutes
  • C) Seconds (sub-10 seconds)
  • D) Milliseconds
Snowpipe Streaming provides data availability within seconds (typically under 10 seconds), compared to ~1 minute for file-based Snowpipe.
Q23Streaming
Does Snowpipe Streaming require a stage?
  • A) Yes, an internal stage
  • B) Yes, an external stage
  • C) No, data is sent directly to the table via SDK
  • D) Only for initial setup
Snowpipe Streaming bypasses the file/stage paradigm entirely. Data is written directly to tables via the Ingest SDK's insertRows API.
Q24Kafka
What does the Snowflake Kafka Connector use internally for low-latency ingestion?
  • A) Bulk COPY INTO with a warehouse
  • B) File-based Snowpipe (writes to stage first)
  • C) Snowpipe Streaming (row-level direct insert)
  • D) Direct SQL INSERT statements
The modern Snowflake Kafka Connector uses Snowpipe Streaming internally for seconds-level latency.
Q25Streaming
What is a "channel" in Snowpipe Streaming?
  • A) A notification pathway like SQS
  • B) A logical connection from one client to one table with its own offset
  • C) A partition in the target table
  • D) A Kafka consumer group
A channel is a logical connection from one client to one table. Each channel maintains its own offset token for exactly-once delivery.
Q26Comparison
50,000 IoT events/sec with sub-10 second latency needed. Best method?
  • A) Snowpipe with auto-ingest
  • B) Bulk COPY INTO every 30 seconds via Task
  • C) Snowpipe Streaming via the Ingest SDK
  • D) INSERT INTO via stored procedure
Snowpipe Streaming handles 50K+ events/sec with seconds latency and no file staging overhead.
Q27Comparison
200MB files arrive every 5 minutes in S3. Most cost-effective approach?
  • A) Snowpipe Streaming
  • B) Snowpipe with auto-ingest
  • C) Bulk COPY INTO via hourly Task
  • D) Dynamic Tables
200MB files every 5 minutes is the sweet spot for file-based Snowpipe auto-ingest (optimal file size, continuous arrival, event-driven).
Q28Comparison
50GB data export once per day at midnight. Most cost-effective loading?
  • A) Snowpipe with auto-ingest
  • B) Snowpipe Streaming
  • C) Bulk COPY INTO triggered by a Task
  • D) Multiple Snowpipes in parallel
For large, infrequent batches, bulk COPY INTO is more cost-effective. Snowpipe has ~10% serverless overhead.
Q29Kafka
Recommended approach to stream data from Kafka to Snowflake?
  • A) Write Kafka messages to S3 files then use Snowpipe
  • B) Use the Snowflake Kafka Connector with Kafka Connect
  • C) Spark Structured Streaming to Snowflake
  • D) Custom consumer running INSERT INTO
The Snowflake Kafka Connector is purpose-built, uses Snowpipe Streaming internally, handles exactly-once semantics, and requires minimal setup.
Q30Streaming
How does Snowpipe Streaming achieve exactly-once delivery?
  • A) 14-day file metadata deduplication
  • B) Offset tokens provided by the client with each insert
  • C) Transaction IDs from the source system
  • D) Exactly-once is not supported
Client-provided offset tokens. On recovery, the client checks the last committed offset and resumes, ensuring no duplicates or data loss.

RBAC & Privileges (Q31-Q37)

Q31Privileges
What privilege is needed to create a pipe in a schema?
  • A) CREATE PIPE on the database
  • B) CREATE PIPE on the schema
  • C) OWNERSHIP on the schema
  • D) INSERT on any table in the schema
CREATE PIPE privilege on the schema is required. The role also needs USAGE on the stage and INSERT on the target table for the pipe to function.
Q32Owner's Rights
Whose privileges are used when Snowpipe loads data?
  • A) The user who ran ALTER PIPE REFRESH
  • B) The role that owns the pipe (owner's rights)
  • C) ACCOUNTADMIN always
  • D) The role that created the stage
Pipes execute using the owner's privileges. The owner role must have INSERT on the table and USAGE on the stage.
Q33OPERATE
What can a role with OPERATE privilege on a pipe do?
  • A) Drop the pipe
  • B) Pause and resume the pipe
  • C) Change the COPY INTO definition
  • D) Transfer ownership
OPERATE allows pausing and resuming (ALTER PIPE SET PIPE_EXECUTION_PAUSED). Does not allow modifying definition or dropping.
Q34MONITOR
What can a role with only MONITOR privilege on a pipe do?
  • A) Pause and resume the pipe
  • B) View pipe status (SYSTEM$PIPE_STATUS)
  • C) Run ALTER PIPE REFRESH
  • D) View COPY_HISTORY for the table
MONITOR allows viewing status via SYSTEM$PIPE_STATUS and SHOW PIPES. No operational actions allowed.
Q35Transfer
After pipe ownership is transferred, what must be verified?
  • A) Original owner still has USAGE on stage
  • B) New owner has INSERT on table and USAGE on stage
  • C) Pipe is recreated with CREATE OR REPLACE
  • D) ACCOUNTADMIN approves the transfer
Since pipes run with owner's rights, the new owner must have USAGE on stage, INSERT on table, and USAGE on file format. Without these, loads fail.
Q36Integration
Who can grant USAGE on a storage integration?
  • A) Any role with CREATE INTEGRATION privilege
  • B) ACCOUNTADMIN only (account-level objects)
  • C) SYSADMIN
  • D) The schema owner
Storage integrations are account-level objects. Only ACCOUNTADMIN (or a role with OWNERSHIP on the integration) can grant USAGE.
Q37RBAC
Pipe fails with "Insufficient privileges to operate on table." Most likely cause?
  • A) User triggering REFRESH doesn't have INSERT
  • B) Pipe owner's role doesn't have INSERT on the target table
  • C) ACCOUNTADMIN needs to grant EXECUTE PIPE
  • D) The warehouse is suspended
Pipes use owner's rights. The pipe OWNER's role must have INSERT on the target table. The caller only needs OWNERSHIP or OPERATE on the pipe itself.

Production & Troubleshooting (Q38-Q44)

Q38File Size
Recommended file size for optimal Snowpipe performance?
  • A) 1-10 KB
  • B) 10-50 MB
  • C) 100-250 MB compressed
  • D) 1-5 GB
Snowflake recommends 100-250 MB compressed. Too small = per-file overhead. Too large = slow processing and queue backlog.
Q39Debug
Files arriving in S3 but pendingFileCount=0 and no data loading. Check first?
  • A) The warehouse is suspended
  • B) S3 event notification configured to correct SQS ARN
  • C) The table is full
  • D) The file format is wrong
If pendingFileCount is 0 and no data loading, the pipe isn't receiving notifications. Check S3 event notifications point to the correct Snowflake-managed SQS ARN.
Q40Debug
COPY_HISTORY shows "Numeric value 'abc' is not recognized." What happened?
  • A) The stage is misconfigured
  • B) File data doesn't match target table column types
  • C) The pipe is paused
  • D) The file is too large
A column expected numeric but received text. Fix the file or adjust COPY INTO (add CAST or change ON_ERROR to CONTINUE).
Q41History
How to check load history for a pipe over the last 7 days?
  • A) SELECT * FROM PIPE_HISTORY
  • B) SHOW PIPE HISTORY
  • C) Query COPY_HISTORY() with the target TABLE_NAME
  • D) Query SYSTEM$PIPE_HISTORY()
Use TABLE(INFORMATION_SCHEMA.COPY_HISTORY(TABLE_NAME=>'table', START_TIME=>...)). Note: takes TABLE name, not pipe name. Returns PIPE_NAME column in results.
Q42Cost
Company loads 100,000 tiny files (1KB each) per day via Snowpipe. Issue?
  • A) Files are too large
  • B) High per-file overhead; should batch into fewer, larger files
  • C) Snowpipe cannot handle this volume
  • D) They need multiple pipes
With 100K tiny files, per-file overhead is disproportionately expensive. Batch into fewer 100-250MB files upstream before staging.
Q43Backfill
Files uploaded to S3 BEFORE the pipe was created. How to load them?
  • A) They'll be picked up by auto-ingest
  • B) Use ALTER PIPE REFRESH to scan stage for existing files
  • C) Drop and recreate the pipe
  • D) Use SYSTEM$PIPE_RELOAD()
ALTER PIPE REFRESH scans the stage for files and queues them. Designed for backfill - loading files that arrived before the pipe existed.
Q44ON_ERROR
With ON_ERROR='CONTINUE', file has 100 rows but 5 have errors. What happens?
  • A) All 100 rows are skipped
  • B) 95 valid rows loaded; 5 bad rows skipped
  • C) File marked as partially loaded and retried
  • D) Pipe pauses automatically
ON_ERROR=CONTINUE loads all valid rows and skips only bad rows. COPY_HISTORY shows "Partially loaded" with ROW_COUNT=95 and ERROR_COUNT=5.

Advanced Concepts (Q45-Q50)

Q45Monitoring
Which view provides 365 days of Snowpipe credit consumption?
  • A) INFORMATION_SCHEMA.PIPE_USAGE_HISTORY
  • B) SNOWFLAKE.ACCOUNT_USAGE.PIPE_USAGE_HISTORY
  • C) SNOWFLAKE.ACCOUNT_USAGE.COPY_HISTORY
  • D) INFORMATION_SCHEMA.COPY_HISTORY
SNOWFLAKE.ACCOUNT_USAGE.PIPE_USAGE_HISTORY provides 365 days (1-2hr latency). INFORMATION_SCHEMA version gives 14 days real-time.
Q46Transformations
Which transformation is supported in a Snowpipe COPY INTO?
  • A) JOIN with another table
  • B) GROUP BY with aggregation
  • C) CAST and column reordering using $1, $2 notation
  • D) Calling a UDF
Snowpipe supports CAST, column reordering ($1,$2), SUBSTR, TRIM, METADATA$ columns. JOINs, aggregations, UDFs are NOT supported.
Q47Metadata
What METADATA columns can be referenced in Snowpipe COPY INTO?
  • A) METADATA$FILENAME and METADATA$FILE_ROW_NUMBER
  • B) METADATA$TABLE_NAME and METADATA$SCHEMA_NAME
  • C) METADATA$PIPE_NAME and METADATA$LOAD_TIME
  • D) METADATA$SOURCE and METADATA$DESTINATION
Available: METADATA$FILENAME, METADATA$FILE_ROW_NUMBER, METADATA$FILE_CONTENT_KEY, METADATA$FILE_LAST_MODIFIED, METADATA$START_SCAN_TIME.
Q48Architecture
Can multiple Snowpipes load into the same target table simultaneously?
  • A) No, only one pipe per table allowed
  • B) Yes, but not recommended due to lock contention
  • C) Yes, with no performance impact
  • D) Only if they read from the same stage
Multiple pipes CAN target the same table, but it causes micro-partition contention. Best practice: one pipe per table.
Q49Operations
Safe way to modify a pipe's COPY INTO definition?
  • A) ALTER PIPE SET DEFINITION = '...'
  • B) CREATE OR REPLACE PIPE (accept metadata loss)
  • C) Pause, note last load, Drop, Create new, Refresh with MODIFIED_AFTER
  • D) You cannot change a pipe's definition
COPY INTO cannot be altered. Safe approach: 1) Pause, 2) Wait pending=0, 3) Note timestamp, 4) Drop, 5) Create new, 6) REFRESH with MODIFIED_AFTER for the gap.
Q50Comparison
Which is TRUE about Snowpipe vs Dynamic Tables?
  • A) Both are for data ingestion from external sources
  • B) Snowpipe loads raw data from files; Dynamic Tables transform existing data
  • C) Dynamic Tables replace Snowpipe for all use cases
  • D) Snowpipe can do transformations Dynamic Tables cannot
Snowpipe = INGESTION (external files into Snowflake). Dynamic Tables = TRANSFORMATION (data already in Snowflake). They often work together.
