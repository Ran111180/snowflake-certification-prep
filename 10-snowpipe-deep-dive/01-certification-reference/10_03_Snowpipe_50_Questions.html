Fundamentals (Q1-Q10)

Q1Basics
What compute resource does Snowpipe use to load data?
  • A) The virtual warehouse specified in the pipe definition
  • B) The user's default warehouse
  • C) Snowflake-supplied compute (serverless)
  • D) The warehouse associated with the target table
Answer: C
Snowpipe uses Snowflake-managed serverless compute. It does NOT use any user warehouse. This is a key billing and architecture difference from bulk COPY INTO.
Q2Metadata
How long does Snowpipe retain file load metadata to prevent duplicate loading?
  • A) 7 days
  • B) 14 days
  • C) 30 days
  • D) 64 days
Answer: B
Snowpipe retains load metadata for 14 days. After 14 days, if the same file is still on the stage and a new notification arrives, it WILL be reloaded (causing duplicates).
Q3CREATE OR REPLACE
What happens when you run CREATE OR REPLACE PIPE on an existing pipe?
  • A) The pipe is paused and the definition is updated
  • B) The pipe is updated in-place with no data impact
  • C) The load history (metadata) is purged, risking duplicate loads
  • D) An error is thrown because pipes cannot be replaced
Answer: C
CREATE OR REPLACE drops and recreates the pipe, purging all load metadata. Previously loaded files will be loaded again if still on the stage, causing duplicates. Always prefer ALTER PIPE when possible.
Q4Latency
What is the typical latency for data to be queryable after a file arrives in the stage with auto-ingest enabled?
  • A) Milliseconds
  • B) About 1 minute
  • C) 5-10 minutes
  • D) Depends on warehouse size
Answer: B
Snowpipe typically loads data within about 1 minute of the file notification. It does not depend on warehouse size since Snowpipe uses its own serverless compute.
Q5Billing
How is Snowpipe billed?
  • A) Per hour of active pipe time
  • B) Per file loaded (compute time for each file)
  • C) Per warehouse credit-second while loading
  • D) Flat monthly fee per pipe
Answer: B
Snowpipe billing is based on the serverless compute time used to load each file. It's approximately 0.06 credits per 1000 files, but actual cost depends on file size and complexity.
Q6Auto-Ingest
Which stage type supports AUTO_INGEST for Snowpipe?
  • A) User stage (@~)
  • B) Table stage (@%table)
  • C) Named internal stage
  • D) Named external stage
Answer: D
AUTO_INGEST only works with external stages because it requires cloud event notifications (S3 events, Azure Event Grid, GCS Pub/Sub). Internal stages have no notification mechanism.
Q7PATTERN
How does PATTERN matching in Snowpipe differ from bulk COPY INTO?
  • A) Snowpipe doesn't support PATTERN
  • B) Snowpipe trims the stage URL before applying the regex; bulk COPY applies to the full path
  • C) Both behave identically
  • D) Bulk COPY trims the URL; Snowpipe applies to the full path
Answer: B
In Snowpipe, the stage's URL (including prefix) is trimmed from the file path BEFORE the regex pattern is applied. In bulk COPY INTO, the pattern is matched against the full path. This difference can cause patterns that work in COPY to fail in Snowpipe.
Q8Transaction
How does Snowpipe handle transactions when loading multiple files?
  • A) All files in one transaction (atomic)
  • B) Each file is a separate micro-transaction
  • C) Files are grouped into batches of 10
  • D) Transaction depends on ON_ERROR setting
Answer: B
Each file loaded by Snowpipe is its own micro-transaction. If one file fails, others are not affected. This differs from bulk COPY INTO where all files can be in a single transaction.
Q9Basics
What does a Snowpipe object contain?
  • A) A COPY INTO statement that defines how to load data
  • B) A warehouse reference and schedule
  • C) A stream definition and merge logic
  • D) A SELECT statement for data transformation
Answer: A
A pipe object encapsulates a COPY INTO statement that defines the source stage, target table, file format, and error handling. It does not contain a warehouse reference or schedule.
Q10Operations
What is the purpose of ALTER PIPE REFRESH?
  • A) Restart the pipe after an error
  • B) Force Snowpipe to scan the stage and queue files for loading
  • C) Clear the pipe's load history
  • D) Update the pipe's COPY INTO definition
Answer: B
ALTER PIPE REFRESH instructs Snowpipe to scan the stage for files and queue them for loading. It's used for backfill (files that arrived before the pipe existed) or when auto-ingest notifications were missed.

Auto-Ingest & Cloud Setup (Q11-Q20)

Q11AWS
For AWS auto-ingest, what notification mechanism does Snowflake use?
  • A) S3 Event Notification → SNS topic
  • B) S3 Event Notification → SQS queue (Snowflake-managed)
  • C) CloudWatch Events → Lambda
  • D) S3 Event Notification → Kinesis stream
Answer: B
Snowflake uses an SQS queue that it creates and manages. You configure S3 bucket events to send notifications TO this Snowflake-managed SQS queue. You find the SQS ARN in the notification_channel column of SHOW PIPES.
Q12AWS
Where do you find the SQS queue ARN for configuring S3 event notifications?
  • A) AWS SQS console
  • B) SHOW PIPES output (notification_channel column)
  • C) DESCRIBE INTEGRATION output
  • D) Snowflake account settings
Answer: B
After creating a pipe with AUTO_INGEST=TRUE, run SHOW PIPES and look at the notification_channel column. It contains the Snowflake-managed SQS ARN that you configure as the destination in S3 bucket event notifications.
Q13Azure
For Azure auto-ingest, what notification mechanism is used?
  • A) Azure Functions → HTTP trigger
  • B) Event Grid → Storage Queue
  • C) Service Bus → Topic subscription
  • D) Azure Monitor → Alert rule
Answer: B
Azure auto-ingest uses Event Grid subscriptions that route blob storage events to a Storage Queue that Snowflake polls. This requires creating a notification integration in Snowflake.
Q14GCS
For GCS auto-ingest, what notification mechanism is used?
  • A) GCS → Pub/Sub subscription
  • B) Cloud Functions → HTTP callback
  • C) Eventarc → Cloud Run
  • D) GCS → Cloud Scheduler
Answer: A
GCS auto-ingest uses GCS notifications to a Pub/Sub topic, and Snowflake subscribes to that topic via a notification integration.
Q15Integration
What Snowflake object is required for auto-ingest on Azure and GCS (but NOT AWS)?
  • A) Storage Integration
  • B) Notification Integration
  • C) Security Integration
  • D) API Integration
Answer: B
Azure and GCS require a notification integration to connect to Event Grid or Pub/Sub. AWS uses a Snowflake-managed SQS queue directly and doesn't require a separate notification integration for auto-ingest.
Q16Setup
What is the correct order to set up auto-ingest Snowpipe on AWS?
  • A) Create pipe → Create stage → Configure S3 events
  • B) Create storage integration → Create stage → Create pipe → Configure S3 events
  • C) Configure S3 events → Create stage → Create pipe
  • D) Create pipe → Configure S3 events → Create stage
Answer: B
The correct order is: 1) Create storage integration (IAM trust), 2) Create external stage using integration, 3) Create pipe with AUTO_INGEST=TRUE, 4) Get SQS ARN from SHOW PIPES, 5) Configure S3 bucket events to that SQS.
Q17Internal
How can you trigger Snowpipe to load files from an internal stage?
  • A) AUTO_INGEST = TRUE
  • B) Snowpipe REST API (insertFiles) or ALTER PIPE REFRESH
  • C) It happens automatically when files are PUT to the stage
  • D) EXECUTE PIPE command
Answer: B
Internal stages don't support AUTO_INGEST (no cloud notification system). You must trigger Snowpipe manually via the REST API (insertFiles endpoint) or by running ALTER PIPE REFRESH.
Q18Status
What does SYSTEM$PIPE_STATUS return when called on a paused pipe?
  • A) An error because the pipe is inactive
  • B) JSON with executionState = "PAUSED"
  • C) NULL
  • D) The status of the last successful load
Answer: B
SYSTEM$PIPE_STATUS returns JSON including executionState ("RUNNING", "PAUSED", or "STOPPED_FEATURE_DISABLED"), pendingFileCount, lastIngestedTimestamp, and lastIngestedFilePath.
Q19Notifications
Who creates and manages the SQS queue used for Snowpipe auto-ingest on AWS?
  • A) The customer creates it in their AWS account
  • B) Snowflake creates and manages it automatically
  • C) Both customer and Snowflake co-manage it
  • D) It's created by the storage integration
Answer: B
The SQS queue is created and managed entirely by Snowflake. The customer only needs to configure their S3 bucket to send event notifications to this Snowflake-managed SQS queue.
Q20ERROR_INTEGRATION
What is the purpose of ERROR_INTEGRATION in a pipe definition?
  • A) Retries failed file loads automatically
  • B) Sends notifications when files fail to load
  • C) Routes error records to a dead-letter table
  • D) Transforms error messages before logging
Answer: B
ERROR_INTEGRATION sends push notifications (via SNS, Event Grid, or Pub/Sub) when files fail to load. It does not retry or route data — it only alerts.

Snowpipe Streaming & Kafka (Q21-Q30)

Q21Streaming
What is the key difference between Snowpipe and Snowpipe Streaming?
  • A) Snowpipe Streaming uses a warehouse; Snowpipe does not
  • B) Snowpipe is file-based; Snowpipe Streaming is row-based (no files/stages needed)
  • C) Snowpipe Streaming requires Kafka; Snowpipe does not
  • D) They are the same service with different names
Answer: B
Snowpipe (classic) loads FILES from stages. Snowpipe Streaming inserts ROWS directly via SDK (Java/Python) without needing files or stages. Streaming has seconds latency vs ~1 minute for file-based.
Q22Streaming
What is the typical data availability latency for Snowpipe Streaming?
  • A) ~1 minute
  • B) ~5 minutes
  • C) Seconds (sub-10 seconds)
  • D) Milliseconds
Answer: C
Snowpipe Streaming provides data availability within seconds (typically under 10 seconds), compared to ~1 minute for file-based Snowpipe.
Q23Streaming
Does Snowpipe Streaming require a Snowflake stage?
  • A) Yes, an internal stage is required
  • B) Yes, an external stage is required
  • C) No, data is sent directly to the table via SDK
  • D) Only for the initial setup
Answer: C
Snowpipe Streaming bypasses the file/stage paradigm entirely. Data is written directly to Snowflake tables via the Ingest SDK's insertRows API call.
Q24Kafka
What does the Snowflake Kafka Connector use internally for low-latency ingestion?
  • A) Bulk COPY INTO with a warehouse
  • B) File-based Snowpipe (writes to stage first)
  • C) Snowpipe Streaming (row-level direct insert)
  • D) Direct SQL INSERT statements
Answer: C
The modern Snowflake Kafka Connector uses Snowpipe Streaming internally, providing seconds-level latency from Kafka to Snowflake tables. The legacy version used file-based Snowpipe (writing to an internal stage first).
Q25Streaming
What is a "channel" in Snowpipe Streaming?
  • A) A notification pathway like SQS
  • B) A logical connection from one client to one table with its own offset
  • C) A partition in the target table
  • D) A Kafka consumer group
Answer: B
A channel is a logical connection from one client/partition to one table. Each channel maintains its own offset token for exactly-once delivery and recovery.
Q26Comparison
A company needs to load IoT sensor data at 50,000 events per second with sub-10 second latency. Which method is best?
  • A) Snowpipe with auto-ingest
  • B) Bulk COPY INTO every 30 seconds via Task
  • C) Snowpipe Streaming via the Ingest SDK
  • D) INSERT INTO via stored procedure
Answer: C
Snowpipe Streaming is designed for high-velocity, low-latency scenarios. It handles 50K+ events/sec with seconds latency and no file staging overhead. File-based Snowpipe would have ~1 minute latency and require writing files first.
Q27Comparison
Files of 200MB each arrive every 5 minutes in S3. What is the most cost-effective loading approach?
  • A) Snowpipe Streaming
  • B) Snowpipe with auto-ingest
  • C) Bulk COPY INTO via hourly Task
  • D) Dynamic Tables
Answer: B
200MB files every 5 minutes is the sweet spot for file-based Snowpipe auto-ingest (optimal file size, continuous arrival, event-driven). Streaming is unnecessary since data is already in files. Hourly Task would add latency.
Q28Comparison
A 50GB data export arrives once per day at midnight. What loading method is most cost-effective?
  • A) Snowpipe with auto-ingest
  • B) Snowpipe Streaming
  • C) Bulk COPY INTO triggered by a Task
  • D) Multiple Snowpipes in parallel
Answer: C
For large, infrequent batch loads, bulk COPY INTO with a dedicated warehouse is more cost-effective than Snowpipe. Snowpipe has ~10% overhead for serverless compute. A task can trigger the load at the right time.
Q29Kafka
What is the recommended approach to stream data from Kafka to Snowflake?
  • A) Write Kafka messages to S3 files, then use Snowpipe auto-ingest
  • B) Use the Snowflake Kafka Connector with Kafka Connect
  • C) Use Spark Structured Streaming to read Kafka and write to Snowflake
  • D) Custom consumer that runs INSERT INTO statements
Answer: B
The Snowflake Kafka Connector (via Kafka Connect) is the recommended approach. It's purpose-built, uses Snowpipe Streaming internally for low latency, handles exactly-once semantics, and requires minimal setup.
Q30Streaming
How does Snowpipe Streaming achieve exactly-once delivery?
  • A) 14-day file metadata deduplication
  • B) Offset tokens provided by the client with each insert
  • C) Transaction IDs from the source system
  • D) Exactly-once is not supported
Answer: B
Snowpipe Streaming uses client-provided offset tokens. On recovery, the client can check the last committed offset and resume from there, ensuring no data is duplicated or lost.

RBAC & Privileges (Q31-Q37)

Q31Privileges
What privilege is needed to create a pipe in a schema?
  • A) CREATE PIPE on the database
  • B) CREATE PIPE on the schema
  • C) OWNERSHIP on the schema
  • D) INSERT on any table in the schema
Answer: B
CREATE PIPE privilege on the schema is required to create a pipe. The role also needs USAGE on the stage and INSERT on the target table (for the pipe to actually function).
Q32Owner's Rights
Whose privileges are used when Snowpipe loads data?
  • A) The user who ran ALTER PIPE REFRESH
  • B) The role that owns the pipe (owner's rights)
  • C) ACCOUNTADMIN always
  • D) The role that created the stage
Answer: B
Pipes execute using the pipe owner's privileges (owner's rights model). The owner role must have USAGE on the stage and INSERT on the target table. If ownership is transferred, the new owner needs these privileges.
Q33OPERATE
What can a role with OPERATE privilege on a pipe do?
  • A) Drop the pipe
  • B) Pause and resume the pipe
  • C) Change the COPY INTO definition
  • D) Transfer ownership
Answer: B
OPERATE privilege allows pausing and resuming the pipe (ALTER PIPE SET PIPE_EXECUTION_PAUSED). It does not allow modifying the pipe definition or dropping it — those require OWNERSHIP.
Q34MONITOR
What can a role with only MONITOR privilege on a pipe do?
  • A) Pause and resume the pipe
  • B) View pipe status (SYSTEM$PIPE_STATUS)
  • C) Run ALTER PIPE REFRESH
  • D) View COPY_HISTORY for the table
Answer: B
MONITOR allows viewing the pipe's status via SYSTEM$PIPE_STATUS and SHOW PIPES. It does not allow any operational actions like pausing, refreshing, or modifying.
Q35Transfer
After pipe ownership is transferred to a new role, what must be verified?
  • A) The original owner still has USAGE on the stage
  • B) The new owner role has INSERT on the table and USAGE on the stage
  • C) The pipe is recreated with CREATE OR REPLACE
  • D) ACCOUNTADMIN approves the transfer
Answer: B
Since pipes run with owner's rights, the new owner role must have all necessary privileges: USAGE on the stage, INSERT on the target table, and USAGE on the file format. Without these, loads will fail with permission errors.
Q36Integration
Who can grant USAGE on a storage integration?
  • A) Any role with CREATE INTEGRATION privilege
  • B) ACCOUNTADMIN only (since integrations are account-level objects)
  • C) SYSADMIN
  • D) The schema owner
Answer: B
Storage integrations are account-level objects. Only ACCOUNTADMIN (or a role with OWNERSHIP on the integration) can grant USAGE to other roles.
Q37RBAC
A pipe fails with "Insufficient privileges to operate on table." What is the most likely cause?
  • A) The user triggering REFRESH doesn't have INSERT on the table
  • B) The pipe owner's role doesn't have INSERT on the target table
  • C) ACCOUNTADMIN needs to grant EXECUTE PIPE privilege
  • D) The warehouse is suspended
Answer: B
Since pipes use owner's rights, the pipe owner's role must have INSERT on the target table. The caller who triggers REFRESH only needs OWNERSHIP or OPERATE on the pipe itself — the actual load runs as the owner.

Production & Troubleshooting (Q38-Q44)

Q38File Size
What is the recommended file size for optimal Snowpipe performance?
  • A) 1-10 KB
  • B) 10-50 MB
  • C) 100-250 MB compressed
  • D) 1-5 GB
Answer: C
Snowflake recommends 100-250 MB compressed files for Snowpipe. Too small = excessive per-file overhead. Too large = slow processing and queue backlog.
Q39Debug
Files are arriving in S3 but the pipe shows pendingFileCount = 0 and no data is loading. What should you check first?
  • A) The warehouse is suspended
  • B) S3 event notification is correctly configured to send to the pipe's SQS ARN
  • C) The table is full
  • D) The file format is wrong
Answer: B
If pendingFileCount is 0 and no data is loading, the pipe is not receiving notifications. The most common cause is S3 event notifications not properly configured to send to the Snowflake-managed SQS queue ARN.
Q40Debug
COPY_HISTORY shows STATUS='Load failed' with error "Numeric value 'abc' is not recognized." What happened?
  • A) The stage is misconfigured
  • B) A file contains data that doesn't match the target table's column types
  • C) The pipe is paused
  • D) The file is too large
Answer: B
This error means a column expected a numeric value but received text ('abc'). The file data doesn't match the target table schema. Fix the file or adjust the COPY INTO (add CAST or change ON_ERROR to CONTINUE).
Q41Debug
How do you check the load history for a specific pipe over the last 7 days?
  • A) SELECT * FROM PIPE_HISTORY WHERE pipe_name = '...'
  • B) SHOW PIPE HISTORY for pipe_name
  • C) Query COPY_HISTORY() Information Schema function with the target TABLE_NAME
  • D) Query SYSTEM$PIPE_HISTORY()
Answer: C
Use TABLE(INFORMATION_SCHEMA.COPY_HISTORY(TABLE_NAME=>'table', START_TIME=>...)) which returns load details including the PIPE_NAME column. Note: this function takes the TABLE name, not the pipe name.
Q42Cost
A company loads 100,000 tiny files (1KB each) per day via Snowpipe. What is the likely issue?
  • A) Files are too large
  • B) High per-file overhead makes this expensive; they should batch into fewer, larger files
  • C) Snowpipe cannot handle this volume
  • D) They need multiple pipes for this
Answer: B
With 100K tiny files, the per-file overhead is disproportionately expensive. The fix is to batch small records into fewer, larger files (100-250MB) upstream before staging. The total data may be tiny but the per-file billing adds up.
Q43Backfill
Files were uploaded to S3 BEFORE the pipe was created. How do you load them?
  • A) They will be picked up automatically by auto-ingest
  • B) Use ALTER PIPE REFRESH to scan the stage for existing files
  • C) Drop and recreate the pipe
  • D) Use SYSTEM$PIPE_RELOAD()
Answer: B
ALTER PIPE REFRESH scans the stage for files and queues them for loading. This is specifically designed for backfill — loading files that arrived before the pipe existed or during periods when notifications were missed.
Q44ON_ERROR
With ON_ERROR = 'CONTINUE', what happens when a file has 100 rows but 5 have errors?
  • A) All 100 rows are skipped
  • B) 95 valid rows are loaded; 5 bad rows are skipped
  • C) The file is marked as partially loaded and retried
  • D) The pipe pauses automatically
Answer: B
ON_ERROR = CONTINUE loads all valid rows and skips only the rows with errors. The COPY_HISTORY will show the file as "Partially loaded" with ROW_COUNT=95 and ERROR_COUNT=5.

Advanced Concepts (Q45-Q50)

Q45Monitoring
Which view provides 365 days of Snowpipe credit consumption history?
  • A) INFORMATION_SCHEMA.PIPE_USAGE_HISTORY
  • B) SNOWFLAKE.ACCOUNT_USAGE.PIPE_USAGE_HISTORY
  • C) SNOWFLAKE.ACCOUNT_USAGE.COPY_HISTORY
  • D) INFORMATION_SCHEMA.COPY_HISTORY
Answer: B
SNOWFLAKE.ACCOUNT_USAGE.PIPE_USAGE_HISTORY provides 365 days of credit usage data (with 1-2 hour latency). INFORMATION_SCHEMA.PIPE_USAGE_HISTORY provides 14 days with real-time data.
Q46Transformations
Which transformation is supported in a Snowpipe COPY INTO statement?
  • A) JOIN with another table
  • B) GROUP BY with aggregation
  • C) CAST and column reordering using $1, $2 notation
  • D) Calling a UDF
Answer: C
Snowpipe supports limited transformations: CAST, column reordering ($1, $2), SUBSTR, TRIM, METADATA$ columns, and column omission. JOINs, aggregations, UDFs, and subqueries are NOT supported.
Q47Metadata
What METADATA columns can be referenced in a Snowpipe COPY INTO?
  • A) METADATA$FILENAME and METADATA$FILE_ROW_NUMBER
  • B) METADATA$TABLE_NAME and METADATA$SCHEMA_NAME
  • C) METADATA$PIPE_NAME and METADATA$LOAD_TIME
  • D) METADATA$SOURCE and METADATA$DESTINATION
Answer: A
METADATA$FILENAME (source file name), METADATA$FILE_ROW_NUMBER (row position in file), METADATA$FILE_CONTENT_KEY, METADATA$FILE_LAST_MODIFIED, and METADATA$START_SCAN_TIME are available in COPY INTO statements.
Q48Architecture
Can multiple Snowpipes load into the same target table simultaneously?
  • A) No, only one pipe per table is allowed
  • B) Yes, but it's not recommended due to lock contention
  • C) Yes, with no performance impact
  • D) Only if they read from the same stage
Answer: B
Multiple pipes CAN target the same table, but it's not recommended. It can cause micro-partition contention and slightly degrade performance. Best practice is one pipe per table, using path prefixes to partition if needed.
Q49Operations
What is the safe way to modify a pipe's COPY INTO definition?
  • A) ALTER PIPE SET DEFINITION = '...'
  • B) CREATE OR REPLACE PIPE (accepting metadata loss risk)
  • C) Pause → note last load time → Drop → Create new pipe → Refresh with MODIFIED_AFTER
  • D) You cannot change a pipe's definition
Answer: C
The COPY INTO statement cannot be altered — you must drop and recreate. The safe approach is: 1) Pause pipe, 2) Wait for pending=0, 3) Note last load timestamp, 4) Drop pipe, 5) Create new pipe, 6) ALTER PIPE REFRESH with MODIFIED_AFTER to load only the gap.
Q50Comparison
Which statement is TRUE about Snowpipe vs Dynamic Tables?
  • A) Both are used for data ingestion from external sources
  • B) Snowpipe loads raw data from files; Dynamic Tables transform existing Snowflake data
  • C) Dynamic Tables replace Snowpipe for all use cases
  • D) Snowpipe can do transformations that Dynamic Tables cannot
Answer: B
Snowpipe is for INGESTION — getting data from external files into Snowflake. Dynamic Tables are for TRANSFORMATION — declaratively transforming data already in Snowflake. They serve different purposes and often work together: Snowpipe loads raw data, then Dynamic Tables transform it.
