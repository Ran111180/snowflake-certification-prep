0. What Can Snowpipe Load Into & From?

Key Rule: Snowpipe wraps a COPY INTO <table> FROM <stage> statement. The constraints are: what stages can be sources, and what tables can be targets.

Supported Source Stages

Stage TypeAuto-IngestREST API (insertFiles)Notes
Internal named stage (@my_stage) NO YES No cloud event notifications for internal stages. Must use REST API to trigger.
Internal user stage (@~) NO YES Same as named internal — REST API only.
Internal table stage (@%table) NO YES Same — REST API only.
External stage — S3 YES (SQS) YES Event notifications via SQS queue. Most common auto-ingest pattern.
External stage — GCS YES (Pub/Sub) YES Event notifications via GCS Pub/Sub subscription.
External stage — Azure Blob YES (Event Grid) YES Event notifications via Azure Event Grid + Queue Storage.

Supported Target Objects (COPY INTO destination)

Target ObjectSupportedNotes
Permanent tablesYESMost common target. Full support.
Transient tablesYESSupported — same as permanent for loading.
Temporary tablesNOPipe persists across sessions; temp table is session-scoped. Incompatible.
External tablesNOExternal tables are read-only. Cannot COPY INTO them.
ViewsNOCannot COPY INTO a view. Must target the underlying table.
Dynamic tablesNODTs are managed by Snowflake (auto-refresh). Cannot manually insert.
Materialized viewsNOMVs are auto-maintained. Cannot manually insert.
Iceberg tablesYESSupported — Snowpipe can load into Snowflake-managed Iceberg tables.

Supported File Formats

FormatSupportedNotes
CSV / TSVYESDelimited text files. Most common.
JSONYESLoads into VARIANT column or structured columns.
AvroYESSchema embedded in file.
ParquetYESColumnar format. Efficient for large datasets.
ORCYESColumnar format (Hadoop ecosystem).
XMLYESLoads into VARIANT column.

What Snowpipe CANNOT Do

OperationWhyAlternative
UPDATE existing rowsSnowpipe only does INSERT (COPY INTO is append-only)Use Stream + Task + MERGE for upserts
DELETE rowsCOPY INTO doesn't support DELETEUse Stream + Task pattern
MERGE / UpsertSnowpipe = COPY INTO only (no MERGE)Load to staging table → MERGE via task
Transform during loadLimited — can do simple column mapping in COPY's SELECTLoad raw → transform with task/DT
Load to multiple tablesOne pipe = one COPY INTO = one target tableCreate multiple pipes or use Stream fan-out
Unload data (COPY INTO @stage)Snowpipe is ingest-onlyUse task with COPY INTO @stage for unloading
Exam Traps:
  • Internal stages do NOT support auto-ingest (no event notifications). REST API only.
  • Snowpipe cannot load into temporary tables (session mismatch).
  • Snowpipe cannot UPDATE/DELETE/MERGE — it's pure COPY INTO (append).
  • One pipe = one target table. Cannot fan out to multiple tables from one pipe.
  • Snowpipe does NOT use your warehouse — it's 100% serverless compute.

1. Pipe DDL Impact

DDL OperationLoad HistoryQueued FilesAuto-Ingest
CREATE OR REPLACE PIPE RESET — load metadata wiped clean LOST — queued files dropped Files reloaded — same files appear "new" = DUPLICATES
ALTER PIPE SET PIPE_EXECUTION_PAUSED = TRUE Preserved Accumulates — notifications queue up Resumes — processes queued files when unpaused
ALTER PIPE REFRESH Preserved — skips already-loaded files Adds missed files to queue Safe — uses metadata to dedup
DROP PIPE LOST — all metadata gone LOST Stopped — notifications go nowhere
ALTER PIPE ... SET (change COPY INTO options) Preserved Preserved Continues — new options apply to future loads
The #1 Snowpipe Killer: CREATE OR REPLACE PIPE resets the 14-day load metadata. Every file that was loaded in the last 14 days will be loaded AGAIN, creating duplicates in your target table. This is the most common production incident with Snowpipe.

Safe Way to Modify a Pipe

-- WRONG: Causes duplicates
CREATE OR REPLACE PIPE my_pipe AS COPY INTO t FROM @s;

-- CORRECT: Preserves metadata
ALTER PIPE my_pipe SET PIPE_EXECUTION_PAUSED = TRUE;
-- Make your changes (limited to what ALTER supports)
ALTER PIPE my_pipe SET PIPE_EXECUTION_PAUSED = FALSE;

-- If you MUST recreate (e.g., changing COPY INTO target table):
-- Step 1: Record what's been loaded
SELECT * FROM TABLE(INFORMATION_SCHEMA.COPY_HISTORY(...));
-- Step 2: CREATE OR REPLACE PIPE ...
-- Step 3: Manually deduplicate or accept one-time reload

2. File & Stage Edge Cases

ScenarioWhat HappensRisk Level
Same filename, different content (overwrite file on stage) Snowpipe will NOT reload it. Metadata says "already loaded" based on filename + path. Data loss — new content never loaded
Same content, different filename Snowpipe loads it again — metadata tracks by filename, not content hash. Duplicates in target table
File modified after initial load Internal stage: NOT reloaded (same filename). External stage: depends on event notification — if new PUT event fires, may reload. Unpredictable
File deleted from stage after loading No impact — data already in table. Metadata still remembers the file for 14 days. Safe
Very large file (5+ GB) Single file = single thread. No parallelism within one file. Pipe processes it as one unit. Slow — split into smaller files for parallelism
Thousands of tiny files (<100KB each) Overhead per file exceeds benefit. High metadata cost, inefficient micro-batches. Expensive — batch into 100-250 MB files
File with 0 rows (empty) Snowpipe processes it, records in load history as "0 rows loaded". No error. Safe but wastes a credit micro-charge
Compressed file (.gz) on stage Snowpipe handles transparently if FILE_FORMAT specifies COMPRESSION. One compressed file = one load unit (no split). Normal
File arrives BEFORE pipe is created Auto-ingest won't pick it up (no notification was sent to pipe). Use ALTER PIPE REFRESH to catch it. Missed — manual intervention needed
PATTERN regex in COPY INTO Uses SQL LIKE pattern (% and _), NOT regex. Common mistake: using .* instead of %. Silent miss — no files match, no error
Optimal File Size: 100-250 MB compressed. This balances parallelism (many files = many threads) with per-file overhead. Snowpipe's sweet spot for cost and speed.

3. Duplicate Loading Scenarios

How Snowpipe Prevents Duplicates (Normal Operation)

Snowpipe maintains a 14-day rolling metadata window of loaded filenames. If the same filename appears again within 14 days, it's skipped. This is NOT content-based — it's purely filename + path.

ScenarioDuplicates?Why
Same file, same pipe, within 14 days NO Metadata remembers the filename
Same file, same pipe, AFTER 14 days YES Metadata expired — file appears "new"
Same file, DIFFERENT pipe (same table) YES Each pipe has its own metadata — no cross-pipe dedup
CREATE OR REPLACE PIPE, then same file arrives YES Metadata was wiped by REPLACE
ALTER PIPE REFRESH on already-loaded files NO REFRESH checks metadata before loading
Same content in file with different name YES Dedup is by filename only, not content
Manual COPY INTO + Snowpipe for same file YES Manual COPY doesn't update Snowpipe's metadata
File loaded via Pipe A, same file sent to Pipe B (same target) YES Pipes don't share metadata

Deduplication Strategies

-- Strategy 1: Use METADATA$FILENAME to detect duplicates
CREATE TABLE raw_data (
  data VARIANT,
  loaded_file VARCHAR DEFAULT METADATA$FILENAME,
  loaded_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP()
);

-- Strategy 2: Downstream MERGE (stream + task pattern)
MERGE INTO clean_data t
USING (SELECT DISTINCT * FROM raw_data QUALIFY ROW_NUMBER()
       OVER (PARTITION BY id ORDER BY loaded_at DESC) = 1) s
ON t.id = s.id
WHEN MATCHED THEN UPDATE SET ...
WHEN NOT MATCHED THEN INSERT ...;

-- Strategy 3: Unique constraint (won't prevent load, but downstream detection)
-- Snowpipe does NOT enforce unique constraints during COPY

4. Error & Failure Scenarios

Error ScenarioDefault BehaviorWith ON_ERROR Setting
One bad row in file (type mismatch, extra column) Entire file skipped (ON_ERROR=SKIP_FILE default for Snowpipe) CONTINUE: loads good rows, skips bad. SKIP_FILE: entire file rejected.
All rows bad in file File skipped. Recorded in COPY_HISTORY with errors_seen > 0. Same — file is marked as "loaded with errors" in metadata (won't retry).
Stage permission revoked Pipe fails silently for new files. No error notification by default. Check PIPE_USAGE_HISTORY for failures. Set up error notification integration.
Target table dropped Pipe enters error state. Files queue up but fail to load. Recreate table, pause/unpause pipe. Queued files will retry.
Target table columns changed If new schema incompatible with COPY INTO definition, all new files fail. Fix the table schema or recreate the pipe with new column mapping.
Warehouse suspended (REST API pipe) N/A — Snowpipe uses serverless compute, not your warehouse. Common misconception: Snowpipe NEVER uses your warehouse.
File partially loaded then system crash Transaction rolled back. File marked as not loaded. Will retry automatically. Snowpipe guarantees at-least-once delivery (whole file or nothing).
Key Difference from Manual COPY: Snowpipe's default ON_ERROR is SKIP_FILE (not ABORT_STATEMENT like manual COPY). This means a single bad row causes the ENTIRE file to be skipped, and Snowpipe moves to the next file.

Error Notification Setup

-- Get notified about Snowpipe errors
CREATE NOTIFICATION INTEGRATION pipe_errors
  TYPE = QUEUE
  ENABLED = TRUE
  ...;

CREATE PIPE my_pipe
  AUTO_INGEST = TRUE
  ERROR_INTEGRATION = pipe_errors  -- Sends to SNS/SQS on failure
  AS COPY INTO my_table FROM @my_stage;

-- Check error history manually
SELECT * FROM TABLE(INFORMATION_SCHEMA.COPY_HISTORY(
  TABLE_NAME => 'MY_TABLE',
  START_TIME => DATEADD(hours, -24, CURRENT_TIMESTAMP())
)) WHERE STATUS = 'LOAD_FAILED';

5. Auto-Ingest Edge Cases

ScenarioWhat HappensResolution
S3 event notification delayed File sits on stage unloaded until notification arrives. Could be seconds to minutes. SLA is "within minutes" not "instant". Use Snowpipe Streaming for sub-second.
Notification arrives but pipe is paused Notification queues internally. When pipe resumes, processes queued notifications. Queue has limits — if paused too long (14+ days), oldest notifications may expire.
Multiple files arrive simultaneously Each file generates its own notification. Snowpipe processes them in parallel (serverless scales). Normal operation — Snowpipe handles burst well.
S3 bucket policy changed (blocked) Notifications still fire but Snowpipe can't read files. Files fail silently. Check SYSTEM$PIPE_STATUS and COPY_HISTORY for access errors.
SQS queue deleted/recreated Pipe loses connection to notification channel. All new files missed. Must recreate the pipe or reconfigure the notification integration.
File PUT to wrong subdirectory If pipe's COPY INTO uses a path prefix, files outside that prefix are ignored. Ensure file paths match the stage + path defined in the pipe.
GCS notification: eventual consistency GCS Pub/Sub can have ordering issues. Files may be notified out of order. Snowpipe processes each file independently — order doesn't matter for loading.
Azure Event Grid throttling Under extreme load, Event Grid may batch/delay notifications. Use ALTER PIPE REFRESH as periodic backup to catch any missed files.
Auto-Ingest Latency: Snowpipe auto-ingest is "near real-time" (typically 1-5 minutes), NOT real-time. If you need sub-second latency, use Snowpipe Streaming instead.

6. The 14-Day Metadata Window

Understanding the 14-Day Rule

Snowpipe stores metadata about loaded files for exactly 14 days. This metadata includes: filename, file path, file size, load timestamp, rows loaded, errors. After 14 days, metadata is purged — the file becomes "unknown" to Snowpipe.

What Happens After 14 DaysImpact
File still sitting on stage If a new notification fires (or REFRESH is called), file WILL be loaded again → duplicates
COPY_HISTORY query for old files Returns no results — metadata expired. Use ACCOUNT_USAGE.COPY_HISTORY for up to 365 days.
ALTER PIPE REFRESH on stage with old files Old files (beyond 14 days) will be loaded again if still on stage
Pipe recreated (CREATE OR REPLACE) Metadata wiped to zero. ALL files on stage appear new regardless of age.

Best Practice: Stage File Lifecycle

-- RECOMMENDED: Remove files from stage after confirmed load
-- Option 1: PURGE in pipe definition
CREATE PIPE my_pipe AS
COPY INTO table FROM @stage
  PURGE = TRUE;  -- Auto-deletes files after successful load

-- Option 2: Scheduled cleanup task
CREATE TASK cleanup_stage
  WAREHOUSE = my_wh
  SCHEDULE = 'USING CRON 0 2 * * * UTC'  -- Daily at 2 AM
AS
  REMOVE @my_stage PATTERN = '.*loaded.*';

-- Option 3: Move loaded files to archive path
-- (External stage: use cloud lifecycle policies to move/delete after 7 days)
Exam Trap: The 14-day metadata is NOT configurable. You cannot extend or shorten it. It's a hard system limit. If files remain on stage beyond 14 days and any re-notification occurs, duplicates WILL happen.

7. Recovery Playbook

Scenario A: Duplicates After CREATE OR REPLACE PIPE

-- 1. Identify duplicate rows
SELECT filename, COUNT(*) as load_count
FROM TABLE(INFORMATION_SCHEMA.COPY_HISTORY(
  TABLE_NAME => 'MY_TABLE',
  START_TIME => DATEADD(days, -14, CURRENT_TIMESTAMP())
)) GROUP BY filename HAVING COUNT(*) > 1;

-- 2. Deduplicate the target table
CREATE TABLE my_table_clean AS
SELECT * FROM my_table
QUALIFY ROW_NUMBER() OVER (
  PARTITION BY primary_key_columns
  ORDER BY _loaded_at DESC  -- Keep most recent
) = 1;

-- 3. Swap tables
ALTER TABLE my_table RENAME TO my_table_backup;
ALTER TABLE my_table_clean RENAME TO my_table;

-- 4. Verify and drop backup
-- DROP TABLE my_table_backup;

Scenario B: Files Not Loading (Auto-Ingest Silent Failure)

-- 1. Check pipe status
SELECT SYSTEM$PIPE_STATUS('my_db.my_schema.my_pipe');
-- Look for: executionState, pendingFileCount, lastReceivedMessageTimestamp

-- 2. Check if notifications are arriving
-- If lastReceivedMessageTimestamp is old → notification issue

-- 3. Check COPY_HISTORY for errors
SELECT * FROM TABLE(INFORMATION_SCHEMA.COPY_HISTORY(
  TABLE_NAME => 'MY_TABLE',
  START_TIME => DATEADD(hours, -24, CURRENT_TIMESTAMP())
)) WHERE STATUS != 'LOADED';

-- 4. Try manual refresh to load missed files
ALTER PIPE my_pipe REFRESH;

-- 5. If still failing, check stage access
LIST @my_stage;  -- Can you see files?

-- 6. Verify notification integration
SHOW INTEGRATIONS LIKE '%notification%';
DESC INTEGRATION my_notification_int;

Scenario C: Bad Data Loaded (Need to Rollback)

-- Snowpipe does NOT support UNDO. But you can:

-- Option 1: Delete bad rows using METADATA$FILENAME tracking
DELETE FROM my_table
WHERE _metadata_filename = 'bad_file_2026-08-15.csv';

-- Option 2: Time Travel (if within retention)
CREATE TABLE my_table_restored CLONE my_table
  AT(TIMESTAMP => '2026-08-15 08:00:00'::TIMESTAMP_LTZ);

-- Option 3: Reload correctly
-- Fix the file, rename it (new name!), and PUT again
-- (Same filename won't reload due to 14-day metadata)

Scenario D: Pipe Paused Too Long (Files Piling Up)

-- 1. Check how many files are pending
SELECT SYSTEM$PIPE_STATUS('my_pipe');
-- pendingFileCount shows backlog

-- 2. Resume the pipe
ALTER PIPE my_pipe SET PIPE_EXECUTION_PAUSED = FALSE;

-- 3. Snowpipe processes backlog automatically (serverless scales up)
-- Monitor progress:
SELECT * FROM TABLE(INFORMATION_SCHEMA.COPY_HISTORY(
  TABLE_NAME => 'MY_TABLE',
  START_TIME => DATEADD(hours, -1, CURRENT_TIMESTAMP())
)) ORDER BY LAST_LOAD_TIME DESC;

-- 4. If paused > 14 days: oldest notifications may have expired
-- Run REFRESH to catch anything missed:
ALTER PIPE my_pipe REFRESH;

Scenario E: Need to Reprocess a Specific File

-- Snowpipe won't reload a file with the same name (14-day metadata)
-- Options:

-- Option 1: Rename the file and re-upload
-- old: data_2026-08-15.csv → new: data_2026-08-15_v2.csv
PUT file://data_2026-08-15_v2.csv @my_stage;

-- Option 2: Wait 14 days (not practical)

-- Option 3: Use manual COPY INTO (bypasses pipe metadata)
COPY INTO my_table FROM @my_stage/data_2026-08-15.csv
  FORCE = TRUE;  -- FORCE ignores COPY's own load history

-- Option 4: Nuclear — CREATE OR REPLACE PIPE (resets ALL metadata)
-- DANGER: Will reload ALL files on stage. Only if you can deduplicate after.

8. Exam Scenario Questions

ScenarioCorrect Answer
"A developer runs CREATE OR REPLACE PIPE. What happens to files loaded in the last 3 days?" They will be loaded AGAIN (duplicates). The 14-day metadata is wiped, so all files on stage appear new.
"A file is modified on the external stage after being loaded. Will Snowpipe reload it?" NO. Snowpipe tracks by filename only. Same filename = already loaded (within 14 days). Modified content is ignored.
"Snowpipe's default ON_ERROR behavior is?" SKIP_FILE (not ABORT_STATEMENT like manual COPY). One bad row skips the entire file.
"A file was loaded 15 days ago and still sits on stage. A REFRESH is triggered. What happens?" File is loaded AGAIN (duplicate). 14-day metadata has expired, so the file appears new.
"Does Snowpipe use the customer's virtual warehouse?" NO. Snowpipe uses Snowflake-managed serverless compute. You're billed per-file, not per-warehouse-credit.
"Two pipes load from the same stage into the same table. File X arrives. What happens?" File X is loaded TWICE (once per pipe). Each pipe has independent metadata. Result: duplicates.
"A pipe is paused for 10 days. When resumed, do queued files load?" YES. Notifications queue while paused. When resumed, all queued files process. (But if paused > 14 days, oldest may expire.)
"What's the guaranteed delivery semantics of Snowpipe?" At-least-once. Exactly-once for each file within 14 days (via metadata dedup). But cross-pipe or post-14-days: duplicates possible.
"Can you use ALTER PIPE to change the target table?" NO. You cannot ALTER the COPY INTO definition. Must CREATE OR REPLACE (which resets metadata).
"Snowpipe auto-ingest latency SLA is?" Near real-time (typically 1-5 minutes). NOT guaranteed sub-second. Use Snowpipe Streaming for low-latency.
Most Common Production Incident: CREATE OR REPLACE PIPE causing mass duplicate loading. Always use ALTER PIPE when possible. If you must replace, plan for deduplication BEFORE executing.
