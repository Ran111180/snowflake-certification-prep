1. What are Streams?

Definition

A Stream is a Snowflake object that records data manipulation language (DML) changes made to a table — inserts, updates, and deletes. It provides a Change Data Capture (CDC) mechanism without requiring you to compare snapshots or maintain timestamps.

AspectDetail
PurposeTrack changes (inserts, updates, deletes) to a source table
Storage CostNear zero — streams store only metadata (offset pointers), not data copies
ComputeNo compute to maintain; cost only when you QUERY the stream
How It WorksStores an offset (point-in-time marker) on the source table's change history
ConsumptionReading a stream in a DML transaction advances the offset (changes are "consumed")
Multiple StreamsMultiple streams can track the same table independently
Common PatternStream + Task = automated incremental ETL pipeline

Key Concept: Streams Don't Store Data

Exam Trap: Streams do NOT create a copy of the data. They store only an offset pointer to the table's change tracking metadata. The "data" you see when you SELECT from a stream is computed at query time by comparing the current table state to the offset. This is why streams have near-zero storage cost.

2. How Streams Work (Offset Model)

Stream Offset Model:

Table Timeline: [T1] ----insert 5 rows---- [T2] ----update 2 rows---- [T3] ----delete 1 row---- [T4]

Stream Offset: ^
(points here)

SELECT * FROM stream; --> Shows: 5 inserts + 2 updates + 1 delete (all changes since T1)

After DML using stream data --> Offset advances to T4 (changes consumed)
SELECT * FROM stream; --> Empty (no new changes since T4)

Offset Advancement Rules

ActionDoes Offset Advance?Why
SELECT from stream (read-only)NOJust viewing doesn't consume
DML (INSERT/UPDATE/DELETE/MERGE) using stream in a transactionYESConsuming changes advances offset
CREATE TABLE AS SELECT from streamYESIt's a DML operation
Transaction that reads stream but ROLLS BACKNORollback = offset stays
Task reads stream but SYSTEM$STREAM_HAS_DATA = FALSENONo changes = nothing consumed
Critical Exam Concept: The offset advances ONLY when a stream is consumed within a committed DML transaction. A simple SELECT does NOT advance it. A rolled-back transaction does NOT advance it.

3. Complete Syntax Reference

CREATE STREAM

CREATE [ OR REPLACE ] STREAM [ IF NOT EXISTS ] <stream_name>
  ON TABLE <table_name>
  [ ON VIEW <view_name> ]
  [ ON DIRECTORY TABLE <stage_name> ]
  [ ON EXTERNAL TABLE <ext_table_name> ]
  [ APPEND_ONLY = TRUE | FALSE ]         -- Default FALSE (standard)
  [ INSERT_ONLY = TRUE ]                  -- For external tables only
  [ SHOW_INITIAL_ROWS = TRUE | FALSE ]    -- Include existing rows at creation
  [ AT ( { TIMESTAMP => <t> | OFFSET => <n> | STATEMENT => '<id>' | STREAM => '<stream_name>' } ) ]
  [ BEFORE ( ... ) ]
  [ COMMENT = '<string>' ]

Example - Standard Stream (tracks INSERT, UPDATE, DELETE):

CREATE STREAM orders_stream ON TABLE orders;

Example - Append-Only Stream (tracks only INSERTs):

CREATE STREAM orders_append_stream
  ON TABLE orders
  APPEND_ONLY = TRUE;

Example - Stream with Initial Rows:

-- Include all existing rows as INSERTs at creation time
CREATE STREAM orders_full_stream
  ON TABLE orders
  SHOW_INITIAL_ROWS = TRUE;

Example - Stream at a point in time:

-- Start tracking from a specific timestamp
CREATE STREAM orders_stream
  ON TABLE orders
  AT (TIMESTAMP => '2026-08-14 09:00:00'::TIMESTAMP_LTZ);

ALTER STREAM

-- Add/change comment
ALTER STREAM <stream_name> SET COMMENT = 'Updated comment';

-- Cannot change the source table or type after creation!
-- Must DROP and CREATE a new stream.

DESCRIBE / SHOW

DESCRIBE STREAM <stream_name>;
-- Returns: created_on, name, database, schema, owner, table_name,
--          type, stale, stale_after, mode

SHOW STREAMS [ LIKE '<pattern>' ] [ IN SCHEMA <schema> ];

DROP STREAM

DROP STREAM [ IF EXISTS ] <stream_name>;

4. Stream Types

TypeTracksSyntaxBest For
Standard (Default) INSERT, UPDATE, DELETE CREATE STREAM s ON TABLE t; Full CDC - SCD Type 2, MERGE operations
Append-Only INSERT only CREATE STREAM s ON TABLE t APPEND_ONLY=TRUE; Event/log tables, append-only workloads
Insert-Only INSERT only (external tables) CREATE STREAM s ON EXTERNAL TABLE t INSERT_ONLY=TRUE; External tables (can only detect new files)

Standard vs Append-Only: Key Differences

ScenarioStandard Stream ShowsAppend-Only Stream Shows
INSERT 1 row1 row: INSERT1 row: INSERT
UPDATE that row1 row: INSERT (net effect, with ISUPDATE=TRUE)Nothing (update ignored)
DELETE that rowNothing (insert+delete cancel out)Still shows the original INSERT
INSERT then DELETENothing (net zero change)Shows the INSERT (delete ignored)
Standard streams show NET changes. If you insert a row and then delete it before consuming the stream, the standard stream shows nothing (they cancel out). Append-only streams always show every INSERT regardless of subsequent changes.

5. Metadata Columns

When you SELECT from a stream, three special metadata columns are included:

ColumnTypeDescription
METADATA$ACTION VARCHAR INSERT or DELETE (updates = DELETE old + INSERT new)
METADATA$ISUPDATE BOOLEAN TRUE if the row is part of an UPDATE operation; FALSE for pure inserts/deletes
METADATA$ROW_ID VARCHAR Unique ID for the row across changes (used to match DELETE+INSERT pairs for updates)

How Updates Appear in a Standard Stream

-- Original: UPDATE orders SET amount = 200 WHERE id = 1;
-- Stream shows TWO rows:

-- Row 1: The OLD values (being removed)
-- METADATA$ACTION = 'DELETE', METADATA$ISUPDATE = TRUE, amount = 100 (old value)

-- Row 2: The NEW values (being added)
-- METADATA$ACTION = 'INSERT', METADATA$ISUPDATE = TRUE, amount = 200 (new value)

-- They share the same METADATA$ROW_ID

Processing Pattern for MERGE

MERGE INTO target t
USING (
  SELECT * FROM my_stream
  WHERE METADATA$ACTION = 'INSERT'      -- New/updated rows
    AND METADATA$ISUPDATE = FALSE       -- Only pure inserts (not updates)
) s ON t.id = s.id
WHEN MATCHED THEN UPDATE SET ...
WHEN NOT MATCHED THEN INSERT ...;

-- For handling deletes:
DELETE FROM target
WHERE id IN (
  SELECT id FROM my_stream
  WHERE METADATA$ACTION = 'DELETE'
    AND METADATA$ISUPDATE = FALSE       -- Only pure deletes
);

6. Offset Management & Staleness

What is Stream Staleness?

Stale Stream = Unusable Stream

A stream becomes stale when Snowflake can no longer guarantee it can reconstruct the changes since the offset. This happens when the underlying table's change tracking data (stored in micro-partitions) is garbage-collected past the stream's offset point.

Staleness Rules

FactorDetail
When does a stream go stale?When the offset falls outside the table's DATA_RETENTION_TIME_IN_DAYS window + 14 days
Default retention1 day (Standard) or up to 90 days (Enterprise+)
Staleness windowDATA_RETENTION_TIME_IN_DAYS + 14 days
Example (1-day retention)Stream goes stale if not consumed within 1 + 14 = 15 days
Example (90-day retention)Stream goes stale if not consumed within 90 + 14 = 104 days
Can you recover a stale stream?NO — must drop and recreate
How to checkSHOW STREAMS → stale column = TRUE/FALSE, stale_after = timestamp

Preventing Staleness

  • Consume regularly: Use tasks to consume stream data on a schedule
  • Increase retention: ALTER TABLE SET DATA_RETENTION_TIME_IN_DAYS = 14;
  • Monitor: Check stale_after column in SHOW STREAMS
  • Use SYSTEM$STREAM_HAS_DATA: Only process when there's data (but don't let it sit too long)
Exam Trap: A stale stream CANNOT be recovered. You must DROP it and CREATE a new one. The new stream starts from the current table state — you LOSE all intermediate changes. This is why regular consumption (via Tasks) is critical.

7. Streams on Different Objects

ObjectStream TypeTracksNotes
Regular TableStandard / Append-OnlyINSERT, UPDATE, DELETEMost common use case
View (non-materialized)Standard / Append-OnlyChanges to underlying tablesView must be non-materialized; underlying tables tracked
External TableInsert-OnlyNew files added to stageCannot detect updates/deletes in external files
Directory TableStandardFiles added/removed from stageTracks stage file metadata changes
Shared Table (from Data Sharing)Standard / Append-OnlyChanges from providerConsumer creates stream on shared view/table

Stream on a View

-- Stream tracks changes to ALL underlying tables referenced by the view
CREATE VIEW v_active_orders AS
  SELECT * FROM orders WHERE status = 'active';

CREATE STREAM active_orders_stream ON VIEW v_active_orders;
-- Tracks inserts/updates/deletes that affect the view's result set
View Stream Requirements: The view must be non-materialized. All underlying tables must have change tracking enabled. The stream tracks changes that affect the view's output (not all changes to underlying tables).

8. Consuming Streams (DML Transactions)

The Golden Rule

Stream offset advances ONLY within a committed DML transaction

If you SELECT from a stream 100 times without using it in a DML, the offset never moves. The moment you INSERT INTO ... SELECT FROM stream (and it commits), the offset jumps forward.

Common Consumption Patterns

Pattern 1: Simple INSERT INTO (most common)

INSERT INTO target_table
SELECT col1, col2, col3
FROM my_stream
WHERE METADATA$ACTION = 'INSERT';

Pattern 2: MERGE (for upserts)

MERGE INTO dim_customer t
USING my_stream s
  ON t.customer_id = s.customer_id
WHEN MATCHED AND s.METADATA$ACTION = 'DELETE' AND s.METADATA$ISUPDATE = FALSE
  THEN DELETE
WHEN MATCHED AND s.METADATA$ISUPDATE = TRUE
  THEN UPDATE SET t.name = s.name, t.email = s.email, t.updated_at = CURRENT_TIMESTAMP()
WHEN NOT MATCHED AND s.METADATA$ACTION = 'INSERT'
  THEN INSERT (customer_id, name, email, created_at)
       VALUES (s.customer_id, s.name, s.email, CURRENT_TIMESTAMP());

Pattern 3: SYSTEM$STREAM_HAS_DATA (check before consuming)

-- Used in Task WHEN clause to skip runs when stream is empty
CREATE TASK process_changes
  WAREHOUSE = my_wh
  SCHEDULE = '5 MINUTE'
  WHEN SYSTEM$STREAM_HAS_DATA('my_stream')
  AS
  INSERT INTO processed_table SELECT * FROM my_stream;

Multiple Consumers

Each stream has ONE offset. If you need multiple consumers processing the same changes independently, create multiple streams on the same source table. Each stream maintains its own offset.

11. Best Practices

Consumption
  • Consume streams regularly (via Tasks) to prevent staleness
  • Use SYSTEM$STREAM_HAS_DATA in Task WHEN clause
  • Keep task frequency < half the staleness window
  • Handle empty streams gracefully
Design
  • Use Append-Only for log/event tables (simpler, no update tracking)
  • Use Standard for dimension tables needing SCD2/MERGE
  • Create separate streams for separate consumers
  • Use SHOW_INITIAL_ROWS for first-time full loads
Monitoring
  • Check stale_after in SHOW STREAMS regularly
  • Set DATA_RETENTION_TIME_IN_DAYS appropriately
  • Alert if stream approaches staleness
  • Monitor Task history for consumption failures
Avoid
  • Don't use CREATE OR REPLACE TABLE on streamed tables
  • Don't reduce DATA_RETENTION below stream's needs
  • Don't have single stream for multiple consumers
  • Don't forget that SELECT alone doesn't consume
Top 5 Exam Traps:
  1. SELECT does NOT advance offset — only committed DML does
  2. Staleness = retention + 14 days — not just retention alone
  3. Stale streams CANNOT be recovered — must drop and recreate
  4. Updates appear as DELETE + INSERT pairs with METADATA$ISUPDATE=TRUE
  5. Streams have near-zero storage cost — they store offsets, not data copies
