1. Streams + Tasks Pattern (Automated CDC)

The Classic CDC Pipeline:

[Source Table] --changes--> [Stream (captures CDC)] --WHEN HAS_DATA--> [Task (runs DML)]
|
v
[Target Table (incremental)]

Complete Example: Automated Incremental Load

-- 1. Source table (data arrives here from Snowpipe or other sources)
CREATE TABLE raw_orders (
  order_id INT, customer VARCHAR, amount DECIMAL, status VARCHAR, updated_at TIMESTAMP
);

-- 2. Stream on source (captures all changes)
CREATE STREAM raw_orders_stream ON TABLE raw_orders;

-- 3. Target table (clean/transformed data)
CREATE TABLE processed_orders (
  order_id INT PRIMARY KEY, customer VARCHAR, amount DECIMAL,
  status VARCHAR, updated_at TIMESTAMP, loaded_at TIMESTAMP
);

-- 4. Task that processes changes every 5 minutes
CREATE TASK process_orders_task
  WAREHOUSE = my_wh
  SCHEDULE = '5 MINUTE'
  WHEN SYSTEM$STREAM_HAS_DATA('raw_orders_stream')
AS
  MERGE INTO processed_orders t
  USING (
    SELECT * FROM raw_orders_stream
    WHERE METADATA$ACTION = 'INSERT'
  ) s ON t.order_id = s.order_id
  WHEN MATCHED THEN
    UPDATE SET t.customer = s.customer, t.amount = s.amount,
              t.status = s.status, t.updated_at = s.updated_at,
              t.loaded_at = CURRENT_TIMESTAMP()
  WHEN NOT MATCHED THEN
    INSERT VALUES (s.order_id, s.customer, s.amount, s.status, s.updated_at, CURRENT_TIMESTAMP());

-- 5. Resume the task
ALTER TASK process_orders_task RESUME;

SYSTEM$STREAM_HAS_DATA

AspectDetail
PurposeReturns TRUE/FALSE indicating if stream has unconsumed data
Used inTask WHEN clause (skip run if no changes)
CostVery cheap - metadata check only, no warehouse needed
BehaviorDoes NOT advance offset (it's just a check)
Why use WHEN clause? Without it, the task runs every 5 minutes regardless (wasting credits on empty runs). With SYSTEM$STREAM_HAS_DATA, the task only fires when there are actual changes to process.

Task DAG with Multiple Streams

[orders_table] --> [orders_stream] --> [Task A: MERGE into dim_orders]
|
[customers_table] --> [customers_stream] --> [Task B: MERGE into dim_customers]
|
v
[Task C (child): Build fact_sales from dim tables]

2. SCD Patterns with Streams

SCD Type 1 (Overwrite) — Simple MERGE

-- Changes overwrite existing values. No history kept.
MERGE INTO dim_customer t
USING customer_stream s
  ON t.customer_id = s.customer_id
WHEN MATCHED AND s.METADATA$ACTION = 'INSERT' AND s.METADATA$ISUPDATE = TRUE
  THEN UPDATE SET
    t.name = s.name,
    t.email = s.email,
    t.updated_at = CURRENT_TIMESTAMP()
WHEN MATCHED AND s.METADATA$ACTION = 'DELETE' AND s.METADATA$ISUPDATE = FALSE
  THEN DELETE
WHEN NOT MATCHED AND s.METADATA$ACTION = 'INSERT'
  THEN INSERT (customer_id, name, email, created_at, updated_at)
       VALUES (s.customer_id, s.name, s.email, CURRENT_TIMESTAMP(), CURRENT_TIMESTAMP());

SCD Type 2 (History Preserved) — Multi-Step

-- Step 1: Expire old records (close the previous version)
UPDATE dim_customer_scd2 t
SET t.is_current = FALSE,
    t.valid_to = CURRENT_TIMESTAMP()
WHERE t.customer_id IN (
  SELECT customer_id FROM customer_stream
  WHERE METADATA$ACTION = 'INSERT' AND METADATA$ISUPDATE = TRUE
)
AND t.is_current = TRUE;

-- Step 2: Insert new version of changed records
INSERT INTO dim_customer_scd2 (customer_id, name, email, valid_from, valid_to, is_current)
SELECT customer_id, name, email, CURRENT_TIMESTAMP(), NULL, TRUE
FROM customer_stream
WHERE METADATA$ACTION = 'INSERT' AND METADATA$ISUPDATE = TRUE;

-- Step 3: Insert brand new records
INSERT INTO dim_customer_scd2 (customer_id, name, email, valid_from, valid_to, is_current)
SELECT customer_id, name, email, CURRENT_TIMESTAMP(), NULL, TRUE
FROM customer_stream
WHERE METADATA$ACTION = 'INSERT' AND METADATA$ISUPDATE = FALSE;

-- Step 4: Handle deletes (soft delete = expire)
UPDATE dim_customer_scd2
SET is_current = FALSE, valid_to = CURRENT_TIMESTAMP()
WHERE customer_id IN (
  SELECT customer_id FROM customer_stream
  WHERE METADATA$ACTION = 'DELETE' AND METADATA$ISUPDATE = FALSE
) AND is_current = TRUE;
SCD2 + Streams Gotcha: All these statements must run in the SAME transaction (or be in a stored procedure). If the first DML commits and the second fails, the stream offset has already advanced, and you've lost the change data.

3. Streams vs Dynamic Tables (Decision Framework)

CriteriaStreams + TasksDynamic Tables
ApproachImperative (you write the DML)Declarative (you write SELECT, Snowflake handles refresh)
Logic TypeMERGE, SCD2, conditional logic, multi-stepSELECT-based transformations only
Supported OperationsINSERT, UPDATE, DELETE, MERGEFull table refresh (no MERGE/DELETE on target)
Refresh ControlManual (Task schedule or event)Automatic (TARGET_LAG)
Error HandlingFull control (try/catch, retry, alerting)Snowflake handles (limited visibility)
State ManagementYou manage offset (stream tracks it)Snowflake manages everything
ComplexityMore code, more controlLess code, less control
SCD Type 2Supported (with multi-step logic)NOT supported (no row-level history)
CostWarehouse credits for task runsServerless or warehouse credits for refresh
MonitoringTASK_HISTORY, COPY_HISTORY, customDT refresh history, lag monitoring
Multi-table JOINYou build the logicJust write JOIN in SELECT

Decision Guide

Use Streams + Tasks When:
  • You need MERGE (upsert) behavior
  • You need SCD Type 2 (history tracking)
  • You need DELETE propagation
  • Complex multi-step transformations
  • Custom error handling/alerting
  • Conditional processing logic
  • Need to call stored procedures
Use Dynamic Tables When:
  • Pure SELECT-based transformations
  • Simple aggregations, JOINs, filters
  • Want minimal code/maintenance
  • No DELETE/UPDATE propagation needed
  • Acceptable to have "full refresh" semantics
  • Want Snowflake to auto-manage scheduling
  • Building multi-hop data pipelines

RBAC Setup for Stream + Task Pipeline

-- Roles
-- DATA_ENGINEER: Creates and owns streams, tasks, tables
-- DATA_OPS: Can monitor and operate tasks (pause/resume)
-- DATA_ANALYST: Can query target tables (read-only)

-- Grant stream creation
GRANT CREATE STREAM ON SCHEMA my_schema TO ROLE DATA_ENGINEER;

-- Grant SELECT on source table (needed to create stream)
GRANT SELECT ON TABLE source_table TO ROLE DATA_ENGINEER;

-- Grant INSERT/UPDATE/DELETE on target (needed to consume stream)
GRANT INSERT, UPDATE, DELETE ON TABLE target_table TO ROLE DATA_ENGINEER;

-- For monitoring by ops team
GRANT SELECT ON STREAM my_stream TO ROLE DATA_OPS;
GRANT MONITOR ON TASK my_task TO ROLE DATA_OPS;
GRANT OPERATE ON TASK my_task TO ROLE DATA_OPS;
Key: The role that consumes the stream (runs the DML) needs SELECT on the stream AND appropriate privileges on the target table. The stream itself inherits the source table's access control.

5. Production Debugging

ProblemSymptomRoot CauseFix
Stream is stale SHOW STREAMS shows stale=TRUE Stream not consumed within retention+14 days Drop and recreate stream. Lost data cannot be recovered. Increase retention or consume more frequently.
Stream always empty SYSTEM$STREAM_HAS_DATA = FALSE always 1) No changes on source table 2) Stream was just consumed 3) Changes cancel out (insert+delete) Verify source table is receiving changes. Check if another process consumed it.
Task not firing TASK_HISTORY shows no runs 1) Task not resumed 2) WHEN clause always FALSE 3) No warehouse ALTER TASK RESUME. Verify SYSTEM$STREAM_HAS_DATA returns TRUE.
Duplicate processing Same rows appear twice in target Multiple tasks consuming same stream, or failed transaction + retry Use one consumer per stream. Ensure DML is idempotent (MERGE instead of INSERT).
Missing changes Target table doesn't reflect source changes 1) Standard stream collapsed net-zero changes 2) Stale stream recreated (gap) For standard streams, insert+delete before consumption = invisible. Use append-only if needed.
Permission error on consume "Insufficient privileges" Role lacks SELECT on stream or DML privilege on target Grant SELECT on stream + INSERT/UPDATE/DELETE on target table.
Stream shows unexpected changes Reclustering appears as changes Automatic clustering rewrites micro-partitions (standard streams may reflect this) Use append-only streams for tables with heavy reclustering. Standard streams may show false changes.

Debug Queries

-- Check stream status
SHOW STREAMS LIKE 'my_stream' IN SCHEMA my_schema;
-- Look at: stale, stale_after, mode, type

-- Check if stream has data
SELECT SYSTEM$STREAM_HAS_DATA('my_schema.my_stream');

-- Preview stream contents without consuming
SELECT * FROM my_stream LIMIT 100;
-- (This does NOT advance the offset)

-- Check task run history
SELECT * FROM TABLE(INFORMATION_SCHEMA.TASK_HISTORY(
  TASK_NAME => 'my_task',
  SCHEDULED_TIME_RANGE_START => DATEADD(HOURS, -24, CURRENT_TIMESTAMP())
)) ORDER BY SCHEDULED_TIME DESC;

-- Count changes in stream
SELECT METADATA$ACTION, METADATA$ISUPDATE, COUNT(*)
FROM my_stream
GROUP BY 1, 2;

6. Multi-Stream & Multi-Table Patterns

Pattern: Multiple Independent Consumers

-- Same source table, different consumers with independent offsets
CREATE STREAM orders_stream_analytics ON TABLE orders;   -- For analytics team
CREATE STREAM orders_stream_reporting ON TABLE orders;   -- For reporting team
CREATE STREAM orders_stream_audit ON TABLE orders;       -- For audit log

-- Each stream has its own offset — consuming one doesn't affect others

Pattern: Stream on a View (Multi-Table CDC)

-- Track changes across a JOIN
CREATE VIEW v_order_details AS
SELECT o.order_id, o.amount, c.customer_name, c.email
FROM orders o JOIN customers c ON o.customer_id = c.customer_id;

CREATE STREAM order_details_stream ON VIEW v_order_details;
-- Tracks changes from BOTH orders and customers tables

Pattern: Chained Streams (Pipeline)

[raw_table] --stream_1--> [Task A] --> [staging_table] --stream_2--> [Task B] --> [final_table]

7. Cost & Performance Considerations

Cost ComponentAmountNotes
Stream creation/maintenanceNear zeroOnly stores offset pointers
Querying a stream (SELECT)Warehouse creditsSnowflake computes diff between offset and current state
Change tracking overhead on tableMinimal storageExtra hidden columns for tracking (automatic)
Task execution consuming streamWarehouse creditsSame as any DML operation
SYSTEM$STREAM_HAS_DATA checkNearly freeMetadata check, no warehouse needed

Performance Tips

  • Consume streams frequently (smaller batches = faster processing)
  • Use SYSTEM$STREAM_HAS_DATA to avoid empty warehouse runs
  • For high-volume tables, consider append-only streams (simpler = faster)
  • MERGE is more expensive than INSERT — use INSERT when possible
  • Multiple streams on same table = each one computes diff independently (cost multiplied)

8. Change Tracking (Internal Mechanism)

How Snowflake Tracks Changes Internally

When a stream exists on a table (or change tracking is enabled), Snowflake adds hidden metadata columns to each micro-partition to track which rows were modified and when. This is automatic and transparent.

Enabling Change Tracking Without a Stream

-- You can enable change tracking on a table without creating a stream
-- This is needed for streams on views (underlying tables need tracking)
ALTER TABLE my_table SET CHANGE_TRACKING = TRUE;

-- Check if enabled
SHOW TABLES LIKE 'my_table';
-- Look at 'change_tracking' column

CHANGES Clause (Query Changes Directly)

-- Query changes without a stream object (using Time Travel)
SELECT *
FROM my_table
  CHANGES (INFORMATION => DEFAULT)
  AT (TIMESTAMP => '2026-08-14 09:00:00'::TIMESTAMP_LTZ);

-- Shows METADATA$ACTION, METADATA$ISUPDATE, METADATA$ROW_ID
-- like a stream, but doesn't require a stream object
-- Does NOT advance any offset (no offset exists)
CHANGES clause is useful for ad-hoc change analysis without creating a permanent stream. It uses Time Travel to reconstruct changes between two points in time. Available when CHANGE_TRACKING = TRUE on the table.
Top Exam Traps for Streams Advanced:
  1. Staleness = DATA_RETENTION_TIME + 14 days (not just retention)
  2. Stream on view requires CHANGE_TRACKING=TRUE on ALL underlying tables
  3. One stream = one consumer (need multiple streams for multiple consumers)
  4. CREATE OR REPLACE TABLE breaks streams — all streams become invalid
  5. Standard stream collapses net changes — INSERT+DELETE before consume = invisible
  6. Task WHEN clause prevents the task from running (saves credits) but doesn't advance offset
  7. Dynamic Tables CANNOT do MERGE/DELETE — use Streams+Tasks for those
