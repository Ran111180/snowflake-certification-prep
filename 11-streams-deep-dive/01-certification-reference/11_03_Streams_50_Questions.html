Fundamentals (Q1-Q10)

Q1Basics
What does a Snowflake stream record?
  • A) A full copy of the changed rows in a shadow table
  • B) Change data capture (CDC) information by storing an offset, not the data itself
  • C) A log of all SQL statements executed against the table
  • D) A real-time event queue of row-level changes
Streams record CDC by maintaining an offset (pointer) into the table's change history. They do NOT store copies of the data, resulting in near-zero additional storage cost.
Q2Storage
How much additional storage does a stream consume?
  • A) Equal to the size of changed rows
  • B) 50% of the source table size
  • C) Near-zero (only stores an offset/pointer)
  • D) Depends on the number of DML operations
Streams store only an offset pointer into the table's micro-partition versioning history. They leverage Time Travel data that already exists, consuming near-zero additional storage.
Q3CDC
What type of information does a stream provide when queried?
  • A) Only the current state of all rows in the source table
  • B) The set of changes (inserts, updates, deletes) since the last consumed offset
  • C) A diff between two specified timestamps
  • D) Only rows that were deleted
Querying a stream returns the net set of changes (INSERTs, UPDATEs as DELETE+INSERT pairs, DELETEs) that occurred between the stream's current offset and the table's current version.
Q4Offset
When does a stream's offset advance?
  • A) When you SELECT from the stream
  • B) When the source table changes
  • C) Automatically every 5 minutes
  • D) When a DML statement that consumes the stream is committed in a transaction
A stream's offset advances ONLY when a DML operation (INSERT, UPDATE, DELETE, MERGE) that references the stream is successfully committed. SELECT alone does NOT advance the offset.
Q5Consumption
Which statement is TRUE about consuming a stream?
  • A) Only a committed DML transaction that reads from the stream advances the offset
  • B) Any SELECT query advances the offset
  • C) The offset advances when a Task checks SYSTEM$STREAM_HAS_DATA
  • D) Running SHOW STREAMS advances the offset
Only a committed DML within a transaction that references the stream will advance the offset. If the transaction is rolled back, the offset stays unchanged.
Q6Basics
What happens to stream data if the consuming DML transaction is rolled back?
  • A) The stream data is lost permanently
  • B) The offset does NOT advance; stream data remains available for re-consumption
  • C) The stream becomes stale
  • D) The stream is automatically dropped
If the transaction rolls back, the stream offset remains at its previous position. The changes are still visible in the stream and can be consumed by a subsequent successful transaction.
Q7Updates
How does a stream represent an UPDATE operation?
  • A) A single row with METADATA$ACTION = 'UPDATE'
  • B) Only the new values with METADATA$ACTION = 'INSERT'
  • C) A DELETE row (old values) and an INSERT row (new values), both with METADATA$ISUPDATE = TRUE
  • D) A JSON diff of old vs new column values
Updates appear as a pair: one DELETE row (pre-update values) and one INSERT row (post-update values). Both rows have METADATA$ISUPDATE = TRUE, distinguishing them from actual inserts/deletes.
Q8Metadata
Which metadata columns does a stream add to the output?
  • A) METADATA$FILENAME, METADATA$FILE_ROW_NUMBER
  • B) METADATA$ACTION, METADATA$ISUPDATE, METADATA$ROW_ID
  • C) METADATA$STREAM_NAME, METADATA$OFFSET, METADATA$TIMESTAMP
  • D) METADATA$CDC_TYPE, METADATA$SEQUENCE_NUM
Streams add three metadata columns: METADATA$ACTION (INSERT or DELETE), METADATA$ISUPDATE (TRUE if part of an update pair), and METADATA$ROW_ID (unique row identifier).
Q9Time Travel
How do streams relate to Snowflake Time Travel?
  • A) Streams leverage the same micro-partition versioning used by Time Travel
  • B) Streams replace Time Travel for the source table
  • C) Streams require Time Travel to be disabled
  • D) Streams store data in a separate Time Travel history
Streams use the same underlying micro-partition versioning that powers Time Travel. The stream's offset points to a specific version in this history, which is why streams have near-zero storage overhead.
Q10Basics
A row is inserted and then deleted before the stream is consumed. What does a Standard stream show?
  • A) One INSERT row and one DELETE row
  • B) One INSERT row only
  • C) One DELETE row only
  • D) Nothing - the net change is zero
Standard streams track NET changes. If a row is inserted and then deleted before consumption, the net effect is zero, so nothing appears in the stream output.

Stream Types (Q11-Q18)

Q11Types
What is the default stream type if not specified in CREATE STREAM?
  • A) Append-only
  • B) Standard (delta)
  • C) Insert-only
  • D) Full
The default stream type is Standard (also called delta). It captures the net changes including inserts, updates, and deletes. You must explicitly specify APPEND_ONLY = TRUE for append-only behavior.
Q12Append-Only
What does an Append-Only stream track?
  • A) All DML operations (INSERT, UPDATE, DELETE) with net changes
  • B) Only DELETE operations
  • C) Only INSERT operations (rows added to the table)
  • D) INSERT and UPDATE but not DELETE
Append-only streams track ONLY inserts. They do not record updates or deletes. Ideal for append-heavy workloads like event logs where you only care about new rows arriving.
Q13Insert-Only
Where are Insert-Only streams specifically designed to be used?
  • A) On any standard table
  • B) On external tables
  • C) On materialized views
  • D) On temporary tables
Insert-only streams are the ONLY stream type supported on external tables. External tables are read-only from Snowflake's perspective, so only new file arrivals (inserts) can be tracked.
Q14Net Changes
A row is inserted, updated 5 times, then the stream is consumed. What does a Standard stream show?
  • A) One INSERT row with the final (latest) values
  • B) One INSERT plus 5 UPDATE pairs (11 rows total)
  • C) Six INSERT rows
  • D) Nothing because updates cancel each other
Standard streams show NET changes. Since the row didn't exist before and now exists with final values, the net result is a single INSERT with the latest column values. Intermediate updates are collapsed.
Q15Comparison
A row is inserted, then updated, before an Append-Only stream is consumed. What does it show?
  • A) One INSERT with latest values (like Standard)
  • B) One INSERT with the ORIGINAL inserted values (update is ignored)
  • C) One INSERT and one UPDATE pair
  • D) Nothing
Append-only streams only track inserts. The subsequent update is not captured. The stream shows the row as it was when first inserted, not the updated values.
Q16Types
Which stream type would you use for a staging table that receives INSERT-only loads and needs downstream MERGE processing?
  • A) Insert-only (external tables only)
  • B) Standard (captures all DML including unnecessary delete tracking)
  • C) Append-only (efficient for insert-only workloads)
  • D) Full stream
For tables that only receive INSERTs (like staging/landing tables), append-only streams are more efficient because they skip the overhead of tracking deletes and updates that will never occur.
Q17Metadata
What value does METADATA$ACTION contain for the DELETE part of an UPDATE pair?
  • A) 'UPDATE'
  • B) 'DELETE'
  • C) 'UPDATE_DELETE'
  • D) 'REMOVE'
METADATA$ACTION is always either 'INSERT' or 'DELETE'. For updates, you get a DELETE row and an INSERT row. You distinguish updates from real deletes by checking METADATA$ISUPDATE = TRUE.
Q18Types
Which statement about stream types is FALSE?
  • A) Standard streams show net changes between offset and current state
  • B) Append-only streams only track INSERT operations
  • C) Insert-only streams are the only type supported on external tables
  • D) Standard streams store a full copy of all changed rows for replay
FALSE: Standard streams do NOT store copies of data. They store only an offset pointer and leverage Time Travel versioning to compute the net changes at query time.

Offset & Staleness (Q19-Q26)

Q19Staleness
How is a stream's staleness period calculated?
  • A) DATA_RETENTION_TIME_IN_DAYS only
  • B) 14 days from stream creation
  • C) DATA_RETENTION_TIME_IN_DAYS + 14 days
  • D) MAX_DATA_EXTENSION_TIME_IN_DAYS only
A stream becomes stale if its offset is older than the source table's DATA_RETENTION_TIME_IN_DAYS + 14 days (the extended data retention period for streams). After this, the historical data needed is gone.
Q20Staleness
What happens when a stream becomes stale?
  • A) It automatically resets to the latest offset
  • B) It can be recovered using Time Travel
  • C) It continues to work but with reduced accuracy
  • D) It becomes permanently unusable and must be recreated
A stale stream CANNOT be recovered. The underlying historical data has been purged. You must DROP and recreate the stream, which resets the offset to the current table version (losing intermediate changes).
Q21Staleness
Table has DATA_RETENTION_TIME_IN_DAYS = 1. Maximum time before a stream on it becomes stale?
  • A) 1 day
  • B) 15 days (1 + 14)
  • C) 14 days
  • D) 90 days
Staleness threshold = DATA_RETENTION_TIME_IN_DAYS + 14 days. With retention of 1 day, the stream goes stale after 15 days without consumption. The 14-day extension is specifically for streams.
Q22Offset
Which operation does NOT advance the stream offset?
  • A) SELECT * FROM my_stream
  • B) INSERT INTO target SELECT * FROM my_stream (committed)
  • C) MERGE INTO target USING my_stream (committed)
  • D) CREATE TABLE AS SELECT * FROM my_stream (committed)
A plain SELECT never advances the offset. Only committed DML statements (INSERT INTO...SELECT, MERGE, CTAS) that read from the stream advance it. This is critical for exam questions.
Q23Staleness
How can you prevent a stream from going stale?
  • A) Run SELECT from the stream regularly
  • B) Consume the stream regularly with committed DML within the staleness window
  • C) Set STALENESS_PREVENTION = TRUE on the stream
  • D) Increase the stream's own retention period
The only way to prevent staleness is to consume the stream (advance its offset) before the staleness window expires. Increasing the source table's DATA_RETENTION_TIME_IN_DAYS also extends the window.
Q24Offset
Stream has unconsumed changes. You run: BEGIN; INSERT INTO t2 SELECT * FROM stream; ROLLBACK; What happens?
  • A) Offset advances, changes are lost
  • B) Stream becomes stale
  • C) Offset does NOT advance; changes remain in the stream
  • D) An error is thrown on the next read
Since the transaction was rolled back, the offset does not advance. The stream retains all its changes for the next successful consumption. Only COMMITTED transactions advance the offset.
Q25Staleness
How can you check if a stream is stale?
  • A) Query INFORMATION_SCHEMA.STREAM_STATUS
  • B) Check the STALE_AFTER column in SHOW STREAMS or DESCRIBE STREAM
  • C) Run SYSTEM$STREAM_IS_STALE()
  • D) Try to SELECT from it - stale streams return NULL
SHOW STREAMS and DESCRIBE STREAM include a STALE_AFTER column showing the timestamp when the stream will become stale. If that timestamp has passed, the stream is already stale and queries will error.
Q26Recovery
A stream has gone stale. What is the recovery procedure?
  • A) ALTER STREAM RESET OFFSET
  • B) Use Time Travel to restore the stream to a previous state
  • C) Call SYSTEM$RECOVER_STREAM()
  • D) DROP the stream and CREATE a new one (accepting loss of intermediate changes)
There is NO recovery for a stale stream. You must drop and recreate it. The new stream starts from the current table state, meaning any changes between the old offset and now are permanently lost.

Streams + Tasks (Q27-Q34)

Q27Tasks
What function is used in a Task's WHEN clause to check if a stream has data?
  • A) STREAM_HAS_ROWS()
  • B) SYSTEM$STREAM_HAS_DATA('stream_name')
  • C) CHECK_STREAM('stream_name')
  • D) STREAM_STATUS('stream_name')
SYSTEM$STREAM_HAS_DATA('stream_name') returns TRUE/FALSE. Used in a Task's WHEN clause to skip execution when there are no changes, saving compute costs.
Q28Tasks
What happens when a Task with WHEN SYSTEM$STREAM_HAS_DATA evaluates to FALSE?
  • A) The Task runs but processes zero rows
  • B) The Task fails with an error
  • C) The Task is skipped entirely (no compute used)
  • D) The Task suspends itself
When the WHEN condition evaluates to FALSE, the Task execution is skipped entirely. No warehouse is started, no compute is consumed. This makes the pattern very cost-efficient.
Q29Pattern
What is the standard pattern for a Task consuming a stream?
  • A) Task with WHEN clause checking stream, body does MERGE/INSERT from stream into target
  • B) Task runs SELECT from stream and emails the results
  • C) Task runs ALTER STREAM CONSUME
  • D) Task copies stream data to a stage file
The standard pattern: CREATE TASK with SCHEDULE, WHEN SYSTEM$STREAM_HAS_DATA('stream'), body = MERGE INTO target USING stream ON keys WHEN MATCHED/NOT MATCHED. The committed MERGE advances the offset.
Q30DAG
In a Task DAG, which task has the SCHEDULE and WHEN clause?
  • A) All tasks in the DAG
  • B) Only the root task
  • C) Only the leaf (final) tasks
  • D) Any task can have both
In a Task DAG, only the root task has the SCHEDULE and WHEN clause. Child tasks run after their predecessor completes. If the root task is skipped (WHEN=FALSE), the entire DAG is skipped.
Q31Tasks
Does SYSTEM$STREAM_HAS_DATA consume the stream?
  • A) Yes, it advances the offset like a DML
  • B) Yes, but only if it returns TRUE
  • C) No, it only checks whether unconsumed changes exist
  • D) No, but it resets the staleness timer
SYSTEM$STREAM_HAS_DATA is a read-only check. It does NOT advance the offset or consume data. It simply returns TRUE if there are unconsumed changes, FALSE otherwise.
Q32Automation
What minimum Task schedule would you set for near-real-time CDC processing?
  • A) 30 seconds
  • B) 1 minute (minimum allowed)
  • C) 5 minutes
  • D) Tasks cannot run more often than every 10 minutes
The minimum Task schedule interval is 1 minute. Combined with WHEN SYSTEM$STREAM_HAS_DATA, this gives near-real-time CDC processing without wasted compute on empty runs.
Q33Tasks
A Task consuming a stream fails mid-execution. What happens to the stream offset?
  • A) Offset advances to the point of failure
  • B) Offset advances fully, losing the failed portion
  • C) Stream becomes stale
  • D) Offset does NOT advance (transaction not committed); changes remain for retry
If the Task fails, the implicit transaction is rolled back. Since the DML was not committed, the stream offset stays unchanged. The next Task run will see the same changes again - providing automatic retry semantics.
Q34Serverless
Can serverless Tasks be used with streams?
  • A) Yes, serverless Tasks work with streams and the WHEN clause
  • B) No, streams require a user-managed warehouse
  • C) Only with append-only streams
  • D) Only if the Task has no WHEN clause
Serverless Tasks fully support streams and WHEN SYSTEM$STREAM_HAS_DATA. When the condition is FALSE, no serverless compute is provisioned, making this combination very cost-efficient.

RBAC & Operations (Q35-Q42)

Q35Privileges
What privilege is required to create a stream on a table?
  • A) OWNERSHIP on the table
  • B) CREATE STREAM on the schema + SELECT on the source table
  • C) INSERT on the source table
  • D) ACCOUNTADMIN role
You need CREATE STREAM on the schema where the stream will be created, plus SELECT on the source table (since the stream reads change data from it).
Q36Multiple Streams
Can multiple streams be created on the same source table?
  • A) No, only one stream per table is allowed
  • B) Yes, but they share the same offset
  • C) Yes, each stream maintains its own independent offset
  • D) Yes, but only if they are different types
Multiple streams can exist on the same table, each with an INDEPENDENT offset. This allows different consumers to process changes at their own pace without interfering with each other.
Q37DDL Impact
What happens to streams when you run CREATE OR REPLACE TABLE on the source table?
  • A) Streams automatically adjust to the new table
  • B) Streams pause until manually resumed
  • C) Streams reset their offset to the new table's current state
  • D) All streams on the table become invalid/broken and must be recreated
CREATE OR REPLACE TABLE drops and recreates the table object. All streams referencing the original table break because the underlying object they point to no longer exists. They must be recreated.
Q38Views
What is required to create a stream on a view?
  • A) The view must be a materialized view
  • B) CHANGE_TRACKING = TRUE must be set on ALL underlying base tables
  • C) The view must contain only one table reference
  • D) Streams on views are not supported
Streams on views require CHANGE_TRACKING = TRUE on every base table referenced by the view. The view must also be non-materialized. ALTER TABLE SET CHANGE_TRACKING = TRUE enables this.
Q39Change Tracking
What does ALTER TABLE SET CHANGE_TRACKING = TRUE do?
  • A) Enables the table to have streams created on it and adds hidden metadata columns for tracking
  • B) Creates an automatic stream on the table
  • C) Enables Time Travel on the table
  • D) Starts logging all DML to an audit table
CHANGE_TRACKING = TRUE adds hidden metadata columns to micro-partitions for change tracking. This is required for streams on views and for the CHANGES clause. It has minimal storage overhead.
Q40Operations
How do you check the current position (offset) of a stream?
  • A) SELECT OFFSET FROM STREAM_INFO('my_stream')
  • B) DESCRIBE STREAM shows the exact row offset number
  • C) DESCRIBE STREAM shows STALE_AFTER timestamp; the exact internal offset is not directly exposed
  • D) SELECT SYSTEM$STREAM_OFFSET('my_stream')
The internal offset position is not directly exposed as a number. DESCRIBE STREAM shows the STALE_AFTER timestamp and whether data exists. You can see what changes are pending by querying the stream.
Q41Cloning
What happens when you CLONE a table that has streams on it?
  • A) Streams are cloned with the same offset
  • B) Streams are NOT cloned; the clone has no streams
  • C) Streams are cloned but reset to current offset
  • D) Cloning fails if streams exist
Streams are NOT included when cloning a table. You must create new streams on the cloned table if needed. The original streams continue to track the original table unchanged.
Q42Privileges
What privilege does a role need to consume (read) data from an existing stream?
  • A) SELECT on the stream
  • B) OWNERSHIP on the stream
  • C) SELECT on the source table only
  • D) OPERATE on the stream
To read from a stream (SELECT or use in DML), the role needs SELECT privilege on the stream object. The stream owner's privileges are used to access the underlying table data.

Advanced (Q43-Q50)

Q43Dynamic Tables
When should you use Streams + Tasks instead of Dynamic Tables?
  • A) For simple SELECT-only transformations
  • B) When you need MERGE, DELETE, or SCD Type 2 logic that Dynamic Tables cannot express
  • C) When you want Snowflake to manage the refresh automatically
  • D) Always - Dynamic Tables are deprecated
Dynamic Tables support only SELECT-based declarative transformations. For imperative logic like MERGE (upserts), DELETE with conditions, or SCD Type 2 patterns, you need Streams + Tasks.
Q44Dynamic Tables
Which is TRUE comparing Dynamic Tables and Streams?
  • A) Both use explicit offset tracking
  • B) Dynamic Tables replace streams in all scenarios
  • C) Dynamic Tables are declarative (SELECT only); Streams enable imperative DML logic
  • D) Streams are declarative; Dynamic Tables are imperative
Dynamic Tables: you write a SELECT, Snowflake manages incremental refresh. Streams: you write explicit DML (MERGE/INSERT/DELETE) to process changes. Use DTs for simple transforms, Streams+Tasks for complex logic.
Q45SCD
For SCD Type 2 (slowly changing dimension with history), which approach is correct?
  • A) Stream + Task with MERGE that expires old records and inserts new versions
  • B) Dynamic Table with TARGET_LAG
  • C) Materialized view with AUTO_REFRESH
  • D) A simple INSERT-only stream
SCD Type 2 requires: 1) Detecting changes (stream), 2) Expiring old records (UPDATE SET end_date), 3) Inserting new versions. This multi-step imperative logic requires Streams + Tasks with MERGE.
Q46CHANGES
What does the CHANGES clause do?
  • A) Creates a permanent stream on the table
  • B) Queries change data between two points in time WITHOUT creating a stream object
  • C) Shows the DDL history of a table
  • D) Returns the same data as Time Travel AT
The CHANGES clause (SELECT ... FROM table CHANGES(INFORMATION => ...) AT/BEFORE ... END ...) lets you query CDC information without creating a stream. Requires CHANGE_TRACKING = TRUE on the table.
Q47CHANGES
What INFORMATION mode options are available with the CHANGES clause?
  • A) FULL and PARTIAL
  • B) SUMMARY and DETAIL
  • C) INSERT_ONLY and ALL_CHANGES
  • D) DEFAULT (net changes) and APPEND_ONLY (inserts only)
CHANGES clause supports INFORMATION => DEFAULT (shows net changes like a standard stream) or INFORMATION => APPEND_ONLY (shows only inserts like an append-only stream).
Q48Production
Two Tasks consume the SAME stream concurrently. What risk exists?
  • A) No risk; both will see the same data
  • B) Deadlock on the stream object
  • C) One Task commits first and advances the offset; the other may see empty stream or partial data
  • D) Both will fail with a conflict error
If two consumers share one stream, the first to commit advances the offset. The second consumer may then see no data (or different data). Best practice: use separate streams for each consumer.
Q49Production
Stream shows empty (no rows) but you know changes occurred. Most likely cause?
  • A) The stream is stale
  • B) Another transaction already consumed the stream (advanced the offset)
  • C) The source table was dropped
  • D) SELECT doesn't work on streams
If changes occurred but the stream is empty, another consumer likely already consumed it (committed DML advanced the offset past those changes). Use separate streams per consumer to avoid this.
Q50Best Practice
Which is a best practice for production Streams + Tasks pipelines?
  • A) Use one dedicated stream per consumer, consume within staleness window, use WHEN clause to save compute
  • B) Share a single stream across all consumers to save storage
  • C) Set DATA_RETENTION_TIME_IN_DAYS = 0 to save costs
  • D) Use SELECT queries to periodically check and advance the stream offset
Best practices: 1) One stream per consumer (independent offsets), 2) Consume regularly to avoid staleness, 3) Use WHEN SYSTEM$STREAM_HAS_DATA to skip empty runs, 4) Keep retention adequate for your processing cadence.
