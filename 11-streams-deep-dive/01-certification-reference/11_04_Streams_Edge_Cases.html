0. What Can You Create a Stream On?

Key Rule: Streams need a persistent source that outlives a single session. Any object that is session-scoped (temporary tables) cannot be a stream source because the stream would persist after the session ends with nothing to track.

Supported Source Objects

Source ObjectStream Types SupportedNotes
Standard (permanent) tables Standard, Append-only Most common use case. Full CDC support.
Transient tables Standard, Append-only Supported — shorter retention may increase staleness risk.
External tables Insert-only ONLY Detects new files added to stage. Cannot track UPDATE/DELETE (files are immutable).
Directory tables Insert-only ONLY Tracks files added/removed on a stage. Useful for file-processing pipelines.
Views (including secure views) Standard, Append-only Stream tracks changes to ALL underlying tables. All underlying tables must have CHANGE_TRACKING=TRUE.
Dynamic tables Standard, Append-only Track changes to the DT's materialized output. Useful for chaining DT→Stream→Task patterns.
Shared tables (data sharing) Append-only ONLY Consumer can track changes made by the provider. Standard streams not supported on shared objects.

NOT Supported Source Objects

Source ObjectWhy Not Supported
Temporary tables Temp tables are session-scoped; streams persist across sessions. When session ends, source vanishes but stream would still exist with nothing to track.
Materialized views Not supported as a stream source. Use the underlying base table instead.
Streams (chaining) You CANNOT create a stream on another stream. No stream-on-stream chaining.

Stream Type Compatibility Matrix

Source ObjectStandard StreamAppend-Only StreamInsert-Only Stream
Permanent tableYESYESNO
Transient tableYESYESNO
External tableNONOYES
Directory tableNONOYES
ViewYESYESNO

Syntax Examples

-- Permanent table (standard stream — default)
CREATE STREAM my_stream ON TABLE my_table;

-- View (tracks all underlying table changes)
CREATE STREAM view_stream ON VIEW my_view;

-- External table (insert-only — detects new files)
CREATE STREAM ext_stream ON EXTERNAL TABLE my_ext_table INSERT_ONLY = TRUE;

-- Directory table (insert-only — tracks file additions)
CREATE STREAM dir_stream ON STAGE my_stage;

-- Dynamic table
CREATE STREAM dt_stream ON DYNAMIC TABLE my_dynamic_table;

-- Shared table (append-only only)
CREATE STREAM shared_stream ON TABLE shared_db.schema.shared_table APPEND_ONLY = TRUE;

-- FAILS: Temporary table
CREATE STREAM temp_stream ON TABLE my_temp_table;  -- ERROR: not supported

-- FAILS: Stream on stream
CREATE STREAM chained ON STREAM my_stream;  -- ERROR: not supported
Exam Traps:
  • External tables ONLY support Insert-only streams (files are immutable, no UPDATE/DELETE)
  • Shared tables ONLY support Append-only streams (consumer can't see internal changes)
  • Views require CHANGE_TRACKING=TRUE on ALL underlying base tables
  • You CANNOT create a stream on another stream (no chaining)
  • Temporary tables are NEVER supported (session-scoped vs persistent stream)

1. Source Table Changes

ScenarioStream StatusWhat Happens
DROP TABLE source BROKEN Stream becomes stale/invalid. Querying returns error. Must recreate stream on new table.
CREATE OR REPLACE TABLE source BROKEN Same as DROP — the stream loses its reference to the original table's internal ID. Becomes stale.
TRUNCATE TABLE source VALID Stream captures all deleted rows as DELETE actions (truncate = logical mass delete). Stream remains valid.
ALTER TABLE ADD COLUMN VALID Stream remains valid. New column appears in stream output with NULL for changes before the column was added.
ALTER TABLE DROP COLUMN VALID Stream remains valid. Dropped column disappears from stream output.
ALTER TABLE RENAME COLUMN VALID Stream remains valid. Shows the new column name in output.
ALTER TABLE source RENAME TO new_name VALID Stream still works — it's bound to the table's internal ID, not the name.
ALTER TABLE SET DATA_RETENTION_TIME = 0 RISK Stream may go stale faster! Staleness window shrinks to 0 + 14 = 14 days minimum.
The Two Killers: DROP TABLE and CREATE OR REPLACE TABLE are the only DDL operations that break streams. All ALTER TABLE operations (add/drop/rename columns, rename table) keep streams valid.

2. Target Table Changes

Key Concept: Streams track the source table only. They have NO dependency on any target table. Target changes never affect stream validity or offset.
ScenarioStream ImpactPipeline Impact
DROP TABLE target No impact on stream Consuming DML will FAIL (target doesn't exist). Stream data remains unconsumed.
TRUNCATE TABLE target No impact on stream Stream offset does NOT reset. You've lost processed data but stream only shows new changes. Need full reload.
ALTER target (add/drop columns) No impact on stream Your consuming DML may fail if column mapping breaks. Fix the DML statement.
CREATE OR REPLACE TABLE target No impact on stream Target is empty again. Stream offset still at same point. Need full reload + continue incremental.

The TRUNCATE Target Problem

-- Scenario: You truncated the target by mistake
-- Stream still shows only NEW changes (offset didn't reset)
-- Your target is empty but stream won't replay old data

-- RECOVERY:
-- Step 1: Full reload from source
INSERT INTO target_table SELECT * FROM source_table;

-- Step 2: Stream continues incrementally from current offset
-- (No action needed — it will capture future changes normally)

3. Staleness Deep Dive

When Does a Stream Go Stale?

A stream becomes stale when Snowflake can no longer reconstruct the change history between the stream's offset and the current table state. This happens when the underlying micro-partition data (Time Travel data) is garbage-collected.

Staleness Formula

Staleness Window = DATA_RETENTION_TIME_IN_DAYS + 14 days

Examples:
- Standard table (retention = 1 day):  Stale after 1 + 14 = 15 days without consuming
- Enterprise table (retention = 90 days): Stale after 90 + 14 = 104 days without consuming
- Transient table (retention = 0 days):  Stale after 0 + 14 = 14 days without consuming

Causes of Staleness

CauseWhy It HappensPrevention
Not consuming within retention window Time Travel data is garbage-collected past the offset point Consume via Task with schedule shorter than staleness window
Source table DROP or REPLACE Table's internal ID changes; stream reference becomes invalid Never use CREATE OR REPLACE on tables with active streams
Reducing DATA_RETENTION_TIME Retention shortened past the stream's offset point Check streams before reducing retention: SHOW STREAMS
Task failures (not consuming) If task keeps failing, stream data accumulates and may go stale Monitor task failures; set up alerting

Detecting Staleness

-- Method 1: SHOW STREAMS
SHOW STREAMS LIKE 'my_stream';
-- Check columns: stale (TRUE/FALSE), stale_after (timestamp)

-- Method 2: Query INFORMATION_SCHEMA (if available)
SELECT STREAM_NAME, STALE, STALE_AFTER
FROM INFORMATION_SCHEMA.STREAMS
WHERE STREAM_NAME = 'MY_STREAM';

-- Method 3: Try to query it (stale stream throws error)
SELECT * FROM my_stream;
-- If stale: Error "The stream has become stale"

Prevention Checklist

  • Set task schedule to at most half the staleness window (e.g., if 15 days, consume at least every 7 days)
  • Monitor stale_after timestamp — alert when it's approaching
  • Set appropriate DATA_RETENTION (higher retention = longer before staleness)
  • Never DROP or REPLACE source tables with active streams
  • Monitor task failures — failed consumption = stale risk

4. Recreating Streams (Offset Reset)

MethodWhat Happens to OffsetData Impact
CREATE OR REPLACE STREAM s ON TABLE t Offset resets to current moment All previous unconsumed changes are LOST. Only future changes captured.
CREATE STREAM s ON TABLE t AT(OFFSET => -3600) Offset starts from 1 hour ago Captures changes from last hour (within Time Travel). Partial recovery possible.
CREATE STREAM s ON TABLE t AT(TIMESTAMP => '...') Offset starts from specific timestamp Captures changes since that time (must be within Time Travel retention).
CREATE STREAM s ON TABLE t AT(STREAM => 'old_stream') Offset starts from old stream's position Continues where old stream left off (if old stream isn't stale yet).
CREATE STREAM s ON TABLE t SHOW_INITIAL_ROWS = TRUE Offset at current moment BUT includes all existing rows as INSERTs Full snapshot + future changes. Useful for first-time full load.
AT/BEFORE clauses only work if the target timestamp/offset is within the table's Time Travel retention. If you're recreating after staleness, the original offset is likely OUTSIDE retention — meaning you cannot recover those changes.

5. Other Edge Cases

ScenarioWhat Happens
Transaction ROLLBACK SAFE. If consuming DML is rolled back, stream offset does NOT advance. Data remains in stream for next consumption. This is the key safety guarantee.
Multiple consumers on same stream PROBLEM. Only ONE DML transaction can consume at a time. If two tasks read the same stream concurrently, one gets data and the other gets nothing. Use separate streams for separate consumers.
UNDROP source table UNRELIABLE. Stream may recover if done within retention, but behavior is not guaranteed. Don't depend on it.
CLONE source table Stream stays on original. The clone gets its own data; the stream still points to the original table, NOT the clone. Create a new stream on the clone if needed.
Stream on a VIEW Supported but complex. Tracks changes to ALL underlying tables. All underlying tables must have CHANGE_TRACKING=TRUE. JOINs in views can produce unexpected stream output.
Time Travel on stream itself NOT POSSIBLE. You cannot time-travel a stream. Streams always reflect the current unconsumed offset. Use AT/BEFORE at creation time instead.
Reclustering source table May show phantom changes. Automatic clustering rewrites micro-partitions. Standard streams may reflect this as changes. Use append-only streams for heavily reclustered tables.
Data Sharing (consumer side) Supported. Consumer can create a stream on a shared view/table to track changes made by the provider.
INSERT OVERWRITE on source Stream captures changes. Shows DELETE of old rows + INSERT of new rows. Can be a large change set.
MERGE on source table Stream captures all. INSERTs, UPDATEs (as DELETE+INSERT pairs), and DELETEs from the MERGE are all tracked.

Multiple Consumers — Correct Pattern

-- WRONG: Two tasks consuming the same stream (race condition)
-- Task A and Task B both read from employees_stream
-- Result: One gets data, other gets nothing. Unpredictable.

-- CORRECT: Separate streams for separate consumers
CREATE STREAM employees_stream_analytics ON TABLE employees;  -- For analytics
CREATE STREAM employees_stream_audit ON TABLE employees;      -- For audit
CREATE STREAM employees_stream_reporting ON TABLE employees;  -- For reporting

-- Each stream has its own independent offset
-- Task A consumes stream_analytics (doesn't affect others)
-- Task B consumes stream_audit (doesn't affect others)

6. Recovery Playbook

Scenario A: Stream Went Stale

-- 1. Drop the stale stream
DROP STREAM my_stream;

-- 2. Full reload target from source (bridge the gap)
TRUNCATE TABLE target_table;
INSERT INTO target_table
SELECT col1, col2, col3 FROM source_table;

-- 3. Recreate stream (starts from NOW)
CREATE STREAM my_stream ON TABLE source_table;

-- 4. Resume task
ALTER TASK my_task RESUME;

-- Stream now handles incremental from this point forward
-- Gap between stale point and full reload = potentially lost changes

Scenario B: Source Table Dropped/Replaced

-- 1. Stream is broken (references old table ID)
DROP STREAM my_stream;  -- Clean up invalid stream

-- 2. If table was replaced: new table exists, do full reload
TRUNCATE TABLE target_table;
INSERT INTO target_table SELECT * FROM source_table;

-- 3. Create new stream on the new table
CREATE STREAM my_stream ON TABLE source_table;

-- 4. Resume task
ALTER TASK my_task RESUME;

Scenario C: Target Table Truncated by Mistake

-- Stream is FINE (unaffected by target changes)
-- But target is empty and stream won't replay old data

-- 1. Full reload from source
INSERT INTO target_table SELECT * FROM source_table;

-- 2. Done! Stream continues incrementally from its current offset
-- No stream recreation needed

Scenario D: Task Failing (Stream Approaching Staleness)

-- 1. Check stale_after timestamp
SHOW STREAMS LIKE 'my_stream';
-- If stale_after is approaching, act fast!

-- 2. Fix the task error (check TASK_HISTORY for error message)
SELECT * FROM TABLE(INFORMATION_SCHEMA.TASK_HISTORY(
  TASK_NAME => 'my_task'
)) WHERE STATE = 'FAILED' ORDER BY SCHEDULED_TIME DESC LIMIT 5;

-- 3. Manually consume the stream to advance offset (buys time)
INSERT INTO target_table
SELECT columns FROM my_stream WHERE METADATA$ACTION = 'INSERT';

-- 4. Fix and resume the task
ALTER TASK my_task RESUME;

Scenario E: Need to Recapture Recent Changes (Within Time Travel)

-- If you need to go back in time (within retention period):
DROP STREAM my_stream;

-- Recreate with AT clause (go back 1 hour)
CREATE STREAM my_stream ON TABLE source_table
  AT(OFFSET => -3600);

-- Or go back to specific timestamp
CREATE STREAM my_stream ON TABLE source_table
  AT(TIMESTAMP => '2026-08-14 09:00:00'::TIMESTAMP_LTZ);

-- This only works if the timestamp is within DATA_RETENTION_TIME!

7. Exam Scenario Questions

ScenarioCorrect Answer
"A developer runs CREATE OR REPLACE TABLE on a table that has 3 streams. What happens?" All 3 streams become invalid/stale. They must all be dropped and recreated.
"A stream hasn't been consumed for 20 days. Table retention is 1 day. Is the stream stale?" YES. Staleness window = 1 + 14 = 15 days. 20 days > 15 days = stale.
"A DML transaction reading a stream fails and rolls back. Is data lost?" NO. On rollback, the offset does NOT advance. Data remains in stream for next attempt.
"Two tasks consume the same stream simultaneously. What happens?" One task gets the data; the other gets nothing. Use separate streams for separate consumers.
"TRUNCATE is run on the source table. Does the stream break?" NO. Stream shows all rows as DELETE actions. Stream remains valid.
"A table is renamed. Does the stream break?" NO. Streams are bound to the table's internal ID, not its name.
"Can you recover a stale stream?" NO. A stale stream cannot be recovered. You must drop it, do a full reload of target, and create a new stream.
"A column is added to the source table. What does the stream show?" Stream remains valid. New column appears with NULL for changes that occurred before the column existed.
"How can you create a stream that includes all existing rows?" Use SHOW_INITIAL_ROWS = TRUE. All current rows appear as INSERTs in the stream.
"A clone of the source table is created. Does the stream track the clone?" NO. The stream stays on the original table. Create a new stream on the clone if needed.
Most Dangerous Scenario (Real-World): Stream staleness from task failures that go unnoticed. The stream silently approaches staleness, and once it crosses the threshold, all intermediate changes are permanently lost. Prevention: monitor stale_after, alert on task failures, consume frequently.
