1. What Are Dynamic Tables?

The Core Concept

A Dynamic Table is a declarative, materialized query result that Snowflake automatically keeps up to date. You define WHAT you want (the SQL query) and HOW FRESH you need it (target lag), and Snowflake handles WHEN and HOW to refresh it.

The Problem They Solve

Traditional ApproachDynamic Tables
Write CREATE TABLE + INSERT/MERGE statements Write only the SELECT query — Snowflake handles materialization
Create Streams to track changes No streams needed — DT tracks source changes internally
Create Tasks to schedule refresh No tasks needed — DT auto-refreshes based on target lag
Manage dependencies manually (DAG order) DTs auto-detect dependencies and refresh in correct order
Handle failure/retry logic in tasks Snowflake handles failures and retries automatically
One-Line Summary: Dynamic Tables replace the entire Stream + Task + MERGE pattern with a single declarative SQL statement + a freshness target.

When to Use Dynamic Tables

  • Multi-step data transformation pipelines (bronze → silver → gold)
  • Materialized views that need JOINs (MVs don't support JOINs)
  • ELT pipelines where you define the target state, not the transformation steps
  • Teams that want less operational overhead (no task monitoring, stream management)
  • Continuous data freshness requirements (minutes to hours, not real-time)

2. Syntax & Creation

Basic Syntax

CREATE [ OR REPLACE ] DYNAMIC TABLE <name>
  TARGET_LAG = '<time>' | DOWNSTREAM
  WAREHOUSE = <warehouse_name>
  [ REFRESH_MODE = AUTO | FULL | INCREMENTAL ]
  [ INITIALIZE = ON_CREATE | ON_SCHEDULE ]
  [ CLUSTER BY ( <expr> [, ...] ) ]
  [ DATA_RETENTION_TIME_IN_DAYS = <n> ]
  [ COMMENT = '...' ]
AS
  <select_statement>;

Simple Example

-- Source table (raw data)
CREATE TABLE raw_orders (
  order_id INT,
  customer_id INT,
  product VARCHAR,
  amount DECIMAL(10,2),
  order_date TIMESTAMP,
  status VARCHAR
);

-- Dynamic Table: aggregated daily revenue
CREATE DYNAMIC TABLE daily_revenue
  TARGET_LAG = '10 minutes'
  WAREHOUSE = transform_wh
AS
  SELECT
    DATE_TRUNC('day', order_date) AS revenue_date,
    COUNT(*) AS total_orders,
    SUM(amount) AS total_revenue,
    AVG(amount) AS avg_order_value
  FROM raw_orders
  WHERE status = 'COMPLETED'
  GROUP BY 1;

Multi-Layer Pipeline Example

-- Layer 1: Clean raw data (Bronze → Silver)
CREATE DYNAMIC TABLE orders_cleaned
  TARGET_LAG = '5 minutes'
  WAREHOUSE = transform_wh
AS
  SELECT
    order_id,
    customer_id,
    UPPER(TRIM(product)) AS product,
    amount,
    order_date,
    status
  FROM raw_orders
  WHERE order_id IS NOT NULL AND amount > 0;

-- Layer 2: Enrich with customer data (Silver → Gold)
CREATE DYNAMIC TABLE orders_enriched
  TARGET_LAG = DOWNSTREAM  -- refreshes only when needed by downstream
  WAREHOUSE = transform_wh
AS
  SELECT
    o.*,
    c.customer_name,
    c.region,
    c.segment
  FROM orders_cleaned o
  JOIN customers c ON o.customer_id = c.customer_id;

-- Layer 3: Final reporting table (Gold)
CREATE DYNAMIC TABLE revenue_by_region
  TARGET_LAG = '30 minutes'
  WAREHOUSE = transform_wh
AS
  SELECT
    region,
    segment,
    DATE_TRUNC('day', order_date) AS report_date,
    SUM(amount) AS revenue,
    COUNT(DISTINCT customer_id) AS unique_customers
  FROM orders_enriched
  GROUP BY 1, 2, 3;

Key Parameters

ParameterRequiredDescription
TARGET_LAGYESMaximum staleness allowed. Time string ('5 minutes', '1 hour') or DOWNSTREAM.
WAREHOUSEYESWarehouse used for refresh operations. Must be running or auto-resume enabled.
REFRESH_MODENo (default AUTO)AUTO (Snowflake decides), FULL (always full refresh), INCREMENTAL (delta only).
INITIALIZENo (default ON_CREATE)ON_CREATE: populate immediately. ON_SCHEDULE: wait for first refresh cycle.
CLUSTER BYNoClustering keys for the materialized data. Applied during refresh.
DATA_RETENTION_TIME_IN_DAYSNoTime Travel retention for the DT (0-90 days depending on edition).

3. Target Lag Deep Dive

What is Target Lag?

Target lag is the maximum acceptable staleness of the Dynamic Table's data. It tells Snowflake: "The data in this DT should never be more than X minutes/hours behind the source." Snowflake then schedules refreshes to meet this SLA.

Time-Based Target Lag

ValueMeaningUse Case
'1 minute'Minimum allowed. Near real-time freshness.Operational dashboards, alerting
'5 minutes'Refreshes every ~5 minutes or lessNear real-time analytics
'1 hour'Refreshes at least every hourHourly reporting
'24 hours'At most one day staleDaily batch, cost-efficient

DOWNSTREAM Target Lag

CREATE DYNAMIC TABLE middle_layer
  TARGET_LAG = DOWNSTREAM  -- Don't refresh on your own schedule
  WAREHOUSE = transform_wh
AS SELECT ...;
DOWNSTREAM means: "Only refresh me when a downstream DT (that has a time-based target lag) needs fresh data from me." This avoids unnecessary refreshes for intermediate pipeline layers.

How Target Lag Affects Refresh Scheduling

ScenarioBehavior
Source hasn't changed No refresh triggered — Snowflake is smart enough to skip if data is unchanged.
Source changed, within lag window Refresh may be deferred until approaching the lag deadline.
Source changed, lag window expiring Refresh triggered immediately to meet freshness SLA.
Refresh takes longer than lag window DT may temporarily exceed target lag. Snowflake logs this but continues.
Warehouse suspended Refresh blocked until warehouse resumes. DT becomes stale beyond target lag.
Cost Implication: Shorter target lag = more frequent refreshes = higher compute cost. A 1-minute lag on a complex query can be very expensive. Choose the largest acceptable lag for your use case.

4. Refresh Modes

ModeHow It WorksWhen Used
INCREMENTAL Only processes changed data since last refresh (like a stream). Efficient for large tables with small deltas. Simple queries (filter, project, join on keys). Snowflake auto-detects if possible.
FULL Re-executes the entire query from scratch each refresh. Scans all source data. Complex queries (non-deterministic functions, certain aggregations, UNION ALL).
AUTO (default) Snowflake chooses: INCREMENTAL if the query supports it, FULL otherwise. May switch between them. Recommended — let Snowflake optimize.

What Supports Incremental Refresh?

SQL PatternIncremental?Notes
Simple SELECT with WHERE filtersYESStandard projections and filters
JOIN (INNER, LEFT, RIGHT)YESEqui-joins on key columns
GROUP BY with SUM, COUNT, MIN, MAX, AVGYESCommon aggregations supported incrementally
UNION ALLYESEach branch processed independently
Window functions (ROW_NUMBER, RANK, etc.)DEPENDSSome supported, complex windows may force FULL
Non-deterministic functions (CURRENT_TIMESTAMP, RANDOM)NO → FULLResult changes every execution, can't be incremental
LATERAL FLATTENYESSupported for incremental
Subqueries (correlated)DEPENDSSimple subqueries OK, complex may force FULL
QUALIFY clauseYESSupported with incremental
External functions (UDFs calling APIs)NO → FULLCan't determine incremental behavior for external calls

Checking Refresh Mode

-- See what mode Snowflake chose
SELECT NAME, REFRESH_MODE, REFRESH_MODE_REASON
FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLES())
WHERE NAME = 'MY_DYNAMIC_TABLE';

-- Detailed refresh history
SELECT *
FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLE_REFRESH_HISTORY(
  NAME => 'MY_DYNAMIC_TABLE'
))
ORDER BY REFRESH_END_TIME DESC
LIMIT 10;

5. Architecture & Internals

How Dynamic Tables Work Under the Hood
  1. Dependency Graph: Snowflake builds a DAG of all DTs and their source tables/DTs. This determines refresh order.
  2. Change Tracking: Snowflake internally tracks changes to source tables (similar to streams but fully managed).
  3. Scheduler: Based on target lag, Snowflake's orchestrator decides WHEN to refresh each DT.
  4. Execution: Refresh runs on the specified warehouse. For INCREMENTAL: only delta is processed. For FULL: entire query re-executes.
  5. Materialization: Results are stored as micro-partitions (just like a regular table). Queries against DTs are fast — they read materialized data.

Key Architecture Points

  • DTs are real tables — once materialized, querying them is as fast as querying any table (no re-computation)
  • Automatic dependency detection — if DT_B reads from DT_A, Snowflake knows to refresh DT_A first
  • No manual scheduling — Snowflake handles all timing based on target lag propagation through the DAG
  • Warehouse required — unlike serverless tasks, DTs always need a specified warehouse
  • Change tracking is internal — you don't see or manage streams; Snowflake handles CDC internally

Refresh Lifecycle

Source table changes → Snowflake detects change
  → Checks target lag deadline for all dependent DTs
  → Schedules refresh (respecting dependency order)
  → Starts warehouse (if suspended)
  → Executes query (INCREMENTAL or FULL)
  → Materializes results (replaces old micro-partitions)
  → Updates refresh metadata
  → DT is now fresh (lag clock resets)

When to choose each:
  • Dynamic Tables: Multi-step transformation pipelines, team wants low ops overhead, minutes-to-hours freshness acceptable
  • Streams + Tasks: Need UPDATEs/DELETEs, complex control flow, sub-minute CDC, custom error handling
  • Materialized Views: Single-table aggregations, need real-time freshness, simple queries only

7. Features (15 Key Points)

#FeatureDetail
1Declarative pipelinesDefine target state with SQL SELECT. Snowflake handles the how/when.
2Automatic dependency managementMulti-DT pipelines auto-refresh in correct order based on the DAG.

4Target lag SLADefine maximum staleness. Snowflake guarantees data freshness within this window.

8. Limitations (15 Key Points)

#LimitationDetail / Workaround
1Read-only outputCannot INSERT/UPDATE/DELETE into a DT. It's purely defined by its query.
2No DML allowedIf you need to modify data, use a regular table with Streams + Tasks.
3Warehouse requiredMust specify a warehouse. No serverless option (unlike serverless tasks).
4Minimum lag = 1 minuteCannot achieve sub-second freshness. Use Snowpipe Streaming for that.
5Full refresh for complex queriesNon-deterministic functions, external UDFs, some window functions force FULL refresh.
6No MERGE semanticsDTs are "full state" — the entire result is materialized, not incremental upserts.
7Cannot reference temporary tablesSource objects must be persistent (permanent, transient, other DTs, views).
8Cannot write to DT from externalNo Snowpipe or COPY INTO pointing to a DT. Only the defining query populates it.
9Warehouse costs during refreshRefresh uses full warehouse. Long-running refreshes on large WHs can be expensive.
10No procedural logicDT body is a single SELECT. No IF/ELSE, loops, or multi-statement logic.
11DOWNSTREAM not standaloneAt least one DT in the pipeline must have a time-based lag to drive refreshes.
12Schema evolution limitedChanging the SELECT (adding columns) requires CREATE OR REPLACE — loses history.
13Cross-database referencesSupported but cross-account/share sources have limitations.
14Refresh can exceed target lagIf query is slow, DT may temporarily be staler than target. Snowflake logs this.
15No triggers/events on refreshCannot fire a notification when DT finishes refreshing (unlike task AFTER completion).
The Big Trade-off: Dynamic Tables trade control for convenience. You get automatic orchestration and refresh management, but you lose the ability to do UPDATEs/DELETEs, custom error handling, and procedural logic. For simple pipelines: DTs win. For complex CDC with SCD Type 2: Streams + Tasks may still be better.
