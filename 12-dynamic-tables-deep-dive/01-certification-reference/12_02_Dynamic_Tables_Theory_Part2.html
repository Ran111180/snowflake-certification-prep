1. Pipeline Patterns (Medallion Architecture)

The Medallion Architecture with Dynamic Tables

Dynamic Tables are ideal for implementing the Bronze → Silver → Gold pattern. Each layer is a DT that reads from the previous layer. Snowflake auto-detects the DAG and refreshes in order.

Full Medallion Example

-- ═══════════════════════════════════════════
-- BRONZE: Raw ingestion (regular table, loaded by Snowpipe)
-- ═══════════════════════════════════════════
CREATE TABLE bronze_events (
  raw_data VARIANT,
  _loaded_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP(),
  _source_file VARCHAR DEFAULT METADATA$FILENAME
);

-- ═══════════════════════════════════════════
-- SILVER: Cleaned & typed (Dynamic Table)
-- ═══════════════════════════════════════════
CREATE DYNAMIC TABLE silver_events
  TARGET_LAG = '5 minutes'
  WAREHOUSE = transform_wh
AS
  SELECT
    raw_data:event_id::STRING AS event_id,
    raw_data:user_id::INT AS user_id,
    raw_data:event_type::STRING AS event_type,
    raw_data:properties::VARIANT AS properties,
    TRY_TO_TIMESTAMP(raw_data:timestamp::STRING) AS event_timestamp,
    _loaded_at,
    _source_file
  FROM bronze_events
  WHERE raw_data:event_id IS NOT NULL;

-- ═══════════════════════════════════════════
-- GOLD: Business-level aggregates (Dynamic Table)
-- ═══════════════════════════════════════════
CREATE DYNAMIC TABLE gold_user_activity
  TARGET_LAG = '30 minutes'
  WAREHOUSE = transform_wh
AS
  SELECT
    user_id,
    DATE_TRUNC('day', event_timestamp) AS activity_date,
    COUNT(*) AS total_events,
    COUNT(DISTINCT event_type) AS distinct_event_types,
    MIN(event_timestamp) AS first_event,
    MAX(event_timestamp) AS last_event,
    COUNT_IF(event_type = 'purchase') AS purchases,
    SUM(IFF(event_type = 'purchase',
        properties:amount::DECIMAL(10,2), 0)) AS total_spend
  FROM silver_events
  GROUP BY 1, 2;

Pipeline with DOWNSTREAM

-- Only the FINAL layer has a time-based lag
-- Intermediate layers use DOWNSTREAM (refresh only when needed)

CREATE DYNAMIC TABLE staging_orders
  TARGET_LAG = DOWNSTREAM  -- Won't refresh on its own
  WAREHOUSE = wh AS SELECT ... FROM raw_orders;

CREATE DYNAMIC TABLE staging_customers
  TARGET_LAG = DOWNSTREAM  -- Won't refresh on its own
  WAREHOUSE = wh AS SELECT ... FROM raw_customers;

-- This DT drives the refresh of BOTH upstream DTs
CREATE DYNAMIC TABLE reporting_orders
  TARGET_LAG = '15 minutes'  -- This triggers the chain
  WAREHOUSE = wh
AS
  SELECT o.*, c.customer_name, c.region
  FROM staging_orders o
  JOIN staging_customers c ON o.customer_id = c.customer_id;

Fan-In Pattern (Multiple Sources → One DT)

-- Combine data from multiple sources
CREATE DYNAMIC TABLE unified_transactions
  TARGET_LAG = '10 minutes'
  WAREHOUSE = transform_wh
AS
  SELECT 'ONLINE' AS channel, order_id, amount, ts FROM online_orders
  UNION ALL
  SELECT 'STORE' AS channel, txn_id, amount, ts FROM store_sales
  UNION ALL
  SELECT 'MOBILE' AS channel, purchase_id, amount, ts FROM mobile_purchases;

2. Monitoring & Observability

Key Monitoring Queries

-- 1. Check all Dynamic Tables and their status
SHOW DYNAMIC TABLES;

-- 2. Detailed metadata
SELECT NAME, SCHEMA_NAME, DATABASE_NAME, TARGET_LAG, REFRESH_MODE,
       WAREHOUSE, SCHEDULING_STATE, IS_CLONE, IS_REPLICA
FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLES());

-- 3. Refresh history (most important for debugging)
SELECT NAME, STATE, STATE_MESSAGE, REFRESH_START_TIME, REFRESH_END_TIME,
       DATEDIFF(second, REFRESH_START_TIME, REFRESH_END_TIME) AS duration_sec,
       STATISTICS:numInsertedRows::INT AS rows_inserted,
       STATISTICS:numDeletedRows::INT AS rows_deleted,
       STATISTICS:numUpdatedRows::INT AS rows_updated
FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLE_REFRESH_HISTORY())
WHERE NAME = 'MY_DT'
ORDER BY REFRESH_END_TIME DESC
LIMIT 20;

-- 4. Check current lag (how stale is the data?)
SELECT NAME, DATA_TIMESTAMP, TARGET_LAG,
       DATEDIFF(minute, DATA_TIMESTAMP, CURRENT_TIMESTAMP()) AS current_lag_minutes
FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLES())
WHERE SCHEMA_NAME = 'MY_SCHEMA';

-- 5. Failed refreshes
SELECT NAME, STATE, STATE_MESSAGE, REFRESH_START_TIME
FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLE_REFRESH_HISTORY())
WHERE STATE = 'FAILED'
ORDER BY REFRESH_START_TIME DESC LIMIT 10;

-- 6. Refresh cost estimation (warehouse usage)
SELECT NAME,
       COUNT(*) AS refresh_count,
       AVG(DATEDIFF(second, REFRESH_START_TIME, REFRESH_END_TIME)) AS avg_duration_sec,
       MAX(DATEDIFF(second, REFRESH_START_TIME, REFRESH_END_TIME)) AS max_duration_sec
FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLE_REFRESH_HISTORY())
WHERE REFRESH_START_TIME > DATEADD(day, -7, CURRENT_TIMESTAMP())
GROUP BY NAME
ORDER BY refresh_count DESC;

Scheduling States

StateMeaningAction
ACTIVEDT is being refreshed on scheduleNormal — no action needed
SUSPENDEDDT refresh is pausedALTER DYNAMIC TABLE ... RESUME to reactivate
FAILEDLast refresh failed, waiting to retryCheck STATE_MESSAGE for error, fix root cause

3. Optimization & Cost Management

Cost Factors

FactorImpactOptimization
Target lag (shorter)More frequent refreshes → higher costUse the largest acceptable lag
Warehouse sizeLarger WH = faster refresh but more credits/secondRight-size: don't over-provision
Full vs Incremental refreshFull scans all data every timeWrite queries that support incremental mode
Source data volumeMore source data = longer refreshesFilter early (WHERE clause) to reduce scan
Number of DTs in pipelineEach DT uses warehouse for its refreshConsolidate where possible
Warehouse auto-suspendIf WH suspends between refreshes, startup delaySet auto-suspend ≥ refresh interval to keep warm

Optimization Tips

-- TIP 1: Use DOWNSTREAM for intermediate layers (avoids unnecessary refreshes)
CREATE DYNAMIC TABLE middle_layer TARGET_LAG = DOWNSTREAM ...;

-- TIP 2: Use a dedicated warehouse (avoid contention with ad-hoc queries)
CREATE WAREHOUSE dt_refresh_wh
  WAREHOUSE_SIZE = 'SMALL'
  AUTO_SUSPEND = 300        -- 5 min (keep warm between refreshes)
  AUTO_RESUME = TRUE;

-- TIP 3: Check if your query supports incremental
SELECT NAME, REFRESH_MODE, REFRESH_MODE_REASON
FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLES())
WHERE NAME = 'MY_DT';
-- If FULL and you want INCREMENTAL: rewrite query to avoid non-deterministic functions

-- TIP 4: Add CLUSTER BY for downstream query performance
CREATE DYNAMIC TABLE fact_sales
  TARGET_LAG = '1 hour'
  WAREHOUSE = transform_wh
  CLUSTER BY (sale_date, region)  -- Optimize for common query patterns
AS SELECT ...;

-- TIP 5: Use INITIALIZE = ON_SCHEDULE for non-urgent DTs during migration
CREATE DYNAMIC TABLE big_historical
  TARGET_LAG = '24 hours'
  WAREHOUSE = large_wh
  INITIALIZE = ON_SCHEDULE  -- Don't block CREATE, populate later
AS SELECT ... FROM billion_row_table;

4. RBAC & Permissions

Required Privileges

ActionPrivilege NeededGranted To
Create a DTCREATE DYNAMIC TABLE on schema + USAGE on warehouse + SELECT on sourcesRole that creates the DT
Query a DTSELECT on the DTAny role needing to read
Alter a DT (lag, warehouse)OWNERSHIP or ALTER privilege on DTDT owner role or granted role
Suspend/ResumeOWNERSHIP or OPERATE privilege on DTOperations role
Drop a DTOWNERSHIP on DTOwner role
Monitor refresh historyOWNERSHIP or MONITOR on DT (or INFORMATION_SCHEMA access)Monitoring role

RBAC Setup Example

-- Create role for DT management
CREATE ROLE dt_developer;
GRANT USAGE ON DATABASE analytics_db TO ROLE dt_developer;
GRANT USAGE ON SCHEMA analytics_db.transform TO ROLE dt_developer;
GRANT CREATE DYNAMIC TABLE ON SCHEMA analytics_db.transform TO ROLE dt_developer;
GRANT USAGE ON WAREHOUSE transform_wh TO ROLE dt_developer;
GRANT SELECT ON ALL TABLES IN SCHEMA analytics_db.raw TO ROLE dt_developer;

-- Separate role for consumers (read-only)
CREATE ROLE dt_reader;
GRANT USAGE ON DATABASE analytics_db TO ROLE dt_reader;
GRANT USAGE ON SCHEMA analytics_db.transform TO ROLE dt_reader;
GRANT SELECT ON ALL DYNAMIC TABLES IN SCHEMA analytics_db.transform TO ROLE dt_reader;

-- Operations role (can suspend/resume but not modify)
CREATE ROLE dt_operator;
GRANT OPERATE ON ALL DYNAMIC TABLES IN SCHEMA analytics_db.transform TO ROLE dt_operator;
GRANT MONITOR ON ALL DYNAMIC TABLES IN SCHEMA analytics_db.transform TO ROLE dt_operator;

5. Debugging & Troubleshooting

ProblemLikely CauseFix
DT not refreshing SUSPENDED state, warehouse suspended/dropped, or no source changes Check SCHEDULING_STATE. ALTER DYNAMIC TABLE ... RESUME. Verify warehouse exists.
Refresh failing with error Query error (missing table, permission denied, type mismatch) Check STATE_MESSAGE in DYNAMIC_TABLE_REFRESH_HISTORY for exact error.
Data is stale (exceeding target lag) Refresh takes too long, or warehouse too small, or source changes too frequent Use larger warehouse, simplify query, or increase target lag.
Full refresh when expecting incremental Query uses non-deterministic functions, external UDFs, or unsupported patterns Check REFRESH_MODE_REASON. Rewrite query to support incremental.
High warehouse costs Target lag too short, full refreshes on large data, warehouse oversized Increase lag, optimize query for incremental, right-size warehouse.
DT shows wrong/stale data after ALTER After changing the query (CREATE OR REPLACE), may need full initial refresh Wait for next refresh cycle, or ALTER ... REFRESH to force immediate.
Dependency chain not refreshing Intermediate DT set to DOWNSTREAM but no downstream DT has time-based lag At least one DT in the chain must have a time-based TARGET_LAG.
Cannot create DT: "insufficient privileges" Missing CREATE DYNAMIC TABLE on schema, USAGE on warehouse, or SELECT on source Grant all required privileges (see RBAC section above).

Debug Workflow

-- Step 1: Check DT status
SHOW DYNAMIC TABLES LIKE 'MY_DT%';
-- Look at: scheduling_state, data_timestamp

-- Step 2: Check refresh history for failures
SELECT STATE, STATE_MESSAGE, REFRESH_START_TIME, REFRESH_END_TIME
FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLE_REFRESH_HISTORY(NAME => 'MY_DT'))
WHERE STATE != 'SUCCEEDED'
ORDER BY REFRESH_START_TIME DESC LIMIT 5;

-- Step 3: Check if source tables have been modified
-- (If source dropped/replaced, DT will fail on next refresh)

-- Step 4: Manually trigger a refresh to test
ALTER DYNAMIC TABLE my_dt REFRESH;

-- Step 5: Check the graph (which DTs depend on which)
SELECT * FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLE_GRAPH_HISTORY())
WHERE NAME = 'MY_DT';

6. Advanced Hybrid Patterns

Pattern 1: Snowpipe → DT Pipeline

-- Snowpipe loads raw data into a regular table
CREATE PIPE ingest_pipe AUTO_INGEST = TRUE AS
COPY INTO raw_events FROM @event_stage;

-- DT handles all downstream transformation automatically
CREATE DYNAMIC TABLE processed_events
  TARGET_LAG = '5 minutes'
  WAREHOUSE = transform_wh
AS SELECT ... FROM raw_events WHERE ...;

Pattern 2: DT + Stream (Track DT Output Changes)

-- Create a stream ON a Dynamic Table
CREATE STREAM dt_changes ON DYNAMIC TABLE gold_metrics;

-- Use a task to push DT changes downstream (e.g., to external system)
CREATE TASK export_changes
  WAREHOUSE = export_wh
  SCHEDULE = '5 MINUTE'
  WHEN SYSTEM$STREAM_HAS_DATA('dt_changes')
AS
  INSERT INTO export_queue
  SELECT * FROM dt_changes WHERE METADATA$ACTION = 'INSERT';

Pattern 3: DT for Read, Stream+Task for Write

-- DT handles complex READ transformations (JOINs, aggregations)
CREATE DYNAMIC TABLE customer_360
  TARGET_LAG = '10 minutes'
  WAREHOUSE = wh
AS SELECT ... FROM orders JOIN customers JOIN interactions ...;

-- Stream+Task handles CDC WRITES (SCD Type 2, deletes)
CREATE STREAM customer_changes ON TABLE customers;
CREATE TASK apply_scd2
  WAREHOUSE = wh
  SCHEDULE = '1 MINUTE'
  WHEN SYSTEM$STREAM_HAS_DATA('customer_changes')
AS MERGE INTO dim_customer_history ...;

7. ALTER DYNAMIC TABLE Operations

-- Change target lag (more/less fresh)
ALTER DYNAMIC TABLE my_dt SET TARGET_LAG = '30 minutes';

-- Change warehouse
ALTER DYNAMIC TABLE my_dt SET WAREHOUSE = bigger_wh;

-- Suspend refreshes (stop spending credits)
ALTER DYNAMIC TABLE my_dt SUSPEND;

-- Resume refreshes
ALTER DYNAMIC TABLE my_dt RESUME;

-- Force immediate refresh (useful for debugging)
ALTER DYNAMIC TABLE my_dt REFRESH;

-- Change data retention
ALTER DYNAMIC TABLE my_dt SET DATA_RETENTION_TIME_IN_DAYS = 7;

-- Add/change clustering
ALTER DYNAMIC TABLE my_dt CLUSTER BY (date_col, region);

-- Drop clustering
ALTER DYNAMIC TABLE my_dt DROP CLUSTERING KEY;

-- CANNOT alter the query itself — must use CREATE OR REPLACE
-- (This resets the DT: loses history, triggers full refresh)
Important: Unlike tasks, you do NOT need to suspend a DT before ALTERing its lag or warehouse. The change takes effect on the next scheduled refresh. But to change the underlying query: must CREATE OR REPLACE (destructive).

8. Production Best Practices

Checklist for Production DT Pipelines:
  1. Dedicated warehouse — Don't share with ad-hoc queries. Set auto-suspend slightly above refresh interval.
  2. Use DOWNSTREAM for intermediate layers — Avoid paying for unnecessary refreshes.
  3. Monitor refresh history — Set up alerts on failed refreshes and lag exceeding target.
  4. Right-size target lag — Start generous (1 hour), tighten only if business requires it.
  5. Write incremental-friendly queries — Avoid CURRENT_TIMESTAMP, RANDOM(), volatile UDFs.
  6. Add CLUSTER BY — If downstream queries filter on specific columns, cluster the DT.
  7. Test with REFRESH_MODE = FULL first — Verify correctness, then check if AUTO picks INCREMENTAL.
  8. Use INFORMATION_SCHEMA views — DYNAMIC_TABLES, DYNAMIC_TABLE_REFRESH_HISTORY for monitoring.
  9. Version control your DT definitions — Store CREATE DYNAMIC TABLE in git (can't ALTER the query).
  10. Plan for CREATE OR REPLACE — When changing queries, coordinate with downstream consumers (DT goes empty briefly).
