1. Supported & Unsupported Source/Target Objects

Key Rule: A DT's AS clause is a SELECT query. It can read from anything you can SELECT from, but with some incremental refresh limitations. The DT itself is a read-only materialized output — no one can write to it.

What Can a DT Read FROM (Source Objects)

Source ObjectSupportedIncremental RefreshNotes
Permanent tablesYESYESPrimary use case. Full support.
Transient tablesYESYESSame as permanent for DTs.
Other Dynamic TablesYESYESCore feature — DT chaining for multi-layer pipelines.
Views (including secure)YESDEPENDSIncremental works if underlying tables support it.
External tablesYESFULL onlyExternal tables don't support internal change tracking well.
Shared tables (Data Sharing)YESDEPENDSCan read from shared data. Incremental may be limited.
Temporary tablesNON/ATemp tables are session-scoped; DTs persist across sessions.
StreamsNON/ADTs don't consume streams. They have internal change tracking.
Materialized viewsYESDEPENDSCan read from MVs, but unusual pattern.
Stages (directly)NON/ACannot SELECT FROM @stage in DT body. Load to table first.
Functions / UDFsYESMay force FULLDeterministic UDFs OK. External/volatile UDFs force FULL.

What Can Write TO a Dynamic Table (Target)

OperationAllowedNotes
INSERT INTO dt ...NODTs are read-only. Only the defining query populates them.
UPDATE dt SET ...NONo DML allowed on DTs.
DELETE FROM dt ...NONo DML allowed on DTs.
MERGE INTO dt ...NONo DML allowed on DTs.
COPY INTO dt FROM @stageNOCannot load into DTs via Snowpipe or COPY.
Snowpipe targeting a DTNOPipe's COPY INTO cannot point to a DT.
SELECT FROM dtYESReading is always allowed (with SELECT privilege).
CREATE STREAM ON dtYESStreams can track DT output changes.
CLONE dtYESCreates a point-in-time copy (also a DT).
Exam Trap: DTs are purely declarative and read-only. The ONLY way data gets into a DT is through its defining SELECT query during refresh. No external DML, no Snowpipe, no COPY INTO. If you need to write to a table, use Streams + Tasks with a regular table.

2. DDL Impact

DDL OperationDT DataRefresh HistoryDownstream DTs
CREATE OR REPLACE DYNAMIC TABLE RESET — full re-initialization RESET Downstream DTs see it as new source
ALTER DYNAMIC TABLE ... SET TARGET_LAG Preserved Preserved No impact
ALTER DYNAMIC TABLE ... SET WAREHOUSE Preserved Preserved No impact
ALTER DYNAMIC TABLE ... SUSPEND Preserved (becomes stale) Preserved Downstream may get stale data
ALTER DYNAMIC TABLE ... RESUME Refreshes to catch up Preserved Downstream updates on next cycle
ALTER DYNAMIC TABLE ... REFRESH Immediately updated New entry added May trigger downstream refresh
DROP DYNAMIC TABLE GONE GONE (available in ACCOUNT_USAGE) Downstream DTs FAIL on next refresh
DROP source table DT data preserved (stale) Preserved DT refresh FAILS
ALTER source table (add/drop column) DT refreshes normally if query still valid Preserved No impact if DT query doesn't use changed columns
TRUNCATE source table Next refresh produces empty DT (no source rows) Preserved Downstream DTs also become empty
CREATE OR REPLACE is Destructive: It resets ALL data and history. The DT reinitializes from scratch. If you only need to change lag/warehouse, use ALTER instead.

3. Refresh Edge Cases

ScenarioWhat HappensRisk
Refresh takes longer than target lag DT exceeds lag temporarily. Snowflake logs it. Next refresh starts after completion. Temporary staleness
Warehouse suspended during refresh Won't happen mid-query (warehouse stays active during execution). But if warehouse is dropped: failure. Safe during execution
Warehouse too small (OOM / timeout) Refresh fails. Retries on next cycle. May persistently fail if query needs more resources. Persistent failure
Source data has billions of new rows Incremental: processes only new rows (fast). Full: re-scans everything (slow, may exceed lag). Depends on refresh mode
DT query references CURRENT_TIMESTAMP() Forces FULL refresh mode. Result changes every execution regardless of source changes. Expensive
Concurrent refreshes on shared warehouse Multiple DTs queue on same warehouse. May slow each other down. Performance contention
Source table renamed DT refresh FAILS — DT references original table name in its query definition. Breaking change
DT with DOWNSTREAM lag but no downstream consumer DT never refreshes. It stays at creation state forever until a downstream DT with time-based lag references it. Stale indefinitely
INITIALIZE = ON_SCHEDULE but warehouse suspended DT stays empty until warehouse is available for the first scheduled refresh. Empty DT until warehouse resumes

4. Dependency & Pipeline Edge Cases

ScenarioWhat Happens
Circular dependency (DT_A reads DT_B, DT_B reads DT_A) ERROR at creation time. Snowflake detects cycles and prevents them.
Upstream DT refresh fails Downstream DTs use the last successful state of upstream. They don't fail — they just see stale data.
Upstream DT is SUSPENDED Downstream DTs still refresh, but use upstream's stale (last refreshed) data.
Upstream DT is DROPPED Downstream DTs FAIL on next refresh (source object missing).
All DTs in chain use DOWNSTREAM Nothing refreshes ever. At least one DT must have a time-based lag to drive the chain.
Fan-out: One source → Multiple DTs Normal. Each DT refreshes independently based on its own target lag.
Fan-in: Multiple sources → One DT Normal. DT refreshes when ANY source changes (within lag window).
Cross-database DT pipeline Supported. DTs can reference objects in other databases (with privileges).
DT reads from a view whose underlying table is dropped Refresh FAILS — view query can't resolve.
Key Difference from Tasks: When an upstream DT fails, downstream DTs DON'T fail — they just use stale data. In a Task DAG, predecessor failure causes downstream tasks to be SKIPPED entirely.

5. Other Edge Cases

ScenarioWhat Happens
CLONE a Dynamic Table Clone is also a DT with same definition. Has independent refresh schedule. Gets a snapshot of data at clone time.
Time Travel on a DT Supported. Query historical states within DATA_RETENTION period.
UNDROP DYNAMIC TABLE Supported. Restores the DT with its definition and resumes scheduling.
Masking policy on DT column Works normally. Policy applies to query results from the DT.
Row access policy on DT Works normally. Filters rows when users query the DT.
DT query uses LIMIT clause Caution. Result may be non-deterministic (different rows each refresh). Forces FULL mode.
DT query uses SAMPLE/TABLESAMPLE Forces FULL refresh. Non-deterministic — different sample each time.
Schema evolution (source adds column used in DT) DT query references fixed columns. New column not automatically included. Must CREATE OR REPLACE to add it.
Ownership transfer DT continues refreshing under new owner. Does NOT auto-suspend (unlike tasks).
DT in a Data Share (consumer queries) Consumer sees materialized data. Freshness depends on provider's target lag. Consumer cannot alter refresh.

6. Recovery Playbook

Scenario A: DT Refresh Persistently Failing

-- 1. Identify the error
SELECT NAME, STATE, STATE_MESSAGE, REFRESH_START_TIME
FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLE_REFRESH_HISTORY(NAME => 'MY_DT'))
WHERE STATE = 'FAILED'
ORDER BY REFRESH_START_TIME DESC LIMIT 5;

-- 2. Common causes and fixes:
-- "Object does not exist" → source table dropped/renamed
-- "Insufficient privileges" → permission revoked from DT owner role
-- "Warehouse does not exist" → warehouse dropped

-- 3. Fix root cause, then force refresh to verify
ALTER DYNAMIC TABLE my_dt REFRESH;

-- 4. Verify success
SELECT STATE FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLE_REFRESH_HISTORY(NAME => 'MY_DT'))
ORDER BY REFRESH_START_TIME DESC LIMIT 1;

Scenario B: Need to Change DT Query (Schema Evolution)

-- Cannot ALTER the query. Must CREATE OR REPLACE.
-- WARNING: This resets all data and history!

-- 1. Document current state
SELECT DATA_TIMESTAMP FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLES())
WHERE NAME = 'MY_DT';

-- 2. Warn downstream consumers (DT will be empty briefly)

-- 3. Recreate with new query
CREATE OR REPLACE DYNAMIC TABLE my_dt
  TARGET_LAG = '10 minutes'
  WAREHOUSE = transform_wh
AS
  SELECT ... new query with added column ...;

-- 4. DT reinitializes (full compute). Downstream DTs see fresh data once complete.
-- If INITIALIZE = ON_CREATE (default): starts immediately
-- If using INITIALIZE = ON_SCHEDULE: will be empty until first refresh

Scenario C: DT Exceeding Target Lag (Data Too Stale)

-- 1. Check how stale
SELECT NAME, DATA_TIMESTAMP, TARGET_LAG,
       DATEDIFF(minute, DATA_TIMESTAMP, CURRENT_TIMESTAMP()) AS actual_lag_min
FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLES())
WHERE NAME = 'MY_DT';

-- 2. Check if refresh is slow
SELECT AVG(DATEDIFF(second, REFRESH_START_TIME, REFRESH_END_TIME)) AS avg_refresh_sec
FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLE_REFRESH_HISTORY(NAME => 'MY_DT'))
WHERE REFRESH_START_TIME > DATEADD(day, -1, CURRENT_TIMESTAMP());

-- 3. Solutions:
-- a) Increase warehouse size
ALTER DYNAMIC TABLE my_dt SET WAREHOUSE = larger_wh;

-- b) Increase target lag (accept more staleness)
ALTER DYNAMIC TABLE my_dt SET TARGET_LAG = '30 minutes';

-- c) Optimize query for incremental refresh (remove non-deterministic functions)

-- d) Force immediate refresh
ALTER DYNAMIC TABLE my_dt REFRESH;

Scenario D: Source Table Dropped (Pipeline Broken)

-- 1. DT refresh is failing with "object does not exist"

-- 2. Option A: UNDROP the source (within Time Travel)
UNDROP TABLE source_table;
-- DT will auto-recover on next refresh cycle

-- 3. Option B: Source is gone permanently — recreate DT
-- First recreate or point to new source
CREATE OR REPLACE DYNAMIC TABLE my_dt
  TARGET_LAG = '10 minutes'
  WAREHOUSE = transform_wh
AS SELECT ... FROM new_source_table ...;

-- 4. All downstream DTs will refresh with new data on next cycle

Scenario E: Cost Runaway (DT Refresh Too Expensive)

-- 1. Check refresh frequency and duration
SELECT NAME,
       COUNT(*) AS refreshes_24h,
       SUM(DATEDIFF(second, REFRESH_START_TIME, REFRESH_END_TIME)) AS total_sec
FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLE_REFRESH_HISTORY())
WHERE REFRESH_START_TIME > DATEADD(day, -1, CURRENT_TIMESTAMP())
GROUP BY NAME ORDER BY total_sec DESC;

-- 2. Solutions:
-- a) Increase target lag (fewer refreshes)
ALTER DYNAMIC TABLE expensive_dt SET TARGET_LAG = '1 hour';

-- b) Use smaller warehouse
ALTER DYNAMIC TABLE expensive_dt SET WAREHOUSE = smaller_wh;

-- c) Use DOWNSTREAM for intermediate DTs
ALTER DYNAMIC TABLE middle_dt SET TARGET_LAG = 'DOWNSTREAM';

-- d) Suspend during off-hours (manual cost control)
ALTER DYNAMIC TABLE expensive_dt SUSPEND;
-- Resume during business hours
ALTER DYNAMIC TABLE expensive_dt RESUME;

7. Exam Scenario Questions

ScenarioCorrect Answer
"A DT has TARGET_LAG = '5 minutes' but refresh takes 8 minutes. What happens?" DT temporarily exceeds target lag. Snowflake logs it and tries again after completion. No failure or drop.
"An upstream DT fails to refresh. Do downstream DTs also fail?" NO. Downstream DTs still refresh using the upstream's last successful state (stale but functional). Unlike Tasks where failure cascades.
"All DTs in a pipeline have TARGET_LAG = DOWNSTREAM. What happens?" Nothing refreshes. At least one DT must have a time-based lag to drive the refresh chain.
"Can you INSERT INTO a Dynamic Table?" NO. DTs are strictly read-only. Only the defining SELECT query populates them during refresh.
"A source table has no changes for 3 hours. DT has TARGET_LAG = '10 minutes'. How many refreshes happen?" Zero (or minimal). Snowflake detects no source changes and skips unnecessary refreshes.
"How do you change a DT's underlying SELECT query?" Must use CREATE OR REPLACE DYNAMIC TABLE. Cannot ALTER the query. This resets all data and history.
"A DT uses CURRENT_DATE() in its query. What refresh mode?" FULL refresh mode. Non-deterministic functions prevent incremental refresh.
"Can a DT read from a temporary table?" NO. Temporary tables are session-scoped. DTs persist across sessions and need persistent sources.
"Does ownership transfer auto-suspend a DT (like tasks)?" NO. DTs continue refreshing under the new owner. Tasks auto-suspend on ownership transfer, but DTs do not.
"DT warehouse is dropped. What happens?" DT refresh fails until a new warehouse is assigned via ALTER DYNAMIC TABLE ... SET WAREHOUSE.
Top 5 DT Exam Traps:
  1. DTs are READ-ONLY — no INSERT/UPDATE/DELETE/MERGE/COPY INTO
  2. Upstream DT failure does NOT cascade (unlike task DAGs)
  3. DOWNSTREAM means "no self-refresh" — needs a time-based downstream driver
  4. Source table RENAME breaks DTs (query references original name)
  5. Non-deterministic functions force FULL refresh (expensive)
