1. What Are Iceberg Tables?

The Core Concept

Apache Iceberg is an open table format for large analytic datasets. Snowflake Iceberg Tables store data in Iceberg format (Parquet data files + Iceberg metadata) on your own cloud storage (S3, Azure Blob, GCS), while Snowflake provides the compute engine to query and manage them.

Think of it as: Your storage + Snowflake's compute + Open format = No vendor lock-in

Key Value Propositions

  • Open format: Data stored in Parquet — readable by Spark, Trino, Flink, Dremio, and others
  • No vendor lock-in: Your data lives on YOUR cloud storage account
  • Interoperability: Multiple engines can read/write the same data
  • Full Snowflake features: Time Travel, RBAC, governance, joins with native tables
  • Cost savings: Store once on cheap object storage, query with Snowflake or other engines

2. Why Iceberg? (The Problem It Solves)

Problem with Traditional Data LakesHow Iceberg Solves It
No ACID transactions (corrupt reads during writes) Iceberg provides snapshot isolation and atomic commits
No schema evolution (changing columns breaks everything) Iceberg supports add/rename/drop columns safely
No Time Travel (can't query historical data) Iceberg maintains snapshot history for time travel
File-level scanning (read all files to find rows) Iceberg metadata enables partition pruning and file-level skipping
Vendor lock-in (Snowflake native = Snowflake only) Open Parquet format readable by any engine
No UPDATE/DELETE on data lakes (append-only) Iceberg supports row-level updates and deletes via merge-on-read or copy-on-write

3. Apache Iceberg Architecture

The Three-Layer Metadata Structure

┌─────────────────────────────────────┐
│         CATALOG (pointer)           │  → Points to current metadata file
├─────────────────────────────────────┤
│       METADATA FILE (.json)         │  → Schema, partition spec, snapshots list
│  ┌─────────────────────────────┐    │
│  │    SNAPSHOT → Manifest List │    │  → Each snapshot = state of table at a point in time
│  └─────────────────────────────┘    │
├─────────────────────────────────────┤
│        MANIFEST LIST (.avro)        │  → List of manifest files for this snapshot
├─────────────────────────────────────┤
│      MANIFEST FILES (.avro)         │  → Tracks individual data files + stats (min/max/count)
├─────────────────────────────────────┤
│        DATA FILES (.parquet)        │  → Actual row data in columnar Parquet format
└─────────────────────────────────────┘

Key Components

ComponentFormatPurpose
CatalogExternal (Glue, REST, Snowflake)Root pointer to current metadata location. "Where is this table?"
Metadata FileJSONSchema definition, partition spec, properties, snapshot history
Manifest ListAvroList of manifest files for a given snapshot
Manifest FileAvroTracks data files with column-level stats (min, max, null count)
Data FilesParquet (or ORC/Avro)Actual table data in columnar format
Why This Matters for Queries: Snowflake reads the metadata to figure out WHICH data files contain relevant rows (file pruning). If your query filters on WHERE date = '2026-08-15', Snowflake skips files that don't contain that date — without scanning them.

4. Snowflake-Managed vs Externally-Managed

Two Ways to Use Iceberg in Snowflake

Snowflake supports two operational modes for Iceberg tables. The key difference is: who manages the Iceberg metadata and catalog?

AspectSnowflake-Managed IcebergExternally-Managed Iceberg
Who writes data?Snowflake (full read/write)External engine (Spark, etc.)
Who manages catalog?Snowflake (internal)External catalog (AWS Glue, REST, Polaris)
Snowflake accessFull DML: INSERT, UPDATE, DELETE, MERGEREAD-ONLY (cannot write)
Data locationYour external volume (S3/Azure/GCS)Your external storage (managed by external catalog)
Time TravelYES (Snowflake manages snapshots)LIMITED (depends on external catalog snapshot retention)
ClusteringYESNO (Snowflake doesn't control physical layout)
Use caseSnowflake is primary engine but want open format for portabilitySpark/Flink writes data, Snowflake reads for analytics
InteroperabilityOther engines can read (Parquet files are open)Full multi-engine read/write via shared catalog
Catalog integrationNot neededREQUIRED (AWS Glue, Polaris, REST, etc.)
External volumeREQUIREDREQUIRED
When to Choose:
  • Snowflake-Managed: Snowflake is your primary write engine. You want open format for future portability or compliance, but Snowflake handles day-to-day operations.
  • Externally-Managed: Another engine (Spark, Flink) writes the data. You use Snowflake for querying/analytics on that same data without copying it.

5. External Volumes

What is an External Volume?

An External Volume is a Snowflake object that defines WHERE Iceberg data files and metadata are stored. It points to a cloud storage location (S3 bucket, Azure container, GCS bucket) and includes the IAM/access configuration.

Creating External Volumes

-- AWS S3 External Volume
CREATE OR REPLACE EXTERNAL VOLUME my_s3_volume
  STORAGE_LOCATIONS = (
    (
      NAME = 'my-s3-location'
      STORAGE_BASE_URL = 's3://my-bucket/iceberg-data/'
      STORAGE_PROVIDER = 'S3'
      STORAGE_AWS_ROLE_ARN = 'arn:aws:iam::123456789012:role/snowflake-iceberg-role'
    )
  );

-- Azure External Volume
CREATE OR REPLACE EXTERNAL VOLUME my_azure_volume
  STORAGE_LOCATIONS = (
    (
      NAME = 'my-azure-location'
      STORAGE_BASE_URL = 'azure://myaccount.blob.core.windows.net/iceberg-container/'
      STORAGE_PROVIDER = 'AZURE'
      AZURE_TENANT_ID = 'your-tenant-id'
    )
  );

-- GCS External Volume
CREATE OR REPLACE EXTERNAL VOLUME my_gcs_volume
  STORAGE_LOCATIONS = (
    (
      NAME = 'my-gcs-location'
      STORAGE_BASE_URL = 'gcs://my-gcs-bucket/iceberg-data/'
      STORAGE_PROVIDER = 'GCS'
    )
  );

-- Verify external volume
DESC EXTERNAL VOLUME my_s3_volume;

External Volume Requirements

CloudAccess MethodPermissions Needed
AWS S3IAM Role (cross-account trust)s3:GetObject, s3:PutObject, s3:DeleteObject, s3:ListBucket
Azure BlobService Principal + Tenant IDStorage Blob Data Contributor role on container
GCSService Accountstorage.objects.* on bucket
For Snowflake-Managed Iceberg: The external volume needs WRITE permissions (PutObject, DeleteObject) because Snowflake writes data files and metadata. For externally-managed: READ permissions may suffice (GetObject, ListBucket).

6. Creation Syntax & Examples

Snowflake-Managed Iceberg Table

-- Create a Snowflake-managed Iceberg table
CREATE OR REPLACE ICEBERG TABLE sales_iceberg (
    sale_id INT,
    product_name VARCHAR(100),
    quantity INT,
    unit_price DECIMAL(10,2),
    sale_date DATE,
    region VARCHAR(50)
)
  CATALOG = 'SNOWFLAKE'               -- Snowflake manages the catalog
  EXTERNAL_VOLUME = 'my_s3_volume'    -- Where to store data
  BASE_LOCATION = 'sales/'            -- Subdirectory within external volume
;

-- Insert data (full DML supported!)
INSERT INTO sales_iceberg VALUES
  (1, 'Laptop', 2, 999.99, '2026-08-15', 'US-West'),
  (2, 'Monitor', 1, 499.99, '2026-08-15', 'EU-North');

-- UPDATE works!
UPDATE sales_iceberg SET quantity = 3 WHERE sale_id = 1;

-- DELETE works!
DELETE FROM sales_iceberg WHERE sale_id = 2;

-- MERGE works!
MERGE INTO sales_iceberg t
USING staging s ON t.sale_id = s.sale_id
WHEN MATCHED THEN UPDATE SET t.quantity = s.quantity
WHEN NOT MATCHED THEN INSERT VALUES (s.*);

Externally-Managed Iceberg Table (Read-Only in Snowflake)

-- First: Create a catalog integration
CREATE OR REPLACE CATALOG INTEGRATION glue_catalog_int
  CATALOG_SOURCE = GLUE
  CATALOG_NAMESPACE = 'my_database'
  TABLE_FORMAT = ICEBERG
  GLUE_AWS_ROLE_ARN = 'arn:aws:iam::123456789012:role/glue-access'
  GLUE_CATALOG_ID = '123456789012'
  GLUE_REGION = 'us-east-1'
  ENABLED = TRUE;

-- Create externally-managed Iceberg table
CREATE OR REPLACE ICEBERG TABLE external_events
  EXTERNAL_VOLUME = 'my_s3_volume'
  CATALOG = 'glue_catalog_int'             -- Points to Glue catalog
  CATALOG_TABLE_NAME = 'events'            -- Table name in Glue
  -- AUTO_REFRESH = TRUE                   -- Optional: auto-detect new snapshots
;

-- Query (READ-ONLY — cannot INSERT/UPDATE/DELETE)
SELECT * FROM external_events WHERE event_date = '2026-08-15';

-- Refresh metadata manually (detect new data written by Spark)
ALTER ICEBERG TABLE external_events REFRESH;

Convert Native Table to Iceberg

-- Convert an existing Snowflake native table to Iceberg format
ALTER TABLE my_native_table
  CONVERT TO ICEBERG
  EXTERNAL_VOLUME = 'my_s3_volume'
  BASE_LOCATION = 'converted/my_table/'
  CATALOG = 'SNOWFLAKE';

7. Iceberg Tables vs Native Tables vs External Tables

AspectNative Snowflake TableIceberg Table (Snowflake-Managed)External Table
Data formatSnowflake proprietary (FDN)Open Parquet + Iceberg metadataAny (CSV, JSON, Parquet on stage)
Storage locationSnowflake-managed storageYOUR cloud storage (external volume)YOUR cloud storage (stage)
DML supportFull (INSERT, UPDATE, DELETE, MERGE)Full (Snowflake-managed) / Read-only (external)READ-ONLY (no DML)
Time TravelYES (1-90 days)YES (Snowflake-managed) / Limited (external)NO
Fail-safeYES (7 days)NONO
ClusteringYESYES (Snowflake-managed only)NO
PerformanceFASTEST (optimized storage format)Fast (Parquet + metadata pruning)SLOWEST (no optimization)
InteroperabilitySnowflake onlyAny Iceberg-compatible engineFiles accessible to any tool
GovernanceFull (masking, RAP, tags)Full (same as native)Limited
CostSnowflake storage billingYOUR cloud storage cost (cheaper)YOUR cloud storage cost
Vendor lock-inHIGH (proprietary format)LOW (open format)LOW (raw files)
Decision Guide:
  • Native table: Maximum performance, don't need interoperability, okay with Snowflake lock-in
  • Iceberg (Snowflake-managed): Want open format + Snowflake features + cost savings on storage + portability
  • Iceberg (externally-managed): Other engines write data, Snowflake reads for analytics
  • External table: Simple file-based access, no schema enforcement needed, minimal Snowflake features

9. Limitations (15 Key Points)

#LimitationDetail / Workaround
1No Fail-safeIceberg tables do NOT have Snowflake's 7-day fail-safe period. Time Travel is available but no post-TT safety net.
2Performance gap vs nativeParquet format is slightly slower to query than Snowflake's optimized FDN format. ~10-20% overhead for most queries.
3External volume requiredMust set up cloud storage + IAM permissions before creating Iceberg tables. More setup than native tables.
4Externally-managed = read-onlyCannot INSERT/UPDATE/DELETE into externally-managed Iceberg tables from Snowflake.
5No materialized views on IcebergCannot create materialized views on Iceberg tables.
6Limited search optimizationSearch Optimization Service (SOS) support may be limited for Iceberg tables.
7Metadata refresh lag (external)Externally-managed tables need REFRESH to detect new data. Not instant.
8Storage costs are separateYou pay your cloud provider for storage (not included in Snowflake billing). Must manage lifecycle yourself.
9No temporary/transient IcebergIceberg tables are always permanent. Cannot be temporary or transient.
10Catalog integration complexitySetting up Glue/REST/Polaris catalogs requires cross-service IAM configuration.
11Partition evolution complexityWhile supported, changing partitions on large tables can create mixed-format state.
12Cross-cloud limitationsExternal volume must be in same cloud/region as Snowflake account for optimal performance.
13No VARIANT columnsIceberg tables use Iceberg schema types. Snowflake VARIANT must be mapped to Iceberg struct/list/map types.
14Clone limitationsCloning Iceberg tables creates a new table but still references same underlying data files until modified.
15Compaction managementSnowflake-managed handles compaction automatically, but externally-managed tables need external compaction.
The Big Trade-off: Iceberg tables give you openness and portability at the cost of slightly reduced performance and no fail-safe. For most analytics workloads the performance difference is negligible, but for latency-sensitive dashboards hitting large tables, native format may still be better.
