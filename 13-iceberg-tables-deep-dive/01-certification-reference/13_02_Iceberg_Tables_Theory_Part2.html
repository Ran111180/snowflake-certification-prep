1. Catalog Integrations

Why Do You Need a Catalog?

An Iceberg catalog is a registry that tracks which tables exist and where their current metadata file lives. For externally-managed tables, Snowflake needs a catalog integration to find and read tables managed by other engines.

Supported Catalog Types

CatalogProviderUse CaseIntegration Type
AWS GlueAWSSpark on EMR/Glue writes Iceberg → Snowflake readsCATALOG_SOURCE = GLUE
Snowflake Open Catalog (Polaris)SnowflakeMulti-engine access with centralized governanceCATALOG_SOURCE = POLARIS
REST CatalogAny (Tabular, custom)Standard Iceberg REST API catalogCATALOG_SOURCE = ICEBERG_REST
Object StorageAny cloudDirect path to metadata.json (no catalog server)CATALOG_SOURCE = OBJECT_STORE
Unity CatalogDatabricksDatabricks manages tables → Snowflake readsVia REST catalog API

Creating Catalog Integrations

-- AWS Glue Catalog Integration
CREATE OR REPLACE CATALOG INTEGRATION glue_int
  CATALOG_SOURCE = GLUE
  CATALOG_NAMESPACE = 'my_glue_database'
  TABLE_FORMAT = ICEBERG
  GLUE_AWS_ROLE_ARN = 'arn:aws:iam::123456789:role/snowflake-glue-access'
  GLUE_CATALOG_ID = '123456789012'
  GLUE_REGION = 'us-east-1'
  ENABLED = TRUE;

-- REST Catalog Integration (Polaris, Tabular, etc.)
CREATE OR REPLACE CATALOG INTEGRATION rest_int
  CATALOG_SOURCE = ICEBERG_REST
  TABLE_FORMAT = ICEBERG
  CATALOG_URI = 'https://my-polaris-server.com/api/catalog'
  WAREHOUSE = 'my_warehouse_in_catalog'
  ENABLED = TRUE;

-- Object Store (direct metadata path — simplest, no catalog server)
CREATE OR REPLACE CATALOG INTEGRATION object_store_int
  CATALOG_SOURCE = OBJECT_STORE
  TABLE_FORMAT = ICEBERG
  ENABLED = TRUE;

-- Using Object Store: point directly to metadata
CREATE ICEBERG TABLE my_table
  EXTERNAL_VOLUME = 'my_volume'
  CATALOG = 'object_store_int'
  METADATA_FILE_PATH = 'path/to/metadata/v1.metadata.json';

2. Snowflake Open Catalog (Polaris)

What is Polaris?

Polaris (now "Snowflake Open Catalog") is Snowflake's open-source Iceberg catalog implementation. It provides a central place to manage Iceberg tables that can be accessed by Snowflake, Spark, Trino, Flink, and other engines — all with centralized access control.

Polaris Key Features

  • Open-source: Apache 2.0 licensed — no vendor lock-in for the catalog itself
  • Multi-engine: Any Iceberg REST-compatible engine can connect
  • Centralized access control: One place to manage who can read/write which tables
  • Managed by Snowflake: Available as a managed service within Snowflake
  • Namespace hierarchy: Organize tables in catalogs → namespaces → tables

Common Multi-Engine Pattern

-- Pattern: Spark writes, Snowflake reads
-- 
-- 1. Spark job writes Iceberg table to S3 (registered in Glue)
-- 2. Snowflake has catalog integration pointing to Glue
-- 3. Snowflake queries the same data without copying
--
-- Spark (PySpark):

-- Snowflake:
SELECT * FROM external_events  -- reads same Parquet files

-- Refresh if Spark wrote new data

4. Performance & Optimization

Performance Factors

FactorImpactOptimization
File sizeToo many small files = overhead; too few large = poor pruningTarget 100-250MB per Parquet file
Partition strategyGood partitioning enables file skippingPartition by date or high-cardinality filter columns
Clustering (Snowflake-managed)Physical sort order for common query patternsCLUSTER BY frequently-filtered columns
Metadata overheadMany manifest files = slow planningCompact metadata periodically
Cross-region accessStorage in different region = high latency + egress costsKeep external volume in same region as Snowflake
File formatParquet is columnar = good for analytics, bad for point lookupsUse native tables for OLTP-style queries

Optimization SQL

-- Add clustering to Snowflake-managed Iceberg table
ALTER ICEBERG TABLE my_iceberg_table CLUSTER BY (sale_date, region);

-- Check clustering depth
SELECT SYSTEM$CLUSTERING_INFORMATION('my_iceberg_table', '(sale_date, region)');

-- Manual compaction (for Snowflake-managed)
-- Snowflake handles this automatically, but you can influence via clustering

-- For externally-managed: compaction must happen in the source engine (Spark)

Governance Features on Iceberg Tables

-- Masking policy (works same as native tables)
ALTER ICEBERG TABLE customer_iceberg
  MODIFY COLUMN email SET MASKING POLICY email_mask;

-- Row Access Policy
ALTER ICEBERG TABLE sales_iceberg
  ADD ROW ACCESS POLICY region_filter ON (region);

-- Tags
ALTER ICEBERG TABLE customer_iceberg
  SET TAG pii_classification = 'SENSITIVE';

-- Data sharing (Iceberg tables can be shared!)
GRANT SELECT ON ICEBERG TABLE analytics_iceberg TO SHARE my_share;

6. Production Architecture Patterns

Pattern 1: Lakehouse (Snowflake-Managed)

-- All data in open format, Snowflake as primary engine
-- Benefit: Portability + full Snowflake features

-- Raw layer (Snowpipe loads into Iceberg)
CREATE ICEBERG TABLE raw_events (...)
  CATALOG = 'SNOWFLAKE'
  EXTERNAL_VOLUME = 'my_vol'
  BASE_LOCATION = 'raw/events/';

CREATE PIPE raw_events_pipe AS
  COPY INTO raw_events FROM @event_stage;

-- Transform layer (DT reads from Iceberg)
CREATE DYNAMIC TABLE clean_events
  TARGET_LAG = '5 minutes'
  WAREHOUSE = transform_wh
AS SELECT ... FROM raw_events WHERE ...;

-- Serve layer (Iceberg for portability)
CREATE ICEBERG TABLE reporting_events (...)
  CATALOG = 'SNOWFLAKE'
  EXTERNAL_VOLUME = 'my_vol'
  BASE_LOCATION = 'gold/reporting/';

Pattern 2: Multi-Engine Data Lake

-- Spark writes, Snowflake reads (shared Glue catalog)
-- Benefit: Best-of-breed engines for different workloads

-- Spark handles: streaming ingestion, ML training data prep
-- Snowflake handles: ad-hoc analytics, dashboards, governance

-- In Snowflake:
CREATE ICEBERG TABLE ml_features
  EXTERNAL_VOLUME = 'shared_vol'
  CATALOG = 'glue_int'
  CATALOG_TABLE_NAME = 'ml_features';

-- Analytics team queries in Snowflake
SELECT * FROM ml_features
WHERE feature_date >= DATEADD(day, -7, CURRENT_DATE());

-- ML team reads same data in Spark
-- spark.read.format("iceberg").load("glue.ml_features")

Pattern 3: Hybrid (Native + Iceberg)

-- Critical performance tables: NATIVE (fastest queries)
-- Archival/shared tables: ICEBERG (open format, cheaper storage)

-- Hot data: Native Snowflake table (maximum performance)
CREATE TABLE active_orders (...);  -- Last 30 days

-- Cold data: Iceberg on cheap storage
CREATE ICEBERG TABLE historical_orders (...)
  CATALOG = 'SNOWFLAKE'
  EXTERNAL_VOLUME = 'archive_vol'
  BASE_LOCATION = 'archive/orders/';

-- Query across both seamlessly
SELECT * FROM active_orders
UNION ALL
SELECT * FROM historical_orders
WHERE order_date BETWEEN '2025-01-01' AND '2025-12-31';

7. Monitoring & Operations

-- List all Iceberg tables
SHOW ICEBERG TABLES;

-- Describe table details
DESC ICEBERG TABLE my_iceberg_table;

-- Check external volume
DESC EXTERNAL VOLUME my_vol;

-- View table metadata (snapshots, manifests)
SELECT * FROM TABLE(INFORMATION_SCHEMA.ICEBERG_TABLE_METADATA(
  TABLE_NAME => 'MY_ICEBERG_TABLE'
));

-- Check storage footprint
SELECT TABLE_NAME, ACTIVE_BYTES, TIME_TRAVEL_BYTES
FROM INFORMATION_SCHEMA.TABLE_STORAGE_METRICS
WHERE TABLE_CATALOG = 'MY_DB'
  AND TABLE_SCHEMA = 'MY_SCHEMA'
  AND TABLE_NAME = 'MY_ICEBERG_TABLE';

-- For externally-managed: check last refresh time
SHOW ICEBERG TABLES LIKE 'external%';
-- Look at: last_refreshed_at, catalog_sync_status

8. Best Practices

Production Checklist:
  1. Same region: Keep external volume in the same cloud region as your Snowflake account
  2. File sizing: Target 100-250MB Parquet files for optimal query performance
  3. Partition wisely: Partition by date/time for time-series data; by region for geo data
  4. Use CLUSTER BY: For Snowflake-managed tables, add clustering on frequently-filtered columns
  5. Set up AUTO_REFRESH: For externally-managed tables, enable auto-refresh to detect new snapshots
  6. Monitor storage costs: You manage cloud storage lifecycle (retention, tiering) — not Snowflake
  7. Separate volumes by environment: dev/staging/prod should use different external volumes
  8. Test interoperability: Verify other engines (Spark, Trino) can read your Snowflake-managed Iceberg data
  9. Document catalog strategy: Team should agree on one catalog (Glue, Polaris, or Snowflake internal)
  10. Plan for schema evolution: Use ADD COLUMN / RENAME instead of CREATE OR REPLACE when possible
