2. DDL Impact

OperationData Files on StorageMetadataNotes
CREATE OR REPLACE ICEBERG TABLE Old files may remain on storage Reset New table starts fresh. Old Parquet files may linger (orphaned) on your storage.
DROP ICEBERG TABLE Files remain on storage (not auto-deleted) Removed from Snowflake You must manually clean up orphaned files from your external volume.
UNDROP TABLE Files still there Restored Works within Time Travel retention (Snowflake-managed only).
ALTER TABLE ADD COLUMN No file rewrite Schema evolution Iceberg's schema evolution — existing files unchanged, new column = NULL for old rows.
ALTER TABLE DROP COLUMN No file rewrite Updated Column hidden from metadata. Old files still contain the data (not physically removed).
ALTER TABLE RENAME COLUMN No file rewrite Updated Metadata-level rename. Data files unchanged.
TRUNCATE TABLE Old files become orphaned New empty snapshot Table is empty. Old data files still on storage until compaction/cleanup.
ALTER TABLE CONVERT TO ICEBERG Data migrated to external volume as Parquet Iceberg metadata created One-way conversion. Cannot convert back to native.
Orphaned Files: Unlike native tables, Iceberg table operations (DROP, TRUNCATE, UPDATE/DELETE) can leave orphaned Parquet files on your storage. These don't auto-delete. You must manage storage lifecycle (cloud bucket policies or manual cleanup).

3. Storage & External Volume Edge Cases

ScenarioWhat HappensFix
Storage bucket deleted All data LOST. Queries fail. No recovery possible from Snowflake side. Restore from cloud backup/versioning if enabled. This is YOUR responsibility.
IAM role permissions revoked All queries fail with access denied. DML fails. Re-grant permissions to the IAM role referenced in external volume.
Storage in different region than Snowflake Works but SLOW (cross-region latency) + egress charges. Move data to same region or accept the cost/latency trade-off.
Storage encryption key rotated Old files become unreadable if previous key not retained. Use cloud KMS with key rotation that retains old versions.
External volume dropped while table exists Iceberg table becomes non-functional. Queries fail. Recreate external volume with same name/config, or drop and recreate table.
Cloud lifecycle policy deletes old files Time Travel fails for snapshots that referenced deleted files. Set lifecycle retention longer than Iceberg snapshot retention.
Concurrent writes from Snowflake + external engine CONFLICT. Snowflake-managed Iceberg should NOT have external writers. Use externally-managed mode if multiple writers exist. One writer per mode.
Storage full / quota exceeded Write operations fail. Reads still work (existing data). Increase storage quota or clean up orphaned files.

4. Catalog & Metadata Edge Cases

ScenarioWhat HappensFix
Glue catalog table deleted externally Snowflake's externally-managed table becomes stale/fails on refresh. Recreate in Glue, or drop the Snowflake table.
External engine changes schema (add column) After REFRESH, new column appears in Snowflake. Auto schema evolution. No fix needed — Iceberg handles this gracefully.
External engine drops column After REFRESH, column disappears from Snowflake's view. Update any queries that referenced the dropped column.
Catalog integration credentials expire REFRESH and AUTO_REFRESH fail. Existing cached data still queryable (stale). Update the catalog integration with new credentials.
METADATA_FILE_PATH becomes invalid Table becomes unqueryable. All operations fail. Update the metadata file path: ALTER ICEBERG TABLE ... SET METADATA_FILE_PATH = '...'
Catalog and storage out of sync Catalog points to metadata that references missing/moved files. Run table maintenance in the external engine (Spark rewrite_data_files).
Multiple Snowflake accounts reading same external table Safe for reads. Each account has independent catalog integration. No issue — concurrent readers are fine.

5. Interoperability Edge Cases

ScenarioWhat Happens
Spark reads Snowflake-managed Iceberg directly from storage Works. Parquet files are standard. Spark can read them with Iceberg connector pointed at the metadata.
Spark writes to a Snowflake-managed Iceberg table CONFLICT. Snowflake manages the catalog. External writes bypass Snowflake's tracking. Data corruption possible.
Iceberg V2 features used by external engine Snowflake supports Iceberg V2 (row-level deletes, equality deletes). Most features work across engines.
Data types not supported in Snowflake If external engine uses Iceberg types without Snowflake mapping, those columns may show as unsupported.
Sort order (Iceberg SortOrder) set by external engine Snowflake respects file-level sort for pruning but doesn't enforce sort order on its own writes.
Partition spec changed externally Snowflake handles partition evolution. After REFRESH, new partition spec is visible.

6. Recovery Playbook

Scenario A: Accidental DROP TABLE (Snowflake-Managed)

-- 1. UNDROP if within Time Travel retention
UNDROP TABLE my_iceberg_table;

-- 2. If beyond Time Travel but files still on storage:
-- Files are still in the BASE_LOCATION on your external volume!
-- Recreate table pointing to same location
CREATE ICEBERG TABLE my_iceberg_table (...)
  CATALOG = 'SNOWFLAKE'
  EXTERNAL_VOLUME = 'my_vol'
  BASE_LOCATION = 'same/path/as/before/';
-- Note: Snowflake may need to rebuild metadata from data files

Scenario B: External Volume Permissions Broken

-- 1. Check the error
SELECT * FROM my_iceberg_table LIMIT 1;
-- Error: "Access denied to storage location"

-- 2. Verify external volume config
DESC EXTERNAL VOLUME my_vol;
-- Check the STORAGE_AWS_ROLE_ARN / Azure Tenant / GCS config

-- 3. Fix in cloud provider (re-grant IAM role permissions):
-- s3:GetObject, s3:PutObject, s3:DeleteObject, s3:ListBucket

-- 4. Test
SELECT * FROM my_iceberg_table LIMIT 1;  -- Should work now

Scenario C: Externally-Managed Table Shows Stale Data

-- Spark wrote new data but Snowflake still shows old data

-- 1. Manual refresh
ALTER ICEBERG TABLE my_external_table REFRESH;

-- 2. If using OBJECT_STORE, update metadata path
ALTER ICEBERG TABLE my_external_table
  SET METADATA_FILE_PATH = 'path/to/latest/v2.metadata.json';

-- 3. Enable AUTO_REFRESH for future updates
ALTER ICEBERG TABLE my_external_table SET AUTO_REFRESH = TRUE;

-- 4. Verify
SELECT COUNT(*) FROM my_external_table;  -- Should show new row count

Scenario D: Orphaned Files Consuming Storage

-- After many UPDATE/DELETE operations, old data files accumulate

-- For Snowflake-managed: Snowflake handles compaction automatically
-- But old snapshots' files may linger

-- Cloud-side cleanup options:
-- AWS: S3 Lifecycle policy to delete objects older than X days in base_location
-- Azure: Blob lifecycle management
-- GCS: Object Lifecycle Management

-- IMPORTANT: Don't delete files still referenced by active snapshots!
-- Wait for Snowflake to expire snapshots (controlled by DATA_RETENTION_TIME)

Scenario E: Convert Back from Iceberg to Native (Not Possible Directly)

-- There is NO ALTER TABLE ... CONVERT TO NATIVE command

-- Workaround: Copy data to a new native table
CREATE TABLE my_native_table AS
SELECT * FROM my_iceberg_table;

-- Drop the Iceberg table
DROP TABLE my_iceberg_table;

-- Rename native table
ALTER TABLE my_native_table RENAME TO my_iceberg_table;

-- Note: You lose Iceberg benefits (open format, portability)
-- but gain fail-safe and slightly better performance

7. Exam Scenario Questions

ScenarioCorrect Answer
"Can you UPDATE rows in an externally-managed Iceberg table?" NO. Externally-managed tables are READ-ONLY in Snowflake. Only the external engine can write.
"Do Iceberg tables have Snowflake fail-safe?" NO. Neither Snowflake-managed nor externally-managed Iceberg tables have fail-safe. Only Time Travel (if Snowflake-managed).
"What happens when you DROP an Iceberg table?" Snowflake removes its reference. Data files typically REMAIN on your external storage (not auto-deleted). You manage cleanup.
"Can Snowpipe load into an Iceberg table?" YES — but only Snowflake-managed Iceberg tables. Not externally-managed (read-only).
"Where is Iceberg table data actually stored?" On YOUR cloud storage (S3/Azure/GCS) in the external volume location. NOT on Snowflake's internal storage.
"Can you create a materialized view on an Iceberg table?" NO. Materialized views are not supported on Iceberg tables.
"What format is Iceberg data stored in?" Parquet (data files) + JSON (metadata) + Avro (manifests). All open formats.
"Can you convert an Iceberg table back to native Snowflake format?" NOT directly. There's no CONVERT TO NATIVE command. Must copy data to a new native table (CTAS).
"What is an external volume?" A Snowflake object that defines the cloud storage location (S3/Azure/GCS) and access credentials for Iceberg data.
"Can multiple engines write to the same Snowflake-managed Iceberg table?" NO. Only Snowflake should write to Snowflake-managed tables. For multi-writer, use externally-managed with a shared catalog.
Top 5 Iceberg Exam Traps:
  1. NO fail-safe for any Iceberg table type
  2. Externally-managed = STRICTLY read-only in Snowflake (no DML at all)
  3. Data lives on YOUR storage, not Snowflake's — you manage costs and lifecycle
  4. DROP TABLE does NOT auto-delete data files from your storage
  5. Cannot convert Iceberg back to native (one-way conversion)
