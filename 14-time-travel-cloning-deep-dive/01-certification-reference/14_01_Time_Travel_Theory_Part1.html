SnowPro Core High-Weight Topic

Exam Relevance: Heavily tested in SnowPro Core & Advanced exams (Data Protection & Continuity domain)

Date: August 15, 2026

1. What is Time Travel?

Time Travel enables accessing historical data (data that has been changed or deleted) at any point within a defined retention period. It is a powerful feature for data recovery, auditing, and analytical purposes.

Core Concept: Time Travel works because Snowflake uses immutable micro-partitions. When data changes, old partitions are not overwritten; they are retained for the retention period, allowing queries against prior states.

Time Travel Query Syntax

Snowflake provides two main clauses for querying historical data:

ClauseBehaviorDescription
ATInclusiveReturns data at or as of the specified point in time (includes the change)
BEFOREExclusiveReturns data immediately before the specified point (excludes the change)

Three Methods to Specify a Point in Time

MethodSyntaxDescription
TIMESTAMP AT(TIMESTAMP => '...') Specifies an exact date/time. Must be a valid timestamp expression.
OFFSET AT(OFFSET => -N) Specifies a relative time difference in seconds from the current time. Negative values go back in time.
STATEMENT BEFORE(STATEMENT => 'id') Uses a Query ID to reference the exact point before or at which a specific statement was executed.

Time Travel SQL Examples

-- Method 1: TIMESTAMP - Query data as it existed at a specific time
SELECT * FROM my_table
  AT(TIMESTAMP => '2026-08-14 10:00:00'::TIMESTAMP_LTZ);

-- Method 2: OFFSET - Query data as it was 5 minutes ago (300 seconds)
SELECT * FROM my_table
  AT(OFFSET => -300);

-- Method 3: OFFSET - Query data 1 hour ago
SELECT * FROM my_table
  AT(OFFSET => -3600);

-- Method 4: STATEMENT - Query data just before a specific query ran
SELECT * FROM my_table
  BEFORE(STATEMENT => '01abc123-0000-0000-0000-000000000001');

-- Method 5: AT with STATEMENT - Query data at the time a query completed
SELECT * FROM my_table
  AT(STATEMENT => '01abc123-0000-0000-0000-000000000001');

-- Using Time Travel with CREATE TABLE (cloning historical state)
CREATE TABLE my_table_restored CLONE my_table
  AT(TIMESTAMP => '2026-08-14 10:00:00'::TIMESTAMP_LTZ);

-- Using Time Travel in CTAS
CREATE TABLE my_backup AS
  SELECT * FROM my_table
  BEFORE(STATEMENT => '01abc123-0000-0000-0000-000000000001');
Exam Tip: The OFFSET value is in seconds (not minutes or hours). A value of -300 means 5 minutes ago. The offset must be negative to go back in time.
AT vs BEFORE with STATEMENT:
  • AT(STATEMENT => 'id') - Returns data after the statement completed (includes changes made by that statement)
  • BEFORE(STATEMENT => 'id') - Returns data before the statement ran (excludes changes made by that statement)
This is the most common pattern for recovering from accidental DML.

2. DATA_RETENTION_TIME_IN_DAYS

The DATA_RETENTION_TIME_IN_DAYS parameter controls how long historical data is preserved for Time Travel. It can be set at the account, database, schema, or table level.

Retention Period by Edition

Snowflake EditionMinimumMaximumDefault
Standard0 days1 day1 day
Enterprise0 days90 days1 day
Business Critical0 days90 days1 day
VPS (Virtual Private Snowflake)0 days90 days1 day
Critical Exam Point: Standard Edition is limited to a maximum of 1 day of Time Travel. Only Enterprise and higher editions can extend up to 90 days. This is one of the most frequently tested edition differences.

Setting Retention at Different Levels

-- Account level (requires ACCOUNTADMIN)
ALTER ACCOUNT SET DATA_RETENTION_TIME_IN_DAYS = 30;

-- Database level
ALTER DATABASE my_db SET DATA_RETENTION_TIME_IN_DAYS = 14;

-- Schema level
ALTER SCHEMA my_db.my_schema SET DATA_RETENTION_TIME_IN_DAYS = 7;

-- Table level (most granular)
ALTER TABLE my_db.my_schema.my_table SET DATA_RETENTION_TIME_IN_DAYS = 90;

-- Disable Time Travel entirely for a table (saves storage)
ALTER TABLE staging_table SET DATA_RETENTION_TIME_IN_DAYS = 0;

-- Check current retention setting
SHOW PARAMETERS LIKE 'DATA_RETENTION_TIME_IN_DAYS' IN TABLE my_table;

Inheritance Hierarchy

Account (DATA_RETENTION_TIME_IN_DAYS = 30)
  |
  +-- Database (inherits 30 unless overridden)
       |
       +-- Schema (inherits from DB unless overridden)
            |
            +-- Table (inherits from Schema unless overridden)
                 |
                 +-- Most specific setting wins
Exam Tip: When you set retention to 0 days, Time Travel is effectively disabled for that object. There is no way to query historical data for that object, and UNDROP is not available either. Use carefully for transient/staging tables.

Transient & Temporary Tables

Table TypeMax RetentionFail-safeUse Case
Permanent90 days (Enterprise+)7 daysProduction data requiring full protection
Transient1 day (all editions)No fail-safeETL staging, intermediate results
Temporary1 day (all editions)No fail-safeSession-scoped work; dropped at session end
Key Distinction: Transient and Temporary tables have a maximum retention of 1 day regardless of edition, and they have no Fail-safe period. This significantly reduces storage costs but provides less protection.

3. Fail-safe

Fail-safe provides a 7-day period of data recovery that begins immediately after the Time Travel retention period ends. It is a last-resort data recovery mechanism managed entirely by Snowflake.

|<--- Active Data --->|<--- Time Travel (1-90 days) --->|<--- Fail-safe (7 days) --->|
|                      |                                  |                              |
| Current queryable    | User-accessible via AT/BEFORE    | Snowflake-managed only       |
| state of data        | and UNDROP                       | Contact Support to recover   |
|                      |                                  |                              |
|  No extra cost       |  Storage cost incurred           |  Storage cost incurred       |

Fail-safe Characteristics

CharacteristicDetails
DurationFixed at 7 days (cannot be changed)
User AccessNon-queryable - users cannot directly access Fail-safe data
Recovery ProcessMust contact Snowflake Support for recovery
Recovery TimeMay take hours to days depending on data volume
GuaranteeBest-effort recovery (not a guaranteed SLA)
Storage CostIncurs storage charges during the 7-day window
Applies ToPermanent tables only (not transient or temporary)
Starts WhenImmediately after the Time Travel retention period expires
Exam Critical: Fail-safe is NOT accessible to users. You cannot query data in Fail-safe. You cannot use UNDROP to recover data that has passed into Fail-safe. The ONLY option is to contact Snowflake Support, and recovery is on a best-effort basis.
Exam Tip: The extended Time Travel (up to 90 days) is available on Enterprise edition and higher. Standard Edition is limited to 1 day TT + 7 days Fail-safe = 8 days total protection. Enterprise Edition can have up to 90 days TT + 7 days Fail-safe = 97 days total protection.

Fail-safe Does NOT Apply To

  • Transient tables (CREATE TRANSIENT TABLE)
  • Temporary tables (CREATE TEMPORARY TABLE)
  • Transient databases (all tables within inherit no Fail-safe)
  • Transient schemas (all tables within inherit no Fail-safe)

4. Zero-Copy Cloning

Zero-Copy Cloning creates a copy of a database, schema, or table that initially shares the underlying micro-partitions with the source. No data is physically copied at the time of cloning, making it nearly instantaneous regardless of data size.

How Zero-Copy Cloning Works

          BEFORE CLONE                              AFTER CLONE
  +------------------+                    +------------------+   +------------------+
  |  Source Table    |                    |  Source Table    |   |  Cloned Table    |
  |                  |                    |                  |   |                  |
  |  Partition A     |                    |  Partition A ----+---+--- Partition A   |
  |  Partition B     |         ==>        |  Partition B ----+---+--- Partition B   |
  |  Partition C     |                    |  Partition C ----+---+--- Partition C   |
  +------------------+                    +------------------+   +------------------+
                                                    |                     |
                                               SHARED (zero extra storage cost)

          AFTER MODIFICATIONS TO CLONE
  +------------------+   +------------------+
  |  Source Table    |   |  Cloned Table    |
  |                  |   |                  |
  |  Partition A ----+---+--- Partition A   |  (still shared)
  |  Partition B ----+---+--- Partition B   |  (still shared)
  |  Partition C     |   |   Partition D    |  (diverged - new storage cost)
  +------------------+   +------------------+

Cloning Syntax

-- Clone a table
CREATE TABLE my_clone CLONE my_source_table;

-- Clone a schema (includes all objects within)
CREATE SCHEMA my_schema_clone CLONE my_source_schema;

-- Clone a database (includes all schemas and objects)
CREATE DATABASE my_db_clone CLONE my_source_db;

-- Clone with Time Travel (clone data from a past point in time)
CREATE TABLE my_restored CLONE my_table
  AT(TIMESTAMP => '2026-08-14 10:00:00'::TIMESTAMP_LTZ);

CREATE TABLE my_restored CLONE my_table
  BEFORE(STATEMENT => '01abc123-0000-0000-0000-000000000001');

-- Clone with OFFSET
CREATE TABLE my_restored CLONE my_table
  AT(OFFSET => -3600);

What Gets Cloned

Object TypeCloned?Notes
Tables (data + structure)YesData is zero-copy; structure is duplicated
ViewsYesDefinition cloned (references may need updating)
SequencesYesCloned with current value snapshot
Stages (named internal)Yes (empty)Stage object cloned but files are NOT copied
File FormatsYesDefinitions are duplicated
StreamsYesCloned but offset is reset; historical data not preserved
TasksYesCloned in suspended state
PipesNot clonedMust be recreated manually
External tablesNot clonedMust be recreated manually
Privileges/GrantsNot clonedClone owner gets OWNERSHIP; existing grants not copied
Key Points for Exam:
  • Cloning is metadata-only at creation time - instantaneous regardless of table size
  • Storage charges begin only when data diverges (DML on source or clone creates new partitions)
  • Cloning works with databases, schemas, and tables (not individual rows or columns)
  • You can clone a clone (nested cloning is supported)
  • Cloning respects Time Travel - you can clone from a historical point
Exam Tip: When cloning a database or schema, internal named stages are cloned empty (the stage object exists but files within are NOT copied). This is frequently tested. External stages are not cloned at all.
Common Use Cases for Cloning:
  • Creating development/test environments from production (instant, zero cost until modifications)
  • Data recovery combined with Time Travel (clone from a historical point)
  • Creating sandboxes for data scientists to experiment without affecting production
  • Backup snapshots before large migrations or transformations

5. UNDROP

UNDROP restores a dropped object (table, schema, or database) within the Time Travel retention period. It is the primary mechanism for recovering accidentally dropped objects.

UNDROP Syntax

-- Undrop a table
UNDROP TABLE my_table;

-- Undrop a schema
UNDROP SCHEMA my_schema;

-- Undrop a database
UNDROP DATABASE my_database;

UNDROP Rules and Behavior

RuleDetails
Time LimitMust be within the DATA_RETENTION_TIME_IN_DAYS period
Name ConflictIf an object with the same name already exists, UNDROP fails
Resolution for ConflictsRename the existing object first, then UNDROP
Multiple DropsUNDROP restores the most recently dropped version
CascadeUNDROP DATABASE/SCHEMA also restores child objects
Retention = 0UNDROP is not available if retention was set to 0
Fail-safe DataUNDROP cannot recover data that has moved past Time Travel into Fail-safe
Transient/TempAvailable if within retention (max 1 day for these types)

Handling Name Conflicts

-- Scenario: You dropped TABLE_A, then created a new TABLE_A
-- UNDROP TABLE TABLE_A; would FAIL because TABLE_A already exists

-- Solution: Rename the new table first
ALTER TABLE table_a RENAME TO table_a_new;

-- Now UNDROP the original
UNDROP TABLE table_a;

-- You now have both: TABLE_A (original restored) and TABLE_A_NEW
Exam Tip: If a table is dropped and recreated with the same name, you must rename the current table before you can UNDROP the previous version. UNDROP always fails if there is a naming conflict.
Critical: Once the Time Travel retention period expires, data moves to Fail-safe. UNDROP will no longer work. The only recovery path at that point is to contact Snowflake Support (best-effort recovery).

UNDROP with Multiple Versions

-- If TABLE_A was dropped 3 times, UNDROP brings back the MOST RECENT drop
-- To access older dropped versions, you must UNDROP and rename iteratively:

UNDROP TABLE table_a;                       -- Restores most recent drop
ALTER TABLE table_a RENAME TO table_a_v3;   -- Rename to avoid conflict

UNDROP TABLE table_a;                       -- Restores next most recent
ALTER TABLE table_a RENAME TO table_a_v2;   -- Rename again

UNDROP TABLE table_a;                       -- Restores oldest drop (if still in retention)

6. Storage Costs

Snowflake storage charges are based on three components: active data, Time Travel data, and Fail-safe data. Understanding how these interact is critical for both the exam and real-world cost optimization.

Storage Cost Components

Total Storage Cost = Active Storage + Time Travel Storage + Fail-safe Storage

+-------------------------------------------------------------------+
|  Component           | What it stores                              |
+-------------------------------------------------------------------+
|  Active Storage      | Current state of data (compressed)          |
|  Time Travel Storage | Changed/deleted micro-partitions retained   |
|                      | for the retention period                    |
|  Fail-safe Storage   | Micro-partitions retained beyond TT         |
|                      | for the 7-day fail-safe window              |
+-------------------------------------------------------------------+

How DML Affects Storage

OperationActive StorageTime Travel StorageNotes
INSERT (new data)IncreasesNo changeNew partitions created; no old partitions to retain
DELETEDecreasesIncreasesOld partitions move to TT storage
UPDATEMay increaseIncreasesOld partitions retained; new partitions created
TRUNCATEDecreases to ~0Increases significantlyAll old partitions move to TT storage
DROP TABLEDecreases to 0IncreasesAll data moves to TT (for UNDROP)
Exam Tip - Surprising Cost Scenario: A large UPDATE on a table with 90-day retention effectively doubles the storage for that table (both old and new partitions are stored). This is because the original micro-partitions are retained in Time Travel while new ones are created for the updated data.

Checking Storage Usage

-- View storage for tables including Time Travel and Fail-safe
SELECT table_name,
       active_bytes,
       time_travel_bytes,
       failsafe_bytes,
       active_bytes + time_travel_bytes + failsafe_bytes AS total_bytes
FROM snowflake.account_usage.table_storage_metrics
WHERE table_catalog = 'MY_DB'
ORDER BY total_bytes DESC;

-- Simpler view at the table level
SELECT * FROM TABLE(INFORMATION_SCHEMA.TABLE_STORAGE_METRICS())
WHERE TABLE_NAME = 'MY_TABLE';

-- Account-level storage usage
SELECT * FROM snowflake.account_usage.storage_usage
ORDER BY usage_date DESC
LIMIT 30;

Cost Optimization Strategies

StrategyApproachSavings
Use Transient tables for stagingNo Fail-safe; max 1-day TTEliminates 7 days of Fail-safe storage

Storage Billing: Storage is billed based on the average compressed bytes stored per month across all three tiers (active + TT + Fail-safe). On-demand storage is typically ~$40/TB/month (varies by cloud/region). Capacity storage is typically ~$23/TB/month.

Quick Reference: Exam Scenarios

Q: A user accidentally deleted rows 30 minutes ago. How do they recover?
A: Use INSERT INTO my_table SELECT * FROM my_table BEFORE(STATEMENT => 'query_id_of_delete') or create a clone from the time before the DELETE.
Q: A table was dropped 5 days ago on Standard Edition. Can it be recovered?
A: No. Standard Edition has max 1-day retention. After 1 day, data moves to Fail-safe (non-queryable). User must contact Snowflake Support for best-effort recovery.
Q: Does cloning a 10 TB database immediately consume 10 TB of additional storage?
A: No. Zero-copy cloning shares the underlying micro-partitions. Storage cost is zero until data in the source or clone diverges through DML operations.
Q: What is the total maximum data protection window on Enterprise Edition?
A: 97 days (90 days Time Travel + 7 days Fail-safe).
Q: Can you UNDROP a transient table dropped 2 days ago?
A: No. Transient tables have a maximum retention of 1 day. After 1 day, the data is gone permanently (transient tables have no Fail-safe).
Q: What happens to grants when you clone a database?
A: Grants/privileges are NOT cloned. The user who runs the CLONE command becomes the owner. All other grants must be explicitly re-granted.
