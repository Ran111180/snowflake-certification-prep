1. Advanced Time Travel Patterns

Point-in-Time Recovery

Time Travel allows querying data as it existed at any point within the retention period. This enables surgical recovery of accidentally modified or deleted data without restoring entire backups.

Recovery via CLONE AT

-- Recover a table to a specific timestamp
CREATE TABLE sales_recovered CLONE sales
  AT (TIMESTAMP => '2026-08-14 10:30:00'::TIMESTAMP_LTZ);

-- Recover using a query ID (the statement that caused damage)
CREATE TABLE sales_recovered CLONE sales
  BEFORE (STATEMENT => '01abc123-0000-0000-0000-000000000001');

-- Recover using an offset (5 minutes ago)
CREATE TABLE sales_recovered CLONE sales
  AT (OFFSET => -300);

Selective Row Recovery

-- Restore only specific deleted rows
INSERT INTO orders
SELECT * FROM orders AT (TIMESTAMP => '2026-08-14 09:00:00'::TIMESTAMP_LTZ)
WHERE order_id NOT IN (SELECT order_id FROM orders);

-- Restore specific column values that were incorrectly updated
UPDATE customers c
SET c.email = hist.email
FROM customers AT (TIMESTAMP => '2026-08-14 08:00:00'::TIMESTAMP_LTZ) hist
WHERE c.customer_id = hist.customer_id
  AND c.email != hist.email;
Exam Tip BEFORE (STATEMENT => ...) returns data as it was immediately before that statement executed. AT (STATEMENT => ...) includes changes made by that statement.

Comparing Historical vs. Current Data

Time Travel is powerful for auditing drift, debugging data pipeline issues, and validating transformations.

-- Compare row counts: current vs 24 hours ago
SELECT
  'current' AS snapshot, COUNT(*) AS row_count FROM inventory
UNION ALL
SELECT
  '24h_ago' AS snapshot, COUNT(*) AS row_count FROM inventory AT (OFFSET => -86400);

-- Find rows that changed in the last hour
SELECT curr.*, 'modified' AS change_type
FROM products curr
JOIN products AT (OFFSET => -3600) prev
  ON curr.product_id = prev.product_id
WHERE curr.price != prev.price

UNION ALL

-- Find newly inserted rows
SELECT curr.*, 'inserted' AS change_type
FROM products curr
LEFT JOIN products AT (OFFSET => -3600) prev
  ON curr.product_id = prev.product_id
WHERE prev.product_id IS NULL;

Auditing Changes

Combine Time Travel with QUERY_HISTORY and ACCESS_HISTORY for full audit trails.

-- Find who made changes to a sensitive table
SELECT query_id, user_name, query_text, start_time
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY
WHERE query_text ILIKE '%UPDATE%employee_salaries%'
  AND start_time > DATEADD(day, -7, CURRENT_TIMESTAMP())
ORDER BY start_time DESC;

-- Then use the query_id to see data before that change
SELECT * FROM employee_salaries
  BEFORE (STATEMENT => '<query_id_from_above>');
Pattern Combine QUERY_HISTORY to find the offending DML statement, then use BEFORE(STATEMENT => ...) to recover the pre-change state.

2. Clone Patterns

Dev/Test from Production

Zero-copy cloning creates instant development environments from production data without additional storage cost (until the clone diverges).

-- Clone entire database for development
CREATE DATABASE dev_analytics CLONE prod_analytics;

-- Clone specific schema for feature testing
CREATE SCHEMA staging.test_feature_x CLONE prod.public;

-- Clone a single table for experimentation
CREATE TABLE sandbox.experiment_cohort CLONE prod.public.customers;

Best Practice: Timestamped Clones

-- Create time-stamped clone for reproducible testing
CREATE DATABASE dev_analytics_20260815
  CLONE prod_analytics
  AT (TIMESTAMP => '2026-08-15 00:00:00'::TIMESTAMP_LTZ);

-- Automated nightly clone (via task)
CREATE OR REPLACE TASK clone_nightly
  WAREHOUSE = admin_wh
  SCHEDULE = 'USING CRON 0 2 * * * America/New_York'
AS
  CREATE OR REPLACE DATABASE dev_nightly CLONE prod_analytics;

Schema Migration Testing

Test DDL changes (ALTER TABLE, new columns, type changes) on a clone before applying to production.

-- 1. Clone the target schema
CREATE SCHEMA migration_test CLONE production.public;

-- 2. Apply migration scripts against the clone
ALTER TABLE migration_test.orders ADD COLUMN shipping_method VARCHAR(50);
ALTER TABLE migration_test.customers ALTER COLUMN phone SET DATA TYPE VARCHAR(20);

-- 3. Run validation queries
SELECT COUNT(*) FROM migration_test.orders WHERE shipping_method IS NULL;

-- 4. If successful, apply to production; if not, drop the clone
DROP SCHEMA migration_test;

Clone + Stream for CDC Replay

Streams track DML changes on a table. Cloning a table with an active stream allows replaying or re-processing change data.

-- Setup: create stream on source table
CREATE STREAM orders_stream ON TABLE production.orders;

-- Process some changes...
-- Now clone the table AT a point before the stream was consumed
CREATE TABLE orders_replay CLONE production.orders
  AT (OFFSET => -7200);  -- 2 hours ago

-- Create a new stream on the clone to capture changes from that point
CREATE STREAM replay_stream ON TABLE orders_replay;

-- The replay stream will capture all changes that occurred
-- on the original table since the clone point
Exam Tip When you clone a table that has a stream, the stream itself is NOT cloned. You must create a new stream on the cloned table. The clone's Time Travel data preserves the change tracking metadata from the source.

Clone for Zero-Downtime Swap

-- Clone, transform, then swap
CREATE TABLE customers_v2 CLONE customers;

-- Apply transformations to the clone
UPDATE customers_v2 SET region = 'APAC' WHERE country IN ('Japan','Korea','Australia');

-- Atomic swap
ALTER TABLE customers SWAP WITH customers_v2;
-- Original is now named customers_v2 (can drop it)
DROP TABLE customers_v2;

What IS Cloned

What is NOT Cloned

Object/PropertyBehavior
Privileges / GrantsNOT cloned. Clone owner gets OWNERSHIP; all other grants must be re-applied.

Future grantsNOT cloned for child objects.
Critical Exam Point Grants/privileges are NEVER cloned. The role that runs CREATE...CLONE becomes the owner. This is the #1 tested detail about cloning on the certification exam.

Child Objects for Database/Schema Clone

When you clone a database or schema, all child objects are recursively cloned:

  • Database clone: All schemas, and all objects within each schema
  • Schema clone: All tables, views, stages, file formats, sequences, pipes, tasks, streams (definitions only), UDFs, procedures

Pipes: Suspended on Clone

Exam Tip Cloned pipes are created in a SUSPENDED state. They will NOT auto-ingest until explicitly resumed with ALTER PIPE ... RESUME. This prevents duplicate data ingestion. 
-- After cloning a database with pipes:
SHOW PIPES IN DATABASE dev_clone;
-- All pipes show state = 'SUSPENDED'

-- To resume a specific pipe:
ALTER PIPE dev_clone.public.my_pipe RESUME;

Tasks: Suspended on Clone

Similar to pipes, cloned tasks are always created in a SUSPENDED state regardless of their original state.

-- After cloning, tasks must be explicitly resumed
ALTER TASK dev_clone.public.etl_task RESUME;

-- For task trees, resume in reverse dependency order (leaf tasks first)
ALTER TASK dev_clone.public.child_task RESUME;
ALTER TASK dev_clone.public.root_task RESUME;

Stage Cloning Behavior

Stage TypeClone Behavior
Internal (named) stagesStage object is cloned but files are NOT copied. The cloned stage is empty.
External stagesStage definition is cloned (URL, credentials reference). Both original and clone point to the same external location.
Table stagesFiles in table stages are NOT cloned. Only the table data (micro-partitions) is shared.
Key Detail Internal named stages are cloned as empty containers. If your pipeline depends on files in a stage (e.g., for COPY INTO), those files will NOT be present in the clone.

4. Storage Impact

Zero-Copy Clone: How It Works

Cloning uses a copy-on-write model at the micro-partition level:

  1. At clone creation: zero additional storage. Both source and clone share identical micro-partition pointers.
  2. When DML modifies the clone: only the new/modified micro-partitions created by that DML consume additional storage.
  3. When DML modifies the source: same principle — new partitions on the source do not affect the clone's storage.
At Clone Time
0 bytes additional
After DML on Clone
Only changed partitions
Shared Partitions
Billed once (to source owner)
Time Travel on Clone
Independent retention

Storage Divergence Example

-- Source table: 1000 micro-partitions, 500 GB
-- Clone at T0: 0 additional storage

-- T1: UPDATE 10% of rows in clone
-- Result: ~100 new micro-partitions created for clone
-- Clone storage: ~50 GB (only the modified partitions)
-- Shared: 900 partitions still zero-cost to clone

-- T2: DELETE 50% of rows from source
-- Source creates new partitions, old shared ones enter Time Travel
-- Clone still references original shared partitions (unaffected)

Monitoring Clone Storage

-- Check storage breakdown
SELECT
  table_catalog,
  table_schema,
  table_name,
  active_bytes,
  time_travel_bytes,
  failsafe_bytes,
  retained_for_clone_bytes
FROM SNOWFLAKE.ACCOUNT_USAGE.TABLE_STORAGE_METRICS
WHERE table_name = 'MY_CLONED_TABLE'
ORDER BY active_bytes DESC;
Exam Tip RETAINED_FOR_CLONE_BYTES in TABLE_STORAGE_METRICS shows storage that the source table retains because a clone still references those micro-partitions. Dropping the clone releases this storage.

Storage Billing Rules

ScenarioWho Pays
Shared micro-partitions (unchanged)Source table owner
New partitions from DML on cloneClone owner
Time Travel on clone's changed partitionsClone owner
Source dropped, clone still references partitionsRetained storage charged to the account until clone is dropped or partitions age out

5. Fail-safe Operations

What is Fail-safe?

Fail-safe is a 7-day period that begins immediately after Time Travel expires. It provides a last-resort data recovery mechanism accessible only by Snowflake Support.

Duration
7 days (non-configurable)
Access
Snowflake Support only
Applies to
Permanent tables only
Transient/Temporary
NO Fail-safe

Contacting Snowflake Support

  1. File a support case via the Snowflake Support portal
  2. Provide: account identifier, database/schema/table name, approximate timestamp of data loss
  3. Snowflake attempts recovery on a best-effort basis
  4. Recovery is NOT guaranteed and may take hours to days
  5. Recovered data is placed in a new table (not restored in-place)

What CAN Be Recovered

RecoverableNot Recoverable
Table data (rows/micro-partitions)Metadata-only objects (views, stages, pipes)
Data from permanent tablesTransient table data (no fail-safe)
Data that was in fail-safe windowTemporary table data (no fail-safe)
Specific point-in-time within fail-safeData older than Time Travel + 7 days

Cost During Fail-safe

Storage Cost Fail-safe storage is billed at the same rate as active storage. For a table with 90-day retention, total protected period is 90 + 7 = 97 days of historical storage charges. This can significantly increase costs for high-churn tables. 
-- Monitor fail-safe storage costs
SELECT
  table_catalog AS database,
  SUM(failsafe_bytes) / POWER(1024,4) AS failsafe_tb
FROM SNOWFLAKE.ACCOUNT_USAGE.TABLE_STORAGE_METRICS
WHERE deleted IS NULL
GROUP BY table_catalog
ORDER BY failsafe_tb DESC;

-- Total storage breakdown
SELECT
  SUM(active_bytes) / POWER(1024,3) AS active_gb,
  SUM(time_travel_bytes) / POWER(1024,3) AS time_travel_gb,
  SUM(failsafe_bytes) / POWER(1024,3) AS failsafe_gb
FROM SNOWFLAKE.ACCOUNT_USAGE.TABLE_STORAGE_METRICS;

Fail-safe Timeline

-- Permanent table lifecycle:
-- |--- Active ---|--- Time Travel (0-90 days) ---|--- Fail-safe (7 days) ---|--- Purged ---|

-- Transient table lifecycle:
-- |--- Active ---|--- Time Travel (0-1 day) ---|--- Purged (NO Fail-safe) ---|

-- Temporary table lifecycle:
-- |--- Active (session) ---|--- Time Travel (0-1 day) ---|--- Purged (NO Fail-safe) ---|

6. Retention Interaction with Streams

Stream Staleness Rule

A stream becomes stale when the change data it needs to report has aged beyond the underlying table's data retention period. The effective staleness window is:

Critical Formula Stream Staleness Threshold = DATA_RETENTION_TIME_IN_DAYS + 14 days
The extra 14 days is an internal Snowflake extension that provides a grace buffer. However, you should NOT rely on this buffer in production — treat it as undocumented grace.

How It Works

  • A stream tracks an offset (a point-in-time marker) on the source table
  • If the stream is not consumed within the retention window, the micro-partitions it needs to read from may be purged
  • Once stale, the stream is unusable — you must recreate it
  • Staleness is checked when the stream is queried, not continuously

Examples

Table RetentionStream Staleness ThresholdRecommendation
1 day (default)~15 daysConsume stream at least daily
14 days~28 daysConsume at least every 2 weeks
90 days~104 daysConsume within 90 days

Preventing Stream Staleness

-- Check stream staleness
SHOW STREAMS LIKE 'my_stream' IN SCHEMA my_db.my_schema;
-- Check STALE column and STALE_AFTER column

-- Proactive: query the stream regularly (even if no processing needed)
-- A SELECT on the stream does NOT advance the offset
-- Only DML in a transaction that reads the stream advances it

-- Increase retention on the source table if streams go stale
ALTER TABLE source_table SET DATA_RETENTION_TIME_IN_DAYS = 14;

-- Monitor staleness with a task
CREATE TASK check_stream_staleness
  WAREHOUSE = admin_wh
  SCHEDULE = 'USING CRON 0 8 * * * UTC'
AS
  SELECT stream_name, stale, stale_after
  FROM TABLE(INFORMATION_SCHEMA.STREAMS())
  WHERE stale = TRUE;
Best Practice Set table retention to at least 2x your expected stream consumption interval. If you process streams daily, keep at least 2 days retention. If weekly, keep at least 14 days.

Stream + Clone Interaction

-- Streams are NOT cloned with the table
-- After cloning, create a fresh stream:
CREATE TABLE orders_clone CLONE orders;
CREATE STREAM orders_clone_stream ON TABLE orders_clone;
-- This new stream starts tracking from the clone point forward

-- The original stream on the original table is unaffected

Clone Scheduling Strategy

-- Production clone schedule pattern:
-- 1. Nightly dev refresh
CREATE OR REPLACE TASK nightly_dev_clone
  WAREHOUSE = admin_wh
  SCHEDULE = 'USING CRON 0 2 * * * America/New_York'
AS
  CREATE OR REPLACE DATABASE dev CLONE prod;

-- 2. Weekly QA snapshot (preserved for a week)
CREATE OR REPLACE TASK weekly_qa_clone
  WAREHOUSE = admin_wh
  SCHEDULE = 'USING CRON 0 3 * * 1 America/New_York'
AS
  BEGIN
    DROP DATABASE IF EXISTS qa_previous_week;
    ALTER DATABASE qa_current_week RENAME TO qa_previous_week;
    CREATE DATABASE qa_current_week CLONE prod;
  END;

-- 3. Pre-release clone for migration testing
-- (Manual, triggered before deployments)
CREATE DATABASE release_test_v2_5 CLONE prod
  AT (TIMESTAMP => CURRENT_TIMESTAMP());

Cost Monitoring

-- Daily storage cost monitoring query
SELECT
  DATE_TRUNC('day', usage_date) AS day,
  SUM(storage_bytes + stage_bytes + failsafe_bytes) / POWER(1024,4) AS total_tb,
  SUM(storage_bytes) / POWER(1024,4) AS active_tb,
  SUM(failsafe_bytes) / POWER(1024,4) AS failsafe_tb
FROM SNOWFLAKE.ACCOUNT_USAGE.STORAGE_USAGE
WHERE usage_date > DATEADD(month, -1, CURRENT_DATE())
GROUP BY 1 ORDER BY 1;

-- Identify tables with expensive Time Travel
SELECT
  table_catalog || '.' || table_schema || '.' || table_name AS full_name,
  active_bytes / POWER(1024,3) AS active_gb,
  time_travel_bytes / POWER(1024,3) AS tt_gb,
  failsafe_bytes / POWER(1024,3) AS fs_gb,
  ROUND(time_travel_bytes * 100.0 / NULLIF(active_bytes,0), 1) AS tt_pct_of_active
FROM SNOWFLAKE.ACCOUNT_USAGE.TABLE_STORAGE_METRICS
WHERE time_travel_bytes > 1073741824  -- > 1 GB
ORDER BY time_travel_bytes DESC
LIMIT 20;

-- Alert on unexpected storage growth
CREATE ALERT storage_growth_alert
  WAREHOUSE = admin_wh
  SCHEDULE = 'USING CRON 0 7 * * * UTC'
  IF (EXISTS (
    SELECT 1 FROM SNOWFLAKE.ACCOUNT_USAGE.STORAGE_USAGE
    WHERE usage_date = CURRENT_DATE() - 1
      AND storage_bytes > (
        SELECT storage_bytes * 1.2  -- 20% growth threshold
        FROM SNOWFLAKE.ACCOUNT_USAGE.STORAGE_USAGE
        WHERE usage_date = CURRENT_DATE() - 8
      )
  ))
  THEN CALL SYSTEM$SEND_EMAIL(...);

Cost Reduction Tactics

  • Use transient tables for staging/ETL (no fail-safe = 7 days less storage)
  • Lower retention on high-churn tables where data is reproducible
  • Drop unused clones promptly to release retained_for_clone storage
  • Set retention to 0 on tables during bulk loads, then restore after
  • Monitor RETAINED_FOR_CLONE_BYTES to find hidden storage costs

Privileges After Cloning

-- The role executing CREATE...CLONE becomes OWNER of the clone
-- No other privileges are carried over!

-- Typical post-clone grant pattern:
CREATE DATABASE dev_db CLONE prod_db;

-- Grant access to development roles
GRANT USAGE ON DATABASE dev_db TO ROLE developer;
GRANT USAGE ON ALL SCHEMAS IN DATABASE dev_db TO ROLE developer;
GRANT SELECT ON ALL TABLES IN DATABASE dev_db TO ROLE developer;
GRANT ALL ON ALL TABLES IN DATABASE dev_db TO ROLE developer;

-- Set up future grants for objects created in the clone
GRANT SELECT ON FUTURE TABLES IN DATABASE dev_db TO ROLE developer;

Time Travel Query Privileges

-- To query historical data with AT/BEFORE:
-- You need SELECT on the table (same as a regular query)
-- No special "Time Travel privilege" exists

-- Example: analyst can query historical data if they have SELECT
GRANT SELECT ON TABLE prod.public.orders TO ROLE analyst;
-- Analyst can now run:
-- SELECT * FROM orders AT (OFFSET => -3600);

Recommended Role Hierarchy for Clone Operations

-- Create a clone administration role
CREATE ROLE clone_admin;
GRANT CREATE DATABASE ON ACCOUNT TO ROLE clone_admin;
GRANT USAGE ON DATABASE prod TO ROLE clone_admin;
GRANT USAGE ON ALL SCHEMAS IN DATABASE prod TO ROLE clone_admin;
GRANT SELECT ON ALL TABLES IN DATABASE prod TO ROLE clone_admin;

-- Grant to sysadmin hierarchy
GRANT ROLE clone_admin TO ROLE sysadmin;

-- For automated cloning tasks, grant to task-executing role
GRANT ROLE clone_admin TO ROLE task_executor;
GRANT USAGE ON WAREHOUSE admin_wh TO ROLE task_executor;
GRANT EXECUTE TASK ON ACCOUNT TO ROLE task_executor;
