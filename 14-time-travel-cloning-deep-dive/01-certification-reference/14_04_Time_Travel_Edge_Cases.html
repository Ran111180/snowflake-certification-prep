Key Exam Insight

Time Travel applies to data-bearing objects (tables, schemas, databases). Non-data objects like views, stages, pipes, tasks, and UDFs do NOT have Time Travel — they can be cloned but not time-traveled.

2. DDL Impact on Time Travel

DROP and UNDROP Behavior

ActionTime Travel BehaviorRecovery
DROP TABLE t1TT retention clock starts at drop timeUNDROP TABLE t1 within retention period
DROP SCHEMA s1All child tables enter TT simultaneouslyUNDROP SCHEMA s1 restores all children
DROP DATABASE db1All schemas/tables enter TTUNDROP DATABASE db1 restores entire DB
Drop + recreate same nameOld object still in TT, shadowed by newMust rename new, UNDROP old, then rename back

UNDROP Name Conflict

If you DROP a table then CREATE a new table with the same name, UNDROP TABLE will fail with a name conflict. You must first ALTER TABLE new_name RENAME TO temp_name, then UNDROP TABLE original_name.

CREATE OR REPLACE Behavior

CREATE OR REPLACE = DROP + CREATE (Atomically)

CREATE OR REPLACE TABLE t1 ... effectively drops the old table and creates a new one. The old table enters Time Travel. The new table has no history — it's a brand new object with a new internal ID.

StatementEffect on Old ObjectEffect on New Object
CREATE OR REPLACE TABLEOld table enters TT (recoverable via UNDROP after renaming new)New table, new object ID, no history
CREATE OR REPLACE VIEWOld view gone (no TT for views)New definition active
CREATE TABLE IF NOT EXISTSNo effect if existsOnly creates if missing

Retention Period Changes

ScenarioBehavior
Increase retention (e.g., 1 → 14 days)Applies immediately; historical data already purged is not recovered
Decrease retention (e.g., 14 → 1 day)Data older than new retention immediately moves to Fail-safe (permanent tables) or is purged (transient)

Retention Hierarchy

Table setting overrides Schema setting, which overrides Database setting. Existing objects keep their current setting — only newly created objects inherit the parent's default.

3. Clone Edge Cases

Clone of a Clone

Fully Supported

You can clone a clone. Each clone is an independent object. Snowflake uses metadata pointers — cloning a clone does NOT double storage. All clones share micro-partitions until data diverges.

Privileges NOT Inherited

Critical Exam Point

Clones do NOT copy grants/privileges from the source. The cloned object is owned by the role that performed the clone. You must explicitly GRANT access after cloning — unless you use ...CLONE source COPY GRANTS (available for databases, schemas, and tables).

-- Without COPY GRANTS (default): no privileges transferred
CREATE DATABASE dev_db CLONE prod_db;

-- With COPY GRANTS: privileges duplicated on clone
CREATE DATABASE dev_db CLONE prod_db COPY GRANTS;

Clone and Streams

ScenarioBehavior
Stream on table, clone the schema/databaseStream cloned, points to cloned table, offset preserved
Stream on table, clone only the tableStream is NOT cloned (stream is a separate object)
Clone a table that a stream points toOriginal stream still points to original table (unaffected)
Stream offset validityIf cloned table's offset data has been purged beyond TT, stream becomes STALE

Clone and Pipes

Pipes Are Cloned as SUSPENDED

When you clone a schema or database containing pipes:

  • Snowpipe objects are cloned but set to PAUSED/SUSPENDED
  • They do NOT automatically resume — you must explicitly ALTER PIPE ... SET PIPE_EXECUTION_PAUSED = FALSE
  • Load history is NOT cloned — the pipe will not know what files were already loaded
  • Risk: if resumed without care, the pipe may re-ingest files already loaded into the source

Clone and Tasks

Tasks Are Cloned as SUSPENDED

When you clone a schema or database containing tasks:

  • All tasks are cloned in SUSPENDED state
  • Task graphs (DAGs) are preserved but all nodes are suspended
  • You must ALTER TASK ... RESUME each task individually (leaf tasks first, then root)
  • Scheduled times and CRON expressions are preserved but execution does not begin until resumed

Storage Divergence After Clone

TimeStorage Used by CloneExplanation
Immediately after clone~0 bytesClone shares all micro-partitions with source (zero-copy)
After DML on cloneOnly new/modified partitionsChanged data written to new partitions owned by clone
After DML on sourceShared partitions unchanged for cloneSource writes new partitions; clone still references old shared ones
After source table DROPClone now "owns" any partitions not shared with other clonesStorage attributed to clone increases if source is purged

Storage Billing Surprise

If you clone a 1TB table and then DROP the source after Time Travel + Fail-safe expires, the clone will be billed for the full 1TB (because it's now the sole owner of those micro-partitions). Plan accordingly!

4. Retention Edge Cases

Retention Rules by Table Type

Transient & Temporary = No Safety Net

Transient and temporary tables have NO fail-safe. Once Time Travel expires (max 1 day), the data is permanently gone. Snowflake Support cannot recover it. Use these only for reproducible/ephemeral data.

Lifecycle Timeline Comparison

Permanent Table (Enterprise, 14-day TT):
  |--- Active ---|--- Time Travel (14d) ---|--- Fail-safe (7d) ---|--- PURGED ---|
  
Permanent Table (Standard, 1-day TT):
  |--- Active ---|--- TT (1d) ---|--- Fail-safe (7d) ---|--- PURGED ---|

Transient Table (1-day TT):
  |--- Active ---|--- TT (1d) ---|--- PURGED (no fail-safe) ---|

Temporary Table (1-day TT):
  |--- Active (session only) ---|--- TT (1d) ---|--- PURGED ---|

Transient/Temporary (TT = 0):
  |--- Active ---|--- PURGED IMMEDIATELY (no TT, no fail-safe) ---|

Edge Case: Table in a Transient Schema

Schema Type Determines Child Defaults

A table created in a transient schema is automatically transient (max 1 day TT, no fail-safe) — even if you don't explicitly say CREATE TRANSIENT TABLE. You cannot create a permanent table inside a transient schema or database.

Edge Case: Fail-safe Is Not Self-Service

Fail-safe != Time Travel

Fail-safe is Snowflake-internal only. You cannot query fail-safe data with AT/BEFORE clauses. Recovery requires contacting Snowflake Support and is best-effort with no SLA. It exists for disaster recovery only.

5. Recovery Playbook

Scenario 1: Accidental DROP TABLE

Situation: Someone accidentally dropped PROD_DB.ANALYTICS.SALES_FACT

-- Step 1: UNDROP the table (within retention period)
UNDROP TABLE PROD_DB.ANALYTICS.SALES_FACT;

-- If name conflict exists (new table created with same name):
ALTER TABLE PROD_DB.ANALYTICS.SALES_FACT RENAME TO PROD_DB.ANALYTICS.SALES_FACT_NEW;
UNDROP TABLE PROD_DB.ANALYTICS.SALES_FACT;

Recovery: Immediate, zero data loss

Scenario 2: Wrong UPDATE (Mass Data Corruption)

Situation: UPDATE customers SET status = 'INACTIVE' was run without a WHERE clause at 10:30 AM

-- Option A: Clone from before the bad UPDATE
CREATE TABLE PROD_DB.ANALYTICS.CUSTOMERS_RESTORED
  CLONE PROD_DB.ANALYTICS.CUSTOMERS
  AT (TIMESTAMP => '2026-08-15 10:29:00'::TIMESTAMP_LTZ);

-- Verify the restored data
SELECT COUNT(*) FROM CUSTOMERS_RESTORED WHERE status = 'ACTIVE';

-- Swap tables
ALTER TABLE PROD_DB.ANALYTICS.CUSTOMERS RENAME TO CUSTOMERS_BAD;
ALTER TABLE PROD_DB.ANALYTICS.CUSTOMERS_RESTORED RENAME TO CUSTOMERS;

-- Option B: Selective restore using INSERT from historical state
INSERT INTO PROD_DB.ANALYTICS.CUSTOMERS (id, status)
  SELECT id, status
  FROM PROD_DB.ANALYTICS.CUSTOMERS
    AT (TIMESTAMP => '2026-08-15 10:29:00'::TIMESTAMP_LTZ)
  WHERE id IN (SELECT id FROM PROD_DB.ANALYTICS.CUSTOMERS WHERE status = 'INACTIVE');

Recovery: Full recovery if within retention period

Scenario 3: Restore Historical State (Point-in-Time Query)

Situation: Need to see what the data looked like at end-of-quarter for audit

-- Query historical state without creating any objects
SELECT *
FROM PROD_DB.ANALYTICS.REVENUE
  AT (TIMESTAMP => '2026-06-30 23:59:59'::TIMESTAMP_LTZ);

-- Using OFFSET (seconds before current time)
SELECT *
FROM PROD_DB.ANALYTICS.REVENUE
  AT (OFFSET => -86400);  -- 24 hours ago

-- Using STATEMENT (before a specific query)
SELECT *
FROM PROD_DB.ANALYTICS.REVENUE
  BEFORE (STATEMENT => '01abc234-0000-0000-0000-000000000001');

Recovery: Read-only access to any point within retention window

Scenario 4: Compare Before/After a Change

Situation: A transformation ran overnight — verify what changed

-- Find rows that were modified
SELECT current.*, 'MODIFIED' AS change_type
FROM PROD_DB.ANALYTICS.ORDERS current
INNER JOIN PROD_DB.ANALYTICS.ORDERS
  AT (TIMESTAMP => '2026-08-14 18:00:00'::TIMESTAMP_LTZ) historical
  ON current.order_id = historical.order_id
WHERE current.amount != historical.amount;

-- Find rows that were added (not in historical)
SELECT current.*, 'INSERTED' AS change_type
FROM PROD_DB.ANALYTICS.ORDERS current
LEFT JOIN PROD_DB.ANALYTICS.ORDERS
  AT (TIMESTAMP => '2026-08-14 18:00:00'::TIMESTAMP_LTZ) historical
  ON current.order_id = historical.order_id
WHERE historical.order_id IS NULL;

-- Find rows that were deleted (in historical, not in current)
SELECT historical.*, 'DELETED' AS change_type
FROM PROD_DB.ANALYTICS.ORDERS
  AT (TIMESTAMP => '2026-08-14 18:00:00'::TIMESTAMP_LTZ) historical
LEFT JOIN PROD_DB.ANALYTICS.ORDERS current
  ON historical.order_id = current.order_id
WHERE current.order_id IS NULL;

Recovery: Full diff analysis within retention

Scenario 5: Recovery Beyond Retention Period

Situation: Data was lost 10 days ago, 1-day TT expired, need recovery

-- Check: Is the data still in Fail-safe? (Permanent tables only)
-- Fail-safe = 7 days AFTER Time Travel expires
-- If TT = 1 day → Fail-safe covers days 2-8 after the event
-- Day 10 = BEYOND fail-safe for 1-day TT permanent tables

-- Options:
-- 1. Contact Snowflake Support (if within Fail-safe window, best-effort)
-- 2. Check if a clone exists from before the loss
-- 3. Check if data was replicated to another account
-- 4. Restore from external backups (S3, Azure Blob, etc.)

-- Prevention: Set longer retention for critical tables
ALTER TABLE PROD_DB.ANALYTICS.CRITICAL_DATA
  SET DATA_RETENTION_TIME_IN_DAYS = 90;  -- Enterprise+ only

Recovery: Limited — depends on fail-safe window and Snowflake Support

Prevention Best Practices

  • Set 90-day retention on mission-critical tables (Enterprise+ required)
  • Use database replication for cross-region/cross-account DR
  • Maintain nightly clones as "snapshots" for point-in-time recovery
  • Never use transient tables for data that cannot be reproduced

6. Exam Scenario Questions

Q1: A user runs CREATE OR REPLACE TABLE orders AS SELECT * FROM staging.orders. The original orders table had 90 days of Time Travel data. What happens to that historical data?

Answer: The original table is effectively dropped and enters Time Travel as a dropped object. The new table starts fresh with no Time Travel history. The old table can be recovered via UNDROP (after renaming the new table) within the retention period. The 90-day history of the OLD table is preserved in TT — but the NEW table's clock starts at zero.

Q2: A transient table with DATA_RETENTION_TIME_IN_DAYS = 1 is dropped. For how many total days can the data potentially be recovered?

Answer: 1 day only. Transient tables have NO fail-safe period. Once the 1-day Time Travel window expires after the DROP, the data is permanently purged. Compare to a permanent table: 1 day TT + 7 days fail-safe = 8 days total.

Q3: You clone a database that contains a Snowpipe, a task graph (3 tasks), and 5 streams. What is the state of these objects in the clone?

Answer:

  • Pipes: Cloned but SUSPENDED/PAUSED — must be manually resumed
  • Tasks: All 3 cloned but SUSPENDED — must resume leaf tasks first, then root
  • Streams: Cloned with offset preserved (source tables also in clone scope) — but may go STALE if offset references data beyond TT retention of the cloned table

Q4: An Enterprise account sets DATA_RETENTION_TIME_IN_DAYS = 90 at the database level. A new table is created in that database with no explicit retention setting. What is the table's retention?

Answer: 90 days. New objects inherit the retention setting from their parent (table inherits from schema, schema from database). Since no schema or table override exists, the table gets the database-level setting of 90 days.

Q5: You clone a table and then DROP the original source table. After Time Travel and Fail-safe expire for the source, who pays for the storage of the shared micro-partitions?

Answer: The clone becomes the sole owner of all micro-partitions that were previously shared. The full storage cost is now attributed to the clone. This is a common exam trap — zero-copy cloning means zero additional storage at creation time, but ownership transfers when the source is purged.

Q6: Can you perform Time Travel on a view? What about a materialized view?

Answer: NO for regular views — views have no data, only a definition. For materialized views: you cannot directly time-travel the MV object, but you CAN time-travel the underlying base table and the MV's cached results reflect the base table's state at that point (indirectly).

Q7: A table in a TRANSIENT schema has DATA_RETENTION_TIME_IN_DAYS explicitly set to 5. Is this valid?

Answer: NO — this will fail. Tables in transient schemas are implicitly transient, and transient tables have a maximum retention of 1 day. Setting retention > 1 on a transient table produces an error. The valid range is 0 or 1.

Q8: You DROP a schema, then CREATE a new schema with the same name, then try UNDROP SCHEMA. What happens?

Answer: UNDROP fails with an object-already-exists error. The new schema occupies the same namespace. Resolution: ALTER SCHEMA new_schema RENAME TO temp_name, then UNDROP SCHEMA original_name. This is the same pattern as table UNDROP name conflicts.

Q9: You clone a production database for development. A developer in dev runs a DELETE on a cloned table. Does this affect production storage costs?

Answer: NO. The clone and source are independent after creation. The DELETE in the clone writes new micro-partitions (or marks existing ones as deleted) only in the clone's context. Production's storage is unaffected. However, the clone's TT will store the pre-DELETE state, increasing the clone's storage footprint.

Q10: An internal stage exists in a schema. You clone the schema. What happens to the files in that stage?

Answer: The cloned schema contains a new, empty stage with the same name and properties. Files are NOT copied. Internal stage data is not cloned — only the stage definition. External stages are cloned with their definition (URL, credentials reference), pointing to the same external location. This is a critical exam distinction.

Quick Exam Mnemonics

  • T-T-P: Transient/Temporary = no fail-safe, Permanent = 7-day fail-safe
  • S-P-T: Streams, Pipes, Tasks in clones = Suspended (must manually resume)
  • COR = D+C: CREATE OR REPLACE = DROP (old enters TT) + CREATE (new, no history)
  • Clone ≠ Grants: Privileges never auto-copied unless COPY GRANTS specified
  • Zero-copy ≠ Zero-cost: Storage diverges over time, especially after source DROP
