1. What is Snowflake Data Sharing

Core Concept: Zero-Copy Data Sharing

Snowflake Data Sharing enables providers to share live, read-only data with consumers without copying or moving the data. Consumers access the provider's actual storage layer directly through Snowflake's metadata and access-control layer.

┌─────────────────────┐ ┌─────────────────────┐ │ DATA PROVIDER │ │ DATA CONSUMER │ │ │ │ │ │ ┌───────────────┐ │ Share Object │ ┌───────────────┐ │ │ │ Database │ │ ──────────────────►│ │ Imported DB │ │ │ │ └─ Schema │ │ (metadata only) │ │ (read-only) │ │ │ │ └─ Tables │ │ │ │ └─ Tables │ │ │ └───────────────┘ │ │ └───────────────┘ │ │ │ │ │ │ ┌───────────────┐ │ │ │ │ │ Cloud Storage │◄─┼────────────────────┼─── Queries read │ │ │ (micro-parts) │ │ Zero-copy access │ directly from │ │ └───────────────┘ │ │ provider storage │ └─────────────────────┘ └─────────────────────┘

Key Principles

  • Zero-Copy: No data is duplicated; consumers query the provider's stored micro-partitions directly
  • No Data Movement: Data never leaves the provider's account storage; only metadata pointers are shared
  • Real-Time Access: Consumers see data changes immediately — no ETL lag, no stale copies
  • Provider/Consumer Model: Providers create shares; consumers create databases from shares
  • Same Region/Cloud Required: Both accounts must be in the same cloud region (unless using replication for cross-region)
  • Consumer Pays for Compute: The consumer uses their own virtual warehouses; provider pays only for storage
Exam Tip

The most tested concept: "No data is copied or transferred". Snowflake sharing leverages the services layer and metadata — the underlying micro-partitions are accessed in place. The consumer never owns or stores the shared data.

How it Works (Under the Hood)

  1. Provider creates a SHARE object and grants privileges on databases/schemas/objects
  2. Provider adds consumer account(s) to the share
  3. Consumer creates a database FROM SHARE (this is an imported/mounted database)
  4. Consumer queries shared objects using their own compute (warehouse)
  5. Queries read directly from the provider's cloud storage layer (S3, Azure Blob, GCS)
Key Distinction

Sharing ≠ Replication. Sharing provides read-only access via metadata. Replication physically copies data across accounts/regions for DR or performance. Sharing is instant and free for the provider (no storage cost); replication incurs storage and compute costs.

2. Share Objects

Creating and Managing Shares

A SHARE is a named Snowflake object that encapsulates all the information needed to share data. Only ACCOUNTADMIN (or roles with CREATE SHARE privilege) can create shares.

-- Step 1: Create a share
CREATE SHARE sales_share
  COMMENT = 'Quarterly sales data for partner accounts';

-- Step 2: Grant usage on database and schema
GRANT USAGE ON DATABASE sales_db TO SHARE sales_share;
GRANT USAGE ON SCHEMA sales_db.public TO SHARE sales_share;

-- Step 3: Grant SELECT on specific objects
GRANT SELECT ON TABLE sales_db.public.orders TO SHARE sales_share;
GRANT SELECT ON VIEW sales_db.public.v_order_summary TO SHARE sales_share;

-- Step 4: Add consumer accounts
ALTER SHARE sales_share ADD ACCOUNTS = org1.consumer_acct1, org1.consumer_acct2;

-- Optional: Restrict share to specific accounts with SHARE_RESTRICTIONS
ALTER SHARE sales_share ADD ACCOUNTS = org1.consumer_acct1
  SHARE_RESTRICTIONS = FALSE; -- Allow sharing across Business Critical editions

Required Grant Hierarchy

Privileges must be granted in order — you cannot skip levels:

StepCommandPurpose
1GRANT USAGE ON DATABASEConsumer can see the database exists
2GRANT USAGE ON SCHEMAConsumer can see the schema within the DB
3GRANT SELECT ON TABLE/VIEWConsumer can query specific objects
Common Exam Trap

If you grant SELECT on a table but forget to grant USAGE on the database or schema, the consumer will get an error. All three levels must be granted. This is the #1 troubleshooting question on data sharing.

Consumer Side: Creating a Database from a Share

-- Consumer account creates a database from the share
CREATE DATABASE shared_sales_db FROM SHARE provider_org.provider_acct.sales_share;

-- Grant access to roles in the consumer account
GRANT IMPORTED PRIVILEGES ON DATABASE shared_sales_db TO ROLE analyst_role;

-- Consumers can now query (read-only)
SELECT * FROM shared_sales_db.public.orders LIMIT 10;

Managing Shares

-- View all outbound shares from your account
SHOW SHARES;

-- Describe what's in a share
DESCRIBE SHARE sales_share;

-- Revoke access from a consumer
ALTER SHARE sales_share REMOVE ACCOUNTS = org1.consumer_acct2;

-- Revoke an object from the share
REVOKE SELECT ON TABLE sales_db.public.orders FROM SHARE sales_share;

-- Drop a share entirely
DROP SHARE sales_share;
Exam Tip

Only ACCOUNTADMIN or a role with the CREATE SHARE global privilege can create shares. On the consumer side, only ACCOUNTADMIN can create a database from an inbound share (using CREATE DATABASE ... FROM SHARE). They can then grant IMPORTED PRIVILEGES to other roles.

3. Secure Views

Why Secure Views Are Needed for Sharing

Regular views expose their DDL definition to anyone with access, which means a consumer could see the underlying table structure, filter logic, and business rules. Secure Views hide the view definition and prevent query optimization techniques that could leak data.

Regular View

  • View DDL visible via GET_DDL() or SHOW VIEWS
  • Query optimizer can push predicates past the view
  • Consumer could infer filtered-out data
  • Cannot be shared — Snowflake blocks non-secure views in shares

Secure View

  • View DDL is hidden from non-owners
  • Optimizer bypasses disabled — prevents data leakage
  • Consumer sees only the output, never the logic
  • Can be shared — required for view-based sharing
-- Create a secure view for sharing
CREATE OR REPLACE SECURE VIEW sales_db.public.sv_customer_orders AS
SELECT
    o.order_id,
    o.order_date,
    o.total_amount,
    c.customer_name,
    c.region
FROM sales_db.private.orders o
JOIN sales_db.private.customers c ON o.customer_id = c.customer_id
WHERE c.sharing_consent = TRUE;  -- Only share consented data

-- Convert an existing view to secure
ALTER VIEW sales_db.public.v_summary SET SECURE;

-- Verify a view is secure
SHOW VIEWS LIKE 'sv_%' IN SCHEMA sales_db.public;
-- Check 'is_secure' column = 'true'

Query Optimization Implications

Performance Trade-off

Secure views disable the optimizer's ability to push predicates and pruning logic into the view definition. This means:

  • Predicate pushdown is blocked: A consumer's WHERE clause cannot be optimized past the view boundary
  • Potential performance impact: The view must materialize its full result set before the consumer's filters apply
  • No access to internal functions: Functions like CURRENT_ACCOUNT() work correctly inside secure views for row-level filtering

Secure View + Multi-Tenant Sharing Pattern

-- Multi-tenant secure view using CURRENT_ACCOUNT()
CREATE SECURE VIEW shared_data.public.sv_tenant_sales AS
SELECT order_id, product, quantity, amount
FROM internal.dw.fact_sales
WHERE tenant_account = CURRENT_ACCOUNT();
-- Each consumer only sees their own rows
Exam Tip

You CANNOT share regular (non-secure) views. Snowflake enforces this — attempting to grant a non-secure view to a share will fail. This is a frequently tested point. Always use CREATE SECURE VIEW for any view intended for sharing.

4. Secure UDFs

Why Secure UDFs?

Similar to secure views, Secure UDFs hide the function's internal logic (source code) from consumers. Without the SECURE keyword, any user with USAGE on a UDF can view its definition, potentially exposing proprietary algorithms or business logic.

-- Create a secure scalar UDF
CREATE OR REPLACE SECURE FUNCTION pricing.public.calculate_discount(
    base_price NUMBER(10,2),
    customer_tier VARCHAR
)
RETURNS NUMBER(10,2)
LANGUAGE SQL
AS
$$
  CASE customer_tier
    WHEN 'PLATINUM' THEN base_price * 0.75
    WHEN 'GOLD'     THEN base_price * 0.85
    WHEN 'SILVER'   THEN base_price * 0.92
    ELSE base_price
  END
$$;

-- Grant UDF usage to a share
GRANT USAGE ON FUNCTION pricing.public.calculate_discount(NUMBER, VARCHAR)
  TO SHARE partner_share;

Secure UDF Behavior

AspectRegular UDFSecure UDF
Source code visibilityVisible via GET_DDL()Hidden from non-owners
Can be sharedYes, but logic exposedYes, logic protected
Optimizer behaviorInline expansion possibleTreated as opaque/black-box
Error messagesMay reveal internal detailsGeneric error messages only
Supported languagesSQL, JavaScript, Python, Java, ScalaSame — all languages supported
 
-- Convert existing UDF to secure
ALTER FUNCTION pricing.public.calculate_discount(NUMBER, VARCHAR) SET SECURE;

-- Secure table function (UDTF) example
CREATE OR REPLACE SECURE FUNCTION analytics.public.get_risk_scores(acct_id VARCHAR)
RETURNS TABLE (risk_category VARCHAR, score FLOAT)
LANGUAGE SQL
AS
$$
  SELECT category, calculated_score
  FROM internal.ml.risk_model_output
  WHERE account_id = acct_id
$$;
Key Point

Secure UDFs are commonly used in sharing to provide derived/computed values to consumers without exposing the underlying formula or source data. The consumer can call the function but cannot reverse-engineer how it works.

5. Reader Accounts (Managed Accounts)

What Are Reader Accounts?

Reader accounts (also called Managed Accounts) are Snowflake accounts created by a data provider specifically for consumers who do not have their own Snowflake account. They allow non-Snowflake organizations to access shared data.

┌─────────────────────────────────────────────────────┐ │ DATA PROVIDER │ │ │ │ ┌──────────┐ ┌──────────────────────────┐ │ │ │ Share │─────►│ Reader Account │ │ │ │ Object │ │ (managed by provider) │ │ │ └──────────┘ │ │ │ │ │ - Provider pays compute │ │ │ │ - Limited functionality │ │ │ │ - Read-only access │ │ │ │ - Uses resource monitors │ │ │ └──────────────────────────┘ │ └─────────────────────────────────────────────────────┘ 
-- Create a reader (managed) account
CREATE MANAGED ACCOUNT partner_reader
  ADMIN_NAME = 'reader_admin',
  ADMIN_PASSWORD = 'StrongP@ss123!',
  TYPE = READER;

-- Add the reader account to a share
ALTER SHARE sales_share ADD ACCOUNTS = <reader_account_locator>;

-- Show managed accounts
SHOW MANAGED ACCOUNTS;

Who Pays?

Critical for Exam

The PROVIDER pays for all compute (warehouse) costs consumed by reader accounts. This is the single most important fact about reader accounts. The provider should set up resource monitors to control costs.

Reader Accounts vs Full Accounts

CapabilityReader AccountFull Snowflake Account
Query shared dataYesYes
Create own databases/tablesNo (read-only)Yes
Load dataNoYes
Create shares (re-share)NoYes

Data replicationNoYes

Exam Tip

Reader accounts can ONLY consume data from the provider that created them. They cannot receive shares from other providers, cannot create their own data, and cannot share data with others. Think of them as read-only terminals into the provider's shared data.

6. Listing Types

Snowflake Marketplace & Listings Overview

Listings are the mechanism for publishing shared data (or apps) to consumers through Snowflake's collaboration features. There are three primary listing types:

Listing TypeAudienceDiscoveryPricingUse Case
Private Listing Specific, named accounts Not discoverable; provider invites consumer Free (no commercial terms via Snowflake) B2B data sharing with known partners, subsidiaries, or teams in different accounts
Personalized Listing Any consumer who requests access Visible in Marketplace; requires approval Free or Paid (custom commercial terms) Data products needing provider approval before access (compliance, onboarding)
Marketplace Listing All Snowflake customers (public) Discoverable in Snowflake Marketplace Free or Paid Public data products (weather, financial, demographics, etc.)

Free vs Paid Listings

Free Listings

  • Consumer gets instant access (or after approval for Personalized)
  • No payment flow through Snowflake
  • Provider may have external billing arrangements
  • Common for: open data, freemium models, internal org sharing

Paid Listings

  • Commercial terms defined in the listing
  • Snowflake handles billing/payment
  • Provider receives payment via Snowflake
  • Common for: premium data providers, data-as-a-service products

Listing Workflow

  1. Provider creates a share (data) or application package (app)
  2. Provider creates a listing in the Snowflake UI or via SQL/API, selecting type and terms
  3. Consumer discovers the listing (via Marketplace or direct invitation)
  4. Consumer requests access (Personalized) or gets instant access (Private/Public Free)
  5. Consumer creates a database from the share in their account
Cross-Cloud & Cross-Region Sharing

Listings can be configured for cross-cloud/cross-region auto-fulfillment. Snowflake uses database replication behind the scenes to serve consumers in different regions. The provider sets replication policies; costs apply for cross-region data replication.

Exam Tip

Know the differences: Private = invitation-only, no Marketplace visibility. Personalized = visible in Marketplace but requires approval. Standard Marketplace = open to all. Private listings use direct shares; Marketplace listings use the Snowflake Marketplace infrastructure.

Shareable Objects

Object TypeShareable?Notes
TablesYESStandard, dynamic, external, and Iceberg tables
Secure ViewsYESRequired — non-secure views cannot be shared
Secure Materialized ViewsYESMust be marked SECURE
Secure UDFsYESAll languages (SQL, JS, Python, Java, Scala)

Schemas (USAGE)YESRequired grant for any sharing

Objects That CANNOT Be Shared

Object TypeShareable?Why Not
Stages (Internal/External)NOFiles in stages are not queryable objects; use tables instead
Pipes (Snowpipe)NOIngestion infrastructure; not data objects
TasksNOScheduling/orchestration; consumer must create their own
StreamsNOChange tracking metadata; specific to provider's operations
SequencesNOAuto-increment generators are account-level objects
Non-Secure ViewsNOSecurity risk — DDL would be exposed to consumers
Stored ProceduresNOCannot be granted to shares (use secure UDFs instead)
File FormatsNOMetadata for staging; not data objects
WarehousesNOCompute resources cannot be shared across accounts
Users / RolesNOIdentity and access are account-local
Exam Tip

Memorize this list: Cannot share: Stages, Pipes, Tasks, Streams, Sequences, Non-secure Views, Stored Procedures, File Formats, Warehouses, Users/Roles. A common question format: "Which of the following can be included in a share?" — eliminate anything infrastructure/operational.

Mnemonic: "SPTSF" Cannot Be Shared

Stages, Pipes, Tasks, Streams, File Formats — these are all operational/ingestion objects, not data objects. If it helps data get INTO a table (rather than being the table itself), it probably can't be shared.

8. 15 Key Features & 15 Limitations

15 Key Features of Snowflake Data Sharing

1
Zero-Copy Architecture: No data duplication; consumers read from provider's storage
2
Real-Time Access: Changes to provider data are instantly visible to consumers
3
No ETL Required: Eliminates data pipelines between provider and consumer
4
Secure by Default: Consumers cannot modify shared data; access is always read-only
5
Granular Control: Share individual tables, views, or UDFs — not everything-or-nothing
6
Multi-Tenant Views: CURRENT_ACCOUNT() enables row-level filtering per consumer
7
Instant Provisioning: Consumers get access in seconds (no file transfers or setup)
8
Consumer Pays Compute: Provider has zero compute cost for full-account consumers
9
Reader Accounts: Share with non-Snowflake users via managed accounts
10
Marketplace Distribution: Publish data products to all Snowflake customers globally
11
Cross-Region Replication: Auto-fulfillment replicates data for cross-region consumers
12
Revocable Access: Provider can remove accounts or objects from shares at any time
13
No Vendor Lock-in for Consumer: Consumer uses standard SQL to query shared data
14
Time Travel on Shared Data: Consumers can use Time Travel on shared tables (within provider's retention)
15
Secure Function Sharing: Share computed results via secure UDFs without exposing algorithms

15 Limitations of Snowflake Data Sharing

1
Same Region Required: Direct sharing needs both accounts in same cloud/region (replication for cross-region)
2
Read-Only Only: Consumers cannot write, update, or delete shared data
3
No Operational Objects: Cannot share stages, pipes, tasks, streams, or sequences
4
Secure Views Required: Non-secure views cannot be included in shares
5
No Stored Procedures: Cannot share procedures; only UDFs (with SECURE) are supported
6
Provider Storage Cost: Provider pays all storage regardless of how many consumers exist
7
Reader Account Costs: Provider pays all compute for reader (managed) accounts
8
ACCOUNTADMIN Required: Only ACCOUNTADMIN can create databases from shares (consumer side)
9
No Cloning Shared DBs: Consumers cannot clone a database created from a share
10
Secure View Performance: Optimizer restrictions on secure views can reduce query performance
11
No Re-Sharing (Direct): Consumers cannot re-share data received from another provider's share
12
Schema Evolution Risks: If provider drops a shared table, consumer queries break immediately
13
No Cross-Database Views in Shares: Shared secure views cannot reference objects in other databases
14
Limited Reader Functionality: Reader accounts cannot load data, create shares, or access Marketplace
15
Time Travel Limited: Consumer Time Travel is bounded by provider's DATA_RETENTION_TIME_IN_DAYS setting

Study Strategy

For the SnowPro Core exam, focus on: (1) what makes sharing "zero-copy", (2) the required privilege hierarchy for shares, (3) why secure views are mandatory, (4) who pays for reader accounts, and (5) what objects cannot be shared. These five areas cover roughly 80% of data sharing questions on the exam.
