1. Provider Workflow

The provider (data owner) creates and manages outbound shares. The complete lifecycle:

CREATE SHARE → GRANT privileges on objects → ADD ACCOUNTS → Consumer creates DB FROM SHARE

Step-by-Step SQL

-- 1. Create the share
CREATE SHARE sales_share
  COMMENT = 'Q4 Sales Data for Partner Corp';

-- 2. Grant usage on database and schema
GRANT USAGE ON DATABASE analytics_db TO SHARE sales_share;
GRANT USAGE ON SCHEMA analytics_db.public TO SHARE sales_share;

-- 3. Grant SELECT on specific objects
GRANT SELECT ON TABLE analytics_db.public.orders TO SHARE sales_share;
GRANT SELECT ON VIEW analytics_db.public.orders_secure_vw TO SHARE sales_share;

-- 4. Add consumer account(s)
ALTER SHARE sales_share ADD ACCOUNTS = xy12345, ab67890;

-- 5. (Optional) Add with SHARE_RESTRICTIONS override
ALTER SHARE sales_share ADD ACCOUNTS = cd99999
  SHARE_RESTRICTIONS = false;

Key Rules for Providers

  • Only secure views, secure UDFs, and secure UDTFs can be shared (not regular views)
  • Tables, external tables, and secure views are the primary shareable object types
  • You cannot share a transient or temporary table directly (wrap with a secure view)
  • Shares are read-only — consumers cannot write to shared objects
  • A share can include objects from only one database
  • Each share is an independent unit — objects cannot belong to multiple shares unless added individually to each

Revoking/Removing Access

-- Remove specific account
ALTER SHARE sales_share REMOVE ACCOUNTS = xy12345;

-- Revoke object from share
REVOKE SELECT ON TABLE analytics_db.public.orders FROM SHARE sales_share;

-- Drop entire share
DROP SHARE sales_share;
Exam Tip: Dropping a share instantly removes consumer access. The consumer's database created from the share becomes invalid and must be dropped.

2. Consumer Workflow

Consumers create a local database from an inbound share and query shared data as if it were local.

Viewing Available Shares

-- Show all inbound shares (from other accounts)
SHOW SHARES;

-- Filter to only inbound
SHOW SHARES LIKE '%sales%';

-- Describe share contents before creating DB
DESC SHARE provider_org.provider_acct.sales_share;

Creating a Database from a Share

-- Create database from the share
CREATE DATABASE partner_sales_db FROM SHARE provider_org.provider_acct.sales_share;

-- Grant access to roles in consumer account
GRANT IMPORTED PRIVILEGES ON DATABASE partner_sales_db TO ROLE analyst_role;

Querying Shared Data

-- Query as if it's a local table
SELECT order_id, customer_name, amount
FROM partner_sales_db.public.orders
WHERE order_date >= '2026-01-01';

-- Joins with local data are fully supported
SELECT s.order_id, l.customer_segment
FROM partner_sales_db.public.orders s
JOIN local_db.public.customers l ON s.customer_id = l.id;

Consumer Constraints

ActionAllowed?Notes
SELECT from shared objectsYesPrimary use case
CREATE VIEW on shared dataYesLocal views referencing shared tables
INSERT/UPDATE/DELETENoShares are strictly read-only
Clone shared objectsNoCannot clone shared databases or tables
Time Travel on shared dataNoNot available for consumers
Create additional schemas in shared DBNoThe shared DB is read-only
Re-share to another accountNoCannot share a share
Exam Tip: Use GRANT IMPORTED PRIVILEGES (not GRANT SELECT) to give roles access to a shared database. This is the only privilege type that applies to databases created from shares.

3. Data Marketplace

The Snowflake Marketplace is a platform for discovering, publishing, and consuming data listings.

Listing Types

TypeVisibilityDescription
Standard ListingPublicVisible to all Snowflake accounts on the Marketplace
Personalized ListingTargetedShared with specific accounts via private link
Free ListingPublic/TargetedInstant access, no payment required
Paid ListingPublic/TargetedRequires commercial agreement, usage-based or fixed pricing

Publishing a Listing (Provider)

  1. Create a share with the data products
  2. Navigate to Data > Provider Studio in Snowsight
  3. Create a new listing:
    • Select the share as the data source
    • Add title, description, sample queries, and documentation
    • Choose listing visibility (public vs. targeted)
    • Set pricing (free or paid)
    • Configure auto-fulfillment regions (if cross-region)
  4. Submit for review (public listings require Snowflake approval)

Getting/Consuming a Listing (Consumer)

  1. Browse Marketplace in Snowsight or search by category/provider
  2. Click Get on a free listing (instant) or Request for paid
  3. Snowflake creates a database from the listing's share automatically
  4. Grant IMPORTED PRIVILEGES to roles that need access
  5. Begin querying — data is live, not a copy

Key Marketplace Concepts

  • No data movement — consumers access live data in provider's account (same region)
  • Instant access for free listings; paid requires provider approval
  • Usage-based billing possible for paid listings via Snowflake's billing integration
  • Provider Studio — the UI for managing listings, analytics, and fulfillment
  • Data Exchange (legacy) — private, invite-only marketplace for groups of accounts
Important: Public listings require Snowflake review. Personalized/private listings do not require review and are available immediately.

4. Cross-Region/Cloud Sharing

Snowflake's native sharing is same-region only. For cross-region or cross-cloud sharing, replication is required.

How Cross-Region Sharing Works

Provider (us-east-1) → DATABASE REPLICATION → Secondary DB (eu-west-1) → Share served from secondary

Replication Requirements

RequirementDetails
Business Critical EditionRequired for replication (or higher)
Replication enabled on accountALTER ACCOUNT SET ENABLE_ACCOUNT_REPLICATION = TRUE;
Replication group or DB replicationMust replicate the DB containing shared objects
Network connectivityAutomatic between Snowflake regions

Auto-Fulfillment

For Marketplace listings, Snowflake supports auto-fulfillment, which automates replication:

  • Provider configures which regions to serve from in Provider Studio
  • Snowflake automatically replicates data to those regions
  • Consumers in those regions get the listing served locally
  • Provider pays for replication storage and compute costs
  • Refresh frequency is configurable (e.g., daily, hourly)

Manual Cross-Region Setup

-- On PRIMARY account: enable replication
ALTER DATABASE analytics_db ENABLE REPLICATION TO ACCOUNTS org.target_acct;

-- On SECONDARY account: create replica
CREATE DATABASE analytics_db AS REPLICA OF org.source_acct.analytics_db;

-- Refresh the replica
ALTER DATABASE analytics_db REFRESH;

-- Create share on secondary account referencing replicated DB
CREATE SHARE sales_share;
GRANT USAGE ON DATABASE analytics_db TO SHARE sales_share;
-- ... add objects and consumer accounts
Exam Tip: Cross-region sharing always incurs replication costs (storage + data transfer). The provider pays these costs, not the consumer.

5. Multi-Account Sharing Patterns

Hub-and-Spoke Model

A central account (hub) shares data with multiple consumer accounts (spokes):

Spoke A ←— HUB ACCOUNT (provider) —→ Spoke B
               ↓
          Spoke C
  • Single source of truth in the hub
  • Each spoke gets its own share (or shared share with multiple accounts)
  • Common for organizations with regional subsidiaries or partner networks

Mesh Model

Multiple accounts share bidirectionally:

  • Each account is both a provider and a consumer
  • Requires separate shares for each direction
  • Complex RBAC requirements — each account manages its own shares

Reader Accounts

For sharing with non-Snowflake customers:

-- Create a managed (reader) account
CREATE MANAGED ACCOUNT partner_reader
  ADMIN_NAME = 'partner_admin'
  ADMIN_PASSWORD = '***'
  TYPE = READER;

-- Add reader account to share
ALTER SHARE sales_share ADD ACCOUNTS = <reader_account_locator>;
FeatureFull AccountReader Account
Can load own dataYesNo
Can create objectsYesLimited (views on shared data)
Compute costs paid byConsumerProvider
Can share data outboundYesNo
Managed bySelfProvider account
Cost Alert: Provider pays ALL compute costs for reader accounts. Monitor usage carefully with resource monitors.

6. RBAC for Sharing

Key Privileges

PrivilegeScopeDescription
CREATE SHAREAccountCreate outbound shares (provider side)
IMPORT SHAREAccountCreate databases from inbound shares (consumer side)
OVERRIDE SHARE RESTRICTIONSAccountShare with Business Critical to non-BC accounts
IMPORTED PRIVILEGESDatabaseGrant all privileges on a shared database to a role
CREATE DATA EXCHANGE LISTINGAccountPublish listings to a data exchange

Default Role Assignments

-- ACCOUNTADMIN has all sharing privileges by default

-- Grant sharing ability to a custom role
GRANT CREATE SHARE ON ACCOUNT TO ROLE data_provider_role;
GRANT IMPORT SHARE ON ACCOUNT TO ROLE data_consumer_role;

-- Override share restrictions (Business Critical → non-BC)
GRANT OVERRIDE SHARE RESTRICTIONS ON ACCOUNT TO ROLE data_provider_role;

OVERRIDE SHARE RESTRICTIONS

By default, Business Critical accounts cannot share with non-Business-Critical accounts (security guardrail). This privilege overrides that restriction:

  • Required when a BC account needs to share with Standard/Enterprise accounts
  • The SHARE_RESTRICTIONS parameter on ALTER SHARE ADD ACCOUNTS must also be set to false
  • Exam may test this as a scenario: "Why can't my BC account share with account X?"

Provider-Side RBAC Pattern

-- Recommended: Dedicated role for managing shares
CREATE ROLE share_admin;
GRANT CREATE SHARE ON ACCOUNT TO ROLE share_admin;
GRANT USAGE ON DATABASE analytics_db TO ROLE share_admin;
GRANT USAGE ON SCHEMA analytics_db.public TO ROLE share_admin;
GRANT SELECT ON ALL TABLES IN SCHEMA analytics_db.public TO ROLE share_admin;

-- Role hierarchy
GRANT ROLE share_admin TO ROLE sysadmin;
Exam Tip: Only ACCOUNTADMIN has IMPORT SHARE by default. It must be explicitly granted to other roles for them to create databases from shares.

7. Monitoring Shares

SHOW Commands

-- All shares (outbound + inbound)
SHOW SHARES;

-- Outbound shares only
SHOW SHARES LIKE '%sales%';

-- Describe specific share (see objects included)
DESC SHARE sales_share;

-- Show grants to a share
SHOW GRANTS TO SHARE sales_share;

-- Show grants of a share (which accounts have access)
SHOW GRANTS OF SHARE sales_share;

INFORMATION_SCHEMA Views

ViewPurpose
APPLICABLE_ROLESRoles with sharing-related privileges
OBJECT_PRIVILEGESPrivileges granted on shared objects

ACCOUNT_USAGE Views

ViewPurposeLatency
SNOWFLAKE.ACCOUNT_USAGE.SHARESAll shares (created, dropped, modified)Up to 120 min
SNOWFLAKE.ACCOUNT_USAGE.DATA_TRANSFER_HISTORYReplication transfers for cross-region sharesUp to 120 min
SNOWFLAKE.ACCOUNT_USAGE.REPLICATION_USAGE_HISTORYReplication compute and costUp to 120 min
SNOWFLAKE.ACCOUNT_USAGE.ACCESS_HISTORYWho accessed shared objectsUp to 120 min
SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORYQueries run against shared objectsUp to 45 min

Monitoring Queries

-- List all active outbound shares with consumer accounts
SELECT share_name, created_on, database_name, comment
FROM SNOWFLAKE.ACCOUNT_USAGE.SHARES
WHERE deleted_on IS NULL;

-- Replication costs for cross-region shares
SELECT start_time, database_name, credits_used, bytes_transferred
FROM SNOWFLAKE.ACCOUNT_USAGE.REPLICATION_USAGE_HISTORY
WHERE start_time >= DATEADD(day, -30, CURRENT_TIMESTAMP())
ORDER BY start_time DESC;

-- Consumer query activity on shared data (provider side)
-- Available only via READER_ACCOUNT_USAGE for reader accounts
SELECT query_id, user_name, warehouse_name, execution_time
FROM SNOWFLAKE.READER_ACCOUNT_USAGE.QUERY_HISTORY
WHERE start_time >= DATEADD(day, -7, CURRENT_TIMESTAMP());
Exam Tip: Providers can see metadata about reader account usage via SNOWFLAKE.READER_ACCOUNT_USAGE, but cannot see queries run by full consumer accounts.

8. Best Practices

Governance

  • Always use secure views — regular views expose their DDL to consumers, potentially leaking business logic
  • Apply row-level security via secure views with CURRENT_ACCOUNT() or CURRENT_ROLE()
  • Document shared objects with COMMENT on shares and objects
  • Use column-level masking policies on underlying tables (applied before share)
  • Audit consumer access patterns via ACCOUNT_USAGE views

Secure Views — Required for Sharing

-- Regular view: DDL visible to consumers (NOT shareable)
CREATE VIEW orders_vw AS SELECT * FROM orders;

-- Secure view: DDL hidden, optimizer fence applied (shareable)
CREATE SECURE VIEW orders_secure_vw AS
SELECT order_id, customer_name, amount, order_date
FROM orders
WHERE region = 'NA';

Performance Considerations

  • Secure views disable certain optimizer pushdowns — design underlying queries carefully
  • Consumers use their own warehouses for compute — no provider cost for full accounts
  • Clustering keys on shared tables benefit consumer query performance
  • Avoid overly complex secure views (multi-level nesting) that slow consumer queries
  • Reader accounts use provider warehouses — set resource monitors

Cost Management

Cost TypePaid ByApplies When
Storage of shared dataProviderAlways (data stays in provider account)
Compute for queriesConsumerFull accounts querying shared data
Compute for reader accountsProviderReader accounts querying shared data
Replication (cross-region)ProviderCross-region/cloud sharing
Data transfer (egress)ProviderCross-cloud replication

Security Best Practices

  • Never share base tables directly — wrap in secure views for column/row filtering
  • Periodically review SHOW GRANTS OF SHARE to verify consumer list
  • Use SHARE_RESTRICTIONS thoughtfully with Business Critical accounts
  • Implement data retention policies — shared data follows provider's Time Travel/Fail-safe settings
  • Separate share-management duties with a dedicated SHARE_ADMIN role
Exam Tip: The provider bears NO compute cost for full consumer accounts querying shared data. Compute cost is only a provider concern for reader accounts and replication.
