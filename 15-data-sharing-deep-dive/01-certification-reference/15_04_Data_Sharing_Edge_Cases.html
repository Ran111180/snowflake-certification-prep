Data Sharing Edge Cases

Critical scenarios, limitations, and gotchas for SnowPro Certification

1. Supported & Unsupported Objects for Sharing

Object Type Shareable? Notes
Tables YES Standard, dynamic, and external tables
Secure Views YES Most common sharing pattern; hides DDL from consumer
Secure Materialized Views YES Must be SECURE; regular mat views cannot be shared
Secure UDFs YES Must be SECURE; SQL and JavaScript UDFs supported
Schemas (containing above) YES Grant at schema level shares all qualifying objects within
Stages NO Cannot share internal or external stages
Pipes NO Snowpipe objects are account-specific
Tasks NO Scheduling objects cannot cross account boundary
Streams NO Change tracking is local to the source account
Non-Secure Views NO Must be SECURE to prevent DDL exposure
Sequences NO Not shareable; consumer must create own
Stored Procedures NO Cannot share procedures directly
Exam Tip: The exam loves testing whether non-secure views can be shared (they CANNOT). Only SECURE views, SECURE materialized views, and SECURE UDFs are shareable. Regular views expose their DDL definition.

2. Provider DDL Impact on Consumers

DROP Shared Object

Action Consumer Impact Recovery
DROP TABLE in shared schema Immediate query failure for consumers UNDROP TABLE (if within Time Travel) or re-add new table to share
DROP SCHEMA containing shared objects All shared objects in schema become unavailable UNDROP SCHEMA or recreate & re-grant
DROP DATABASE with active shares Entire share becomes empty; consumer DB shows no objects UNDROP DATABASE or rebuild share
DROP SHARE Consumer's imported database is immediately dropped Must recreate share and consumer must re-import

ALTER Operations

  • ALTER TABLE ... RENAME — Consumer sees the new name immediately; existing queries using old name break
  • ALTER TABLE ... ADD COLUMN — New column visible to consumer immediately
  • ALTER TABLE ... DROP COLUMN — Column disappears immediately; consumer queries referencing it fail
  • ALTER VIEW ... AS (redefine) — Consumer sees new definition on next query

Revoke Access

  • REVOKE SELECT ON TABLE ... FROM SHARE — Table no longer visible to consumer
  • ALTER SHARE ... REMOVE ACCOUNTS = ... — Consumer loses access entirely; imported DB is dropped
  • REVOKE USAGE ON SCHEMA ... FROM SHARE — All objects in that schema become invisible
Critical: When a provider drops a share (DROP SHARE), the consumer's imported database is automatically and immediately dropped. There is no grace period or warning. This is a frequently tested edge case.

3. Consumer Limitations

Limitation Details
Read-Only Access Cannot INSERT, UPDATE, DELETE, or MERGE on shared objects. SELECT and show metadata only.
Cannot Clone Shared Database CREATE DATABASE ... CLONE fails on an imported (shared) database. Must clone individual tables into a local DB instead.
Cannot Re-Share A consumer cannot add objects from a shared database to their own outbound share. Data cannot be re-shared to third parties.
Cannot Create Objects in Shared DB Cannot create tables, views, schemas, or any object inside the imported database. It is entirely provider-controlled.
Cannot Use Time Travel Time Travel queries (AT/BEFORE) are not available on shared objects. Only current data is accessible.
No Fail-safe Access Consumer has no access to fail-safe data for shared objects.
Cannot Create Streams on Shared Objects Change tracking (streams) cannot be created on objects in an imported database.
Limited SHOW Commands Some metadata commands may show limited info compared to owned objects.
Workaround Pattern: To transform or persist shared data locally, consumers can CREATE TABLE ... AS SELECT from the shared view/table into their own database. This creates a local copy they fully control (but it won't auto-update).

4. Reader Account Edge Cases

What is a Reader Account?

A reader account (formerly "read-only account") is a Snowflake account created BY the provider specifically for consumers who do not have their own Snowflake account.

Aspect Reader Account Full Account (Consumer)
Compute Cost Provider Pays Consumer pays own compute
Can access shares from other providers? NO YES
Can create own databases/tables? NO (very limited) YES
Replication support NO YES
Resource Monitors Provider sets via resource monitors on reader warehouse Consumer manages own
Who manages users? Provider creates/manages users in reader account Consumer manages own users
Data loading NO YES
Exam Favorite: "Who pays for compute when a reader account queries shared data?" — The PROVIDER pays. The reader account's warehouse credits are billed to the provider's account. This is the #1 reason providers use resource monitors on reader accounts.

Reader Account Limitations

  • Can ONLY consume data from the provider that created it
  • Cannot access Snowflake Marketplace listings
  • Cannot use features like data loading, Snowpipe, tasks, or streams
  • Provider must create warehouses for the reader account
  • Provider should always configure resource monitors to control costs
  • Cannot be converted to a full Snowflake account (must create new)

5. Cross-Region & Cross-Cloud Edge Cases

Same Region Sharing

Default behavior: Sharing within the same cloud region is instant, zero-copy, and incurs NO additional storage or data transfer costs. This is the ideal scenario.

Cross-Region / Cross-Cloud Sharing

Challenge Details
Replication Required Data must be replicated to the consumer's region. Provider must set up database replication or use listings (auto-fulfillment).
Additional Cost Data transfer fees + storage for the replica. Provider bears replication cost.
Latency Initial replication can take time. Ongoing refresh has a lag (not real-time).
Replication Lag Consumer sees data as fresh as the last replication refresh, not real-time.
Auto-Fulfillment (Listings) Snowflake Marketplace handles cross-region via auto-fulfillment, abstracting replication complexity.
Key Exam Point: Direct sharing (CREATE SHARE) works ONLY within the same region. For cross-region consumers, you MUST use either: (1) Database Replication + sharing in target region, or (2) Snowflake Marketplace listings with auto-fulfillment.

Cross-Region Architecture

  • Step 1: Provider enables replication for the source database
  • Step 2: Create a replica in the consumer's region
  • Step 3: Create a share in the target region from the replica
  • Step 4: Consumer imports from the local-region share
  • Alternative: Publish as a Marketplace listing with auto-fulfillment enabled

6. Recovery Playbook

Scenario 1: Provider Accidentally Drops a Shared Table

  1. Consumer reports immediate query failures
  2. Provider runs: UNDROP TABLE schema.table_name;
  3. If within Time Travel retention, table is restored and share auto-recovers
  4. If past retention: recreate table, re-load data, re-grant to share
  5. Verify consumer access: SHOW GRANTS TO SHARE share_name;

Scenario 2: Provider Drops the Share Itself

  1. Consumer's imported database is immediately and automatically dropped
  2. UNDROP SHARE is NOT supported — shares cannot be undropped
  3. Provider must: recreate share, re-add all objects, re-add consumer accounts
  4. Consumer must: CREATE DATABASE ... FROM SHARE again
  5. Prevention: use role separation; only ACCOUNTADMIN or designated role can DROP SHARE

Scenario 3: Consumer Cannot See Newly Added Table

  1. Verify table is granted to share: SHOW GRANTS TO SHARE share_name;
  2. Verify USAGE on schema is granted to share
  3. Verify USAGE on database is granted to share
  4. Consumer may need to refresh metadata: exit and re-enter the database context
  5. Check if the table is in a schema not yet added to the share

Scenario 4: Reader Account Running Up Excessive Costs

  1. Check warehouse usage: SELECT * FROM SNOWFLAKE.ACCOUNT_USAGE.WAREHOUSE_METERING_HISTORY;
  2. Create/adjust resource monitor on reader's warehouse
  3. Set SUSPEND and SUSPEND_IMMEDIATELY triggers at credit thresholds
  4. Consider reducing warehouse size or AUTO_SUSPEND timing
  5. Review and revoke unnecessary user access in the reader account

Scenario 5: Cross-Region Share Data is Stale

  1. Check replication status: SELECT * FROM TABLE(INFORMATION_SCHEMA.DATABASE_REFRESH_HISTORY());
  2. Verify replication schedule frequency
  3. Trigger manual refresh: ALTER DATABASE replica_db REFRESH;
  4. Check for replication failures in REPLICATION_HISTORY view
  5. Consider increasing refresh frequency if business requires fresher data

7. Exam Scenario Questions

1Object Sharing Eligibility

A provider wants to share a view that joins three tables and applies row-level filtering. What must be true about this view for it to be shareable?

  1. The view must be created with the SECURE keyword
  2. The view must reference only external tables
  3. The view must have fewer than 1000 rows
  4. The underlying tables must all be in the same schema
Show Answer
A. Only SECURE views can be shared. The SECURE keyword prevents the consumer from seeing the view definition (DDL), which is required for data sharing. Non-secure views expose their SQL definition and cannot be added to a share.
2Consumer Attempts DML

A consumer runs INSERT INTO shared_db.public.customers VALUES (...) on a table from a shared database. What happens?

  1. The insert succeeds but is only visible to the consumer
  2. The insert fails with an insufficient privileges error
  3. The insert succeeds and is visible to both provider and consumer
  4. The insert is queued for provider approval
Show Answer
B. Shared databases are strictly read-only for consumers. Any DML operation (INSERT, UPDATE, DELETE, MERGE) will fail. Consumers can only run SELECT queries and certain metadata commands on shared objects.
3Reader Account Billing

Company A creates a reader account for Company B (which has no Snowflake account). Company B's analysts run queries using a warehouse in the reader account. Who is billed for the compute credits?

  1. Company B (the consumer/reader)
  2. Snowflake absorbs the cost
  3. Company A (the provider)
  4. The cost is split 50/50
Show Answer
C. The provider (Company A) pays ALL compute costs for reader accounts. Reader account warehouses are billed to the provider's account. This is why resource monitors are critical for reader accounts.
4Cross-Region Sharing

A provider in AWS US-East-1 wants to share data with a consumer in AWS EU-West-1 using a direct share (not Marketplace). What is required?

  1. Nothing extra; direct sharing works across regions automatically
  2. The provider must replicate the database to EU-West-1 and create a share there
  3. The consumer must create a VPN connection to US-East-1
  4. Both accounts must upgrade to Business Critical edition
Show Answer
B. Direct sharing (CREATE SHARE) only works within the same region. For cross-region sharing, the provider must replicate the database to the consumer's region and create a share from the replica. Alternatively, Marketplace listings with auto-fulfillment handle this automatically.
5DROP SHARE Impact

A provider accidentally runs DROP SHARE marketing_share;. Three consumer accounts had imported databases from this share. What happens to the consumers?

  1. Consumer databases remain but become read-only stale copies
  2. Consumer databases are immediately and automatically dropped
  3. Consumer databases remain for 24 hours then are dropped
  4. Consumers are notified and have 7 days to export data
Show Answer
B. When a share is dropped, ALL consumer databases created from that share are immediately and automatically dropped. There is no grace period, no notification, and UNDROP SHARE is not supported. The provider must recreate the share and consumers must re-import.
6Clone Shared Database

A consumer wants to create a development copy of a shared database by running CREATE DATABASE dev_copy CLONE shared_database;. What is the result?

  1. The clone succeeds and creates a writable copy
  2. The clone succeeds but remains read-only
  3. The operation fails; shared databases cannot be cloned
  4. The clone succeeds only if the provider grants CLONE privilege
Show Answer
C. Shared (imported) databases cannot be cloned. The CLONE operation will fail. To get a local copy, consumers must use CREATE TABLE ... AS SELECT to copy individual tables into their own database, or use CREATE DATABASE ... AS SELECT patterns.
7Re-Sharing Data

Consumer X receives data via a share from Provider P. Consumer X now wants to share that same data with another company (Consumer Y) by adding it to their own outbound share. Can they do this?

  1. Yes, if Consumer X has ACCOUNTADMIN role
  2. Yes, but only via a secure view on top of the shared data
  3. No, objects in an imported database cannot be added to an outbound share
  4. Yes, but only if Provider P explicitly grants re-sharing permission
Show Answer
C. Data from imported (shared) databases cannot be re-shared. This is a hard limitation regardless of roles or permissions. If Consumer X needs to share derived data, they must copy it to a local table first (breaking the live link) and share from their own database.
8Sharing Non-Secure View

A provider runs: GRANT SELECT ON VIEW analytics.public.revenue_summary TO SHARE data_share; where revenue_summary is a regular (non-secure) view. What happens?

  1. The grant succeeds and consumers can query the view
  2. The grant fails with an error because only secure views can be shared
  3. The grant succeeds but the view definition is visible to consumers
  4. The grant succeeds only on Enterprise edition or higher
Show Answer
B. Only SECURE views can be granted to a share. Attempting to grant a non-secure view to a share will produce an error. The provider must first run ALTER VIEW revenue_summary SET SECURE; before granting it to the share.
9Time Travel on Shared Data

A consumer wants to query yesterday's version of a shared table using: SELECT * FROM shared_db.public.orders AT(OFFSET => -86400);. What is the result?

  1. Returns data from 24 hours ago successfully
  2. Fails because Time Travel is not available on shared objects for consumers
  3. Returns current data with a warning about Time Travel limitations
  4. Works only if the provider has enabled Time Travel sharing
Show Answer
B. Consumers cannot use Time Travel (AT/BEFORE clauses) on objects in shared databases. Only the current state of the data is accessible. Time Travel is controlled by and accessible only to the provider account that owns the data.
10Reader Account Capabilities

A provider has created a reader account. Which of the following can the reader account do?

  1. Access Snowflake Marketplace listings from other providers
  2. Load data from an external stage into a local table
  3. Query shared data using a warehouse created by the provider
  4. Create a share to provide data to another account
Show Answer
C. Reader accounts can ONLY query data shared by the provider that created them, using warehouses that the provider has set up. They cannot access other providers' shares, load data, create shares, or use Marketplace. They are strictly limited consumption-only accounts.
