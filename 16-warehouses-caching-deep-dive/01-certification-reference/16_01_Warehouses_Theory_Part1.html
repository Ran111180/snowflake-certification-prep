1. Virtual Warehouses Overview

A virtual warehouse is a cluster of compute resources in Snowflake. Warehouses provide the CPU, memory, and temporary storage needed to execute SQL queries and DML operations. They are completely independent of storage.

Exam Tip

Warehouses do NOT store data. They are pure compute. Storage is separate (in cloud object storage). This separation is a core Snowflake architectural principle.

Key Characteristics

  • Warehouses can be started/stopped at any time (no data loss)
  • Warehouses can be resized at any time (even while running queries)
  • Each warehouse is an independent compute cluster — no resource contention between warehouses
  • Multiple warehouses can query the same data simultaneously
  • Billing is per-second with a 60-second minimum each time a warehouse resumes
Architecture Note

When you resize a warehouse while queries are running, existing queries use the original resources. New queries after the resize use the new resources.

-- Create a warehouse with specific size
CREATE WAREHOUSE analytics_wh
  WAREHOUSE_SIZE = 'LARGE'
  AUTO_SUSPEND = 300
  AUTO_RESUME = TRUE

ALTER WAREHOUSE analytics_wh SET WAREHOUSE_SIZE = 'XLARGE';

3. Auto-Suspend & Auto-Resume

Auto-Suspend

  • Specified in seconds (minimum 60 seconds, or 0 for immediate)
  • Timer starts when the last query finishes and no queries are queued
  • When suspended, the warehouse consumes zero credits
  • Default: 600 seconds (10 minutes)
  • Setting to 0 means: suspend immediately when idle (subject to the 60s minimum billing)

Auto-Resume

  • When enabled, warehouse automatically starts when a query is submitted to it
  • Enabled by default (AUTO_RESUME = TRUE)
  • If disabled, users must manually resume with ALTER WAREHOUSE ... RESUME
Exam Tip

Auto-suspend timer is specified in seconds in SQL but displayed in minutes in the UI. A common exam trap: AUTO_SUSPEND = 300 means 5 minutes, not 300 minutes.

-- Aggressive auto-suspend for dev warehouses
ALTER WAREHOUSE dev_wh SET AUTO_SUSPEND = 60;

-- Manual suspend
ALTER WAREHOUSE dev_wh SUSPEND;

-- Manual resume
ALTER WAREHOUSE dev_wh RESUME;

4. Multi-Cluster Warehouses

Multi-cluster warehouses automatically add or remove clusters of the same size to handle concurrency fluctuations. Available in Enterprise Edition+.

Configuration

  • MIN_CLUSTER_COUNT — minimum clusters always running (1-10)
  • MAX_CLUSTER_COUNT — maximum clusters that can be added (1-10)
  • Each additional cluster = same size and credit rate as one cluster
  • Example: A LARGE warehouse with MAX=3 can use up to 24 credits/hour (8 x 3)

Scaling Policies

PolicyBehaviorBest For
Standard (default) Starts additional cluster as soon as a query is queued (or estimated to queue). Shuts down extra clusters after 2-3 consecutive checks (each 1 minute apart) showing reduced load. Minimize queuing; prioritize performance. Higher credit usage.
Economy Starts additional cluster only after enough load to keep it busy for at least 6 minutes. Shuts down after 5-6 consecutive checks showing reduced load. Minimize credit costs; tolerate some queuing. Lower credit usage.
Key Detail

When MIN_CLUSTER_COUNT = MAX_CLUSTER_COUNT, the warehouse runs in "Maximized" mode — all clusters are always running. There is no autoscaling. This guarantees maximum concurrency but consumes constant credits.

-- Create multi-cluster warehouse
CREATE WAREHOUSE reporting_wh
  WAREHOUSE_SIZE = 'MEDIUM'
  MIN_CLUSTER_COUNT = 1
  MAX_CLUSTER_COUNT = 4
  SCALING_POLICY = 'STANDARD'
  AUTO_SUSPEND = 120
  AUTO_RESUME = TRUE;

6. Cache Layers

Snowflake uses three distinct caching layers to optimize query performance and reduce costs.

Query Execution Flow with Caching ┌─────────────────────────────────────────────────────────┐ │ Query Submitted │ └──────────────────────────┬──────────────────────────────┘ │ ┌───────────▼───────────┐ │ 1. Result Cache │ (Cloud Services Layer) │ Same query + same │ FREE - no warehouse │ data? Return cached. │ needed └───────────┬───────────┘ │ miss ┌───────────▼───────────┐ │ 2. Metadata Cache │ (Cloud Services Layer) │ MIN/MAX/COUNT/etc. │ FREE - no warehouse │ answered from metadata│ needed └───────────┬───────────┘ │ miss ┌───────────▼───────────┐ │ 3. Warehouse Local │ (Compute Layer) │ Disk Cache (SSD) │ Warehouse must be │ Raw data cached on │ running │ local SSD from prior │ │ queries │ └───────────┬───────────┘ │ miss ┌───────────▼───────────┐ │ 4. Remote Storage │ (Storage Layer) │ Read from S3/Azure/ │ Slowest path │ GCS │ └───────────────────────┘

Result Cache (Query Result Cache)

  • Stores exact results of previously executed queries
  • Valid for 24 hours from last access (resets each time reused)
  • Conditions for reuse: same query text, same role, same database/schema context, underlying data unchanged
  • Does NOT require a running warehouse — served from cloud services layer
  • Can be disabled per session: ALTER SESSION SET USE_CACHED_RESULT = FALSE
  • Persists even if the warehouse is suspended
Exam Tip

Result cache is invalidated if the underlying data changes (any DML on the table). It is also user/role-specific — a cached result from ROLE_A cannot be served to ROLE_B (due to access control).

Metadata Cache

  • Cloud services layer maintains metadata about all micro-partitions
  • Answers queries like SELECT COUNT(*), MIN(col), MAX(col) without scanning data
  • Also used for SHOW commands, DESCRIBE, schema information
  • No warehouse needed — completely free
  • No expiration — always up to date as it reflects current partition metadata

Warehouse Local Disk Cache (SSD Cache)

  • Each warehouse node caches recently accessed micro-partitions on local SSD
  • Persists as long as the warehouse is running (cleared on suspend)
  • LRU (Least Recently Used) eviction policy
  • Larger warehouse = more SSD cache capacity
  • This is why re-running a query on the same warehouse is faster the second time
Important

Suspending a warehouse clears its local disk cache. This is a key trade-off when setting AUTO_SUSPEND: shorter suspend saves credits but loses cache. Longer suspend keeps cache warm but costs more.

-- Disable result cache for testing
ALTER SESSION SET USE_CACHED_RESULT = FALSE;

7. Query Queuing

When a warehouse cannot execute a query immediately due to resource constraints, the query enters a QUEUED state.

Why Queries Queue

  • All available compute threads are busy (concurrency limit reached)
  • Insufficient memory for the query given current load
  • Warehouse is resuming (starting up) — queries wait briefly

Key Parameters

ParameterDefaultDescription
MAX_CONCURRENCY_LEVEL8Max concurrent queries per cluster. Snowflake auto-adjusts, but this sets an upper bound.
STATEMENT_QUEUED_TIMEOUT_IN_SECONDS0 (no limit)Max seconds a query can wait in queue before being cancelled.
How Snowflake Manages Concurrency

Snowflake dynamically allocates memory per query. If a query needs more memory (large sorts, joins), fewer queries run concurrently. The MAX_CONCURRENCY_LEVEL is a soft cap — Snowflake may run fewer queries concurrently if they are memory-intensive.

8. Sizing Guidelines: Scale Up vs Scale Out

Scale Up (Larger Warehouse)

  • Individual queries are slow/complex
  • Large scans, complex joins, heavy aggregations
  • Query uses significant spilling to disk
  • Single-user or low-concurrency workloads
  • Increase warehouse SIZE (e.g., M to L)

Scale Out (Multi-Cluster)

  • Many simple/moderate queries concurrently
  • Dashboard workloads with many users
  • Queries are queuing (QUEUED state)
  • Individual queries are fast but too many at once
  • Increase MAX_CLUSTER_COUNT
Exam Tip

"Query is slow" → Scale Up (bigger warehouse). "Queries are queuing" → Scale Out (more clusters). This distinction appears frequently on the exam.

Decision Framework

SymptomSolutionAction

9. Features & Limitations

15 Key Features

✓ Instant elasticity — resize while running
✓ Per-second billing (60s minimum)
✓ Auto-suspend to stop billing when idle
✓ Auto-resume on query submission
✓ Multi-cluster autoscaling (Enterprise+)
✓ Complete workload isolation between warehouses
✓ Three-layer caching (result, metadata, SSD)
✓ Result cache serves queries without warehouse
✓ Multiple warehouses can read same data concurrently
✓ Snowpark-optimized type for ML/memory workloads
✓ Resource monitors for cost control
✓ RBAC with USAGE, OPERATE, MONITOR, MODIFY
✓ Query Acceleration Service for outlier queries
✓ Statement timeouts and queue timeouts configurable
✓ Sizes from XS (1 credit/hr) to 6XL (512 credits/hr)

15 Key Limitations

✕ Cannot share warehouse across accounts
✕ Local SSD cache lost on suspend
✕ Minimum 60-second billing per resume
✕ Multi-cluster requires Enterprise Edition
✕ Max 10 clusters per multi-cluster warehouse
✕ Result cache invalid if underlying data changes
✕ Result cache is role-specific (no cross-role sharing)
✕ Snowpark-optimized costs 1.5x credits
✕ Snowpark-optimized only available XL and above
✕ Cannot pin specific queries to specific clusters
✕ Economy scaling tolerates queuing (up to 6 min)
✕ No GPU-based warehouse option for SQL
✕ Warehouse resume adds ~1-2 seconds latency
✕ Cannot choose underlying cloud hardware directly
✕ Doubling size does not guarantee 2x performance
