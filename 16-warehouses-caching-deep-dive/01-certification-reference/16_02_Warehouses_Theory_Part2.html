1. Query Acceleration Service (QAS)

QAS offloads portions of eligible queries to shared compute resources managed by Snowflake, reducing the impact of outlier queries on warehouse performance. Available in Enterprise Edition+.

How It Works

  • QAS identifies query operations that can benefit from additional compute (large scans with selective filters)
  • It transparently offloads those scan-heavy operations to serverless compute
  • The warehouse and QAS work in parallel — the warehouse handles the rest of the query
  • No data movement — QAS reads directly from Snowflake's shared storage layer

SCALE_FACTOR

  • Controls the maximum amount of serverless compute QAS can use
  • Range: 0 (disabled) to 100
  • Represents a multiplier relative to warehouse size
  • Example: SCALE_FACTOR = 8 on a Medium warehouse means QAS can use up to 8x the warehouse compute
  • Higher SCALE_FACTOR = more acceleration potential but higher cost

Eligible Queries

EligibleNot Eligible
Queries with large scans + selective filtersQueries that are already fast
Queries with LIKE/ILIKE on stringsINSERT/UPDATE/DELETE (DML)
Queries with IN clauses on high-cardinality columnsQueries dominated by joins (not scan-bound)
Aggregations over large datasets with filtersQueries with small result sets that scan little data
Exam Tip

QAS is best for "outlier" queries — those occasional ad-hoc queries that scan significantly more data than typical workload queries. It does NOT help with concurrency (that's multi-cluster) or DML operations.

-- Enable QAS on a warehouse
ALTER WAREHOUSE analytics_wh SET
  ENABLE_QUERY_ACCELERATION = TRUE
  QUERY_ACCELERATION_MAX_SCALE_FACTOR = 8;

-- Check QAS eligibility for past queries
SELECT query_id, eligible_query_acceleration_time
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_ACCELERATION_ELIGIBLE
WHERE warehouse_name = 'ANALYTICS_WH'
ORDER BY eligible_query_acceleration_time DESC;
Cost Model

QAS is billed on a serverless credit model — you pay only for the compute used during acceleration. The SCALE_FACTOR caps the maximum spend per query. Credits consumed appear in QUERY_ACCELERATION_HISTORY.

2. Resource Monitors

Resource monitors track credit consumption and can notify or suspend warehouses when thresholds are reached.

Key Concepts

  • Set at account level (all warehouses) or warehouse level (specific warehouses)
  • Define a credit quota for a monitoring interval (daily, weekly, monthly, yearly, or custom)
  • Support multiple trigger thresholds at different percentages
  • Only ACCOUNTADMIN can create resource monitors (by default)

Trigger Actions

ActionBehaviorImpact
NOTIFY Sends notification (email) to account admins No impact on queries — monitoring only
NOTIFY & SUSPEND Sends notification and suspends warehouse after current queries finish Running queries complete, new queries blocked
NOTIFY & SUSPEND IMMEDIATELY Sends notification and immediately kills all running queries, then suspends Running queries are cancelled immediately
Important

SUSPEND IMMEDIATELY cancels running queries — this can cause data loading failures or incomplete results. Use with caution in production.

-- Create a resource monitor
CREATE RESOURCE MONITOR monthly_monitor
  WITH CREDIT_QUOTA = 1000
  FREQUENCY = MONTHLY
  START_TIMESTAMP = IMMEDIATELY
  TRIGGERS
    ON 75 PERCENT DO NOTIFY
    ON 90 PERCENT DO NOTIFY
    ON 100 PERCENT DO SUSPEND
    ON 110 PERCENT DO SUSPEND_IMMEDIATE;

-- Assign to a warehouse
ALTER WAREHOUSE analytics_wh SET RESOURCE_MONITOR = monthly_monitor;

-- Assign at account level (all warehouses)
ALTER ACCOUNT SET RESOURCE_MONITOR = monthly_monitor;
Exam Tip

Resource monitors track credit usage, not dollar cost. They include credits from warehouse compute AND cloud services (if exceeding 10% threshold). They do NOT track storage costs or serverless feature costs (like Snowpipe, QAS).

3. Warehouse Parameters

ParameterLevelDefaultDescription
STATEMENT_TIMEOUT_IN_SECONDS Account, Warehouse, Session 172800 (48 hrs) Max execution time for a statement. Cancelled if exceeded.
STATEMENT_QUEUED_TIMEOUT_IN_SECONDS Account, Warehouse, Session 0 (unlimited) Max time a statement can wait in queue. Cancelled if exceeded.
MAX_CONCURRENCY_LEVEL Warehouse 8 Max concurrent statements per cluster. Snowflake may lower dynamically.
AUTO_SUSPEND Warehouse 600 (seconds) Seconds of inactivity before warehouse suspends.
AUTO_RESUME Warehouse TRUE Whether warehouse auto-starts on query submission.
WAREHOUSE_SIZE Warehouse X-Small The T-shirt size (XS through 6XL).
WAREHOUSE_TYPE Warehouse STANDARD STANDARD or SNOWPARK-OPTIMIZED.
SCALING_POLICY Warehouse STANDARD STANDARD or ECONOMY for multi-cluster.
INITIALLY_SUSPENDED Warehouse (CREATE only) FALSE If TRUE, warehouse is created in suspended state.
Parameter Hierarchy

When a parameter is set at multiple levels, the most restrictive value wins. For timeouts: Account > Warehouse > Session (the lowest value takes effect). This means a session cannot override a shorter warehouse timeout with a longer one.

-- Set statement timeout at warehouse level
ALTER WAREHOUSE analytics_wh SET STATEMENT_TIMEOUT_IN_SECONDS = 3600;

-- Set queue timeout
ALTER WAREHOUSE analytics_wh SET STATEMENT_QUEUED_TIMEOUT_IN_SECONDS = 300;

-- Set at session level (cannot exceed warehouse/account level)
ALTER SESSION SET STATEMENT_TIMEOUT_IN_SECONDS = 1800;

4. Cost Optimization Strategies

Auto-Suspend Tuning

Workload PatternRecommended AUTO_SUSPENDRationale
Ad-hoc / interactive analysts300-600s (5-10 min)Balance between cache retention and cost
Dashboard / BI tools (frequent queries)600-900s (10-15 min)Keep cache warm for repeated patterns
ETL / batch (bursty, infrequent)60s (minimum)Suspend fast — cache is less valuable
Dev / test (sporadic)60sMinimize idle costs
Continuous / streaming ingestNever (or very long)Always active, suspend/resume overhead adds up

Right-Sizing Strategy

  1. Start with X-Small or Small
  2. Run representative workload; check QUERY_HISTORY for spilling and duration
  3. If queries spill to remote storage, increase size
  4. If queries are fast with no queuing, do NOT increase size
  5. Monitor for 1-2 weeks; adjust based on patterns

Multi-Cluster Configuration for Cost

  • Economy policy saves 20-40% credits vs Standard for tolerant workloads
  • Set MIN_CLUSTER_COUNT = 1 to allow full scale-down during off-peak
  • Avoid Maximized mode (MIN=MAX) unless constant high concurrency is required
  • Use separate warehouses for different workload types (ETL vs BI vs ad-hoc)
Best Practice

Workload isolation is the #1 cost optimization: give ETL, BI dashboards, and ad-hoc users their own warehouses. This prevents expensive ETL queries from blocking cheap BI queries (and vice versa) and allows independent sizing.

5. RBAC for Warehouses

PrivilegeAllowsTypical Role
USAGE Execute queries using the warehouse All query roles (analysts, devs)
OPERATE Start, stop, suspend, resume the warehouse Team leads, DBAs
MONITOR View warehouse utilization metrics and queries Monitoring / FinOps roles
MODIFY Change warehouse properties (size, auto-suspend, etc.) Admins, platform team
CREATE WAREHOUSE Create new warehouses (granted on ACCOUNT, not warehouse) SYSADMIN (default)
OWNERSHIP Full control including DROP and GRANT SYSADMIN (default owner)
Exam Tip

USAGE only lets you use the warehouse to run queries. It does NOT let you suspend/resume (OPERATE), change settings (MODIFY), or view metrics (MONITOR). These are distinct and commonly tested.

-- Grant usage to analysts
GRANT USAGE ON WAREHOUSE analytics_wh TO ROLE analyst_role;

-- Grant operate to team leads (can suspend/resume)
GRANT OPERATE ON WAREHOUSE analytics_wh TO ROLE team_lead;

-- Grant monitor to FinOps
GRANT MONITOR ON WAREHOUSE analytics_wh TO ROLE finops_role;

-- Grant modify to platform admins
GRANT MODIFY ON WAREHOUSE analytics_wh TO ROLE platform_admin;

-- Grant ability to create warehouses
GRANT CREATE WAREHOUSE ON ACCOUNT TO ROLE platform_admin;

6. Monitoring & Observability

Key Views for Warehouse Monitoring

View / FunctionLocationUse Case
WAREHOUSE_METERING_HISTORY ACCOUNT_USAGE / TABLE FUNCTION Credit consumption per warehouse per hour
QUERY_HISTORY ACCOUNT_USAGE / TABLE FUNCTION Query performance, execution time, bytes scanned, queuing
WAREHOUSE_LOAD_HISTORY ACCOUNT_USAGE / TABLE FUNCTION Avg/peak running & queued queries per interval
WAREHOUSE_EVENTS_HISTORY ACCOUNT_USAGE Suspend/resume/resize events with timestamps
QUERY_ACCELERATION_HISTORY ACCOUNT_USAGE QAS credit usage and time saved
RESOURCE_MONITORS INFORMATION_SCHEMA Current resource monitor status and consumption 
-- Credit usage by warehouse (last 30 days)
SELECT warehouse_name,
       SUM(credits_used) AS total_credits,
       SUM(credits_used_compute) AS compute_credits,
       SUM(credits_used_cloud_services) AS cs_credits
FROM SNOWFLAKE.ACCOUNT_USAGE.WAREHOUSE_METERING_HISTORY
WHERE start_time >= DATEADD(day, -30, CURRENT_TIMESTAMP())
GROUP BY warehouse_name
ORDER BY total_credits DESC;

-- Queries that spilled to disk (candidates for resize)
SELECT query_id, warehouse_name, warehouse_size,
       bytes_spilled_to_local_storage,
       bytes_spilled_to_remote_storage,
       total_elapsed_time/1000 AS elapsed_sec
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY
WHERE bytes_spilled_to_remote_storage > 0
  AND start_time >= DATEADD(day, -7, CURRENT_TIMESTAMP())
ORDER BY bytes_spilled_to_remote_storage DESC
LIMIT 20;

-- Warehouse load (queuing analysis)
SELECT warehouse_name, start_time,
       avg_running, avg_queued,
       avg_blocked
FROM SNOWFLAKE.ACCOUNT_USAGE.WAREHOUSE_LOAD_HISTORY
WHERE start_time >= DATEADD(day, -7, CURRENT_TIMESTAMP())
  AND avg_queued > 0
ORDER BY avg_queued DESC;
Latency Note

ACCOUNT_USAGE views have up to 45-minute latency. For real-time monitoring, use the TABLE FUNCTION variants (e.g., TABLE(INFORMATION_SCHEMA.WAREHOUSE_METERING_HISTORY(...))) or the Snowsight Query History UI.

7. Production Best Practices

Warehouse Strategy

  1. Workload isolation — Separate warehouses for ETL, BI/dashboards, ad-hoc, and data science
  2. Right-size first, then multi-cluster — Ensure individual query performance is good before adding clusters
  3. Use INITIALLY_SUSPENDED = TRUE — Prevent accidental credit burn on warehouse creation
  4. Set STATEMENT_QUEUED_TIMEOUT — Prevent queries from waiting indefinitely in queue
  5. Set STATEMENT_TIMEOUT — Prevent runaway queries from consuming credits for hours

Cost Control

  1. Resource monitors on every warehouse — At minimum, NOTIFY at 80% and SUSPEND at 100%
  2. Aggressive auto-suspend for dev/test — 60 seconds is appropriate
  3. Monitor spilling — Remote spill indicates warehouse is too small for the query
  4. Review WAREHOUSE_METERING_HISTORY weekly — Identify idle or over-provisioned warehouses
  5. Use QAS instead of over-sizing — For occasional large queries, QAS is cheaper than permanently sizing up

Performance

  1. Keep cache warm — For BI workloads, use 10-15 min auto-suspend to retain SSD cache
  2. Leverage result cache — Ensure dashboards reuse identical queries where possible
  3. Avoid unnecessary SUSPEND/RESUME cycles — Each resume has 1-2s overhead + cold cache
  4. Monitor queuing — If avg_queued > 1 consistently, add multi-cluster or increase size
  5. Use Standard scaling policy — Unless you explicitly need to save credits at the cost of latency
Production Checklist
  • Every warehouse has a resource monitor
  • Statement timeout set (e.g., 3600s for ad-hoc, 7200s for ETL)
  • Queue timeout set (e.g., 300s for interactive workloads)
  • AUTO_RESUME = TRUE for all user-facing warehouses
  • INITIALLY_SUSPENDED = TRUE in all CREATE WAREHOUSE DDL
  • Weekly review of WAREHOUSE_METERING_HISTORY
  • QAS enabled for warehouses with outlier query patterns
