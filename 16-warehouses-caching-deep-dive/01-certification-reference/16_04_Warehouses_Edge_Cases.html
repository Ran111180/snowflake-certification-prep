Exam Focus Key Sizing Rules

  • Each size doubles credits AND compute resources from the previous size
  • Bigger warehouse does NOT mean faster for all queries - simple queries gain nothing
  • Query complexity and data volume determine ideal size, not just data amount
  • Snowflake recommends starting small and scaling up based on query performance
  • Resizing takes effect for the next query (existing queries use current resources)

2. Multi-Cluster Warehouse Edge Cases

Scaling Delay

  • New clusters take 30-90 seconds to provision (not instant)
  • During provisioning, queries continue to queue on existing clusters
  • Scaling policy triggers are evaluated every few seconds
  • Scale-out happens when queuing is detected, not preemptively
  • Gotcha A burst of 100 queries at once will queue before scale-out completes

Credit Consumption During Scale-Out

  • Each additional cluster consumes credits at the full warehouse rate
  • A 3-cluster Medium warehouse = 12 credits/hr (not 4)
  • Minimum 60-second billing per cluster start event
  • Clusters that start and stop rapidly still incur minimum charges
  • Gotcha Economy mode can cause cluster "flapping" - repeatedly starting/stopping

Standard vs Economy Scaling Policy

BehaviorStandardEconomy
Scale-out triggerQuery queuing detected OR system estimates additional cluster would improve throughputOnly when system estimates query load will keep cluster busy for at least 6 minutes
Scale-in trigger2-3 consecutive checks show cluster underutilized (checks every ~15-20 sec)Same as Standard but waits longer to confirm underutilization
Response timeFaster - favors performanceSlower - favors cost savings
RiskMay over-provision brieflyMay queue queries longer than needed
Best forUser-facing workloads, SLA-bound queriesBatch ETL, cost-sensitive environments

Gotcha Multi-Cluster Exam Traps

  • Multi-cluster does NOT make individual queries faster - it handles more concurrent queries
  • Setting MIN_CLUSTER_COUNT = MAX_CLUSTER_COUNT creates a static multi-cluster (always-on)
  • Multi-cluster is only available in Enterprise Edition and above
  • The SCALING_POLICY parameter only applies when MIN < MAX clusters
  • Auto-suspend applies to the entire warehouse - all clusters suspend together after no activity
  • Each cluster maintains its own local disk cache (SSD) - scale-out means cold caches

3. Cache Edge Cases

Three Cache Layers in Snowflake

Cache TypeScopeLocationPersistence
Metadata CacheAccount-wideCloud Services layerAlways available
Result CacheAccount-wide (role-scoped)Cloud Services layer24 hours max
Local Disk Cache (SSD)Per-warehouseWarehouse compute nodesUntil suspend or resize

Result Cache Invalidation Triggers

The result cache is invalidated when ANY of these occur:

  1. 24-hour expiry - Results older than 24 hours are purged regardless of other factors
  2. Underlying data change - Any DML (INSERT, UPDATE, DELETE, MERGE) on referenced tables
  3. Role change - Different role = different cache entry (even for identical SQL)
  4. Different query text - Even whitespace or comment differences = cache miss
  5. Session parameter change - Different TIMEZONE, DATE_FORMAT, etc. that affects results
  6. Micro-partition changes - Background reclustering or time travel cleanup

Exam Focus Result Cache Gotchas

  • SELECT * FROM t WHERE date = CURRENT_DATE() - cache hit only within same calendar day
  • SELECT * FROM t vs select * from t - cache HIT (case-insensitive matching)
  • SELECT * FROM t -- comment1 vs SELECT * FROM t -- comment2 - cache MISS
  • Non-deterministic functions (RANDOM(), UUID_STRING()) - result cache still works (returns same random result within 24hr!)
  • USE_CACHED_RESULT = FALSE bypasses result cache but result is still stored for others
  • Result cache works even when warehouse is suspended (it's in Cloud Services layer)
  • DDL on a table (ALTER TABLE ADD COLUMN) invalidates result cache for that table

Local Disk Cache (SSD) Behavior

  • Caches raw micro-partition data read from remote storage
  • Lost on suspend - warehouse restart means cold cache
  • Lost on resize - nodes are replaced, cache is cleared
  • LRU (Least Recently Used) eviction policy when cache is full
  • Each node caches different partitions - no duplication across nodes
  • Gotcha Setting AUTO_SUSPEND too low causes frequent cache rebuilds
  • Tip For repeated scan-heavy workloads, longer AUTO_SUSPEND = better cache hit ratio

4. Auto-Suspend Edge Cases

Critical Auto-Suspend Rules

  • Minimum value: 60 seconds (cannot set lower via SQL; UI shows minimum of 1 minute)
  • Setting AUTO_SUSPEND = 0 means never auto-suspend (warehouse runs forever)
  • NULL for AUTO_SUSPEND also means never suspend
  • Timer resets with every query completion or statement execution
  • Timer starts from the last query completion, not from warehouse start

Gotcha Queries In Flight Prevent Suspend

  • A warehouse will NOT auto-suspend while any query is still running
  • A long-running query (e.g., 4 hours) keeps the warehouse alive the entire time
  • Queued queries (waiting for resources) also prevent suspend
  • Background services (result scanning, cleanup) may briefly delay suspend
  • If a query starts just before suspend timer fires, suspend is deferred

Auto-Resume Behavior

  • AUTO_RESUME = TRUE (default) - warehouse starts automatically on query submission
  • Resume takes ~1-5 seconds typically for provisioning
  • If AUTO_RESUME = FALSE, queries against a suspended warehouse fail immediately
  • Exam Queued queries DO trigger auto-resume and start the warehouse
  • A warehouse in RESIZING state can still accept and queue queries

5. Resource Monitor Edge Cases

Action Types and Their Behavior

ActionBehaviorEdge Cases
NOTIFY Sends notification only Notification goes to account admins. Queries continue running. Can set multiple NOTIFY thresholds.
SUSPEND Suspends after running queries finish Queries in flight complete before suspend. New queries are queued then fail. Credit usage can exceed threshold while queries finish.
SUSPEND_IMMEDIATE Kills running queries and suspends Running queries are aborted (not graceful). Users get error. Most aggressive option.

Gotcha Percentage Trigger Behavior

  • Triggers are checked periodically (not in real-time) - actual usage may exceed trigger %
  • A 90% NOTIFY + 100% SUSPEND means you might hit ~95% before notification fires
  • Multiple NOTIFY triggers: you can set 50%, 75%, 90% to get progressive warnings
  • Only one SUSPEND or SUSPEND_IMMEDIATE trigger per monitor
  • Monitor checks happen approximately every 15 minutes (not per-query)
  • Gotcha A fast-consuming workload can blow past 100% between checks

Credit Reset Schedule

  • Daily - resets at midnight (account timezone)
  • Weekly - resets Monday at midnight
  • Monthly - resets 1st of each month
  • Yearly - resets January 1st
  • NEVER - lifetime monitor, never resets
  • Exam The START_TIMESTAMP can be set to control when the schedule begins (defaults to IMMEDIATELY)
  • Account-level monitors cover all warehouses including serverless compute
  • Warehouse-level monitors only cover their assigned warehouse(s)

Resource Monitor Scope Rules

  • Only ACCOUNTADMIN can create resource monitors (by default)
  • A warehouse can only have one resource monitor assigned
  • Account-level monitor applies in addition to warehouse-level monitors
  • If both account and warehouse monitors exist, the more restrictive one wins
  • Resource monitors do NOT track Cloud Services credits (only warehouse compute)
  • Gotcha Serverless features (Snowpipe, auto-clustering, materialized views) are NOT covered by warehouse monitors

6. Query Acceleration Service (QAS) Edge Cases

QAS Eligibility Requirements

  • Query must have significant scan-to-filter ratio (scans many partitions, returns few rows)
  • Works best with: selective filters, LIMIT clauses, aggregations on large tables
  • Does NOT accelerate: queries that return most of the data, small table scans
  • Only applies to SELECT statements (not DML, DDL, or COPY)
  • Enterprise Edition or higher required

Gotcha QAS Credit Consumption

  • QAS credits are separate from warehouse credits (serverless compute)
  • Billed per-second for the serverless resources used
  • QUERY_ACCELERATION_MAX_SCALE_FACTOR controls cost ceiling (0 = disabled, default = 8)
  • Scale factor is a multiplier of warehouse size (factor 8 on Medium = up to 32 credits/hr of QAS)
  • Setting scale factor to 0 disables QAS for that warehouse
  • QAS charges appear in QUERY_ACCELERATION_HISTORY view, NOT warehouse metering

Compatible vs Incompatible Query Patterns

Compatible

  • Ad-hoc analytics with selective filters
  • Queries with LIMIT on large tables
  • Aggregations (SUM, COUNT, AVG) with WHERE
  • Point lookups on non-clustered columns
  • Queries scanning many partitions but returning few rows

Incompatible

  • Full table scans returning all data
  • INSERT, UPDATE, DELETE, MERGE
  • Queries already running fast (no benefit)
  • Queries on small tables (<few partitions)
  • COPY INTO commands
  • Queries requiring UDFs in WHERE clause

Checking QAS Eligibility

-- Check if specific queries would benefit from QAS
SELECT query_id, eligible_query_acceleration_time
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY
WHERE eligible_query_acceleration_time > 0
ORDER BY eligible_query_acceleration_time DESC;

-- System function for specific query
SELECT SYSTEM$ESTIMATE_QUERY_ACCELERATION('<query_id>');

7. Recovery Playbook

Scenario 1: Runaway Query Consuming Excessive Resources

Identify the query - Check SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY or INFORMATION_SCHEMA.QUERY_HISTORY() for long-running queries 
SELECT query_id, query_text, execution_status, 
       DATEDIFF('minute', start_time, CURRENT_TIMESTAMP()) as running_mins
FROM TABLE(INFORMATION_SCHEMA.QUERY_HISTORY())
WHERE execution_status = 'RUNNING'
ORDER BY start_time;
Cancel the query - Use SELECT SYSTEM$CANCEL_QUERY('<query_id>')
Investigate root cause - Check query profile for explosion (cartesian joins, recursive CTEs)
Prevent recurrence - Set STATEMENT_TIMEOUT_IN_SECONDS on the warehouse or user 
ALTER WAREHOUSE my_wh SET STATEMENT_TIMEOUT_IN_SECONDS = 3600;

Scenario 2: Credit Overspend Alert

Check current consumption 
SELECT warehouse_name, SUM(credits_used) as total_credits
FROM SNOWFLAKE.ACCOUNT_USAGE.WAREHOUSE_METERING_HISTORY
WHERE start_time >= DATEADD('day', -1, CURRENT_TIMESTAMP())
GROUP BY warehouse_name ORDER BY total_credits DESC;
Suspend offending warehouses - ALTER WAREHOUSE my_wh SUSPEND;
Review resource monitor settings - Ensure monitors have SUSPEND actions, not just NOTIFY
Adjust auto-suspend - Reduce idle time to avoid credit burn during inactivity

Scenario 3: Warehouse Stuck in Resizing/Provisioning

Check warehouse state - SHOW WAREHOUSES LIKE 'my_wh'; (look at "state" column)
Wait briefly - Resizing typically completes in 1-2 minutes. Provisioning after resume takes seconds.
If stuck > 5 minutes - Try ALTER WAREHOUSE my_wh SUSPEND; then ALTER WAREHOUSE my_wh RESUME;
If still stuck - Contact Snowflake support; potential infrastructure issue in the region

Scenario 4: Cache Miss Diagnosis

Check if result cache was used 
SELECT query_id, query_text, 
       PERCENTAGE_SCANNED_FROM_CACHE,
       BYTES_SCANNED
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY
WHERE query_text ILIKE '%your_query_pattern%'
ORDER BY start_time DESC LIMIT 10;
Verify cache conditions - Same role? Same query text exactly? Within 24 hours? No DML on underlying table?
Check for SSD cache misses - PERCENTAGE_SCANNED_FROM_CACHE = 0 means cold warehouse cache. Was warehouse recently resumed or resized?
Optimize - Consider longer AUTO_SUSPEND for SSD cache; ensure consistent query formatting for result cache

Scenario 5: Multi-Cluster Thrashing (Frequent Scale In/Out)

Identify thrashing 
SELECT start_time, end_time, warehouse_name, cluster_number,
       DATEDIFF('second', start_time, end_time) as active_seconds
FROM SNOWFLAKE.ACCOUNT_USAGE.WAREHOUSE_METERING_HISTORY
WHERE warehouse_name = 'MY_WH' AND cluster_number > 1
ORDER BY start_time DESC;
Assess pattern - If clusters run < 2-3 minutes repeatedly, this is thrashing
Switch to ECONOMY scaling policy - Requires sustained load before scale-out 
ALTER WAREHOUSE my_wh SET SCALING_POLICY = 'ECONOMY';
Or increase MIN_CLUSTER_COUNT - If workload is predictably concurrent, keep minimum clusters warm 
ALTER WAREHOUSE my_wh SET MIN_CLUSTER_COUNT = 2;

8. Exam Scenario Questions

Q1: A user runs the same SELECT query twice within 5 minutes. The second execution takes 0 seconds and shows 0 bytes scanned. The warehouse was suspended between the two runs. What explains this?

Answer: The result cache served the second query. Result cache lives in the Cloud Services layer, not the warehouse. It works even when the warehouse is suspended. The 0 bytes scanned and instant response confirm a result cache hit.

Q2: A Large multi-cluster warehouse (MIN=1, MAX=4, STANDARD policy) is running 200 concurrent queries. A user reports their query is queuing. What is the most likely explanation?

Answer: The warehouse is in the process of scaling out additional clusters (provisioning delay of 30-90 seconds). During this time, queries queue on existing clusters. The STANDARD policy detected the load and initiated scale-out, but new clusters aren't ready yet.

Q3: A resource monitor is set to SUSPEND at 100%. The monitor uses a MONTHLY reset. On January 15th, credit usage reaches 105%. How did usage exceed 100%?

Answer: Resource monitor checks are periodic (approximately every 15 minutes), not real-time. Between checks, running queries continued consuming credits. Additionally, SUSPEND (not SUSPEND_IMMEDIATE) allows in-flight queries to complete, which can push usage above the threshold.

Q4: Two users with different roles run identical SELECT statements on the same table. User B's query does a full scan instead of using the result cache. Why?

Answer: Result cache entries are scoped by role. Even though the SQL is identical, User B's active role is different from User A's. Each role has its own result cache namespace to enforce access control (the role might have different row-access policies applied).

Q5: A warehouse has AUTO_SUSPEND = 300 (5 minutes). A stored procedure starts, runs for 45 minutes, then completes. When will the warehouse suspend?

Answer: The warehouse will suspend 5 minutes after the stored procedure completes (at the ~50 minute mark from start). Running queries prevent auto-suspend - the timer only starts counting after the last query finishes.

Q6: A customer enables QAS on a warehouse with scale_factor = 8. They notice increased costs but query performance hasn't improved. What's the likely issue?

Answer: Their queries are likely not eligible for QAS. QAS only helps queries with high scan-to-output ratios (selective filters on large tables). If queries are full table scans, complex joins without selective predicates, or DML operations, QAS resources spin up but provide no benefit. Check SYSTEM$ESTIMATE_QUERY_ACCELERATION to verify eligibility.

Q7: A warehouse is configured with AUTO_SUSPEND = 60 and AUTO_RESUME = TRUE. Users complain about slow first-query-of-the-day performance. The queries themselves are fast once running. What's happening?

Answer: Two compounding factors: (1) Warehouse resume time (~1-5 seconds added to first query), and (2) Cold SSD cache - with AUTO_SUSPEND = 60, the warehouse suspends quickly, clearing the local disk cache. The first queries must fetch all data from remote storage. Solution: increase AUTO_SUSPEND to maintain warm cache, or accept the trade-off for cost savings.

Q8: A multi-cluster warehouse (MIN=1, MAX=3) uses ECONOMY policy. During peak hours, the warehouse stays at 1 cluster despite query queuing of 30+ seconds. Why doesn't it scale out?

Answer: The ECONOMY policy only scales out when the system estimates the additional cluster will be busy for at least 6 minutes. If the query burst is short-lived (many quick queries finishing within seconds), ECONOMY may calculate that by the time the new cluster provisions, the queue will already be drained. Solution: Switch to STANDARD policy for latency-sensitive workloads.

Q9: A user runs: ALTER WAREHOUSE my_wh SET WAREHOUSE_SIZE = 'XLARGE'; while 10 queries are executing on the currently Medium warehouse. What happens to the running queries?

Answer: Running queries continue on the current (Medium) resources and complete normally. The resize takes effect for subsequent queries. Snowflake provisions the new XL nodes in the background, and once ready, new queries use the larger size. There is no disruption to in-flight queries.

Q10: An account has both an account-level resource monitor (1000 credits/month, SUSPEND at 100%) and a warehouse-level monitor on WH_ANALYTICS (200 credits/month, SUSPEND at 100%). WH_ANALYTICS has used 199 credits and the account total is at 999 credits. A new query would use 5 credits. What happens?

Answer: Both monitors will trigger their SUSPEND action after the next check cycle. The more restrictive one effectively wins - both the warehouse-level (200 exceeded) and account-level (1000 exceeded) will fire. In practice, whichever check runs first suspends the warehouse. The account-level monitor could also suspend OTHER warehouses if their combined usage crosses 1000 credits.
