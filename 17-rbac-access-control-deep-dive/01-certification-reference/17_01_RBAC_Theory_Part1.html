17.01 RBAC Theory Part 1 - Fundamentals

Role-Based Access Control (RBAC) is Snowflake's primary authorization mechanism. Every action in Snowflake requires a privilege, and privileges are granted to roles, which are then assigned to users or other roles.

System-Defined Roles

Snowflake provides five system-defined roles that cannot be dropped. Each has a specific purpose in the access control hierarchy.

ACCOUNTADMIN / \ SECURITYADMIN SYSADMIN | | USERADMIN (custom roles) | | \--- PUBLIC ---/

ACCOUNTADMIN

ACCOUNTADMIN = SYSADMIN + SECURITYADMIN combined

  • Top-level role; encapsulates all other system roles
  • Can manage billing, resource monitors, and account-level parameters
  • Can create data shares (provider side)
  • Can view ACCOUNT_USAGE views in SNOWFLAKE database
  • Should be assigned to a limited number of users
  • Best practice: Enable MFA for all ACCOUNTADMIN users
  • Should NOT be used for daily operations
ACCOUNTADMIN is the only role that can create resource monitors and manage shares (as provider). It is NOT automatically granted to any user upon account creation - it must be explicitly assigned.

SYSADMIN (System Administrator)

SYSADMIN - Object management role

  • Creates and manages warehouses and databases
  • Recommended owner for all custom roles (so SYSADMIN inherits their privileges)
  • All custom roles should ultimately be granted to SYSADMIN
  • Cannot manage users or security-related operations
  • Can grant privileges on objects it owns
Best practice: All custom roles should be granted to SYSADMIN so that system administrators can manage all objects. If a custom role is NOT granted to SYSADMIN, SYSADMIN cannot manage those objects.

SECURITYADMIN

SECURITYADMIN - Security management role

  • Can manage any grant globally (MANAGE GRANTS privilege)
  • Can create, alter, and drop roles
  • Can grant roles to users and other roles
  • Inherits USERADMIN role
  • Can modify or revoke privileges granted to any role
SECURITYADMIN has MANAGE GRANTS, meaning it can revoke privileges from ANY role, even those granted by ACCOUNTADMIN or other roles.

USERADMIN

USERADMIN - User and role management

  • Can create users and roles (CREATE USER, CREATE ROLE privileges)
  • Cannot grant privileges on objects
  • Cannot grant roles to other roles (that requires SECURITYADMIN or the owning role)
  • Granted to SECURITYADMIN by default

PUBLIC

PUBLIC - Universal base role

  • Automatically granted to every user and every role
  • Cannot be revoked from any user or role
  • Any privilege granted to PUBLIC is available to everyone
  • Snowflake grants temporary stage access to PUBLIC by default
  • Should have minimal privileges in production
PUBLIC is implicitly granted to every role. You cannot REVOKE the PUBLIC role from any user or role. Any privilege granted to PUBLIC becomes available to ALL users in the account.

Custom Roles & Role Hierarchy

Creating Custom Roles

-- Create a custom role
CREATE ROLE analyst_role;

-- Create with a comment
CREATE ROLE data_engineer COMMENT = 'For ETL pipeline management';

-- Grant role to a user
GRANT ROLE analyst_role TO USER john_doe;

-- Build hierarchy: grant custom role to SYSADMIN
GRANT ROLE analyst_role TO ROLE sysadmin;

Role Hierarchy Design

Key Principles:

  • Inheritance flows UP: A parent role inherits all privileges of its child roles
  • No circular grants: Snowflake prevents role hierarchy loops
  • Multiple parents allowed: A role can be granted to multiple parent roles
  • Multiple children allowed: A role can have multiple child roles granted to it
  • Depth is unlimited: Role hierarchies can be arbitrarily deep
SYSADMIN ├── DATA_ADMIN_ROLE │ ├── DATA_ENGINEER_ROLE │ └── ETL_ROLE ├── ANALYTICS_ADMIN_ROLE │ ├── ANALYST_ROLE │ └── REPORT_ROLE └── APP_ADMIN_ROLE ├── APP_WRITE_ROLE └── APP_READ_ROLE

Privilege Inheritance

When Role A is granted to Role B, Role B inherits ALL privileges of Role A:

GRANT ROLE analyst_role TO ROLE analytics_admin_role;
-- analytics_admin_role now has all privileges of analyst_role
-- PLUS any additional privileges directly granted to analytics_admin_role

Key point: Users activate a role, and that role includes all inherited privileges from the role hierarchy below it.

GRANT / REVOKE Syntax

Granting Privileges on Objects

-- Grant privilege on a specific object
GRANT SELECT ON TABLE mydb.myschema.sales TO ROLE analyst_role;

-- Grant multiple privileges
GRANT SELECT, INSERT ON TABLE mydb.myschema.sales TO ROLE etl_role;

-- Grant all privileges
GRANT ALL PRIVILEGES ON TABLE mydb.myschema.sales TO ROLE admin_role;

-- Grant USAGE on database and schema (required for access)
GRANT USAGE ON DATABASE mydb TO ROLE analyst_role;
GRANT USAGE ON SCHEMA mydb.myschema TO ROLE analyst_role;

-- Grant on all existing objects in a schema
GRANT SELECT ON ALL TABLES IN SCHEMA mydb.myschema TO ROLE analyst_role;
GRANT SELECT ON ALL VIEWS IN SCHEMA mydb.myschema TO ROLE analyst_role;

-- Grant with GRANT OPTION (allows grantee to re-grant)
GRANT SELECT ON TABLE mydb.myschema.sales TO ROLE analyst_role WITH GRANT OPTION;

Granting Roles

-- Grant role to user
GRANT ROLE analyst_role TO USER jane_doe;

-- Grant role to another role (builds hierarchy)
GRANT ROLE analyst_role TO ROLE sysadmin;

-- Note: A user must USE ROLE to activate a granted role
USE ROLE analyst_role;

Revoking Privileges

-- Revoke a privilege
REVOKE SELECT ON TABLE mydb.myschema.sales FROM ROLE analyst_role;

-- Revoke with CASCADE (revokes from role AND anyone it re-granted to)
REVOKE SELECT ON TABLE mydb.myschema.sales FROM ROLE analyst_role CASCADE;

-- Revoke GRANT OPTION only (keep privilege, remove ability to re-grant)
REVOKE GRANT OPTION FOR SELECT ON TABLE mydb.myschema.sales FROM ROLE analyst_role;

-- Revoke role from user
REVOKE ROLE analyst_role FROM USER jane_doe;
The WITH GRANT OPTION allows the grantee to grant that same privilege to other roles. REVOKE ... CASCADE will revoke the privilege from the role AND from any roles that received the privilege via re-granting.

FUTURE Grants

FUTURE grants automatically apply privileges to objects created in the future within a specified scope.

-- Grant SELECT on all future tables in a schema
GRANT SELECT ON FUTURE TABLES IN SCHEMA mydb.myschema TO ROLE analyst_role;

-- Grant USAGE on all future schemas in a database
GRANT USAGE ON FUTURE SCHEMAS IN DATABASE mydb TO ROLE analyst_role;

-- Grant SELECT on future views
GRANT SELECT ON FUTURE VIEWS IN SCHEMA mydb.myschema TO ROLE analyst_role;

-- Revoke future grants
REVOKE SELECT ON FUTURE TABLES IN SCHEMA mydb.myschema FROM ROLE analyst_role;

-- Show future grants
SHOW FUTURE GRANTS IN SCHEMA mydb.myschema;
SHOW FUTURE GRANTS IN DATABASE mydb;
FUTURE grants do NOT retroactively apply to existing objects. They only apply to objects created AFTER the FUTURE grant is established. Use "GRANT ... ON ALL ..." for existing objects AND "GRANT ... ON FUTURE ..." for new objects.

FUTURE Grants - Important Rules

  • Can be defined at the database level (applies to objects in any schema within the database)
  • Can be defined at the schema level (applies only to objects in that schema)
  • Schema-level FUTURE grants override database-level FUTURE grants for the same object type and role
  • When a schema is dropped, its FUTURE grants are also dropped
  • FUTURE grants on schemas can only be defined at the database level
  • Only the role with OWNERSHIP or MANAGE GRANTS can set FUTURE grants

Features & Limitations

15 Key Features of Snowflake RBAC

  1. Hierarchical roles: Privileges inherit up through the role hierarchy
  2. Multiple role assignments: Users can be granted multiple roles and switch between them
  3. FUTURE grants: Automatically assign privileges to future objects
  4. Managed access schemas: Centralized privilege management by schema owner
  5. Database roles: Roles scoped to a specific database (useful for sharing)
  6. WITH GRANT OPTION: Delegated privilege administration
  7. OWNERSHIP privilege: Clear object ownership model
  8. System-defined roles: Pre-built roles for common administrative patterns
  9. Row-level security: Via secure views or row access policies
  10. Column-level security: Via dynamic data masking policies
  11. Network policies: IP-based access restrictions by user or account
  12. Object tagging: Tag-based governance and policy assignment
  13. SHOW GRANTS: Full auditability of privilege assignments
  14. Secondary roles: USE SECONDARY ROLES ALL enables privilege union
  15. IMPORTED PRIVILEGES: Controlled access to shared databases

15 Key Limitations of Snowflake RBAC

  1. No DENY statement: Cannot explicitly deny access; must manage via careful granting
  2. Single ownership: Each object can only be owned by ONE role at a time
  3. No attribute-based access: Pure RBAC only; no ABAC natively (must use policies)
  4. FUTURE grants not retroactive: Do not apply to already-existing objects
  5. Role switching required: Default role is active; must explicitly switch or enable secondary roles
  6. No time-based grants: Cannot natively grant access for a time window (must script)
  7. No row-level in RBAC directly: Requires row access policies or secure views
  8. Ownership transfer is all-or-nothing: Cannot partially transfer privileges
  9. PUBLIC cannot be restricted: Cannot revoke PUBLIC role from any user
  10. Schema-level override: Schema FUTURE grants override database FUTURE grants (can confuse)
  11. No privilege groups/bundles: Must grant individual privileges (no predefined bundles)
  12. GRANT OPTION cascades: Revoking GRANT OPTION can cascade privilege loss
  13. No conditional privileges: Cannot grant based on data values within RBAC itself
  14. Clone inherits grants differently: Cloned objects inherit source grants but future grants may not apply
  15. Cross-database references: Each database/schema in the chain needs separate USAGE grants
Snowflake has NO DENY. If you want to prevent access, you must NOT grant the privilege. This is fundamentally different from SQL Server or Oracle which support DENY statements.
