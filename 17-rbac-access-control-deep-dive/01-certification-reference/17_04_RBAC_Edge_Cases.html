17.04 RBAC Edge Cases & Exam Scenarios

Ownership Transfer Edge Cases

Edge Case 1: Transfer with REVOKE CURRENT GRANTS (default)

-- Setup
GRANT SELECT ON TABLE t1 TO ROLE reader_role;  -- reader has SELECT
GRANT OWNERSHIP ON TABLE t1 TO ROLE new_owner REVOKE CURRENT GRANTS;

-- Result: reader_role LOSES SELECT!

Impact: All existing grants (except OWNERSHIP) are revoked. Anyone who had access through grants on this object loses it.

Edge Case 2: Transfer with COPY CURRENT GRANTS

-- Setup
GRANT SELECT ON TABLE t1 TO ROLE reader_role;
GRANT OWNERSHIP ON TABLE t1 TO ROLE new_owner COPY CURRENT GRANTS;

-- Result: reader_role KEEPS SELECT

Impact: All existing grants remain intact. The new owner inherits full control without disrupting access.

Edge Case 3: Previous owner loses implicit privileges

-- Role A owns table t1 (has implicit full control)
-- Role A can SELECT, INSERT, UPDATE, DELETE, DROP, GRANT, etc.
GRANT OWNERSHIP ON TABLE t1 TO ROLE B;

-- After transfer: Role A has ZERO privileges on t1
-- Unless Role A was separately GRANTED explicit privileges

Key insight: The previous owner loses ALL implicit privileges from ownership. They have no access unless explicitly granted.

Edge Case 4: Ownership of FUTURE objects

-- Grant future ownership (all future tables will be owned by data_admin)
GRANT OWNERSHIP ON FUTURE TABLES IN SCHEMA s1 TO ROLE data_admin;

-- Now any role creating tables in s1 creates them owned by data_admin
-- The creating role does NOT own the object!
When FUTURE OWNERSHIP is set, the creating role does NOT become the owner. The role specified in the FUTURE grant becomes the owner, even though another role executed the CREATE statement.

FUTURE Grants Behavior - Edge Cases

Edge Case 5: Schema-level overrides database-level

-- Database level: grant SELECT on future tables to role A
GRANT SELECT ON FUTURE TABLES IN DATABASE db1 TO ROLE role_a;

-- Schema level: grant SELECT on future tables to role B  
GRANT SELECT ON FUTURE TABLES IN SCHEMA db1.s1 TO ROLE role_b;

-- Create a table in db1.s1:
CREATE TABLE db1.s1.new_table (id INT);

-- Result: role_b gets SELECT, role_a does NOT get SELECT on this table
-- Schema-level FUTURE overrides database-level for the same object type
This is a common exam trap. When both database-level and schema-level FUTURE grants exist for the same object type, the schema-level grant takes effect and the database-level grant is ignored FOR OBJECTS IN THAT SCHEMA.

Edge Case 6: FUTURE grants and CLONE

-- FUTURE grants on schema s1
GRANT SELECT ON FUTURE TABLES IN SCHEMA db1.s1 TO ROLE reader;

-- Clone the schema
CREATE SCHEMA db1.s1_clone CLONE db1.s1;

-- Result: FUTURE grants are NOT copied to the clone
-- Existing tables in the clone DO retain their grants (from the source)
-- But NEW tables in s1_clone won't get automatic grants

Rule: FUTURE grants are NOT propagated by cloning. You must re-establish them on the cloned schema.

Edge Case 7: Dropping schema removes its FUTURE grants

-- Set FUTURE grants
GRANT SELECT ON FUTURE TABLES IN SCHEMA db1.s1 TO ROLE reader;

-- Drop and recreate schema
DROP SCHEMA db1.s1;
CREATE SCHEMA db1.s1;

-- Result: FUTURE grants are GONE. Must be re-established.

Edge Case 8: FUTURE grants don't affect EXISTING objects

-- Table already exists
CREATE TABLE db1.s1.existing_table (id INT);

-- Now set FUTURE grants
GRANT SELECT ON FUTURE TABLES IN SCHEMA db1.s1 TO ROLE reader;

-- Result: reader does NOT have SELECT on existing_table
-- Only tables created AFTER this point get the grant

-- Fix: also grant on existing objects
GRANT SELECT ON ALL TABLES IN SCHEMA db1.s1 TO ROLE reader;

Managed Access Schema - Edge Cases

Edge Case 9: Object owner cannot grant in managed access

-- Schema with managed access
CREATE SCHEMA db1.secure WITH MANAGED ACCESS;

-- Role A creates a table (owns it)
USE ROLE role_a;
CREATE TABLE db1.secure.my_table (id INT);

-- Role A tries to grant SELECT
GRANT SELECT ON TABLE db1.secure.my_table TO ROLE reader;
-- ERROR: Insufficient privileges. 
-- Only schema owner or MANAGE GRANTS role can grant.

Impact: Even though Role A owns the table, it cannot grant access in a managed access schema. The schema owner controls all grants.

Edge Case 10: Enabling managed access on existing schema

-- Existing schema with grants made by object owners
ALTER SCHEMA db1.s1 ENABLE MANAGED ACCESS;

-- Result: 
-- 1. Existing grants remain valid (not revoked)
-- 2. Going forward, only schema owner can make NEW grants
-- 3. Object owners can no longer grant on their objects
-- 4. FUTURE grants set by non-schema-owner are invalid going forward

Role Hierarchy Rules & Edge Cases

Edge Case 11: Circular grant prevention

CREATE ROLE role_a;
CREATE ROLE role_b;
CREATE ROLE role_c;

GRANT ROLE role_a TO ROLE role_b;  -- OK
GRANT ROLE role_b TO ROLE role_c;  -- OK
GRANT ROLE role_c TO ROLE role_a;  -- ERROR: Circular role grant detected

Snowflake checks for cycles before completing any GRANT ROLE statement.

Edge Case 12: Multiple inheritance paths

-- Role hierarchy:
--   SYSADMIN → admin_role → analyst_role → PUBLIC
--   SYSADMIN → power_user → analyst_role → PUBLIC
-- analyst_role is reachable via TWO paths from SYSADMIN

-- The privileges are the SAME regardless of which path
-- No "double counting" or duplication of privileges

Edge Case 13: Custom role NOT in SYSADMIN hierarchy

CREATE ROLE orphan_role;
GRANT CREATE DATABASE TO ROLE orphan_role; -- Given by ACCOUNTADMIN
-- Note: orphan_role is NOT granted to SYSADMIN

-- Result: SYSADMIN cannot manage objects created by orphan_role
-- ACCOUNTADMIN can (it encompasses all)
-- This is a BAD PRACTICE but is possible
If a custom role is not in the SYSADMIN hierarchy, SYSADMIN has no visibility or control over objects owned by that role. Always grant custom roles to SYSADMIN.

DROP Role Impact

Edge Case 14: Cannot drop role that owns objects

-- Role owns a table
DROP ROLE my_role;
-- ERROR: Role 'MY_ROLE' owns one or more objects. Cannot be dropped.

-- Solution: Transfer ownership first
GRANT OWNERSHIP ON ALL TABLES IN SCHEMA db1.s1 
  OWNED BY ROLE my_role TO ROLE sysadmin COPY CURRENT GRANTS;
DROP ROLE my_role;  -- Now succeeds

Edge Case 15: Dropping role with granted privileges

-- role_x has SELECT on table t1 (granted by someone)
-- role_x does NOT own any objects

DROP ROLE role_x;
-- Succeeds. The grant record is removed.
-- If role_x had re-granted (WITH GRANT OPTION) to others:
--   those downstream grants are also revoked (cascade)

Edge Case 16: User whose active role is dropped

-- User john has DEFAULT_ROLE = my_role
DROP ROLE my_role;  -- (after transferring ownership)

-- Result: 
-- John's DEFAULT_ROLE becomes NULL
-- Next login: John falls back to PUBLIC role
-- John keeps any OTHER roles that were granted to them

Privilege Cascade - REVOKE Behavior

Edge Case 17: REVOKE without CASCADE

-- Chain: GRANT SELECT ON t1 TO role_a WITH GRANT OPTION
--        role_a grants SELECT on t1 TO role_b
REVOKE SELECT ON TABLE t1 FROM ROLE role_a;

-- Result WITHOUT CASCADE:
-- role_a loses SELECT
-- role_b KEEPS SELECT (the downstream grant persists)

-- This seems counterintuitive but is how Snowflake works!
Without CASCADE, revoking from role_a does NOT affect role_b's grant, even though role_b received it via role_a's GRANT OPTION. The grant to role_b becomes "orphaned" but valid.

Edge Case 18: REVOKE with CASCADE

-- Same chain as above
REVOKE SELECT ON TABLE t1 FROM ROLE role_a CASCADE;

-- Result WITH CASCADE:
-- role_a loses SELECT
-- role_b also loses SELECT (cascaded revocation)

Edge Case 19: Revoking from parent vs child role

-- Hierarchy: parent_role → child_role
-- child_role has SELECT on t1

-- Revoking from child_role:
REVOKE SELECT ON TABLE t1 FROM ROLE child_role;
-- child_role loses SELECT
-- parent_role also loses inherited SELECT on t1 (because it came from child)

-- But if parent_role ALSO has a DIRECT grant of SELECT on t1:
-- parent_role keeps it (direct grant is independent of inherited grant)

Edge Case 20: Access after role change mid-session

-- User is in a session with role analyst_role
-- Admin revokes SELECT from analyst_role while session is active

-- Result: The user's CURRENT session is NOT affected
-- The revoke takes effect on the NEXT statement (in most cases)
-- Cached query results may still be accessible
-- New queries will fail with insufficient privileges

10 Exam Scenarios

SCENARIO 1

Setup: User Alice has roles: analyst_role, dev_role, sysadmin. Her DEFAULT_ROLE is analyst_role. She runs USE ROLE dev_role, then creates TABLE t1.

Question: Who owns t1?

Answer: dev_role owns t1.

Objects are owned by the currently active role at the time of creation. Since Alice used USE ROLE dev_role before creating the table, dev_role is the owner.

SCENARIO 2

Setup: A FUTURE grant exists: GRANT SELECT ON FUTURE TABLES IN DATABASE db1 TO ROLE reader; A schema-level FUTURE grant also exists: GRANT SELECT ON FUTURE TABLES IN SCHEMA db1.analytics TO ROLE analyst; A new table is created in db1.analytics.

Question: Which role(s) get SELECT on the new table?

Answer: Only analyst gets SELECT.

Schema-level FUTURE grants override database-level FUTURE grants. The database-level grant to reader is ignored for objects in db1.analytics because a schema-level FUTURE grant exists for the same object type.

SCENARIO 3

Setup: In a managed access schema, Role A creates a table. Role A attempts to grant SELECT on that table to Role B.

Question: Does the grant succeed?

Answer: No, the grant fails.

In a managed access schema, even the object owner cannot grant privileges. Only the schema owner or a role with MANAGE GRANTS can grant access to objects, regardless of who owns them.

SCENARIO 4

Setup: Role hierarchy: sysadmin → data_admin → etl_role. etl_role has SELECT on sensitive_table. An admin revokes SELECT from etl_role.

Question: Can a user with data_admin still access sensitive_table? What about sysadmin?

Answer: Neither data_admin nor sysadmin can access sensitive_table (via this path).

Privilege inheritance flows UP. data_admin and sysadmin only had access because they inherited it from etl_role. Once SELECT is revoked from etl_role, the inherited access is gone. They would still have access if they have a DIRECT grant or inherit from a different child role.

SCENARIO 5

Setup: A network policy with ALLOWED_IP_LIST='192.168.1.0/24' and BLOCKED_IP_LIST='192.168.1.50' is set at the account level. User Bob has a user-level network policy allowing 10.0.0.0/8 only. Bob connects from 192.168.1.100.

Question: Can Bob connect?

Answer: No, Bob cannot connect.

User-level network policies take precedence over account-level policies. Bob's user-level policy only allows 10.0.0.0/8. His IP (192.168.1.100) is not in 10.0.0.0/8, so he is blocked. The account-level policy is irrelevant for Bob.

SCENARIO 6

Setup: GRANT SELECT ON TABLE t1 TO ROLE role_a WITH GRANT OPTION. Role_a then grants SELECT on t1 to role_b. Later: REVOKE SELECT ON TABLE t1 FROM ROLE role_a (without CASCADE).

Question: Can role_b still SELECT from t1?

Answer: Yes, role_b retains SELECT.

Without CASCADE, only role_a loses the privilege. The grant that role_a made to role_b is not revoked. To also remove role_b's access, use REVOKE ... CASCADE.

SCENARIO 7

Setup: User has USE SECONDARY ROLES ALL enabled. Primary role = writer_role. Secondary includes reader_role (which has SELECT on analytics tables). User creates a new table.

Question: Which role owns the new table?

Answer: writer_role owns the new table.

When secondary roles are active, the PRIMARY role determines ownership of newly created objects. Secondary roles contribute privileges for access but not for ownership assignment.

SCENARIO 8

Setup: Schema s1 has FUTURE grants: GRANT SELECT ON FUTURE TABLES IN SCHEMA s1 TO ROLE reader; You clone s1 to s1_copy. You then create a new table in s1_copy.

Question: Does reader get SELECT on the new table in s1_copy?

Answer: No, reader does NOT get SELECT.

FUTURE grants are NOT cloned. The clone inherits existing object grants but not FUTURE grant definitions. You must re-establish FUTURE grants on s1_copy separately.

SCENARIO 9

Setup: Role analyst_role has USAGE on db1, USAGE on db1.schema1, and SELECT on db1.schema1.table1. An admin revokes USAGE on db1.schema1 from analyst_role.

Question: Can analyst_role SELECT from db1.schema1.table1?

Answer: No, analyst_role cannot SELECT from the table.

Even though analyst_role still has SELECT on the table, the access chain is broken. Without USAGE on the schema, the table is unreachable. All links in the chain (warehouse → database → schema → object) must be intact.

SCENARIO 10

Setup: You transfer ownership of table t1 from role_a to role_b using REVOKE CURRENT GRANTS. Before the transfer, role_c had SELECT on t1 (granted by role_a). After the transfer, role_c tries to query t1.

Question: Can role_c query t1? What must be done to restore access?

Answer: No, role_c cannot query t1.

REVOKE CURRENT GRANTS removes all existing privilege grants during ownership transfer. role_c's SELECT was revoked. To restore access, the new owner (role_b) or a role with MANAGE GRANTS must explicitly re-grant: GRANT SELECT ON TABLE t1 TO ROLE role_c;
