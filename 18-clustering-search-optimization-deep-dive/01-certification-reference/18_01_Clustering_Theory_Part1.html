1. Micro-Partitions Fundamentals

What Are Micro-Partitions?

Micro-partitions are Snowflake's fundamental unit of data storage. Every table is automatically divided into micro-partitions during data ingestion, without any user intervention.

Definition: Micro-partitions are immutable, compressed, columnar storage units ranging from 50 to 500 MB of uncompressed data each. They are Snowflake's equivalent of "blocks" but significantly more intelligent.

Core Characteristics

PropertyDetail
Size Range50–500 MB uncompressed (typically 16 MB compressed on disk)
Storage FormatColumnar (PAX-style hybrid)
MutabilityImmutable — DML creates new partitions
CompressionAutomatic, per-column compression algorithms
EncryptionAlways encrypted at rest (AES-256)
User ControlNo manual partition management
Rows per PartitionTypically millions of rows (varies by row width)

Micro-Partition Internal Structure

┌─────────────────────────────────────────────────────────┐ │ MICRO-PARTITION (50-500 MB) │ ├─────────────────────────────────────────────────────────┤ │ │ │ ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐ │ │ │ Col A │ │ Col B │ │ Col C │ │ Col D │ │ │ │ (INT) │ │(VARCHAR)│ │ (DATE) │ │(DECIMAL)│ │ │ │ │ │ │ │ │ │ │ │ │ │ val1 │ │ val1 │ │ val1 │ │ val1 │ │ │ │ val2 │ │ val2 │ │ val2 │ │ val2 │ │ │ │ val3 │ │ val3 │ │ val3 │ │ val3 │ │ │ │ ... │ │ ... │ │ ... │ │ ... │ │ │ │ valN │ │ valN │ │ valN │ │ valN │ │ │ └─────────┘ └─────────┘ └─────────┘ └─────────┘ │ │ │ │ ┌─────────────────────────────────────────────────┐ │ │ │ HEADER: metadata (min/max, null count, etc.) │ │ │ └─────────────────────────────────────────────────┘ │ └─────────────────────────────────────────────────────────┘

Why Columnar Storage Matters

  • Column Pruning: Only columns referenced in a query are read from storage
  • Better Compression: Similar data types compress much better together
  • Vectorized Processing: Operations on columns can be SIMD-optimized
  • Aggregate Efficiency: SUM/AVG/COUNT only read the target column
  • Min/Max Tracking: Per-column statistics enable partition pruning

2. Metadata & Partition Pruning

Metadata Tracked Per Micro-Partition

Snowflake automatically maintains rich metadata for every micro-partition without any user configuration:

Metadata TypeWhat's TrackedPurpose
Range (Min/Max)Min and max values for each columnPartition pruning on range predicates
Distinct ValuesNumber of distinct values per columnCardinality estimation
NULL CountNumber of NULL values per columnNULL predicate optimization
Row CountTotal number of rowsCost estimation
Size InformationCompressed and uncompressed sizesI/O estimation
Partition Pruning: Using min/max metadata, Snowflake can skip entire micro-partitions that cannot contain matching data. This is the primary performance optimization in Snowflake — no user-defined indexes are needed.

Partition Pruning in Action

Query: SELECT * FROM orders WHERE order_date = '2024-06-15' Partition 1: order_date range [2024-01-01, 2024-03-31] → PRUNED ✗ Partition 2: order_date range [2024-04-01, 2024-06-30] → SCANNED ✓ Partition 3: order_date range [2024-07-01, 2024-09-30] → PRUNED ✗ Partition 4: order_date range [2024-10-01, 2024-12-31] → PRUNED ✗ Result: Only 1 of 4 partitions scanned = 75% pruning efficiency

3. Natural Clustering

What Is Natural Clustering?

When data is loaded into Snowflake, it is stored in the order it arrives. This creates natural clustering — data loaded together tends to be in the same micro-partitions.

Key Insight: Tables loaded chronologically (e.g., event logs, transaction records) naturally cluster on their timestamp/date columns. This means queries filtering on date ranges get excellent partition pruning without any explicit clustering key.

When Natural Clustering Works Well

  • Data loaded in time order (append-only patterns)
  • Queries typically filter on the load-order column (date, timestamp)
  • Table is mostly INSERT operations (no heavy UPDATE/DELETE)
  • Sequential IDs that correlate with load order

When Natural Clustering Degrades

  • Heavy DML (UPDATE/DELETE) fragments the clustering
  • Data loaded from multiple sources in random order
  • Queries filter on columns unrelated to load order
  • Bulk loads from shuffled/randomized datasets

4. Explicit Clustering Keys

Defining a Clustering Key

-- Add clustering key to existing table
ALTER TABLE orders CLUSTER BY (order_date, region);

-- Create table with clustering key
CREATE TABLE sales (
    sale_id     INT,
    sale_date   DATE,
    region      VARCHAR(50),
    amount      DECIMAL(10,2)
) CLUSTER BY (sale_date, region);

-- Clustering on expressions
ALTER TABLE events CLUSTER BY (TO_DATE(event_timestamp), event_type);

-- Drop clustering key
ALTER TABLE orders DROP CLUSTERING KEY;

How Clustering Keys Work

Without Clustering Key (random distribution): ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐ │ Part 1 │ │ Part 2 │ │ Part 3 │ │ Part 4 │ │ US,EU,AP │ │ EU,AP,US │ │ AP,US,EU │ │ US,EU,AP │ │ Jan-Dec │ │ Jan-Dec │ │ Jan-Dec │ │ Jan-Dec │ └──────────┘ └──────────┘ └──────────┘ └──────────┘ Query: region = 'US' → Must scan ALL 4 partitions With CLUSTER BY (region, sale_date): ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐ │ Part 1 │ │ Part 2 │ │ Part 3 │ │ Part 4 │ │ AP │ │ EU │ │ US │ │ US │ │ Jan-Dec │ │ Jan-Dec │ │ Jan-Jun │ │ Jul-Dec │ └──────────┘ └──────────┘ └──────────┘ └──────────┘ Query: region = 'US' → Only scan Parts 3 & 4 = 50% pruning

Clustering Key Guidelines

GuidelineExplanation
Max 3-4 columnsMore columns = diminishing returns and higher cost
Order mattersPut most selective (most filtered) column first
Low-to-medium cardinality preferredHigh cardinality (unique IDs) is ineffective
Match query patternsChoose columns used in WHERE clauses
Expressions allowedCan cluster on TO_DATE(ts), MONTH(date), etc.
Only for large tablesSmall tables (<1TB) rarely benefit

6. When to Cluster

Decision Framework

Should I Add a Clustering Key? ┌─────────────────────┐ │ Table size > 1 TB? │ └──────────┬──────────┘ │ NO │ YES ▼ ▼ ┌─────────┐ ┌──────────────────┐ │ Usually │ │ Known filter │ │ NOT │ │ patterns on │ │ needed │ │ specific columns? │ └─────────┘ └────────┬─────────┘ │ NO │ YES ▼ ▼ ┌─────────┐ ┌────────────────┐ │ Not a │ │ Natural clust. │ │ good │ │ already good? │ │ fit │ │ (Check depth) │ └─────────┘ └───────┬────────┘ │ YES │ NO ▼ ▼ ┌────────┐ ┌────────┐ │ Leave │ │ ADD │ │ as-is │ │ CLUSTER│ └────────┘ │ KEY │ └────────┘

Indicators You Need Clustering

  • Table is very large (>1 TB / millions of micro-partitions)
  • Queries consistently filter on specific non-date columns
  • Query Profile shows poor partition pruning (<50% pruned)
  • High average_depth (>5) in SYSTEM$CLUSTERING_INFORMATION
  • Significant bytes scanned vs. bytes returned in queries
  • Table receives heavy DML that disrupts natural order

Indicators You DON'T Need Clustering

  • Table is small (<1 TB) — pruning is already fast
  • Queries are full table scans (analytics/aggregations)
  • Natural clustering is already effective (depth near 1)
  • Query patterns are highly varied (no consistent filters)
  • Cost of reclustering outweighs performance benefit

7. Automatic Reclustering

How Automatic Reclustering Works

Once a clustering key is defined, Snowflake automatically maintains clustering through background reclustering operations.

AspectDetail
TriggerAutomatic — runs when clustering degrades beyond threshold
ExecutionBackground service (no warehouse needed)
Cost ModelServerless compute charged per-credit (like serverless tasks)
BillingCharged to the table owner's account
ConcurrencyDoes NOT block DML or queries
SuspensionALTER TABLE t SUSPEND RECLUSTER
ResumptionALTER TABLE t RESUME RECLUSTER
MonitoringAUTOMATIC_CLUSTERING_HISTORY table function
-- Monitor reclustering costs
SELECT * FROM TABLE(INFORMATION_SCHEMA.AUTOMATIC_CLUSTERING_HISTORY(
    DATE_RANGE_START => DATEADD('day', -7, CURRENT_TIMESTAMP()),
    TABLE_NAME => 'MY_TABLE'
));

-- Suspend reclustering to control costs
ALTER TABLE my_table SUSPEND RECLUSTER;

-- Resume reclustering
ALTER TABLE my_table RESUME RECLUSTER;
Cost Model: Reclustering is charged as serverless compute credits. High-churn tables (frequent INSERT/UPDATE/DELETE) will incur more reclustering costs. Monitor via AUTOMATIC_CLUSTERING_HISTORY.

8. 15 Key Features of Clustering

1. Automatic Micro-Partitioning Data is automatically divided into 50-500MB partitions during ingestion with no user management.
2. Columnar Storage Each micro-partition stores data column-by-column for efficient compression and selective column reads.
3. Rich Metadata Min/max values, distinct counts, and NULL counts maintained per column per partition automatically.
4. Partition Pruning Queries skip irrelevant partitions using metadata — no indexes needed.
5. Natural Clustering Data loaded sequentially clusters naturally on load-order columns (e.g., timestamps).
6. Explicit Clustering Keys CLUSTER BY defines preferred data organization for specific query patterns.
7. Expression-Based Clustering Cluster on expressions like TO_DATE(ts), TRUNC(amount, -3), or SUBSTRING(id, 1, 4).
8. Multi-Column Clustering Support up to 3-4 columns in a clustering key for compound filter patterns.
9. Automatic Reclustering Background serverless process maintains clustering as DML modifies data.
10. Zero-Impact Reclustering Reclustering runs concurrently without blocking queries or DML operations.
11. Clustering Metrics SYSTEM$CLUSTERING_INFORMATION provides depth, overlap, and histogram data for analysis.
12. Recluster Suspension Can suspend/resume automatic reclustering to control costs during specific periods.
13. Column Pruning Queries only read columns referenced in the query — independent of clustering.
14. Immutable Partitions Partitions are never modified in-place — DML creates new versions ensuring consistency.
15. Cost Monitoring AUTOMATIC_CLUSTERING_HISTORY tracks credits consumed by reclustering operations.

9. 15 Limitations

1. No User-Controlled Partitioning Cannot manually define partition boundaries or partition schemes — Snowflake decides.
2. Max ~4 Clustering Key Columns Practical limit of 3-4 columns; more columns yield diminishing returns and higher costs.
3. High Cardinality Ineffective Unique/near-unique columns (UUIDs, email addresses) make poor clustering keys.
4. Ongoing Reclustering Costs Tables with heavy DML churn incur continuous serverless compute charges.
5. Not Instant Defining a clustering key doesn't immediately recluster — it happens gradually in background.
6. Small Tables Don't Benefit Tables under ~1TB rarely see meaningful improvement from explicit clustering.
7. Single Clustering Key A table can only have ONE clustering key definition at a time.
8. Column Order Sensitivity The order of columns in CLUSTER BY affects effectiveness — must match query patterns.
9. DML Degrades Clustering UPDATE/DELETE/MERGE operations create new partitions that may not be well-clustered.
10. Cannot Cluster External Tables External tables don't support clustering keys (data is outside Snowflake's control).
11. No Real-Time Metrics SYSTEM$CLUSTERING_INFORMATION is a point-in-time snapshot, not continuously updated.
12. Storage Overhead During Reclustering Reclustering temporarily creates additional partitions (old ones retained in Time Travel).
13. Not a Replacement for Good Schema Design Clustering cannot compensate for fundamentally poor data modeling or query design.
14. Limited Predicate Types Partition pruning works best with equality/range predicates; LIKE, functions on columns less effective.
15. Materialized View Clustering Materialized views have independent clustering from base tables and separate maintenance costs.
