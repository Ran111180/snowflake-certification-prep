1. Search Optimization Service (SOS)

What Is the Search Optimization Service?

The Search Optimization Service is a serverless, maintenance-free feature that significantly improves performance of selective point-lookup queries. It builds and maintains an optimized search access path in the background.

Key Concept: SOS creates a persistent data structure (search access paths) that allows Snowflake to efficiently locate specific rows without scanning entire partitions. Think of it like a secondary index, but fully managed and serverless.

Supported Predicate Types

Predicate TypeExampleNotes
Equality (=)WHERE id = 12345Primary use case — point lookups
IN listWHERE status IN ('A','B','C')Multiple value lookups
Substring/LIKEWHERE name LIKE '%smith%'Substring search support
Range predicatesWHERE amount BETWEEN 100 AND 200Selective ranges on high-cardinality columns
GEOGRAPHY functionsST_DISTANCE, ST_CONTAINSGeospatial point lookups
VARIANT fieldsWHERE data:key = 'value'Semi-structured field lookups
IS NULL / IS NOT NULLWHERE col IS NULLNULL predicate optimization

Enabling & Managing SOS

-- Enable SOS for entire table (all columns eligible)
ALTER TABLE my_table ADD SEARCH OPTIMIZATION;

-- Enable SOS for specific columns only (cost-effective)
ALTER TABLE my_table ADD SEARCH OPTIMIZATION
  ON EQUALITY(customer_id),
  ON EQUALITY(order_id),
  ON SUBSTRING(product_name),
  ON GEO(geo_column);

-- Disable SOS for specific columns
ALTER TABLE my_table DROP SEARCH OPTIMIZATION
  ON EQUALITY(customer_id);

-- Disable SOS entirely
ALTER TABLE my_table DROP SEARCH OPTIMIZATION;

-- Check SOS status
DESCRIBE SEARCH OPTIMIZATION ON my_table;

-- Monitor SOS costs
SELECT * FROM TABLE(INFORMATION_SCHEMA.SEARCH_OPTIMIZATION_HISTORY(
    DATE_RANGE_START => DATEADD('day', -7, CURRENT_TIMESTAMP()),
    TABLE_NAME => 'MY_TABLE'
));

SOS Cost Model

Cost ComponentDescription
Storage CostSearch access paths consume additional storage (typically small % of table size)
Compute CostServerless compute credits for building and maintaining access paths
Ongoing MaintenanceAutomatic updates after DML — cost proportional to data churn
Cost Warning: SOS incurs costs even when not queried. The background maintenance process runs continuously. Enable SOS selectively on columns that are frequently used in point lookups, not on entire tables with many columns.

When to Use SOS

  • Use when: Queries perform point lookups or selective equality/IN predicates on large tables
  • Use when: Clustering alone doesn't help (e.g., lookup on high-cardinality ID column)
  • Use when: VARIANT field lookups are common
  • Use when: Geospatial queries with selective predicates
  • Don't use when: Queries scan large portions of the table (full scans, broad ranges)
  • Don't use when: Table is small (pruning already effective)
  • Don't use when: Queries already well-served by clustering

2. Query Acceleration Service (QAS)

What Is the Query Acceleration Service?

QAS offloads portions of query processing to shared compute resources provided by Snowflake. It helps queries that scan a lot of data but return a small result set (highly selective after scanning).

Key Concept: QAS works by identifying the "scan-heavy" portions of eligible queries and distributing that scan work to additional serverless compute resources, reducing wall-clock time. The warehouse handles the rest of the query.

SCALE_FACTOR Parameter

-- Enable QAS on a warehouse with scale factor
ALTER WAREHOUSE my_wh SET
  ENABLE_QUERY_ACCELERATION = TRUE
  QUERY_ACCELERATION_MAX_SCALE_FACTOR = 8;

-- Scale factor = 0 means unlimited acceleration
-- Scale factor = N means up to N times the warehouse compute can be added
-- Default max scale factor is 8

-- Disable QAS
ALTER WAREHOUSE my_wh SET
  ENABLE_QUERY_ACCELERATION = FALSE;
Scale FactorMeaning
0No limit — Snowflake uses as much serverless compute as beneficial
1Up to 1x additional compute (double the warehouse capacity)
8 (default max)Up to 8x additional compute resources
Higher valuesMore potential acceleration but higher potential cost

Eligible Queries for QAS

  • Queries that scan many partitions but return few rows (high selectivity after scan)
  • Queries with LIMIT that require scanning broadly to find top results
  • Aggregations with GROUP BY over large datasets
  • Queries where the bottleneck is the scan phase, not joins or sorting

NOT Eligible for QAS

  • Queries already well-pruned by clustering (little scan work to offload)
  • Queries bottlenecked by joins, sorting, or network transfer
  • Queries that return most of the scanned data (non-selective)
  • INSERT, UPDATE, DELETE, MERGE operations
  • Queries using external tables or certain complex operations
-- Check which queries are eligible for QAS
SELECT query_id, eligible_query_acceleration_time
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY
WHERE eligible_query_acceleration_time > 0
ORDER BY eligible_query_acceleration_time DESC
LIMIT 20;

-- System function to check eligibility for a specific query
SELECT SYSTEM$ESTIMATE_QUERY_ACCELERATION('query-id-here');

3. Query Profile Analysis

Key Metrics for Partition Pruning Analysis

The Query Profile in the Snowflake UI provides critical metrics for understanding how well clustering and pruning are working.

MetricWhat It ShowsWhat to Look For
Partitions scannedNumber of micro-partitions readShould be small relative to total
Partitions totalTotal micro-partitions in tableBaseline for pruning ratio
Bytes scannedTotal data read from storageLess = better pruning
Percentage scanned from cacheData served from SSD/memory cacheHigher = faster I/O
Bytes sent over networkData transferred between nodesHigh values indicate spilling or redistribution
Bytes spilled to localData spilled to local SSDIndicates insufficient memory
Bytes spilled to remoteData spilled to remote storageSevere — indicates undersized warehouse

Query Profile — Pruning Efficiency

Query Profile → TableScan Operator: ┌──────────────────────────────────────────────────────┐ │ TableScan [2] │ │ │ │ Table: ORDERS │ │ Columns: 5 / 12 ← Column pruning │ │ │ │ Partitions total: 10,000 │ │ Partitions scanned: 250 ← 97.5% pruned! │ │ │ │ Bytes scanned: 4.2 GB │ │ % scanned from cache: 85% │ │ │ │ Rows produced: 1,250,000 │ └──────────────────────────────────────────────────────┘ Pruning Ratio = (total - scanned) / total = (10000 - 250) / 10000 = 97.5% ← Excellent! Guidelines: > 90% pruning = Excellent clustering 70-90% pruning = Good 50-70% pruning = Consider adding/changing clustering key < 50% pruning = Poor — investigate clustering strategy

Identifying Performance Issues in Query Profile

Spilling

Bytes Spilled to Local Storage: Indicates the warehouse memory is insufficient. Data overflows to local SSD. Performance impact is moderate.

Bytes Spilled to Remote Storage: Indicates severe memory pressure. Data overflows to S3/Azure Blob. Significant performance impact — consider upsizing the warehouse.

Inefficient Pruning

Signs of poor pruning in Query Profile:

  • Partitions scanned close to partitions total (low pruning %)
  • Large bytes scanned relative to result set size
  • Filter operator after TableScan (filtering happening late, not at partition level)

Fix: Add or adjust clustering key to match filter predicates.

Expensive Joins

Join operators consuming most of the query time often indicate:

  • Data explosion (many-to-many joins)
  • Large tables being shuffled/redistributed
  • Missing clustering on join keys in large tables

Query Profile SQL Analysis

-- Find queries with poor pruning
SELECT
    query_id,
    query_text,
    partitions_scanned,
    partitions_total,
    ROUND((partitions_total - partitions_scanned) / partitions_total * 100, 1) AS prune_pct,
    bytes_scanned,
    bytes_spilled_to_local_storage,
    bytes_spilled_to_remote_storage
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY
WHERE start_time > DATEADD('hour', -24, CURRENT_TIMESTAMP())
  AND partitions_total > 100
  AND (partitions_total - partitions_scanned) / partitions_total < 0.5  -- Less than 50% pruning
ORDER BY partitions_scanned DESC
LIMIT 20;

-- Find queries with spilling
SELECT
    query_id,
    query_text,
    warehouse_name,
    warehouse_size,
    bytes_spilled_to_local_storage,
    bytes_spilled_to_remote_storage,
    execution_time
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY
WHERE bytes_spilled_to_remote_storage > 0
  AND start_time > DATEADD('day', -7, CURRENT_TIMESTAMP())
ORDER BY bytes_spilled_to_remote_storage DESC
LIMIT 20;

4. Clustering vs SOS vs QAS — When to Use Each

Comparison Table

Aspect Clustering Keys Search Optimization (SOS) Query Acceleration (QAS)
What It Does Reorganizes data within micro-partitions for better pruning Builds search access paths for point lookups Offloads scan work to additional serverless compute
Best For Range queries on known filter columns Equality/IN lookups on high-cardinality columns Large scans with selective filters; queries with LIMIT
How It Works Background reclustering sorts data by key columns Persistent index-like structure maps values to partitions Parallelizes scan phase across serverless compute

Idle Cost Yes — reclustering runs even without queries Yes — maintenance runs after DML No — only charged per accelerated query

Decision Matrix

Query Pattern Analysis → Choose Optimization: ┌─────────────────────────────────────────────────────────────────┐ │ │ │ "I filter on date ranges and region" │ │ → CLUSTERING KEY on (date, region) │ │ │ │ "I look up individual orders by order_id" │ │ → SEARCH OPTIMIZATION on EQUALITY(order_id) │ │ │ │ "I search for customer names with LIKE '%pattern%'" │ │ → SEARCH OPTIMIZATION on SUBSTRING(customer_name) │ │ │ │ "My aggregation queries scan everything but return few groups" │ │ → QUERY ACCELERATION SERVICE │ │ │ │ "I have a huge table filtered on date AND point-lookup on ID" │ │ → CLUSTERING on date + SOS on EQUALITY(id) (use BOTH) │ │ │ │ "My ad-hoc queries hit random columns with LIMIT 100" │ │ → QUERY ACCELERATION SERVICE │ │ │ └─────────────────────────────────────────────────────────────────┘

Can They Be Combined?

Yes! Clustering, SOS, and QAS are complementary and can all be active on the same table/warehouse simultaneously:
  • Clustering + SOS: Clustering handles range predicates; SOS handles point lookups on different columns
  • Clustering + QAS: Clustering reduces scan volume; QAS parallelizes remaining scans
  • All three: Each addresses a different aspect of query performance
