18.04 Clustering Edge Cases & Gotchas

1. Reclustering Cost Edge Cases

1High-Churn Tables: Silent Cost Explosion

Tables with frequent INSERT/UPDATE/DELETE operations trigger continuous reclustering. Each DML operation creates new micro-partitions that may violate the clustering key order.

Gotcha: A table receiving 100K updates/hour will trigger near-continuous reclustering. The serverless compute costs can exceed the original warehouse costs without any visible query or user action. Monitor via AUTOMATIC_CLUSTERING_HISTORY. 
-- Identify high-churn tables with expensive reclustering
SELECT
    table_name,
    SUM(credits_used) AS total_credits_7d,
    SUM(num_bytes_reclustered) AS bytes_reclustered,
    COUNT(*) AS recluster_operations
FROM TABLE(INFORMATION_SCHEMA.AUTOMATIC_CLUSTERING_HISTORY(
    DATE_RANGE_START => DATEADD('day', -7, CURRENT_TIMESTAMP())
))
GROUP BY table_name
ORDER BY total_credits_7d DESC;
Mitigation: For high-churn tables, consider: (1) suspending reclustering during heavy DML windows, (2) reducing clustering key columns, (3) clustering only if queries benefit enough to justify the cost.

2Time Travel Storage Inflation During Reclustering

Reclustering creates NEW micro-partitions while old ones remain in Time Travel. This means a reclustering cycle temporarily increases storage.

Edge Case: A 5 TB table undergoing heavy reclustering can temporarily consume 7-8 TB of storage (original + new + Time Travel for old partitions). Storage normalizes only after the Time Travel period expires (default: 1 day standard, up to 90 days Enterprise).
Time Travel Storage During Reclustering: Time T0: Table = 5 TB (all partitions) ┌─────────────────────┐ │ 5 TB active data │ └─────────────────────┘ Time T1: Reclustering in progress ┌─────────────────────┐ │ 5 TB active data │ (new well-clustered partitions) ├─────────────────────┤ │ 2 TB Time Travel │ (old replaced partitions) └─────────────────────┘ Total storage: ~7 TB Time T2: After Time Travel expiry ┌─────────────────────┐ │ 5 TB active data │ (back to normal) └─────────────────────┘

3Reclustering a Table with Long Time Travel Retention

If you have DATA_RETENTION_TIME_IN_DAYS = 90 and the table undergoes major reclustering, the old partitions persist in Time Travel for 90 days — tripling storage costs temporarily.

Cost Impact: Tables with 90-day retention that are heavily reclustered can see storage costs balloon. Consider temporarily reducing retention before a large-scale reclustering if storage costs are a concern (but understand the audit/recovery implications).

2. High-Cardinality Clustering Key Problems

4Clustering on UUID/High-Cardinality Columns is Counterproductive

A clustering key on a column with near-unique values (UUID, email, random ID) provides zero pruning benefit and wastes reclustering credits.

Why High-Cardinality Clustering Fails: CLUSTER BY (uuid_column): Partition 1: UUIDs a000...a999 → Contains range a000-a999 Partition 2: UUIDs b000...b999 → Contains range b000-b999 ... Query: WHERE uuid_column = 'b500...' Without clustering: scan ~1-2 partitions (SOS handles this) With clustering: scan ~1 partition (same result, but paid for reclustering!) Net effect: Paid ongoing reclustering costs for zero query improvement. Use SOS on EQUALITY(uuid_column) instead — zero reclustering cost.
Rule of Thumb: If column cardinality exceeds the number of micro-partitions, clustering on it is wasteful. Use SOS instead for high-cardinality point lookups.

5Clustering on Timestamps with Second/Millisecond Precision

Clustering directly on a high-precision TIMESTAMP is effectively high-cardinality clustering. Each second has unique values.

Fix: Use expressions to reduce cardinality: CLUSTER BY (TO_DATE(event_ts)) or CLUSTER BY (DATE_TRUNC('hour', event_ts)). This groups data by date or hour — far more effective for pruning. 
-- BAD: High cardinality (millions of distinct values)
ALTER TABLE events CLUSTER BY (event_timestamp);

-- GOOD: Reduced cardinality (365 distinct values per year)
ALTER TABLE events CLUSTER BY (TO_DATE(event_timestamp));

-- GOOD: Medium cardinality with secondary column
ALTER TABLE events CLUSTER BY (TO_DATE(event_timestamp), event_type);

3. Max Clustering Key Constraints

6Diminishing Returns Beyond 3-4 Columns

While Snowflake technically allows more columns in a clustering key, effectiveness drops sharply after 3-4 due to the "curse of dimensionality."

ColumnsEffectivenessReclustering CostRecommendation
1Good for single-predicate queriesLowSimple range filters
2Excellent for compound filtersModerateMost common sweet spot
3Good if all 3 used in queriesHigherOnly if queries consistently use all 3
4+Diminishing returnsHighRarely justified
Why? With 4+ dimensions, achieving low overlap across ALL dimensions simultaneously requires extreme data reorganization. The reclustering engine may never converge to a "well-clustered" state, running continuously without meaningful improvement.

7Column Order in Clustering Key Matters Dramatically

The first column in the clustering key gets the best partitioning. Subsequent columns partition within the ranges of preceding columns.

CLUSTER BY (A, B) vs CLUSTER BY (B, A): CLUSTER BY (region, date): CLUSTER BY (date, region): ┌──────────────────────┐ ┌──────────────────────┐ │ APAC │ Jan-Jun │ │ Jan │ APAC,EU,US │ │ APAC │ Jul-Dec │ │ Feb │ APAC,EU,US │ │ EU │ Jan-Jun │ │ Mar │ APAC,EU,US │ │ EU │ Jul-Dec │ │ ... │ │ │ US │ Jan-Jun │ │ Dec │ APAC,EU,US │ │ US │ Jul-Dec │ └──────────────────────┘ └──────────────────────┘ Query: WHERE date = '2024-03-15' → CLUSTER BY (region, date): Must check all regions → scans more → CLUSTER BY (date, region): Direct prune to March → scans less Query: WHERE region = 'US' → CLUSTER BY (region, date): Direct prune to US → scans less → CLUSTER BY (date, region): Must check all months → scans more RULE: Put the most frequently filtered column FIRST.

4. Clustering + Streams: Phantom Changes

8Reclustering Generates Stream "Phantom" Changes

When automatic reclustering reorganizes data, it effectively DELETEs rows from old partitions and INSERTs them into new partitions. Streams track this as real DML.

Critical Gotcha: A standard stream on a clustered table will show INSERT/DELETE pairs for rows that were merely moved by reclustering — not actually modified by users. This can cause downstream tasks to process "phantom" changes.
Reclustering + Streams Interaction: Before reclustering: Partition 1: [Row A (US, Jan), Row B (EU, Mar)] Partition 2: [Row C (EU, Jan), Row D (US, Mar)] After CLUSTER BY (region): Partition 1: [Row A (US, Jan), Row D (US, Mar)] ← reorganized Partition 2: [Row B (EU, Mar), Row C (EU, Jan)] ← reorganized Stream sees: DELETE Row B from P1, INSERT Row B into P2 ← "phantom" change DELETE Row C from P2, INSERT Row C into P2 ← "phantom" change DELETE Row D from P2, INSERT Row D into P1 ← "phantom" change These are NOT real user changes but stream reports them!
Solution: Use APPEND-ONLY streams on clustered tables when you only care about new INSERTs. Append-only streams ignore DELETE/UPDATE operations (including those from reclustering). 
-- Standard stream: WILL see phantom changes from reclustering
CREATE STREAM my_stream ON TABLE clustered_table;

-- Append-only stream: Ignores reclustering moves
CREATE STREAM my_stream ON TABLE clustered_table APPEND_ONLY = TRUE;

-- If you need change tracking but not phantom changes:
-- Use CHANGES clause with a timestamp BEFORE reclustering began

9Stream Offset Advancement During Reclustering

If a stream is not consumed before reclustering occurs, the phantom changes accumulate. Consuming the stream then processes all phantom rows as real changes.

Impact: A task consuming a stream may trigger unnecessarily after reclustering, processing zero meaningful changes but incurring compute costs. Design tasks to handle/filter phantom DELETE+INSERT pairs or use APPEND_ONLY streams.

5. Search Optimization Service (SOS) Limitations

10SOS Does NOT Help Broad Range Queries

SOS is designed for selective predicates (finding needles in haystacks). If the predicate matches a large percentage of rows, SOS cannot help — and won't be used by the optimizer.

SOS Effectiveness vs. Selectivity: Selectivity: | SOS Benefit: ───────────────────────────────────── 0.001% (1 row in 1M) │ EXCELLENT 0.01% (100 in 1M) │ EXCELLENT 0.1% (1K in 1M) │ GOOD 1% (10K in 1M) │ MODERATE 10% (100K in 1M) │ MINIMAL/NONE 50% (500K in 1M) │ NONE — full scan faster ───────────────────────────────────── SOS shines when query returns << 1% of table rows.

11SOS Maintenance Cost Scales with DML Volume

Every INSERT/UPDATE/DELETE operation triggers SOS background maintenance to update search access paths. High-frequency micro-batch ingestion can cause continuous maintenance.

Cost Trap: A table receiving 1000 small inserts per hour will trigger frequent SOS maintenance updates. Consider batching inserts or enabling SOS only on specific high-value columns to control costs.

12SOS on VARIANT — Path Specificity Required

SOS can optimize VARIANT field lookups, but you must specify the exact path. It won't automatically index all paths within a VARIANT column.

-- This optimizes lookups on data:customer_id specifically
ALTER TABLE events ADD SEARCH OPTIMIZATION
  ON EQUALITY(data:customer_id::STRING);

-- This does NOT automatically help data:order_id or data:region
-- Each path must be specified separately
ALTER TABLE events ADD SEARCH OPTIMIZATION
  ON EQUALITY(data:customer_id::STRING),
  ON EQUALITY(data:order_id::STRING);

13SOS and Table Restructuring Operations

Certain operations require SOS to be rebuilt from scratch:

  • ALTER TABLE ... CLUSTER BY: Changing clustering key doesn't invalidate SOS, but reclustering causes SOS maintenance
  • Table recreation (CTAS): SOS must be re-added to the new table
  • Column type change: SOS on that column must be dropped and re-added
  • Table clone: Cloned table does NOT inherit SOS configuration
Gotcha: CREATE TABLE new_table CLONE old_table does NOT clone the SOS configuration. You must re-add search optimization to the cloned table separately.

6. Query Acceleration Service (QAS) Edge Cases

14QAS Does NOT Accelerate All Queries

QAS only accelerates queries where the scan phase is the bottleneck AND the result is selective. Many query types cannot benefit:

Query TypeQAS Eligible?Reason
Point lookup (WHERE id = X)Usually NoToo little scan work to offload
Full table aggregationMaybeDepends on result selectivity
Large scan + selective filterYesIdeal case — scan work offloaded
INSERT ... SELECTNoDML not eligible
MERGENoDML not eligible
External table queriesNoNot supported
Queries with UDFs in WHERELimitedOptimizer may not push down
Complex multi-join queriesLimitedBottleneck often not in scan phase

15QAS Scale Factor Misconfigurations

Too High (e.g., 0 unlimited): Can cause unexpectedly high serverless credit consumption for expensive queries that happen to be eligible. A single poorly-written query could consume significant credits.

Too Low (e.g., 1): May limit acceleration benefit for queries that could significantly benefit from more parallelism. Start conservative and increase based on monitoring. 
-- Start conservative
ALTER WAREHOUSE analytics_wh SET
  ENABLE_QUERY_ACCELERATION = TRUE
  QUERY_ACCELERATION_MAX_SCALE_FACTOR = 4;

-- Monitor before increasing
SELECT
    query_id,
    query_acceleration_bytes_scanned,
    query_acceleration_partitions_scanned,
    query_acceleration_upper_limit_scale_factor
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_ACCELERATION_HISTORY
WHERE start_time > DATEADD('day', -7, CURRENT_TIMESTAMP())
ORDER BY query_acceleration_bytes_scanned DESC;

7. Re-Clustering Triggers & Behavior

16What Triggers Reclustering?

TriggerImpactNotes
INSERT (large batch)High — new partitions may violate orderBiggest trigger for reclustering
INSERT (small/micro-batch)Low — few new partitionsMay accumulate over time
UPDATEHigh — creates new partition versionsOld rows deleted, new rows inserted
DELETEModerate — partition rewriteRemaining data may still be clustered
MERGE (matched UPDATE)High — equivalent to UPDATEPartition rewrite triggers recluster
COPY INTOHigh — bulk new dataSame as large INSERT
Snowpipe (streaming)Moderate — continuous small insertsAccumulates clustering debt
Threshold: Snowflake doesn't recluster after every single row change. It waits until clustering quality degrades beyond an internal threshold before initiating reclustering. This prevents excessive micro-reclustering operations.

17Reclustering During Peak Load Windows

While reclustering doesn't block queries, it competes for I/O at the storage layer. During periods of both heavy DML and heavy reclustering, you may observe slightly higher query latencies.

Strategy: For tables with predictable DML patterns (e.g., nightly batch loads), consider suspending reclustering during the load window and resuming after completion: 
-- Before heavy batch load
ALTER TABLE my_table SUSPEND RECLUSTER;

-- Run ETL / batch load
COPY INTO my_table FROM @stage/...;

-- After load completes, resume
ALTER TABLE my_table RESUME RECLUSTER;

18Reclustering Never Fully Converges on High-Churn Tables

If DML rate exceeds reclustering rate, clustering quality will never reach optimal. The reclustering service continuously runs but can't "catch up."

Convergence Problem: DML rate: 500 partitions modified / hour Recluster rate: 200 partitions reorganized / hour Result: Clustering debt grows by 300 partitions/hour → Never converges to good clustering → Continuous credit consumption with no benefit Solution options: 1. Accept natural clustering (drop clustering key) 2. Cluster on fewer columns (faster reclustering) 3. Reduce DML frequency (batch more aggressively) 4. Use SOS/QAS instead for these query patterns

8. Miscellaneous Edge Cases

19Clustering Key and Zero-Copy Clone Behavior

  • Clustering key definition: IS cloned to the new table
  • Clustering state: Clone shares same partitions initially (good clustering preserved)
  • Reclustering: Operates independently on clone after divergence
  • Cost: Both original and clone incur separate reclustering costs after diverging
Gotcha: Cloning a large clustered table and then modifying the clone heavily means you pay reclustering costs on BOTH the original (for its changes) AND the clone (for its changes). Budget accordingly.

20Clustering vs. Materialized Views

Materialized views can have their own independent clustering keys, separate from the base table. This is a powerful but expensive pattern:

-- Base table clustered on date
CREATE TABLE events (...)
  CLUSTER BY (event_date);

-- Materialized view clustered differently for different query patterns
CREATE MATERIALIZED VIEW events_by_user AS
  SELECT * FROM events
  CLUSTER BY (user_id);

-- Now you pay for:
-- 1. Base table reclustering (by date)
-- 2. MV reclustering (by user_id)
-- 3. MV maintenance (refresh after DML)
-- = Triple cost but enables pruning on both date AND user_id queries
When This Makes Sense: Only when the table is queried by two fundamentally different patterns (date ranges AND user lookups) and both patterns need excellent pruning. Usually SOS on the secondary pattern is cheaper.

21SYSTEM$CLUSTERING_INFORMATION Can Be Misleading

The clustering information function shows a point-in-time snapshot. It does not account for:

  • In-flight reclustering operations (currently being reorganized)
  • DML operations executed since the last recluster cycle
  • Whether the "poor" clustering actually matters for your specific queries
Always validate with Query Profile: Don't recluster just because average_depth is high. Check actual query partition pruning statistics first. If queries already prune well despite "poor" clustering metrics, save the reclustering cost.
