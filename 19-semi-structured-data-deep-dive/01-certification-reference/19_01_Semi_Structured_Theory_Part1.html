19.01 Semi-Structured Data Theory - Part 1

Fundamentals: VARIANT, OBJECT, ARRAY, Access Patterns, Parsing, and Loading

VARIANT Data Type

What is VARIANT?

VARIANT is Snowflake's universal semi-structured data type that can store any value: a JSON object, an array, a scalar (string, number, boolean), or NULL. It is stored internally in an efficient columnar format optimized for both storage and query performance.

Exam Alert: VARIANT stores data in a proprietary columnar format, NOT as plain text JSON. Snowflake automatically extracts and optimizes frequently accessed paths for columnar scanning.

Declaring VARIANT Columns

-- Simple table with VARIANT column
CREATE TABLE events (
    event_id INTEGER AUTOINCREMENT,
    event_time TIMESTAMP_NTZ DEFAULT CURRENT_TIMESTAMP(),
    payload VARIANT  -- Stores any semi-structured data
);

-- VARIANT in CTAS
CREATE TABLE parsed_logs AS
SELECT PARSE_JSON(raw_json) AS data
FROM raw_logs;

OBJECT and ARRAY Types

OBJECT

A collection of key-value pairs (like a JSON object / dictionary). Keys are always strings; values can be any VARIANT-compatible type.

-- Construct an OBJECT
SELECT OBJECT_CONSTRUCT(
  'name', 'Alice',
  'age', 30,
  'active', TRUE
) AS obj;
ARRAY

An ordered sequence of values (like a JSON array / list). Elements can be any VARIANT-compatible type including nested objects and arrays.

-- Construct an ARRAY
SELECT ARRAY_CONSTRUCT(
  'red', 'green', 'blue'
) AS colors;

Type Comparison

Exam Alert: OBJECT, ARRAY, and VARIANT are three distinct data types in Snowflake, but VARIANT can contain either an object or an array. When you declare a column as VARIANT, it can store any of them.

Access Patterns

Dot Notation

The most common way to access nested elements. Keys are case-insensitive when using dot notation (Snowflake converts to uppercase internally).

-- Given: payload = {"name": "Alice", "address": {"city": "Seattle"}}
SELECT
    payload:name,                    -- Top-level key
    payload:address.city,            -- Nested key
    payload:address.city::STRING     -- Cast to STRING
FROM events;
Critical Exam Point: Dot notation traversal uses colon (:) for the first level, then dot (.) for deeper levels. Example: col:key1.key2.key3. The colon separates the column name from the path.

Bracket Notation

Required for case-sensitive keys, keys with spaces/special characters, and array index access.

-- Case-sensitive access (preserves exact key casing)
SELECT
    payload['Name'],                 -- Exact case match
    payload['first name'],           -- Key with space
    payload['items'][0],             -- First array element
    payload['items'][0]['price']     -- Nested in array element
FROM events;

Exam Alert: When using dot notation, Snowflake matches keys case-insensitively. If your JSON has mixed-case keys like "Name" and "name", you MUST use bracket notation with quotes to distinguish them: col['Name'] vs col['name'].

GET and GET_PATH Functions

-- GET function - access by key or index
SELECT GET(payload, 'name') FROM events;        -- By key
SELECT GET(payload, 0) FROM events;             -- By index (if array)

-- GET_PATH - navigate a path expression
SELECT GET_PATH(payload, 'address.city') FROM events;
-- Equivalent to payload:address.city

-- Useful when path is dynamic
SELECT GET_PATH(payload, path_column) FROM events;

Parsing Functions

PARSE_JSON

-- Converts a JSON string to VARIANT
SELECT PARSE_JSON('{"name": "Alice", "age": 30}') AS data;

-- Error if invalid JSON
SELECT PARSE_JSON('not valid json');  -- ERROR!

-- Common pattern: parse column
SELECT PARSE_JSON(json_text_column) AS structured_data
FROM raw_table;

TRY_PARSE_JSON

-- Returns NULL instead of error on invalid JSON
SELECT TRY_PARSE_JSON('{"valid": true}');    -- Returns VARIANT
SELECT TRY_PARSE_JSON('invalid json');       -- Returns NULL (no error)

-- Safe parsing pattern
SELECT
    raw_text,
    TRY_PARSE_JSON(raw_text) AS parsed,
    CASE WHEN TRY_PARSE_JSON(raw_text) IS NULL
         THEN 'INVALID' ELSE 'VALID' END AS status
FROM raw_data;

Type Casting with ::

-- Cast VARIANT elements to specific types
SELECT
    payload:name::STRING AS name,
    payload:age::INTEGER AS age,
    payload:salary::FLOAT AS salary,
    payload:active::BOOLEAN AS is_active,
    payload:hire_date::DATE AS hire_date,
    payload:created_at::TIMESTAMP AS created
FROM events;
Exam Alert: Without casting, VARIANT elements return as VARIANT type (shown with quotes in results). You must cast with :: to get native Snowflake types for comparisons, aggregations, and JOINs.

TYPEOF Function

-- Returns the JSON type stored in a VARIANT value
SELECT
    TYPEOF(PARSE_JSON('"hello"')),              -- VARCHAR
    TYPEOF(PARSE_JSON('42')),                   -- INTEGER
    TYPEOF(PARSE_JSON('3.14')),                 -- DECIMAL
    TYPEOF(PARSE_JSON('true')),                 -- BOOLEAN
    TYPEOF(PARSE_JSON('null')),                 -- NULL_VALUE
    TYPEOF(PARSE_JSON('[1,2,3]')),              -- ARRAY
    TYPEOF(PARSE_JSON('{"a":1}')),              -- OBJECT
    TYPEOF(NULL);                               -- NULL (SQL NULL, not JSON null)

Additional Conversion Functions

-- TO_VARIANT: convert scalar to VARIANT
SELECT TO_VARIANT(42), TO_VARIANT('hello'), TO_VARIANT(CURRENT_DATE());

-- TO_JSON: convert VARIANT back to JSON string
SELECT TO_JSON(PARSE_JSON('{"a":1}'));  -- '{"a":1}'

-- TO_OBJECT: convert to OBJECT type
SELECT TO_OBJECT(PARSE_JSON('{"x":1}'));

-- TO_ARRAY: convert to ARRAY type
SELECT TO_ARRAY(PARSE_JSON('[1,2,3]'));

-- AS_INTEGER, AS_DOUBLE, etc. - extract typed value
SELECT AS_INTEGER(PARSE_JSON('42'));     -- 42 (INTEGER)
SELECT AS_DOUBLE(PARSE_JSON('3.14'));   -- 3.14 (DOUBLE)

Loading Semi-Structured Data

Loading JSON

-- File format for JSON
CREATE OR REPLACE FILE FORMAT json_format
    TYPE = 'JSON'
    STRIP_OUTER_ARRAY = TRUE          -- Remove outer [] if file is array of objects
    STRIP_NULL_VALUES = FALSE         -- Keep explicit nulls
    IGNORE_UTF8_ERRORS = FALSE
    ALLOW_DUPLICATE = FALSE
    ENABLE_OCTAL = FALSE
    COMPRESSION = AUTO;

-- COPY INTO with JSON
COPY INTO events (payload)
FROM @my_stage/data/
FILE_FORMAT = (FORMAT_NAME = json_format)
MATCH_BY_COLUMN_NAME = NONE;

Loading XML

-- File format for XML
CREATE OR REPLACE FILE FORMAT xml_format
    TYPE = 'XML'
    STRIP_OUTER_ELEMENT = FALSE
    DISABLE_SNOWFLAKE_DATA = FALSE
    DISABLE_AUTO_CONVERT = FALSE;

-- XML is loaded as VARIANT with special structure
-- Access with $ notation for attributes, @ for element content
COPY INTO xml_table (xml_data)
FROM @my_stage/data.xml
FILE_FORMAT = (FORMAT_NAME = xml_format);

Loading Avro

-- File format for Avro
CREATE OR REPLACE FILE FORMAT avro_format
    TYPE = 'AVRO'
    COMPRESSION = AUTO
    TRIM_SPACE = FALSE;

-- Avro loaded as VARIANT (schema embedded in file)
COPY INTO avro_table (data)
FROM @my_stage/data.avro
FILE_FORMAT = (FORMAT_NAME = avro_format);

Loading Parquet

-- File format for Parquet
CREATE OR REPLACE FILE FORMAT parquet_format
    TYPE = 'PARQUET'
    COMPRESSION = AUTO
    BINARY_AS_TEXT = TRUE;

-- Option 1: Load entire row as single VARIANT
COPY INTO parquet_raw (data)
FROM @my_stage/data.parquet
FILE_FORMAT = (FORMAT_NAME = parquet_format);

-- Option 2: Load with column mapping (Parquet has schema)
COPY INTO structured_table (id, name, amount)
FROM (
    SELECT
        $1:id::INTEGER,
        $1:name::STRING,
        $1:amount::DECIMAL(10,2)
    FROM @my_stage/data.parquet
)
FILE_FORMAT = (FORMAT_NAME = parquet_format);

COPY INTO with Semi-Structured Transformations

-- Transform during load
COPY INTO target_table (user_id, user_name, email, raw_data)
FROM (
    SELECT
        $1:userId::INTEGER,
        $1:name::STRING,
        $1:contact.email::STRING,
        $1
    FROM @my_stage/users/
)
FILE_FORMAT = (TYPE = 'JSON' STRIP_OUTER_ARRAY = TRUE);

-- Using MATCH_BY_COLUMN_NAME for Parquet/Avro
COPY INTO typed_table
FROM @my_stage/data.parquet
FILE_FORMAT = (TYPE = 'PARQUET')
MATCH_BY_COLUMN_NAME = CASE_INSENSITIVE;
Exam Alert: STRIP_OUTER_ARRAY = TRUE is essential when your JSON file contains an array of objects (e.g., [{...}, {...}, {...}]). It strips the outer brackets so each object becomes a separate row. Without it, the entire array loads as a single VARIANT value in one row.

15 Key Features of Semi-Structured Data in Snowflake

  • Schema-on-read: No predefined schema required - structure is interpreted at query time
  • Native VARIANT type: First-class data type with full SQL support, not a text blob
  • Columnar optimization: Snowflake auto-detects repeated paths and stores them in optimized columnar format
  • Multi-format support: Natively handles JSON, Avro, ORC, Parquet, and XML
  • Dot/bracket notation: Intuitive path-based access syntax without requiring FLATTEN for simple access
  • Automatic type detection: TYPEOF function reveals the stored type; automatic casting available
  • LATERAL FLATTEN: Powerful explosion of arrays/objects into rows with full JOIN semantics
  • RECURSIVE flatten: Automatically traverses all nested levels without manual path specification
  • PARSE_JSON / TRY_PARSE_JSON: Safe parsing with error-tolerant option for data pipelines
  • Mixed types in arrays: Arrays can contain heterogeneous types (strings, numbers, objects)
  • COPY INTO transformation: Extract and type fields during load, not just after
  • Query optimization: Pruning and predicate pushdown work on VARIANT path expressions
  • OBJECT_CONSTRUCT / ARRAY_CONSTRUCT: Build semi-structured output from relational data
  • Materialized columns: Define virtual columns from VARIANT paths for better performance
  • MATCH_BY_COLUMN_NAME: Auto-map Parquet/Avro columns to table columns during load

15 Key Limitations of Semi-Structured Data in Snowflake

  • 16 MB max per VARIANT value: Single VARIANT cell cannot exceed 16 MB compressed
  • No native indexing on paths: Cannot create secondary indexes on specific VARIANT paths
  • Case sensitivity confusion: Dot notation is case-insensitive but JSON keys are case-sensitive - requires bracket notation for exact matching
  • NULL ambiguity: SQL NULL (key missing) and JSON null (key present with null value) are different but easily confused
  • No schema enforcement: VARIANT accepts any structure - no constraint to ensure consistent shape across rows
  • Casting required for typed operations: Must explicitly cast (::) to use in JOINs, WHERE, aggregations, or get proper sort order
  • XML limitations: XML support is less intuitive than JSON - special attribute/element notation required
  • No partial updates: Cannot update a single key within a VARIANT - must replace the entire value
  • FLATTEN performance: Deeply nested FLATTEN operations can be expensive on large datasets
  • Search optimization limitations: Search Optimization Service has limited support for VARIANT paths
  • Clustering limitations: Cannot cluster directly on a VARIANT sub-path (must use a virtual/materialized column)
  • No VARIANT in clustering keys directly: Must extract to a typed expression for clustering
  • Type coercion surprises: Numbers stored as strings require explicit casting; automatic coercion rules differ from regular columns
  • ORDER BY on VARIANT: Ordering VARIANT values uses string comparison unless cast to the desired type
  • STRIP_OUTER_ARRAY confusion: Forgetting this option loads entire JSON array as one row instead of multiple rows

Key Differences: SQL NULL vs JSON null

-- Setup
SELECT PARSE_JSON('{"a": null, "b": 1}') AS data;

-- SQL NULL: key does not exist
SELECT data:c IS NULL;           -- TRUE (key 'c' missing = SQL NULL)

-- JSON null: key exists with null value
SELECT data:a IS NULL;           -- FALSE! (it's JSON null, not SQL NULL)
SELECT IS_NULL_VALUE(data:a);    -- TRUE (it IS JSON null)
SELECT TYPEOF(data:a);           -- 'NULL_VALUE'

-- To treat JSON null as SQL NULL:
SELECT STRIP_NULL_VALUE(data:a) IS NULL;  -- TRUE
-- Or cast: data:a::STRING returns NULL for JSON null
Critical Exam Point: This is one of the most commonly tested concepts. IS NULL returns FALSE for JSON null values! Use IS_NULL_VALUE() to check for JSON nulls, or use ::STRING casting which converts JSON null to SQL NULL.
