2. NULL Handling (The #1 Exam Trap)

Critical Distinction:
  • SQL NULL = key doesn't exist → IS NULL returns TRUE
  • JSON null = key exists with value null → IS NULL returns FALSE!
-- Demonstrating the difference:
SELECT
  PARSE_JSON('{"a": null}'):a IS NULL,        -- FALSE (JSON null exists!)
  PARSE_JSON('{"a": null}'):b IS NULL,        -- TRUE (key 'b' missing = SQL NULL)
  PARSE_JSON('{"a": null}'):a = 'null'::VARIANT,  -- TRUE (check for JSON null)
  IS_NULL_VALUE(PARSE_JSON('{"a": null}'):a); -- TRUE (correct way to check JSON null)

3. FLATTEN Edge Cases

ScenarioBehavior
FLATTEN on NULL valueReturns zero rows (row is lost from result). Use OUTER => TRUE to keep.
FLATTEN on empty array []Returns zero rows. Use OUTER => TRUE to get one row with NULL value.
FLATTEN on a scalar (not array/object)Returns one row with the scalar as VALUE. Not an error.
FLATTEN on OBJECT (not array)Produces rows with KEY and VALUE for each key-value pair.
Double FLATTEN (nested arrays)Cartesian-like expansion. Each inner element paired with each outer.
FLATTEN with RECURSIVE => TRUE on deep nestingProduces rows at ALL depth levels. Can be very large result set.
OUTER => TRUE vs FALSE (default)TRUE = keep NULLs (like LEFT JOIN). FALSE = skip NULLs (like INNER JOIN).
Common Mistake: Forgetting OUTER => TRUE causes rows with empty/NULL arrays to disappear silently from results. Always use OUTER => TRUE when you want to preserve all input rows.

5. Loading Edge Cases

ScenarioBehavior
JSON file with outer array: [{...},{...}]Without STRIP_OUTER_ARRAY: loads as ONE row (single VARIANT array). With it: each element = separate row.
JSON with duplicate keysLast value wins (overwrites earlier). No error.
Malformed JSON in one rowDepends on ON_ERROR. Default SKIP_FILE skips entire file.
XML with namespacesNamespaces are preserved in VARIANT. Access requires full qualified names.
Parquet nested typesLoaded as nested VARIANT. Struct→OBJECT, List→ARRAY, Map→OBJECT.
MATCH_BY_COLUMN_NAME with VARIANTMatches by JSON key name to column name. Keys must match exactly (case-sensitive).

6. Exam Scenario Questions

ScenarioAnswer
"data:status IS NULL returns FALSE but the value shows as null. Why?"It's a JSON null (value exists but is null). Use IS_NULL_VALUE() to detect it. SQL NULL means the key doesn't exist.
"FLATTEN returns fewer rows than expected."Likely some rows have NULL or empty arrays for the flattened path. Use OUTER => TRUE to include them.
"Query on VARIANT column scans all partitions."VARIANT paths don't enable partition pruning by default. Materialize the path into a typed column and filter on that.
"Can you use VARIANT in a PRIMARY KEY?"NO. Primary keys require scalar types. Must cast/extract to a typed column first.
"What's the max size of a VARIANT value?"16 MB compressed. Larger documents must be split across multiple rows.
Top 5 Semi-Structured Exam Traps:
  1. JSON null ≠ SQL NULL (IS_NULL_VALUE vs IS NULL)
  2. Keys are CASE-SENSITIVE (data:Name ≠ data:name)
  3. FLATTEN on NULL/empty = zero rows (use OUTER => TRUE)
  4. Must cast (::TYPE) before GROUP BY, JOIN, WHERE for reliable results
  5. STRIP_OUTER_ARRAY needed when JSON file is a top-level array
