1. UDF Language Types

Supported UDF Languages
LanguageLANGUAGE KeywordUse CaseKey Features
SQLLANGUAGE SQLSimple transformations, expressionsBest performance, inline expansion, no context switch
JavaScriptLANGUAGE JAVASCRIPTComplex logic, JSON processingFull JS engine, object/array manipulation, regex

SQL UDF Example
CREATE OR REPLACE FUNCTION celsius_to_fahrenheit(c FLOAT)
RETURNS FLOAT
LANGUAGE SQL
AS
$$
  c * 9/5 + 32
$$;

SQL UDFs are the simplest. The body is a single SQL expression. No procedural logic (no IF, LOOP). They get inlined into the query plan for maximum performance.

JavaScript UDF Example
CREATE OR REPLACE FUNCTION parse_json_field(json_str VARCHAR, field VARCHAR)
RETURNS VARCHAR
LANGUAGE JAVASCRIPT
AS
$$
  try {
    var obj = JSON.parse(JSON_STR);
    return obj[FIELD] || null;
  } catch(e) {
    return null;
  }
$$;

Important: JavaScript UDF parameters are passed as UPPERCASE variable names inside the body regardless of how they are defined.

Python UDF Example
CREATE OR REPLACE FUNCTION sentiment_score(text VARCHAR)
RETURNS FLOAT
LANGUAGE PYTHON
RUNTIME_VERSION = '3.11'
PACKAGES = ('textblob')
HANDLER = 'analyze'
AS
$$
from textblob import TextBlob

def analyze(text):
    if text is None:
        return None
    blob = TextBlob(text)
    return blob.sentiment.polarity
$$;

Python UDFs require: RUNTIME_VERSION, HANDLER function name, and optional PACKAGES from Anaconda channel.

Java UDF Example
CREATE OR REPLACE FUNCTION hash_value(input VARCHAR)
RETURNS VARCHAR
LANGUAGE JAVA
RUNTIME_VERSION = '11'
HANDLER = 'HashUtil.computeHash'
AS
$$
import java.security.MessageDigest;

public class HashUtil {
  public static String computeHash(String input) {
    try {
      MessageDigest md = MessageDigest.getInstance("SHA-256");
      byte[] hash = md.digest(input.getBytes("UTF-8"));
      StringBuilder sb = new StringBuilder();
      for (byte b : hash) {
        sb.append(String.format("%02x", b));
      }
      return sb.toString();
    } catch (Exception e) {
      return null;
    }
  }
}
$$;

Java UDFs require: RUNTIME_VERSION and a fully qualified HANDLER (ClassName.methodName).

JavaScript UDTF
CREATE OR REPLACE FUNCTION split_to_rows(str VARCHAR, delim VARCHAR)
RETURNS TABLE(value VARCHAR, idx NUMBER)
LANGUAGE JAVASCRIPT
AS
$$
{
  processRow: function(row, rowWriter, context) {
    var parts = row.STR.split(row.DELIM);
    for (var i = 0; i < parts.length; i++) {
      rowWriter.writeRow({VALUE: parts[i].trim(), IDX: i});
    }
  }
}
$$;
Python UDTF
CREATE OR REPLACE FUNCTION generate_date_range(
    start_date DATE, end_date DATE)
RETURNS TABLE(generated_date DATE)
LANGUAGE PYTHON
RUNTIME_VERSION = '3.11'
HANDLER = 'DateRange'
AS
$$
from datetime import timedelta

class DateRange:
    def process(self, start_date, end_date):
        current = start_date
        while current <= end_date:
            yield (current,)
            current += timedelta(days=1)
$$;

4. SECURE UDFs

SECURE Functions - Key Points
CREATE OR REPLACE SECURE FUNCTION mask_ssn(ssn VARCHAR)
RETURNS VARCHAR
LANGUAGE SQL
AS
$$
  '***-**-' || RIGHT(ssn, 4)
$$;

What SECURE does:

  • Function definition (body) is hidden from users who are not the owner
  • Query optimizer cannot look inside the function for plan optimization
  • Prevents data leakage through error messages
  • Similar to SECURE VIEWs - protects intellectual property and sensitive logic

When to use SECURE:

  • Masking/tokenization functions shared with other roles
  • Proprietary business logic that should not be exposed
  • Functions used in row-access or masking policies
  • Functions shared via Secure Data Sharing
Exam Tip

SECURE UDFs may have slightly worse performance because the optimizer cannot inline or push predicates through them. This is the trade-off for security.

5. Immutable vs Volatile

Function Volatility
PropertyVOLATILE (default)IMMUTABLE
MeaningMay return different results for same inputsAlways returns same result for same inputs
CachingNo result cachingResults may be cached/memoized
OptimizationCalled every timeOptimizer may reduce calls
ExamplesFunctions using CURRENT_TIMESTAMP, RANDOM()Math functions, string transforms, lookups
Use withNon-deterministic logicPure functions (no side effects)
-- IMMUTABLE: same input always gives same output
CREATE FUNCTION area_circle(radius FLOAT)
RETURNS FLOAT
IMMUTABLE
LANGUAGE SQL
AS $$ 3.14159265 * radius * radius $$;

-- VOLATILE: result could change (accessing table data, time-based)
CREATE FUNCTION get_current_rate(currency VARCHAR)
RETURNS FLOAT
VOLATILE
LANGUAGE SQL
AS $$ (SELECT rate FROM exchange_rates WHERE code = currency LIMIT 1) $$;
Exam Tip

If you mark a function as IMMUTABLE but it actually reads table data or uses non-deterministic functions, Snowflake will NOT prevent this. The results could be incorrect due to caching. It is the developer's responsibility to ensure correctness.

6. Function Overloading

Function Overloading Rules

Snowflake supports function overloading: multiple functions with the same name but different argument signatures.

-- Overload 1: single argument
CREATE FUNCTION format_amount(amount NUMBER)
RETURNS VARCHAR
LANGUAGE SQL
AS $$ '$' || TO_CHAR(amount, '999,999.00') $$;

-- Overload 2: two arguments (with currency)
CREATE FUNCTION format_amount(amount NUMBER, currency VARCHAR)
RETURNS VARCHAR
LANGUAGE SQL
AS $$ currency || ' ' || TO_CHAR(amount, '999,999.00') $$;

-- Overload 3: different type
CREATE FUNCTION format_amount(amount VARCHAR)
RETURNS VARCHAR
LANGUAGE SQL
AS $$ '$' || amount $$;

Resolution Rules:

  • Functions are identified by name + argument types (signature)
  • Number of arguments differentiates overloads
  • Argument data types differentiate overloads
  • Return type alone does NOT differentiate (cannot overload by return type only)
  • Snowflake uses implicit type coercion when resolving calls
  • If ambiguous, an error is raised
DROP Behavior with Overloading

DROP FUNCTION format_amount(NUMBER) drops only that specific overload. You must specify the argument types to identify which overload to drop. DESC FUNCTION format_amount(NUMBER, VARCHAR) describes a specific overload.

7. RETURNS TABLE

RETURNS TABLE Patterns

SQL UDF with RETURNS TABLE:

-- SQL UDF that returns a table (must be a single SELECT statement)
CREATE OR REPLACE FUNCTION get_top_customers(min_orders NUMBER)
RETURNS TABLE(customer_name VARCHAR, order_count NUMBER, total_spend NUMBER)
LANGUAGE SQL
AS
$$
  SELECT c.name, COUNT(o.id), SUM(o.amount)
  FROM customers c
  JOIN orders o ON c.id = o.customer_id
  GROUP BY c.name
  HAVING COUNT(o.id) >= min_orders
  ORDER BY total_spend DESC
$$;

-- Usage:
SELECT * FROM TABLE(get_top_customers(5));

Python UDTF with RETURNS TABLE:

CREATE OR REPLACE FUNCTION explode_json_array(json_str VARCHAR)
RETURNS TABLE(idx NUMBER, element VARCHAR)
LANGUAGE PYTHON
RUNTIME_VERSION = '3.11'
HANDLER = 'JsonExploder'
AS
$$
import json

class JsonExploder:
    def process(self, json_str):
        if json_str is None:
            return
        try:
            arr = json.loads(json_str)
            for i, elem in enumerate(arr):
                yield (i, str(elem))
        except:
            pass
$$;
Key Distinction

A SQL UDF with RETURNS TABLE is different from a UDTF. The SQL version is a table function (its body must be a SELECT). A UDTF (JavaScript/Python/Java) uses a handler class with process() and optionally end_partition() methods to emit rows.

8. Key Features (15)

15 Key Features of Snowflake UDFs
  1. Multi-language support: SQL, JavaScript, Python, Java, Scala - choose the best language for each task
  2. Scalar and tabular: Return single values or entire result sets (UDTF)
  3. Function overloading: Same name with different signatures for polymorphic behavior
  4. SECURE option: Hide function body and prevent optimizer-based data leaks
  5. NULL handling: CALLED ON NULL INPUT vs RETURNS NULL ON NULL INPUT (STRICT)
  6. Python packages: Access to curated Anaconda channel (numpy, pandas, scikit-learn, etc.)
  7. Stage imports: Import JARs, Python wheels, data files from stages via IMPORTS clause
  8. External access: Python/Java UDFs can call external APIs with EXTERNAL_ACCESS_INTEGRATIONS
  9. Secrets management: Securely pass credentials to UDFs via SECRETS clause
  10. Determinism control: IMMUTABLE enables optimizer caching; VOLATILE ensures fresh evaluation
  11. Default arguments: Parameters can have DEFAULT values for optional calling
  12. Schema-level scoping: UDFs belong to a schema and follow RBAC privileges
  13. PARTITION BY for UDTFs: Process groups of rows together in Python/JS/Java UDTFs
  14. Inline SQL expansion: SQL UDFs are expanded inline into the query plan for efficiency
  15. USAGE/OWNERSHIP privileges: Fine-grained access control (GRANT USAGE ON FUNCTION)

9. Limitations (15)

15 Key Limitations of Snowflake UDFs
  1. No side effects: UDFs cannot perform DML (INSERT, UPDATE, DELETE) - use stored procedures instead
  2. No DDL: UDFs cannot create/alter/drop objects
  3. SQL UDF body: Must be a single expression (scalar) or single SELECT (table) - no procedural logic
  4. JavaScript type mapping: Parameters are UPPERCASED inside JS body - easy source of bugs
  5. Python sandbox: No filesystem access (except /tmp with limits), no subprocess, no network (without EAI)
  6. Performance overhead: Non-SQL UDFs have context-switch overhead vs native SQL functions
  7. Memory limits: Each UDF invocation has memory constraints (varies by warehouse size)
  8. No transactions: UDFs cannot BEGIN/COMMIT transactions
  9. SECURE UDF cost: Optimizer cannot push predicates through SECURE UDFs, potentially slower
  10. Package availability: Only packages from Snowflake's curated Anaconda channel are available
  11. Cold start: Python/Java UDFs may have initialization latency on first call
  12. No recursion in SQL UDFs: A SQL UDF cannot call itself recursively
  13. Return type fixed: Cannot return dynamic types; schema must be declared at creation time
  14. Overload ambiguity: Too-similar signatures with implicit coercion can cause resolution errors
  15. No cursor/RESULTSET in UDFs: These are stored procedure features only

10. Certification Exam Focus Points

High-Priority Exam Topics
Key Distinctions to Remember
  • UDF vs Stored Procedure: UDFs return values and are used in queries; Stored Procedures perform actions (DML/DDL) and are called with CALL
  • LANGUAGE keyword: Required for non-SQL UDFs; SQL is the default if omitted
  • HANDLER: Required for Python, Java, Scala - specifies the entry point function/class
  • RUNTIME_VERSION: Required for Python and Java - specifies the language version
  • Scalar vs Table function: Table functions are used in FROM clause with TABLE() wrapper
  • STRICT: Shorthand for RETURNS NULL ON NULL INPUT
  • Privileges: Need USAGE on function to call it; OWNERSHIP to alter/drop
