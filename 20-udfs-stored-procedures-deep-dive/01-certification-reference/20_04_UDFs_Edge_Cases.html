UDFs & Stored Procedures - Edge Cases

SnowPro Core | OWNER vs CALLER, determinism, sandbox limits, external functions | August 2026

1. EXECUTE AS OWNER vs CALLER (Most Tested Topic)

AspectOWNER (default)CALLER
Runs with privileges ofThe role that OWNS the procedureThe role of the USER calling it
Can access owner's objects?YES — regardless of caller's privilegesNO — only what caller has access to
Security modelEncapsulation (hide data behind procedure)Delegation (procedure acts as the caller)
Can caller see intermediate objects?NO — data is hidden from callerYES — caller can see what they own
Use caseSecure data access, admin tasks exposed to lower rolesUtility procedures, session-specific operations
SQL scripting variablesUse owner's context for object resolutionUse caller's context for object resolution
Exam Trap: Default is EXECUTE AS OWNER for stored procedures. If a procedure is owned by SYSADMIN and called by a low-privilege user, the procedure runs with SYSADMIN privileges — this is intentional for secure delegation, but a security risk if the procedure isn't carefully written.

4. Stored Procedure Edge Cases

ScenarioBehavior
Procedure with no RETURNS clauseMust still declare RETURNS (e.g., RETURNS VARCHAR). Even if procedure just does DML.
Transaction inside procedureBEGIN TRANSACTION / COMMIT / ROLLBACK work inside procedures. Caller's transaction context applies.
Exception not caughtProcedure fails. Caller gets error. Any uncommitted work in the procedure is rolled back.
Recursive procedure callsSupported but limited stack depth. Deep recursion will fail with stack overflow.
Procedure calling another procedureSupported. Inner procedure uses CALLER or OWNER based on its own definition.
Anonymous block (BEGIN...END without CREATE)Runs with CALLER privileges always. Cannot be OWNER rights (no owner).
RESULTSET in SQL proceduresOnly available in SQL scripting procedures. Not in JS/Python/Java.

6. SECURE UDF/Procedure Edge Cases

Key Implication: SECURE UDFs hide their definition (body) from non-owners AND prevent the query optimizer from pushing predicates into the function. This can cause performance degradation because the optimizer can't see inside the function.

7. Exam Scenario Questions

ScenarioAnswer
"A procedure is EXECUTE AS OWNER, owned by SYSADMIN. A user with role ANALYST calls it. What privileges does the procedure run with?"SYSADMIN privileges. The procedure executes as if SYSADMIN is running it, regardless of who called it.
"Can a SQL UDF contain multiple statements?"NO. SQL UDFs are a single expression (single SELECT or scalar expression). For multi-statement logic, use a stored procedure or JavaScript/Python UDF.
"A JavaScript UDF receives a SQL NULL. What does it see?"The value is undefined in JavaScript (not null). Must check with: if (x === undefined).
"Can you call a stored procedure inside a SQL UDF?"NO. UDFs cannot call procedures. UDFs can only call other UDFs.
"What is the default execution rights for stored procedures?"EXECUTE AS OWNER (not CALLER). The procedure runs with the owner's privileges by default.
"Can anonymous blocks (BEGIN...END) be EXECUTE AS OWNER?"NO. Anonymous blocks always run as CALLER. They have no owner (not stored objects).
"Can UDFs perform DML (INSERT/UPDATE/DELETE)?"NO. UDFs are read-only (pure functions). Only stored procedures can perform DML.
"Can a UDTF return multiple columns?"YES. UDTFs (table functions) can return multiple columns defined in RETURNS TABLE(col1 TYPE, col2 TYPE, ...).
Top 5 UDF/Procedure Exam Traps:
  1. Default is EXECUTE AS OWNER (not CALLER) for stored procedures
  2. UDFs cannot do DML — only procedures can
  3. SQL UDFs = single expression only (no multi-statement)
  4. JavaScript NULL = undefined (not null)
  5. SECURE functions hide definition AND prevent optimizer pushdown
