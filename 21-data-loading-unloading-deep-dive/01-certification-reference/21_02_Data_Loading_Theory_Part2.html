1. Data Unloading (COPY INTO @stage)

COPY INTO Location (Unload) Syntax
COPY INTO @stage_name[/path/prefix]
  FROM { table_name | ( SELECT query ) }
  [ FILE_FORMAT = ( TYPE = CSV | JSON | PARQUET ... ) ]
  [ MAX_FILE_SIZE = num_bytes ]
  [ SINGLE = TRUE | FALSE ]
  [ HEADER = TRUE | FALSE ]
  [ OVERWRITE = TRUE | FALSE ]
  [ INCLUDE_QUERY_ID = TRUE | FALSE ]
  [ PARTITION BY expression ]
  [ DETAILED_OUTPUT = TRUE | FALSE ];

Key Unload Options

OptionDefaultDescription
MAX_FILE_SIZE16 MB (CSV), 256 MB (Parquet)Maximum size of each output file. Data split across multiple files if exceeded.
SINGLEFALSEIf TRUE, produce exactly one output file (no splitting). May be large.
HEADERFALSEInclude column headers in the first row (CSV only)
OVERWRITEFALSEIf TRUE, overwrite existing files in stage. If FALSE, error if files exist.
INCLUDE_QUERY_IDTRUEInclude query ID in generated filenames for uniqueness
PARTITION BYNonePartition output files by an expression (e.g., date column)
DETAILED_OUTPUTFALSEReturn info about each file written (name, size, row count)
Exam Tip: When unloading to Parquet, the MAX_FILE_SIZE default is 256 MB. For CSV it's 16 MB. SINGLE=TRUE ignores MAX_FILE_SIZE and writes everything to one file.

Unload Examples

-- Basic unload to named stage
COPY INTO @my_stage/export/
  FROM my_table
  FILE_FORMAT = (TYPE = CSV HEADER = TRUE)
  OVERWRITE = TRUE;

-- Unload query results to external stage with partitioning
COPY INTO @s3_stage/reports/
  FROM (SELECT * FROM sales WHERE year = 2026)
  FILE_FORMAT = (TYPE = PARQUET)
  PARTITION BY ('region=' || region)
  MAX_FILE_SIZE = 67108864;  -- 64MB

-- Single file unload
COPY INTO @my_stage/single_export.csv
  FROM my_table
  FILE_FORMAT = (TYPE = CSV HEADER = TRUE COMPRESSION = NONE)
  SINGLE = TRUE
  MAX_FILE_SIZE = 5368709120;  -- 5GB (needed when SINGLE=TRUE for large data)

2. GET Command - Download from Stage to Local

GET Syntax
GET @stage_name[/path/file]  file://local_directory/
  [ PARALLEL = num_threads ]
  [ PATTERN = 'regex_pattern' ];
  • Downloads files from internal stage to local file system
  • Only works with internal stages (not external)
  • Only works from SnowSQL, JDBC/ODBC, Python connector
  • Files are automatically decrypted during download
  • If files were auto-compressed during PUT, they remain compressed during GET
-- Download all files from stage
GET @my_stage file://C:/downloads/;

-- Download specific file
GET @my_stage/data_0001.csv.gz file://C:/downloads/;

-- Download with pattern
GET @my_stage file://C:/downloads/ PATTERN = '.*sales.*';
Key Point: Like PUT, GET only works with internal stages. For external stages, use cloud provider tools (aws s3 cp, azcopy, gsutil) to download files.

3. Transformation During COPY INTO

SELECT List in COPY INTO

You can transform data during loading using a SELECT clause with positional column references ($1, $2, etc.) and expressions.

-- Basic column reordering and transformation
COPY INTO my_table (col_a, col_b, col_c, load_ts, source_file)
  FROM (
    SELECT
      $3,                              -- third column from file -> col_a
      $1,                              -- first column from file -> col_b
      UPPER($2),                       -- transform second column
      CURRENT_TIMESTAMP(),             -- add load timestamp
      METADATA$FILENAME                -- capture source filename
    FROM @my_stage
  )
  FILE_FORMAT = (TYPE = CSV SKIP_HEADER = 1);

-- Using METADATA$ columns
COPY INTO audit_table (row_num, filename, file_row, data_col)
  FROM (
    SELECT
      METADATA$FILE_ROW_NUMBER,        -- row number within the file
      METADATA$FILENAME,               -- full path/filename
      METADATA$FILE_ROW_NUMBER,        -- same as above
      $1                               -- actual data
    FROM @my_stage/data/
  )
  FILE_FORMAT = (TYPE = CSV);

-- Type casting during load
COPY INTO typed_table (id, amount, event_date)
  FROM (
    SELECT
      $1::INTEGER,
      $2::DECIMAL(10,2),
      TO_DATE($3, 'YYYY-MM-DD')
    FROM @my_stage
  )
  FILE_FORMAT = (TYPE = CSV SKIP_HEADER = 1);

Available METADATA$ Columns

ColumnTypeDescription
METADATA$FILENAMEVARCHARName of the staged file being loaded (includes relative path)
METADATA$FILE_ROW_NUMBERNUMBERRow number within the file (1-based)
METADATA$FILE_CONTENT_KEYVARCHARChecksum of the file content
METADATA$FILE_LAST_MODIFIEDTIMESTAMP_NTZLast modified timestamp of the staged file
METADATA$START_SCAN_TIMETIMESTAMP_LTZTimestamp when Snowflake started scanning the file
Critical Limitation: Transformation SELECTs during COPY do NOT support: JOINs, subqueries, aggregate functions (GROUP BY, HAVING), window functions, or UNION. Only simple expressions on positional columns and METADATA$ references are allowed.

4. COPY Load History (64-Day Tracking)

How Load History Works
  • Snowflake tracks every file loaded via COPY INTO for 64 days
  • Tracked by: file name + file checksum (MD5)
  • If same file (name + content) is loaded again within 64 days, it is automatically skipped
  • This prevents duplicate data from repeated COPY commands
  • After 64 days, the file can be reloaded without FORCE=TRUE
  • Modifying the file content (different checksum) allows reload even within 64 days

Querying Load History

-- COPY_HISTORY table function (Information Schema) - last 14 days
SELECT *
FROM TABLE(INFORMATION_SCHEMA.COPY_HISTORY(
  TABLE_NAME => 'MY_TABLE',
  START_TIME => DATEADD(hours, -24, CURRENT_TIMESTAMP())
));

-- LOAD_HISTORY view (Account Usage) - last 365 days
SELECT *
FROM SNOWFLAKE.ACCOUNT_USAGE.LOAD_HISTORY
WHERE TABLE_NAME = 'MY_TABLE'
  AND LAST_LOAD_TIME > DATEADD(days, -7, CURRENT_TIMESTAMP())
ORDER BY LAST_LOAD_TIME DESC;

-- Check for load errors
SELECT FILE_NAME, ERROR_COUNT, ERROR_LIMIT, STATUS
FROM TABLE(INFORMATION_SCHEMA.COPY_HISTORY(
  TABLE_NAME => 'MY_TABLE',
  START_TIME => DATEADD(days, -1, CURRENT_TIMESTAMP())
))
WHERE STATUS = 'LOAD_FAILED';
SourceRetentionLatencyScope
COPY_HISTORY() function14 daysReal-timeSingle table in current schema
LOAD_HISTORY Account Usage view365 daysUp to 45 min delayAll tables in the account
Internal metadata (dedup tracking)64 daysReal-timePer-table load tracking

5. FORCE = TRUE

Bypassing Load History
-- Force reload files even if previously loaded within 64 days
COPY INTO my_table
  FROM @my_stage
  FORCE = TRUE;
  • Bypasses the 64-day load history deduplication check
  • Reloads files regardless of whether they were loaded before
  • Risk: Can cause duplicate data if files haven't changed
  • Use case: Reloading after a failed load was partially committed, or data was deleted
  • Does NOT reset the 64-day timer; just ignores it for this execution
Exam Note: FORCE=TRUE does not check whether data already exists in the table. It simply tells COPY to ignore its internal load history. You may end up with duplicate rows.

6. MATCH_BY_COLUMN_NAME

Column Name Matching
ValueBehaviorSupported Formats
NONE (default)Columns matched by position (first file col -> first table col)All formats
CASE_INSENSITIVEMatch file column headers to table column names (case-insensitive)CSV (with PARSE_HEADER=TRUE), Parquet, Avro, ORC
CASE_SENSITIVEMatch file column headers to table column names (exact case match)CSV (with PARSE_HEADER=TRUE), Parquet, Avro, ORC
 
-- Load Parquet with column name matching
COPY INTO my_table
  FROM @my_stage
  FILE_FORMAT = (TYPE = PARQUET)
  MATCH_BY_COLUMN_NAME = CASE_INSENSITIVE;

-- For CSV, must enable PARSE_HEADER
COPY INTO my_table
  FROM @my_stage
  FILE_FORMAT = (TYPE = CSV PARSE_HEADER = TRUE)
  MATCH_BY_COLUMN_NAME = CASE_INSENSITIVE;
Key Point: For CSV files, MATCH_BY_COLUMN_NAME requires PARSE_HEADER = TRUE in the file format (so Snowflake reads the header row as column names). For Parquet/Avro/ORC, column names are embedded in the file metadata.

7. Storage Integrations for External Stages

Storage Integration Architecture
-- Create storage integration (ACCOUNTADMIN required)
CREATE OR REPLACE STORAGE INTEGRATION my_s3_int
  TYPE = EXTERNAL_STAGE
  STORAGE_PROVIDER = 'S3'
  STORAGE_AWS_ROLE_ARN = 'arn:aws:iam::123456789:role/snowflake-role'
  ENABLED = TRUE
  STORAGE_ALLOWED_LOCATIONS = ('s3://my-bucket/allowed/', 's3://other-bucket/')
  STORAGE_BLOCKED_LOCATIONS = ('s3://my-bucket/sensitive/');

-- Describe to get Snowflake's IAM user and external ID
DESC INTEGRATION my_s3_int;
-- Returns: STORAGE_AWS_IAM_USER_ARN and STORAGE_AWS_EXTERNAL_ID
-- Use these to configure trust policy on your AWS IAM role

-- Use integration in stage
CREATE OR REPLACE STAGE my_ext_stage
  STORAGE_INTEGRATION = my_s3_int
  URL = 's3://my-bucket/allowed/data/';
  • Storage integrations avoid embedding credentials in stage definitions
  • Created by ACCOUNTADMIN, then USAGE granted to other roles
  • Support STORAGE_ALLOWED_LOCATIONS and STORAGE_BLOCKED_LOCATIONS for security
  • One integration can be used by multiple stages

9. Production Best Practices

Loading Best Practices
  1. Split files to 100-250 MB compressed - Maximizes parallelism across warehouse nodes
  2. Use named stages with file formats - Better governance and reusability than user/table stages
  3. Use storage integrations - Never embed credentials in stage definitions
  4. Set PURGE=TRUE for production - Prevent re-processing and reduce storage costs
  5. Use COPY_HISTORY for monitoring - Check for errors and track load status
  6. Match warehouse size to data volume - Larger warehouse = more parallel threads
  7. Use PATTERN for selective loading - Load only relevant files per execution
  8. Pre-sort data if possible - Helps with micro-partition organization post-load
  9. Use VALIDATION_MODE first - Validate file format compatibility before production load
  10. Set appropriate ON_ERROR - ABORT for critical data, CONTINUE for tolerant pipelines
Unloading Best Practices
  1. Use Parquet for analytics consumers - Columnar, compressed, schema-embedded
  2. Set MAX_FILE_SIZE appropriately - Smaller files for faster downstream consumption
  3. Use PARTITION BY for organized output - Creates directory structure (Hive-style partitioning)
  4. Include HEADER=TRUE for CSV - Makes files self-describing for consumers
  5. Use OVERWRITE=TRUE in scheduled unloads - Prevents file accumulation errors
  6. Use SINGLE=TRUE only when needed - Single files don't benefit from parallel writes
Production Anti-Patterns:
  • Loading one huge file (kills parallelism)
  • Using FORCE=TRUE routinely (causes duplicates)
  • Forgetting PURGE (leads to re-processing confusion)
  • Using user stage (@~) for team workloads (no sharing possible)
  • Embedding cloud credentials directly in CREATE STAGE (security risk)
