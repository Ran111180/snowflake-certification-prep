21.04 Data Loading & Unloading - Edge Cases

SnowPro Core | Load History, PATTERN, ON_ERROR, Compression, Transformations, Unload Gotchas | August 2026

1. COPY 64-Day Load History Edge Cases

ScenarioBehaviorKey Detail
Same file loaded again within 64 daysSKIPPEDFile with same name AND same checksum is silently skipped (0 rows loaded)
Same filename, different content (modified file)LOADEDDifferent MD5 checksum = treated as new file, loaded normally
Same file after 64 days elapsedLOADEDLoad history expires; file can be reloaded without FORCE
FORCE = TRUE on previously loaded fileLOADEDBypasses history check; may create duplicates if data unchanged
File loaded, table dropped and recreatedLOADEDNew table has no load history; file is treated as new
File loaded to table A, then COPY to table BLOADEDLoad history is per-table; loading to different table works
File loaded, then PURGE=TRUE deleted it, re-uploaded same fileSKIPPEDLoad history persists even after file is removed from stage
File partially loaded (ON_ERROR=CONTINUE with errors)MARKED AS LOADEDFile appears in history as loaded; won't be retried unless FORCE=TRUE
Exam Trap: The 64-day load history tracks files by name + MD5 checksum per table. Even if you delete the file from the stage and re-upload an identical file, it will still be skipped because the history remembers the checksum. Only FORCE=TRUE or waiting 64 days resets this.

2. PATTERN Uses Regex, NOT SQL LIKE

What People ThinkWhat Actually WorksExplanation
PATTERN = '%.csv'PATTERN = '.*[.]csv'% is not a wildcard in regex; use .* for "any characters"
PATTERN = 'sales_%.csv'PATTERN = '.*sales_.*[.]csv'Must escape literal dot with [.] or \. and use .* for wildcards
PATTERN = '_data.csv'PATTERN = '.data[.]csv'_ is literal in regex (matches underscore only); . matches any char
PATTERN = 'file?.csv'PATTERN = 'file.[.]csv'? in regex means "0 or 1 of preceding"; . matches any single char
Key Rule: COPY INTO PATTERN uses Java regex syntax. Common mistakes: using % instead of .*, not escaping dots (. matches ANY character), forgetting that regex is applied to the full file path (not just filename). Use [.] for literal periods.

3. ON_ERROR Default Differences

ContextDefault ON_ERRORBehavior
Manual COPY INTOABORT_STATEMENTAny error aborts entire load; no data loaded from any file
SnowpipeSKIP_FILESkip file with errors, continue loading other files
COPY with ON_ERROR=CONTINUEN/A (explicit)Skip bad rows, load good rows from all files
Why This Matters: On the exam, if they ask "what is the default behavior when a COPY INTO encounters an error" without specifying Snowpipe, the answer is ABORT_STATEMENT. If they specifically mention Snowpipe/continuous loading, the answer is SKIP_FILE.

4. Compressed Files - Transparent Handling

ScenarioBehavior
gzip file (.gz) with COMPRESSION=AUTOAuto-detected and decompressed during load
bz2 file (.bz2) with COMPRESSION=AUTOAuto-detected and decompressed during load
PUT with AUTO_COMPRESS=TRUE (default)Files compressed with gzip before upload; .gz appended
GET downloading a compressed fileFile remains compressed; NOT auto-decompressed
COMPRESSION=NONE on a gzip fileError - Snowflake tries to read binary as text
Uncompressed file with COMPRESSION=GZIPError - Snowflake tries to decompress non-compressed data
Mixed compression in same stageAUTO handles each file individually based on extension/magic bytes
Edge Case: PUT AUTO_COMPRESS=TRUE adds .gz extension. When you LIST the stage, files show as data.csv.gz. When referencing in COPY, you may need to use the .gz name. COMPRESSION=AUTO in the file format handles both compressed and uncompressed files intelligently.

Sequence references: seq.NEXTVALLIMIT/OFFSET clauses
 
-- VALID transformation examples
COPY INTO target (id, name, load_ts, source)
FROM (
  SELECT
    $1::INT,
    UPPER(TRIM($2)),
    CURRENT_TIMESTAMP(),
    METADATA$FILENAME
  FROM @my_stage
);

-- INVALID - will ERROR
COPY INTO target
FROM (
  SELECT $1, $2, t.lookup_val  -- NO! Cannot JOIN
  FROM @my_stage s
  JOIN lookup_table t ON s.$1 = t.id  -- ILLEGAL
);

6. METADATA$ Columns - Only During COPY

Usage ContextAvailable?Detail
COPY INTO ... FROM (SELECT METADATA$FILENAME ...)YESPrimary use case - capture file info during load
SELECT METADATA$FILENAME FROM @stageNOCannot query METADATA$ columns in regular SELECT from stage
After loading, querying the target tableNOMETADATA$ is not stored unless you explicitly load it into a column
In VALIDATION_MODEYESAvailable during validation dry-runs
With directory tables (SELECT * FROM DIRECTORY(@stage))DIFFERENTDirectory tables have their own columns (FILE_URL, SIZE, etc.) - not METADATA$
Common Mistake: Trying to use SELECT METADATA$FILENAME FROM @my_stage outside of COPY. METADATA$ pseudo-columns only exist in the context of COPY INTO transformations. If you need file metadata for querying, either: (1) load it into a table column during COPY, or (2) use directory tables.

7. VALIDATION_MODE - Does NOT Load Data

ModeWhat It DoesReturns
RETURN_n_ROWSValidates first n rows of dataThe validated rows (as if loaded) - allows preview
RETURN_ERRORSValidates all data in first file with errorsError details for problematic rows
RETURN_ALL_ERRORSValidates all data in all filesAll errors across all files
Critical Point: When VALIDATION_MODE is set, NO data is loaded into the table. It is purely a dry-run. You cannot combine VALIDATION_MODE with actual loading in a single command. You must run separate commands: one to validate, one to load.
-- Validate first 10 rows (preview what would be loaded)
COPY INTO my_table FROM @my_stage
  FILE_FORMAT = (TYPE = CSV)
  VALIDATION_MODE = RETURN_10_ROWS;
-- Returns: 10 rows showing what data looks like (not loaded!)

-- Then actually load (separate command)
COPY INTO my_table FROM @my_stage
  FILE_FORMAT = (TYPE = CSV);

8. Unload Edge Cases

ScenarioDefaultEdge Case Detail
OVERWRITE defaultFALSEIf files with same names exist in stage, unload FAILS. Must set OVERWRITE=TRUE for scheduled unloads.
MAX_FILE_SIZE default (CSV)16 MBOutput split into multiple 16MB files. For single file, use SINGLE=TRUE.
MAX_FILE_SIZE default (Parquet)256 MBLarger default because Parquet benefits from bigger files for columnar reads.
SINGLE=TRUE with large dataOne fileCan create very large files. No parallel write benefit. May hit stage limits.
HEADER defaultFALSECSV output has NO headers by default. Must explicitly set HEADER=TRUE.
INCLUDE_QUERY_ID defaultTRUEQuery ID in filename = unique names but hard to predict. Set FALSE for custom naming.
Unload to user stageAllowedCan unload to @~ but only the owning user can access the files.
Unload to external stageAllowedRequires WRITE privilege on stage (or underlying cloud permission).
Empty result unloadNo file createdIf query returns 0 rows, no output file is generated.
Scheduling Tip: For scheduled unload jobs (tasks), always use OVERWRITE = TRUE. Otherwise, the second execution will fail because files from the first execution still exist in the stage.

9. Additional Gotchas

TopicGotcha
PUT from SnowsightSnowsight web UI has a file upload button for stages, but the PUT command only works from SnowSQL/connectors. The UI upload is a different mechanism.
Table stage file reuseFiles in a table stage (@%table) can ONLY be loaded into that specific table. Cannot COPY from @%table_a INTO table_b.
COPY INTO and StreamsCOPY INTO DOES generate change records captured by streams (treated as INSERT). This is often tested as a "trick" question.
COPY and transactionsCOPY INTO is auto-committed (not transactional). Cannot ROLLBACK a successful COPY. If ABORT_STATEMENT triggers, nothing was committed.
NULL_IF with multiple valuesNULL_IF = ('NULL', 'null', '', 'N/A') - can specify multiple string representations that map to SQL NULL.
Semi-structured loadingJSON/Avro/ORC/Parquet load into a single VARIANT column by default (unless using MATCH_BY_COLUMN_NAME or transformation SELECT).
ENFORCE_LENGTH vs TRUNCATECOLUMNSThese are mutually exclusive in effect. ENFORCE_LENGTH=TRUE (default) errors on too-long strings. TRUNCATECOLUMNS=TRUE silently truncates. Setting both TRUE means TRUNCATECOLUMNS wins.

10. Exam Scenario Questions

ScenarioAnswer
"A daily COPY job loads files from an S3 stage. Yesterday's file was loaded successfully. Today the same file (unchanged) is in the stage. What happens?"The file is silently skipped (0 rows loaded) because its name+checksum match the 64-day load history. No error is raised.
"A user runs COPY INTO with PATTERN = '%.csv'. No files are loaded despite CSV files being in the stage. Why?"PATTERN uses regex, not SQL LIKE. The % character is not a wildcard in regex. Correct pattern: '.*[.]csv'
"A COPY INTO command with ON_ERROR=CONTINUE loads 1000 files. 3 files have errors. What happens to those files in load history?"All files (including the 3 with errors) are marked as "loaded" in history. The error rows are skipped but the files themselves are considered processed. They won't be retried unless FORCE=TRUE.
"Can you use METADATA$FILENAME to query which file each row came from after the data is already in the table?"No. METADATA$ columns only exist during COPY. To track source files post-load, you must include METADATA$FILENAME as a column in the COPY transformation and store it in the target table.
"A COPY INTO uses VALIDATION_MODE=RETURN_ALL_ERRORS and reports 0 errors. Is the data now in the table?"No. VALIDATION_MODE never loads data regardless of the result. A separate COPY INTO (without VALIDATION_MODE) is needed to actually load.
"An unload job runs every hour writing to the same stage path. The second execution fails. Why?"OVERWRITE defaults to FALSE. The second execution fails because files from the first run still exist. Fix: set OVERWRITE = TRUE.
"A COPY INTO with transformation SELECT includes a JOIN to a lookup table. What happens?"Error. COPY transformations do not support JOINs, subqueries, aggregates, or window functions. Only simple expressions on $1/$2/METADATA$ are allowed.
"You PUT a file with AUTO_COMPRESS=TRUE. When you LIST the stage, the file shows as data.csv.gz. You run COPY INTO with FILE_FORMAT TYPE=CSV COMPRESSION=AUTO. Does it work?"Yes. COMPRESSION=AUTO detects the gzip compression from the .gz extension and decompresses automatically during load.
"Can Snowpipe use VALIDATION_MODE to check files before loading?"No. VALIDATION_MODE is not supported with Snowpipe. It only works with manual COPY INTO commands.
"You want to reload data into a table after accidentally deleting rows. The original files are still in the stage (loaded 3 days ago). How?"Use FORCE = TRUE in COPY INTO. This bypasses the 64-day load history and reloads the files. Alternatively, use Time Travel to restore the deleted rows.
Top 5 Data Loading Exam Traps:
  1. Default ON_ERROR: ABORT_STATEMENT (bulk) vs SKIP_FILE (Snowpipe) - ALWAYS asked
  2. PATTERN uses regex (not SQL LIKE % and _) - common trick question
  3. METADATA$ columns ONLY available during COPY INTO - not in regular queries
  4. VALIDATION_MODE does NOT load data - it's purely a dry-run
  5. 64-day history tracks name+checksum PER TABLE - persists even after file deletion from stage
