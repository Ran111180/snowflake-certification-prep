Properties

PropertyDetail
Size range50-500 MB compressed (before compression the data may be much larger)
Row countTypically 50,000 to 500,000 rows per partition
Storage formatColumnar with row groups (PAX-style hybrid)
CompressionAutomatic per-column (dictionary, RLE, delta, etc.)

DML Impact: Updates/Deletes create NEW micro-partitions (old ones marked for garbage collection). A single row update rewrites the entire micro-partition containing that row.

2. Metadata Store

What the Cloud Services Layer Stores

For every micro-partition, Snowflake maintains:

Metadata TypeDescriptionUsed For
Range (min/max)Minimum and maximum value per column per partitionPartition pruning
Distinct countNumber of distinct values per columnQuery optimization, cardinality estimation
Null countNumber of NULL values per columnOptimization, predicate evaluation
Number of rowsRow count per micro-partitionCOUNT(*) without scanning
File referencesLocation of the physical file in cloud storageData retrieval
Table versionVersion tracking for Time TravelHistorical queries
Performance Impact: SELECT COUNT(*) on a table returns instantly because it reads from metadata only - no table scan required. Similarly, MIN() and MAX() on clustered columns can be metadata-only operations.

Metadata Store Location

  • Stored in the Cloud Services layer (NOT in the storage layer)
  • Highly available, replicated within the cloud provider
  • Accessed by all warehouses (shared across compute)
  • Powers the query optimizer and pruning engine

3. Query Compilation and Optimization

Query Lifecycle

SQL Query Submitted │ ▼ ┌──────────────┐ │ PARSING │ Syntax validation, AST generation └──────┬───────┘ ▼ ┌──────────────┐ │ RESOLUTION │ Object names, column refs, permissions └──────┬───────┘ ▼ ┌──────────────┐ │ OPTIMIZATION │ Cost-based optimizer, join reordering, │ │ predicate pushdown, pruning estimates └──────┬───────┘ ▼ ┌──────────────┐ │ COMPILATION │ Generate execution plan (DAG of operators) └──────┬───────┘ ▼ ┌──────────────┐ │ EXECUTION │ Distributed across warehouse nodes └──────────────┘

Optimization Techniques

  • Partition pruning - Skip partitions based on metadata min/max values
  • Predicate pushdown - Push filters as close to storage as possible
  • Join reordering - Rearrange join order for optimal performance
  • Subquery decorrelation - Convert correlated subqueries to joins
  • Common subexpression elimination - Avoid redundant computation
  • Projection pruning - Only read required columns (columnar benefit)

4. Partition Pruning

How Pruning Works

Query: SELECT * FROM orders WHERE order_date = '2024-01-15' Micro-Partition Metadata: ┌──────────┬─────────────────────────────────┬─────────┐ │ Partition│ order_date range │ Pruned? │ ├──────────┼─────────────────────────────────┼─────────┤ │ MP_001 │ 2023-12-01 ... 2023-12-31 │ YES │ │ MP_002 │ 2024-01-01 ... 2024-01-10 │ YES │ │ MP_003 │ 2024-01-11 ... 2024-01-20 │ NO │ ← Scanned │ MP_004 │ 2024-01-21 ... 2024-01-31 │ YES │ │ MP_005 │ 2024-02-01 ... 2024-02-15 │ YES │ └──────────┴─────────────────────────────────┴─────────┘ Result: Only 1 of 5 partitions scanned (80% pruning)

Pruning Effectiveness

  • Works best on columns with natural ordering (timestamps, sequential IDs)
  • Clustering keys improve pruning by reordering data
  • Check pruning with SYSTEM$CLUSTERING_INFORMATION()
  • Query profile shows "Partitions scanned" vs "Partitions total"

5. Transaction Model

ACID Properties

PropertySnowflake Implementation
AtomicityEntire statement succeeds or fails (auto-commit by default)
ConsistencyConstraints enforced (though most are informational only)
IsolationSnapshot isolation (READ COMMITTED level is the only option)
DurabilityCommitted data persisted to cloud storage with replication

Snapshot Isolation and MVCC

  • MVCC (Multi-Version Concurrency Control) - readers never block writers
  • Each transaction sees a consistent snapshot of data at statement/transaction start
  • DML creates new micro-partitions (old versions retained for Time Travel)
  • No dirty reads, no non-repeatable reads within a statement
  • Write conflicts resolved by "first committer wins" (later transaction aborted)

Concurrency Control

Important: Snowflake does NOT support row-level locking. DML on the same table from concurrent transactions may cause conflicts. The second transaction to commit is rolled back if it touches the same micro-partitions.
  • DDL statements are auto-committed immediately
  • Default: each DML statement is its own transaction (auto-commit)
  • Explicit transactions via BEGIN ... COMMIT/ROLLBACK
  • Transaction timeout: 4 hours (default), configurable up to 24 hours
  • Idle transaction timeout: STATEMENT_TIMEOUT_IN_SECONDS

7. Regions and Availability

Deployment Model

  • Each Snowflake account is deployed in a single cloud region
  • Data resides in that region unless explicitly replicated
  • Snowflake manages availability within the region (multi-AZ)
  • Global URL: <account_locator>.<region>.<cloud>.snowflakecomputing.com

High Availability

  • Storage: Cloud provider's built-in redundancy (S3 11-9s durability)
  • Compute: Automatic node replacement on failure
  • Cloud Services: Deployed across multiple availability zones
  • Metadata: Replicated across AZs

9. Data Exchange Architecture

Secure Data Sharing

Provider Account Consumer Account ┌──────────────────┐ ┌──────────────────┐ │ │ │ │ │ Source Table │ │ Shared Database │ │ ┌────────────┐ │ SHARE │ (Read-Only) │ │ │ Data │─┼──────────────►│ ┌────────────┐ │ │ │ (Storage) │ │ No data copy │ │ View of │ │ │ └────────────┘ │ │ │ Provider │ │ │ │ │ │ Data │ │ │ SHARE object │ │ └────────────┘ │ │ (metadata only)│ │ │ └──────────────────┘ └──────────────────┘

Characteristics

  • Zero-copy - Consumer reads provider's storage directly (no data duplication)
  • Real-time - Consumer always sees current data (no ETL delay)
  • Secure - Provider controls what is shared (views, row/column filters)
  • Cross-account only - Must be in same region (unless using listing replication)
  • Reader accounts - Provider can create managed accounts for non-Snowflake consumers

Data Marketplace / Data Exchange

  • Snowflake Marketplace: Public data listings (free and paid)
  • Private Data Exchange: Organization-specific sharing hub
  • Both built on Secure Data Sharing infrastructure
  • No data movement - instant access once shared

10. Caching Layers

Three-Level Cache Hierarchy

Cache LayerLocationDurationScope
Result CacheCloud Services24 hoursCross-warehouse (any user, same role)
Local Disk CacheWarehouse SSDUntil evicted or warehouse suspendedSingle warehouse
Remote DiskCloud StoragePersistentAll warehouses

Result Cache Rules

  • Exact same query text (whitespace and case sensitive)
  • Same role executing the query
  • Underlying data has not changed
  • Micro-partition versions are identical
  • No functions that produce non-deterministic results (CURRENT_TIMESTAMP, RANDOM, etc.)
  • Result set must be under a size threshold
  • Returns in milliseconds (no warehouse needed)
Exam Note: Result cache does NOT require a running warehouse. It is served by the Cloud Services layer. The query uses zero compute credits.
