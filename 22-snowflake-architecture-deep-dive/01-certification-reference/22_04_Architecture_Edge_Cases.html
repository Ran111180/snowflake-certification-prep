22.04 Snowflake Architecture - Edge Cases & Gotchas

Tricky scenarios frequently tested on the certification exam

1. Cloud Services Billing (10% Adjustment)

The Rule

Cloud Services compute is billed ONLY when daily Cloud Services usage exceeds 10% of the total daily warehouse compute credits consumed.

Edge Case: Zero Warehouse Usage

If no warehouses run that day (0 compute credits), then ANY Cloud Services usage above 0 is billed at 100% because 10% of 0 = 0.

Scenario: You run metadata-only queries (COUNT(*), SHOW commands) all day without any warehouse. Cloud Services credits used = 0.5. Since compute = 0, the 10% threshold = 0. You are billed for 0.5 credits of Cloud Services.

Edge Case: High Cloud Services Usage

Scenario: Daily compute = 100 credits. Cloud Services = 15 credits.

10% of 100 = 10 credits free. Billed: 15 - 10 = 5 credits.

Gotcha: The Adjustment is Daily

The 10% calculation resets every day. You cannot "bank" unused Cloud Services allowance from one day to the next. Each day is evaluated independently.

2. Compute Isolation Between Warehouses

Edge Case: Warehouse A Cannot Affect Warehouse B

Even if Warehouse A is running a massive 4-hour query that saturates all its nodes, Warehouse B operates with zero performance degradation. They share NOTHING in the compute layer.

Edge Case: Same Table, Different Warehouses

Multiple warehouses can query the same table simultaneously without contention. Storage is shared, but compute is isolated. Each warehouse reads from cloud storage (or its own cache) independently.

Gotcha: DML Conflicts ARE Possible

While read queries never conflict, two warehouses running DML on the SAME table can conflict at the micro-partition level. The second transaction to commit fails with a serialization error and must be retried.

3. Metadata Cache Persistence

Edge Case: Metadata Persists After Warehouse Suspend

The metadata cache is in the Cloud Services layer, NOT in the warehouse. Suspending or dropping a warehouse does NOT affect metadata. Queries like SELECT COUNT(*) still return instantly.

Edge Case: Metadata Updates are Immediate

After any DML (INSERT, UPDATE, DELETE, MERGE), metadata is updated immediately upon commit. There is no lag between data change and metadata refresh.

Gotcha: Metadata vs. Local Disk Cache

Metadata cache (Cloud Services) = Always available, survives warehouse suspend.
Local disk cache (Warehouse SSD) = Lost when warehouse is suspended. Resumes cold.

4. Result Cache Invalidation

Invalidation Rules

Result cache is invalidated when ANY of these occur:

  1. 24 hours elapse since the result was cached
  2. Underlying data changes (any DML on referenced tables)
  3. Micro-partition versions change (even if values are the same)

Edge Case: DELETE + Re-INSERT Same Data

If you DELETE all rows and re-INSERT the exact same data, the result cache is INVALIDATED. Even though the logical data is identical, the micro-partition versions have changed.

Edge Case: Concurrent Session Cache

User A runs a query. User B runs the exact same query with the same role. User B gets the cached result - the cache is shared across users (scoped by role, not user).

Gotcha: Non-deterministic Functions Break Cache

Queries containing CURRENT_TIMESTAMP(), CURRENT_DATE(), RANDOM(), UUID_STRING(), or external functions will NEVER use the result cache.

Edge Case: USE_CACHED_RESULT Parameter

ALTER SESSION SET USE_CACHED_RESULT = FALSE; disables result cache for that session. The query will always execute fresh. Default is TRUE.

Cache Match Requirements (All Must Be True)

  • Exact same query text (byte-for-byte, including whitespace and comments)
  • Same executing role
  • No data changes to underlying tables
  • No non-deterministic functions
  • Within 24-hour window
  • USE_CACHED_RESULT = TRUE
  • Result fits within cache size limits

5. Warehouse Suspend/Resume Behavior

Edge Case: Suspend with Running Queries

A warehouse will NOT suspend while queries are actively running, even if auto-suspend timer has expired. It waits until all running queries complete, then suspends after the idle timeout.

Edge Case: Resume Latency

Resuming a suspended warehouse takes time (provisioning nodes). Typical: a few seconds for small warehouses, longer for larger sizes. During this time, queries are queued.

Edge Case: 60-Second Minimum Billing

Each time a warehouse resumes, you are billed for a minimum of 60 seconds. If a warehouse processes a 5-second query and suspends, you pay for 60 seconds. If it processes queries continuously for 90 seconds and suspends, you pay for 90 seconds.

Gotcha: Frequent Suspend/Resume Costs More

A warehouse that suspends and resumes 60 times in an hour (1-minute auto-suspend, sporadic queries) costs 60 credits/hour (for X-Small) due to the 60-second minimum. Keeping it running would cost only 1 credit/hour.

Best Practice: Set auto-suspend to 5-10 minutes for interactive workloads to avoid the 60-second minimum penalty on frequent resumes.

Edge Case: Local Disk Cache on Resume

When a warehouse resumes, its local SSD cache is COLD (empty). First queries after resume may be slower as they re-populate the cache from cloud storage.

6. Multi-Cluster Warehouse Scaling

Scaling Policies

PolicyBehaviorBest For
StandardAdds clusters when queries queue; removes after 2-3 checks (conservative scale-down)Steady workloads, predictable concurrency
EconomyWaits longer before adding clusters; removes quickly (aggressive scale-down)Cost-sensitive, bursty workloads

Edge Case: Scale-Out Timing

Adding a new cluster takes time (provisioning + warming). During this window, queries still queue on existing clusters. Multi-cluster is NOT instant - there is a lag of several seconds to a minute.

Edge Case: Minimum and Maximum Clusters

If MIN = MAX (e.g., both set to 3), the warehouse always runs exactly 3 clusters. This eliminates scale-out latency but costs more during low-usage periods.

Gotcha: Scale-Out vs. Scale-Up

Multi-cluster warehouses add MORE clusters of the SAME size. They do NOT increase individual cluster size. If a single query is slow because it needs more compute, you need to resize (scale UP), not add clusters (scale OUT).

  • Scale UP (resize): Single slow query needs more power
  • Scale OUT (multi-cluster): Many concurrent queries need to run simultaneously

Edge Case: Multi-Cluster + Auto-Suspend

With MIN_CLUSTER_COUNT = 1, if all queries complete, extra clusters shut down first. If idle timeout expires, the last cluster also suspends. With MIN > 1, at least MIN clusters always remain running (and billing).

7. Cross-Cloud Limitations

Edge Case: No Cross-Cloud Queries

You CANNOT directly join a table in an AWS account with a table in an Azure account. Data must be replicated first via Database Replication or Replication Groups.

Edge Case: Data Sharing Region Lock

Direct shares only work within the same cloud region. To share cross-region or cross-cloud, you must use a Snowflake listing with auto-fulfillment (which creates a replica in the consumer's region).

Edge Case: Replication Costs

Cross-cloud replication incurs:

  • Data transfer costs (cloud provider egress fees)
  • Compute credits for the replication process
  • Storage costs in the target region

Gotcha: Organization Account Required

Cross-cloud/cross-region replication requires the Organization feature (accounts linked under same org). Replication between unrelated accounts is done via Secure Data Sharing, not Database Replication.

8. Additional Architecture Gotchas

Edge Case: Time Travel + Fail-Safe Storage

A dropped table with 90-day Time Travel + 7-day Fail-Safe means the storage is retained for up to 97 days total. You pay for storage during this entire period.

Gotcha: UNDROP Requires Exact Name

If you create a table, drop it, then create a new table with the same name and drop that too, UNDROP TABLE restores the MOST RECENTLY dropped table with that name. To recover the earlier one, you must first UNDROP the later one (or rename it).

Edge Case: Clone Does Not Clone Privileges

A cloned object does NOT inherit the grants/privileges of the source object. You must re-grant access separately. The exception: cloning a database clones all contained objects AND their grants.

Gotcha: ACCOUNTADMIN and Cloud Services

Operations performed with ACCOUNTADMIN (like SHOW DATABASES across all) may consume more Cloud Services credits than the same operation with a restricted role, because the metadata scan is broader.
