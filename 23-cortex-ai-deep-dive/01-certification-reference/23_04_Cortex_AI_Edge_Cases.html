23.4 Cortex AI - Edge Cases & Gotchas

Tricky details that appear on exam questions. Master these to avoid common mistakes.

Model Availability by Region

Key Facts

  • Not all models are available in all Snowflake regions
  • AWS US regions typically have the widest model availability
  • Azure and GCP regions may have fewer models
  • New models are rolled out to regions progressively
  • Region availability can be checked in Snowflake documentation
ScenarioWhat Happens

Model deprecated/renamedError until you update model name
Cross-region replication with CortexMust verify model availability in target region
If you deploy a Cortex-dependent pipeline to a different region, it may fail because the model isn't available there. Always verify region support before migration.

Rate Limits & Throttling

  • Per-account rate limits - Concurrent request caps vary by model and account tier
  • Throttling behavior - Excess requests are queued or return errors
  • Larger models = lower throughput - 405B models handle fewer concurrent requests than 7B
  • Batch processing impact - Large table scans with AI functions may hit limits
  • No guaranteed SLA on latency - Response time varies with load and model
Mitigation strategies:
  • Process large tables in batches (LIMIT/OFFSET or partitioned queries)
  • Use smaller models when possible (faster, higher throughput)
  • Cache results in tables to avoid reprocessing
  • Implement retry logic in applications calling Cortex

Cortex Search Edge Cases

TARGET_LAG Gotchas

  • Not real-time - Even '1 minute' lag means searches may miss very recent changes
  • Cost increases with smaller lag - More frequent refreshes = more warehouse credits
  • Refresh uses specified warehouse - Must be running or set to auto-resume
  • Initial build can be slow - Large datasets take time for first index build
  • Warehouse suspension - If warehouse suspends, refresh waits until next resume

Column Type Restrictions

  • ON column must be VARCHAR (text only - no VARIANT, BINARY, etc.)
  • ATTRIBUTES columns: VARCHAR, NUMBER, BOOLEAN, DATE, TIMESTAMP
  • Cannot search over ARRAY, OBJECT, or VARIANT columns directly
  • Text must be extracted/flattened before indexing semi-structured data

Document Size Limits

  • Individual text values have a maximum token limit for indexing
  • Very long documents should be chunked before indexing
  • Chunking strategy affects search quality (overlap recommended)
  • The search service handles ranking across chunks internally
If your source table has NULL values in the ON column, those rows are skipped during indexing. They will never appear in search results.

Embedding Edge Cases

Dimension Mismatches

ModelVector Dimensions
snowflake-arctic-embed-m-v1.5768
snowflake-arctic-embed-l-v2.01024
e5-base-v2768
You CANNOT compare vectors of different dimensions. If you embed documents with model A (768-dim) and queries with model B (1024-dim), VECTOR_COSINE_SIMILARITY will ERROR. Always use the same model for both storage and query embeddings.

Other Embedding Gotchas

  • Empty string - Embedding an empty string returns a valid vector (all near-zero), which may cause false matches
  • Token overflow - Text exceeding model's input limit is truncated (not errored)
  • Language sensitivity - Arctic models optimized for English; other languages may have lower quality
  • VECTOR column type is fixed - Must specify dimensions at table creation: VECTOR(FLOAT, 768)
  • Cannot change model after embedding - Re-embedding entire table needed if switching models

Row-by-Row vs. Batch

  • Row-by-row (SELECT AI_COMPLETE(...) FROM table) - Each row is a separate API call
  • No true batch discount - Cost is the same per token regardless of batch size
  • Concurrency limits - Too many simultaneous rows may hit rate limits
  • Best practice - Process in controlled chunks, store results incrementally

ML Function Edge Cases

FORECAST Requirements

  • Minimum data points - At least 2 full seasonal cycles + additional observations (varies by frequency)
  • Regular frequency required - Data must have consistent time intervals (daily, hourly, etc.)
  • Supported frequencies - Second, minute, hour, day, week, month, quarter, year
  • Missing values - Gaps in time series can cause errors or poor predictions
  • Single target column - Forecasts one numeric column at a time
  • No exogenous variables in basic mode - Limited external feature support
FORECAST will fail if your time series has irregular intervals (e.g., only weekday data with no weekend rows). You must either fill gaps or specify the frequency explicitly.

ANOMALY_DETECTION Requirements

  • Minimum training data - Needs sufficient "normal" data to learn patterns (at least 12 data points)
  • Cold start problem - New metrics with little history may produce poor results
  • Seasonality assumption - Works best with regular patterns; random data yields many false positives
  • Unsupervised vs. supervised - Without labels, relies entirely on statistical detection
  • prediction_interval - Higher values (0.99) mean fewer anomalies detected; lower (0.90) means more

CLASSIFICATION Limitations

  • Minimum samples per class - Each class needs sufficient examples for training
  • Imbalanced classes - Very rare classes may be poorly predicted
  • Feature types - Handles numeric and categorical automatically, but not free text
  • No feature engineering control - Automated, cannot specify custom transformations
  • Model is a Snowflake object - Persists until explicitly dropped

Cortex Analyst Limitations

  • Requires semantic view - Cannot work without a properly defined semantic model
  • Complex queries may fail - Multi-hop joins, window functions, or advanced analytics may not generate correctly
  • Ambiguous questions - Vague questions produce unreliable SQL
  • Schema changes break it - If underlying tables change, semantic view must be updated
  • No write operations - Cannot generate INSERT, UPDATE, DELETE (read-only queries)
  • Verified queries improve but don't guarantee accuracy
  • Limited to supported SQL patterns - May not handle recursive CTEs, PIVOT, etc.
  • Performance depends on underlying query - Generated SQL runs against actual tables with real costs
Cortex Analyst generates SQL based on the semantic view. If the semantic view has incorrect join definitions or wrong column mappings, the generated SQL will be wrong - garbage in, garbage out.

Exam Scenario Questions

Click each scenario to reveal the answer.

Scenario 1

A team runs AI_COMPLETE('llama3.1-70b', text_col) on a 50-million row table. The query runs for hours and eventually fails. What is the most likely cause?

Answer: Rate limiting/throttling. Processing 50M rows creates 50M API calls, exceeding per-account concurrency limits. Solution: Process in batches, use LIMIT/OFFSET, or pre-filter to reduce row count. Also consider if a smaller model or a different function (AI_SENTIMENT, AI_CLASSIFY) would suffice.

Scenario 2

You create embeddings with snowflake-arctic-embed-m-v1.5 for 1M documents. Later you want to switch to snowflake-arctic-embed-l-v2.0 for better quality. Can you just re-embed the search queries?

Answer: No. The models produce different dimensions (768 vs 1024). VECTOR_COSINE_SIMILARITY will error on dimension mismatch. You must re-embed ALL stored documents with the new model, not just the queries.

Scenario 3

A Cortex Search Service with TARGET_LAG='1 minute' is created. The source table is updated, but searches don't show the new data even after 5 minutes. Why?

Answer: Most likely the specified warehouse is suspended and not set to auto-resume. The refresh operation needs the warehouse running. Also possible: the refresh errored silently, or the new rows have NULL in the ON column (skipped during indexing).

Scenario 4

A user grants SNOWFLAKE.CORTEX_USER to their role but still gets permission errors when running AI_COMPLETE. What might be wrong?

Answer: The grant syntax must be: GRANT DATABASE ROLE SNOWFLAKE.CORTEX_USER TO ROLE my_role; - it's a DATABASE ROLE, not an account role. If they used GRANT ROLE SNOWFLAKE.CORTEX_USER... it would fail. Also, they need USAGE on the SNOWFLAKE database.

Scenario 5

AI_SENTIMENT returns 0.02 for a customer review that says "The product works fine." Is this a bug?

Answer: No. "Works fine" is a neutral statement - neither strongly positive nor negative. A score near 0 correctly indicates neutral sentiment. Only strongly emotional text produces values near -1 or +1.

Scenario 6

You deploy a pipeline using mistral-large2 in AWS US-East-1. The same pipeline is replicated to Azure West Europe and starts failing. Why?

Answer: Model availability varies by region and cloud provider. mistral-large2 may not be available in the Azure West Europe region. You must verify model availability in the target region and potentially use an alternative model.

Scenario 7

A FORECAST model is created on daily sales data from the last 2 months. It returns an error about insufficient data. The data has 60 rows. Why?

Answer: If the data has weekly seasonality, FORECAST needs at least 2 full seasonal cycles. But the real issue is likely missing weekends (only ~42 actual data points) or the model detecting a seasonal pattern that requires more history to establish. Filling gaps or providing more historical data resolves this.

Scenario 8

A team uses AI_COMPLETE with a 800-token system prompt for sentiment classification on 2M rows. The monthly Cortex bill is extremely high. What's the best optimization?

Answer: Replace AI_COMPLETE + long system prompt with AI_SENTIMENT (purpose-built, much cheaper). The 800-token system prompt x 2M rows = 1.6B unnecessary input tokens. AI_SENTIMENT is designed for exactly this use case and costs a fraction per token.

Scenario 9

A Cortex Analyst query for "show me revenue by quarter for the last 3 years" returns incorrect data. The semantic view was last updated 6 months ago. What happened?

Answer: If the underlying table schema changed in the last 6 months (columns renamed, new tables added, join paths modified), the semantic view is stale. The generated SQL references old schema that may produce wrong results or errors. The semantic view must be updated to match current schema.

Scenario 10

An application calls AI_COMPLETE with temperature=0 twice with the identical prompt but gets slightly different responses. Is this expected?

Answer: Yes, this can happen. Temperature=0 makes the model "most deterministic" but doesn't guarantee bit-for-bit identical responses across calls. Hardware, batching, and numerical precision can cause minor variations. For exact reproducibility, cache the first result.
