SQL Fundamentals - Edge Cases & Exam Scenarios

Critical traps, gotchas, and tricky scenarios that appear on the SnowPro certification exam

Edge Case 1: QUALIFY Execution Order

QUALIFY executes AFTER window functions but BEFORE DISTINCT and ORDER BY. This creates subtle behaviors:

-- This works! QUALIFY can reference window functions not in SELECT
SELECT department, employee, salary
FROM employees
QUALIFY ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) = 1;

-- But WHERE cannot filter window functions (executes too early)
-- This FAILS:
SELECT department, employee, salary,
  ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) as rn
FROM employees
WHERE rn = 1;  -- ERROR: rn not recognized in WHERE
Trap: You cannot use window function results in WHERE (window functions execute after WHERE). You also cannot use them in HAVING. Only QUALIFY or a wrapping subquery works.
Correct: Use QUALIFY for filtering window results. It can reference functions inline OR by alias if in SELECT. It's the only clause that directly filters window function output.

Edge Case 2: ROW_NUMBER vs RANK with Ties

-- Data: Alice 90, Bob 90, Carol 80
-- ROW_NUMBER() OVER (ORDER BY score DESC):
--   Alice=1, Bob=2 (or Bob=1, Alice=2) — NON-DETERMINISTIC!
-- RANK() OVER (ORDER BY score DESC):
--   Alice=1, Bob=1, Carol=3 — DETERMINISTIC, gaps
-- DENSE_RANK() OVER (ORDER BY score DESC):
--   Alice=1, Bob=1, Carol=2 — DETERMINISTIC, no gaps
Trap: If an exam question asks "which query gives deterministic results?" and uses ROW_NUMBER without a unique tiebreaker column, the answer is NON-DETERMINISTIC. Running the same query twice may give different results.
Correct: Always add a unique tiebreaker: ROW_NUMBER() OVER (ORDER BY score DESC, employee_id ASC). For "top-N including ties," use RANK() or DENSE_RANK() instead.

Edge Case 3: MERGE Clause Order and Duplicate Keys

-- MERGE processes clauses in ORDER WRITTEN. First match wins.
MERGE INTO target t USING source s ON t.id = s.id
WHEN MATCHED AND s.action = 'DELETE' THEN DELETE   -- checked first
WHEN MATCHED THEN UPDATE SET t.val = s.val;        -- only if not deleted

-- WRONG order (update happens first, delete never reached for non-delete):
MERGE INTO target t USING source s ON t.id = s.id
WHEN MATCHED THEN UPDATE SET t.val = s.val         -- always matches first!
WHEN MATCHED AND s.action = 'DELETE' THEN DELETE;  -- dead code
Trap: The more specific WHEN MATCHED clause must come FIRST. A general WHEN MATCHED without a condition will consume all matches, making subsequent clauses unreachable. 
-- Duplicate key trap:
-- Source: (id=1, val='A'), (id=1, val='B')
-- Target: (id=1, val='X')
-- MERGE raises ERROR: duplicate keys detected (non-deterministic)

-- Fix: deduplicate source first
MERGE INTO target t
USING (
  SELECT * FROM source QUALIFY ROW_NUMBER() OVER (PARTITION BY id ORDER BY ts DESC) = 1
) s ON t.id = s.id
WHEN MATCHED THEN UPDATE SET t.val = s.val;

Edge Case 4: ROWS vs RANGE — The Subtle Difference

-- Data: date=Jan 1 amt=10, date=Jan 1 amt=20, date=Jan 2 amt=30
-- (Two rows share Jan 1)

-- ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW:
-- Row 1: SUM = 10 (only first physical row)
-- Row 2: SUM = 30 (first + second physical row)
-- Row 3: SUM = 60

-- RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW (default!):
-- Row 1: SUM = 30 (all rows with value <= Jan 1, includes BOTH Jan 1 rows)
-- Row 2: SUM = 30 (same! all rows with value <= Jan 1)
-- Row 3: SUM = 60
Trap: With duplicate ORDER BY values, RANGE groups them together while ROWS treats each physically. The DEFAULT frame is RANGE, so running totals may "jump" at tied values rather than incrementing row-by-row.
Correct: For a strict row-by-row running total, explicitly use ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. The default RANGE frame can produce unexpected results with ties.

Edge Case 6: COALESCE vs NVL — Subtle Differences

-- Difference 1: Argument count
NVL(a, b)           -- exactly 2 arguments
COALESCE(a, b, c)   -- unlimited arguments

-- Difference 2: Evaluation behavior
NVL(expr1, expr2)      -- BOTH arguments always evaluated
COALESCE(expr1, expr2) -- Short-circuits: stops at first non-NULL

-- Difference 3: Type resolution
NVL(1, 'text')         -- May error depending on implicit conversion
COALESCE(1, 'text')    -- Uses SQL standard type precedence rules

-- When it matters (performance):
NVL(col, expensive_function())      -- function ALWAYS called
COALESCE(col, expensive_function()) -- function only called if col IS NULL
Exam Tip: For exam purposes: NVL = 2 args, always evaluates both. COALESCE = N args, short-circuits. Functionally NVL(a,b) = COALESCE(a,b) for results, but performance can differ.

Edge Case 7: Integer Division (5/2 = 2)

-- Integer division TRUNCATES in Snowflake
SELECT 5/2;       -- Returns 2 (not 2.5!)
SELECT 7/3;       -- Returns 2
SELECT -5/2;      -- Returns -2 (truncates toward zero)

-- Solutions to get decimal results:
SELECT 5.0/2;              -- 2.500000 (make one operand decimal)
SELECT 5/2.0;              -- 2.500000
SELECT 5::FLOAT/2;         -- 2.5
SELECT CAST(5 AS FLOAT)/2; -- 2.5
SELECT DIV0(5, 2);         -- Still 2 (DIV0 is for zero-safe division, not decimal)
SELECT 5/NULLIF(2, 0);     -- 2 (integer result, but zero-safe)
Trap: Calculating percentages like correct_count / total_count * 100 gives 0 if both are integers and correct < total! Always cast: correct_count::FLOAT / total_count * 100.

Edge Case 8: REGEXP vs LIKE Pattern Matching

FeatureLIKE / ILIKEREGEXP / RLIKE
Wildcards% (any chars), _ (one char)Full regex: .*, .{1}, [0-9]+
Case sensitivityLIKE=sensitive, ILIKE=insensitiveREGEXP=insensitive by default!
AnchoringImplicit full matchPartial match by default (use ^ and $)
EscapeESCAPE '\'Double backslash or $$ delimiters
PerformanceFaster (simple pattern)Slower (regex engine)
-- LIKE matches entire string implicitly
SELECT 'Hello World' LIKE '%World';      -- TRUE
SELECT 'Hello World' LIKE 'Hello';       -- FALSE (must match entire string)

-- REGEXP matches ANYWHERE by default (partial match!)
SELECT 'Hello World' REGEXP 'Hello';     -- TRUE (found within string)
SELECT 'Hello World' REGEXP '^Hello$';   -- FALSE (anchored to exact match)

-- Case sensitivity surprise:
SELECT 'Hello' LIKE 'hello';             -- FALSE (case-sensitive)
SELECT 'Hello' REGEXP 'hello';           -- TRUE! (case-insensitive by default)
SELECT 'Hello' REGEXP 'hello' ;          -- TRUE
-- Force case-sensitive: REGEXP '(?c)hello' or use REGEXP_LIKE with 'c' flag
Trap: REGEXP is case-INSENSITIVE by default (opposite of LIKE). REGEXP does partial matching (opposite of LIKE which requires full match). These two differences catch many exam takers.

10 Exam Scenarios

Scenario 1: Top-N Per Group

Question: Which query returns the 3 highest-paid employees per department?

-- CORRECT (Snowflake-specific, most concise):
SELECT * FROM employees
QUALIFY ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) <= 3;

-- ALSO CORRECT (standard SQL):
SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) rn
  FROM employees
) WHERE rn <= 3;

-- WRONG: Cannot filter in WHERE
SELECT *, ROW_NUMBER() OVER (...) as rn FROM employees WHERE rn <= 3;

Answer: QUALIFY is preferred in Snowflake. WHERE cannot access window function results.

Scenario 2: Running Total with Ties

Question: Given sales data where two orders share the same date, what does SUM(amount) OVER (ORDER BY date) produce?

-- date=Jan 1, amount=100
-- date=Jan 1, amount=200
-- date=Jan 2, amount=50

-- Default frame = RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
-- Row 1: 300 (both Jan 1 rows included due to RANGE)
-- Row 2: 300 (same! tied dates get same running total)
-- Row 3: 350

Answer: RANGE groups tied values together. Both Jan 1 rows show 300, not 100 and 300. Use ROWS for strict row-by-row accumulation.

Scenario 3: MERGE with Multiple Sources

Question: A staging table has two rows with id=1. What happens when MERGE matches both to the same target row?

Answer: MERGE raises a non-deterministic error. You must deduplicate the source using QUALIFY or GROUP BY before MERGE.

Scenario 4: Integer Division in Percentage

Question: SELECT passed_count / total_count * 100 as pass_rate where passed=3, total=7. What is the result?

Answer: 3/7 = 0 (integer division truncates), 0 * 100 = 0. The pass_rate is 0, not 42.86. Fix: passed_count * 100.0 / total_count or cast to FLOAT.

Scenario 5: NOT IN with NULL

Question: SELECT * FROM orders WHERE status NOT IN (SELECT status FROM excluded_statuses) — the subquery returns ('cancelled', NULL). How many rows returned?

Answer: ZERO rows! NOT IN with NULL in the list always evaluates to NULL/FALSE for every value. Use NOT EXISTS or WHERE status NOT IN (SELECT status FROM excluded_statuses WHERE status IS NOT NULL).

Scenario 6: DATEDIFF Boundary Crossing

Question: What is DATEDIFF('month', '2024-01-31', '2024-02-01')?

Answer: 1. DATEDIFF counts month boundaries crossed (January to February = 1), even though only 1 day elapsed. This catches people who expect 0 because "a full month hasn't passed."

Scenario 7: || vs CONCAT with NULL

Question: What is the difference between first_name || ' ' || last_name and CONCAT(first_name, ' ', last_name) when last_name is NULL?

-- first_name = 'John', last_name = NULL
SELECT 'John' || ' ' || NULL;          -- NULL (|| propagates NULL)
SELECT CONCAT('John', ' ', NULL);      -- 'John ' (CONCAT skips NULL)

Answer: || returns NULL if any operand is NULL. CONCAT() skips NULLs and concatenates the rest. They are NOT interchangeable.

Scenario 8: LAST_VALUE Default Frame Trap

Question: Why does LAST_VALUE(salary) OVER (ORDER BY hire_date) return the current row's salary?

Answer: The default frame with ORDER BY is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. LAST_VALUE can only see up to the current row, so it returns the current row's value. Fix: add ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING.

Scenario 9: DDL Inside Transaction

Question: What happens if you execute CREATE TABLE inside a BEGIN/COMMIT block, then ROLLBACK?

BEGIN;
  INSERT INTO log VALUES ('start');
  CREATE TABLE new_table (id INT);  -- DDL auto-commits HERE
  INSERT INTO log VALUES ('end');
ROLLBACK;  -- Only rolls back 'end' insert!

Answer: DDL statements auto-commit, breaking the transaction. The CREATE TABLE and 'start' INSERT are committed. Only statements after the DDL can be rolled back.

Scenario 10: REGEXP Case Sensitivity Surprise

Question: What does SELECT 'HELLO' REGEXP 'hello' return?

Answer: TRUE! REGEXP/RLIKE is case-insensitive by default in Snowflake (unlike LIKE which is case-sensitive). Use '(?c)hello' flag for case-sensitive matching, or use REGEXP_LIKE(col, 'hello', 'c').
