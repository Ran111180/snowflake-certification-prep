1. Dynamic Data Masking

What is Dynamic Data Masking?

Dynamic Data Masking (DDM) applies a column-level security policy that selectively masks data at query time based on the user's role. The underlying data is never physically modified — masking is applied dynamically when results are returned.

  • Policy is a schema-level object (lives in a database.schema)
  • Applied to a column, not a table
  • Only ONE masking policy per column
  • Works on views, tables, materialized views, and stages (external tables)
  • Policy body is a SQL expression that returns the same data type as the column

Creating a Masking Policy

-- Basic masking policy syntax
CREATE OR REPLACE MASKING POLICY mask_ssn
  AS (val STRING) RETURNS STRING ->
  CASE
    WHEN CURRENT_ROLE() IN ('HR_ADMIN', 'SECURITYADMIN')
      THEN val
    ELSE '***-**-' || RIGHT(val, 4)
  END;

-- Using IS_ROLE_IN_SESSION (respects role hierarchy!)
CREATE OR REPLACE MASKING POLICY mask_email
  AS (val STRING) RETURNS STRING ->
  CASE
    WHEN IS_ROLE_IN_SESSION('DATA_ADMIN')
      THEN val
    ELSE REGEXP_REPLACE(val, '.+@', '****@')
  END;
EXAM TIP: CURRENT_ROLE() checks the EXACT active role only. IS_ROLE_IN_SESSION() checks if the role is in the current session's role hierarchy (includes inherited roles). For exams, know the difference — IS_ROLE_IN_SESSION is the recommended approach.

Applying a Masking Policy

-- Apply to a column
ALTER TABLE employees
  ALTER COLUMN ssn SET MASKING POLICY mask_ssn;

-- Apply during table creation
CREATE TABLE customers (
  id NUMBER,
  email STRING MASKING POLICY mask_email,
  phone STRING MASKING POLICY mask_phone
);

-- Remove a masking policy
ALTER TABLE employees
  ALTER COLUMN ssn UNSET MASKING POLICY;

-- Replace (must unset first, then set new one)
ALTER TABLE employees ALTER COLUMN ssn UNSET MASKING POLICY;
ALTER TABLE employees ALTER COLUMN ssn SET MASKING POLICY mask_ssn_v2;

2. Row Access Policies

What is a Row Access Policy (RAP)?

A Row Access Policy provides row-level security by filtering rows at query time. The policy body returns a boolean — if TRUE, the row is visible; if FALSE, the row is excluded from results.

  • Schema-level object
  • Only ONE row access policy per table/view
  • Evaluated per row (performance consideration)
  • Can reference other tables (mapping tables for dynamic filtering)
  • Applied with ADD (not SET like masking policies)

Creating a Row Access Policy

-- Basic role-based row access policy
CREATE OR REPLACE ROW ACCESS POLICY rap_by_region
  AS (region_col VARCHAR) RETURNS BOOLEAN ->
  CASE
    WHEN CURRENT_ROLE() = 'ADMIN'
      THEN TRUE  -- admin sees all rows
    WHEN CURRENT_ROLE() = 'US_ANALYST'
      AND region_col = 'US'
      THEN TRUE
    WHEN CURRENT_ROLE() = 'EU_ANALYST'
      AND region_col = 'EU'
      THEN TRUE
    ELSE FALSE   -- default: hide row
  END;

-- Mapping table pattern (most common in production)
CREATE OR REPLACE ROW ACCESS POLICY rap_mapping_table
  AS (region_col VARCHAR) RETURNS BOOLEAN ->
    EXISTS (
      SELECT 1 FROM security_db.public.role_region_mapping m
      WHERE m.role_name = CURRENT_ROLE()
        AND m.allowed_region = region_col
    )
    OR IS_ROLE_IN_SESSION('SYSADMIN');

Applying a Row Access Policy

-- Apply (note: ADD not SET)
ALTER TABLE sales
  ADD ROW ACCESS POLICY rap_by_region ON (region);

-- Remove
ALTER TABLE sales
  DROP ROW ACCESS POLICY rap_by_region;

-- The ON clause maps policy arguments to table columns
-- Policy takes (region_col VARCHAR) → maps to table column (region)
ALTER TABLE orders
  ADD ROW ACCESS POLICY rap_by_region ON (ship_region);
EXAM TIP: Masking policies use SET/UNSET. Row access policies use ADD/DROP. This is a common trick question!

3. Object Tagging

What are Tags?

Tags are metadata labels you can assign to Snowflake objects. They enable governance at scale through tag-based policies — assign a masking policy to a tag, and every column with that tag is automatically masked.

  • Tag is a schema-level object with an optional set of allowed values
  • Tags can be applied to: databases, schemas, tables, views, columns, warehouses, users, roles, etc.
  • A column can have multiple different tags (but only one value per tag name)
  • Tags do NOT automatically propagate from parent to child objects

Creating and Assigning Tags

-- Create a tag (with optional allowed values)
CREATE OR REPLACE TAG pii_type
  ALLOWED_VALUES 'email', 'phone', 'ssn', 'name', 'address';

CREATE OR REPLACE TAG sensitivity
  ALLOWED_VALUES 'high', 'medium', 'low';

-- Assign tag to a column
ALTER TABLE customers ALTER COLUMN email SET TAG pii_type = 'email';
ALTER TABLE customers ALTER COLUMN phone SET TAG pii_type = 'phone';
ALTER TABLE customers ALTER COLUMN ssn SET TAG pii_type = 'ssn';

-- Assign tag to a table
ALTER TABLE customers SET TAG sensitivity = 'high';

-- Assign tag to a schema (does NOT cascade to objects inside!)
ALTER SCHEMA hr_data SET TAG sensitivity = 'high';

-- Remove a tag
ALTER TABLE customers ALTER COLUMN email UNSET TAG pii_type;

Tag-Based Masking Policies

-- Assign masking policy to a tag (not to individual columns!)
ALTER TAG pii_type SET MASKING POLICY mask_pii_data;

-- Now EVERY column tagged with pii_type will be masked automatically!
-- This is the scalable approach for large environments
KEY CONCEPT: Tag-based policies allow governance at scale. Instead of assigning masking policies to 1000 columns individually, tag them with pii_type and attach the policy to the tag once. New columns tagged later are automatically protected.

4. Data Classification

Automatic Data Classification

Snowflake can automatically detect sensitive data (PII, financial data, health data) using built-in classifiers. Classification analyzes column names AND data patterns to assign semantic and privacy categories.

Classification Functions

-- Classify all columns in a table (returns JSON)
SELECT SYSTEM$CLASSIFY('my_db.my_schema.customers');

-- Classify with options (sample size, custom categories)
SELECT SYSTEM$CLASSIFY('my_db.my_schema.customers',
  {'auto_tag': true}  -- automatically apply system tags
);

-- Extract semantic categories from classification result
SELECT *
FROM TABLE(
  EXTRACT_SEMANTIC_CATEGORIES('my_db.my_schema.customers')
);

-- Result columns: column_name, semantic_category, privacy_category,
-- probability, alternates

Snowflake System Classification Tags

TagCategoryExamples
SNOWFLAKE.CORE.SEMANTIC_CATEGORYWhat the data ISEMAIL, PHONE_NUMBER, US_SSN, NAME, IP_ADDRESS, CREDIT_CARD
SNOWFLAKE.CORE.PRIVACY_CATEGORYHow sensitive it isIDENTIFIER, QUASI_IDENTIFIER, SENSITIVE

Classification Workflow

-- Step 1: Run classification (detect)
SELECT EXTRACT_SEMANTIC_CATEGORIES('my_db.public.customers');

-- Step 2: Review results (human review recommended)

-- Step 3: Apply system tags (auto or manual)
-- Auto:
CALL ASSOCIATE_SEMANTIC_CATEGORY_TAGS(
  'my_db.public.customers',
  EXTRACT_SEMANTIC_CATEGORIES('my_db.public.customers')
);

-- Step 4: Attach masking policies to tags
ALTER TAG SNOWFLAKE.CORE.SEMANTIC_CATEGORY
  SET MASKING POLICY mask_by_semantic_category;

5. Column-Level Security Overview

Security Layers in Snowflake
LayerMechanismGranularityReturns
Object AccessRBAC (GRANT)Object-levelAllow/Deny
Row FilteringRow Access PolicyRow-levelBoolean
Column MaskingMasking PolicyColumn-levelMasked value
Column EncryptionExternal TokenizationColumn-levelToken/cipher

All layers compose: a user must pass RBAC, then RAP filters rows, then masking transforms column values.

Execution Order: RBAC check → Row Access Policy (filter rows) → Masking Policy (mask columns) → Return results. If a row is filtered by RAP, masking never executes on it (it's already gone).

6. Features (15)

Dynamic masking at query time — no physical data change
Column-level granularity for masking policies
Row-level filtering via Row Access Policies
Tag-based policies for governance at scale
Automatic PII classification with SYSTEM$CLASSIFY
IS_ROLE_IN_SESSION respects full role hierarchy
Mapping table pattern for dynamic role-based access
Policies travel with shared data (enforced on consumer side)
Works on tables, views, materialized views, external tables
Conditional masking (different masks for different roles)
Tags with ALLOWED_VALUES for constrained metadata
POLICY_REFERENCES function for governance auditing
External tokenization integration via secure UDFs
TAG_REFERENCES for tracking tag assignments across objects
Classification probability scores for confidence assessment

7. Limitations (15)

Only ONE masking policy per column (cannot stack)
Only ONE row access policy per table/view (cannot stack)
Cannot mask VARIANT sub-fields individually (whole column only)
Tags do NOT propagate from parent objects (schema→table)
Row access policies evaluated per row (performance impact)
CURRENT_ROLE() does NOT respect role hierarchy (use IS_ROLE_IN_SESSION)
Must UNSET a masking policy before applying a different one
Classification is probabilistic — may produce false positives/negatives
Consumer cannot remove masking policies on shared data
Masking policy body cannot contain subqueries (in some contexts)
Cannot use JavaScript UDFs in masking policy bodies
Row access policy cannot reference the same table it's applied to
Enterprise Edition or higher required for masking/RAP
Tag allowed_values have a maximum limit per tag
Cannot create conditional policies based on the specific query being run
