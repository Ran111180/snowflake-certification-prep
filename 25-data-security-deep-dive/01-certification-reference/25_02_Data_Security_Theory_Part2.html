1. Tag-Based Masking Policies

How Tag-Based Masking Works

Instead of assigning a masking policy to each column individually, you assign the policy to a tag. Any column that has that tag applied will automatically be masked by the tag's policy.

  1. Create a tag (e.g., pii_type)
  2. Create a masking policy
  3. Attach the masking policy to the tag: ALTER TAG ... SET MASKING POLICY
  4. Tag columns: ALTER TABLE ... ALTER COLUMN ... SET TAG pii_type = 'email'
  5. Done! All tagged columns are now masked
-- Step 1: Create tags
CREATE TAG governance_db.tags.pii_type
  ALLOWED_VALUES 'email', 'phone', 'ssn', 'name', 'dob';

-- Step 2: Create a conditional masking policy
CREATE OR REPLACE MASKING POLICY governance_db.policies.mask_by_pii_tag
  AS (val VARCHAR) RETURNS VARCHAR ->
  CASE
    WHEN IS_ROLE_IN_SESSION('DATA_STEWARD') THEN val
    WHEN SYSTEM$GET_TAG_ON_CURRENT_COLUMN('governance_db.tags.pii_type') = 'email'
      THEN REGEXP_REPLACE(val, '.+@', '****@')
    WHEN SYSTEM$GET_TAG_ON_CURRENT_COLUMN('governance_db.tags.pii_type') = 'phone'
      THEN CONCAT('***-***-', RIGHT(val, 4))
    WHEN SYSTEM$GET_TAG_ON_CURRENT_COLUMN('governance_db.tags.pii_type') = 'ssn'
      THEN CONCAT('***-**-', RIGHT(val, 4))
    ELSE '********'
  END;

-- Step 3: Attach policy to tag
ALTER TAG governance_db.tags.pii_type
  SET MASKING POLICY governance_db.policies.mask_by_pii_tag;

-- Step 4: Tag columns (policy automatically applies!)
ALTER TABLE customers ALTER COLUMN email SET TAG governance_db.tags.pii_type = 'email';
ALTER TABLE customers ALTER COLUMN phone SET TAG governance_db.tags.pii_type = 'phone';
ALTER TABLE employees ALTER COLUMN ssn SET TAG governance_db.tags.pii_type = 'ssn';
SYSTEM$GET_TAG_ON_CURRENT_COLUMN: This function can be used inside a tag-based masking policy to read the tag value of the column currently being evaluated. This enables ONE policy to mask differently based on the tag value (email vs phone vs SSN).

2. Masking Policy Patterns

Pattern 1: Full Mask

CREATE MASKING POLICY full_mask AS (val VARCHAR) RETURNS VARCHAR ->
  CASE
    WHEN IS_ROLE_IN_SESSION('ADMIN') THEN val
    ELSE '**MASKED**'
  END;

Pattern 2: Partial Mask (Show Last 4)

CREATE MASKING POLICY partial_mask AS (val VARCHAR) RETURNS VARCHAR ->
  CASE
    WHEN IS_ROLE_IN_SESSION('ADMIN') THEN val
    ELSE CONCAT(REPEAT('*', LENGTH(val) - 4), RIGHT(val, 4))
  END;

Pattern 3: Conditional by Multiple Roles

CREATE MASKING POLICY tiered_mask AS (val VARCHAR) RETURNS VARCHAR ->
  CASE
    WHEN IS_ROLE_IN_SESSION('FULL_ACCESS') THEN val
    WHEN IS_ROLE_IN_SESSION('PARTIAL_ACCESS') THEN LEFT(val, 3) || '***'
    ELSE '**REDACTED**'
  END;

Pattern 4: SHA2 Tokenization (Consistent Hash)

-- Useful for joins/analytics without seeing real values
CREATE MASKING POLICY sha2_mask AS (val VARCHAR) RETURNS VARCHAR ->
  CASE
    WHEN IS_ROLE_IN_SESSION('DATA_STEWARD') THEN val
    ELSE SHA2(val, 256)
  END;
-- Same input always produces same hash → can still JOIN/GROUP BY

Pattern 5: NULL Mask (for numeric/date columns)

CREATE MASKING POLICY null_mask_number AS (val NUMBER) RETURNS NUMBER ->
  CASE
    WHEN IS_ROLE_IN_SESSION('FINANCE') THEN val
    ELSE NULL
  END;

CREATE MASKING POLICY null_mask_date AS (val DATE) RETURNS DATE ->
  CASE
    WHEN IS_ROLE_IN_SESSION('HR_ADMIN') THEN val
    ELSE NULL
  END;

3. Row Access Policy Patterns

Pattern 1: Role-Based Filtering

CREATE ROW ACCESS POLICY rap_role_filter
  AS (department VARCHAR) RETURNS BOOLEAN ->
  IS_ROLE_IN_SESSION('ADMIN')
  OR (IS_ROLE_IN_SESSION('HR') AND department = 'HR')
  OR (IS_ROLE_IN_SESSION('FINANCE') AND department = 'FINANCE');

Pattern 2: Mapping Table (Most Flexible)

-- Mapping table: ROLE_NAME | ALLOWED_VALUE
CREATE ROW ACCESS POLICY rap_mapping
  AS (region VARCHAR) RETURNS BOOLEAN ->
  EXISTS (
    SELECT 1 FROM governance_db.public.access_mapping
    WHERE role_name = CURRENT_ROLE()
      AND allowed_region = region
  )
  OR IS_ROLE_IN_SESSION('SYSADMIN');

-- Mapping table allows dynamic changes without altering the policy!

Pattern 3: Multi-Tenant Isolation

-- Each user only sees their company's data
CREATE ROW ACCESS POLICY rap_multi_tenant
  AS (tenant_id NUMBER) RETURNS BOOLEAN ->
  tenant_id = (
    SELECT t.tenant_id
    FROM governance_db.public.user_tenant_map t
    WHERE t.user_name = CURRENT_USER()
  )
  OR IS_ROLE_IN_SESSION('PLATFORM_ADMIN');

Pattern 4: Time-Based Access

-- Only show records created within the last 90 days for non-admins
CREATE ROW ACCESS POLICY rap_time_based
  AS (created_date DATE) RETURNS BOOLEAN ->
  IS_ROLE_IN_SESSION('ADMIN')
  OR created_date >= DATEADD('day', -90, CURRENT_DATE());

4. Policy Administration & Privileges

Separation of Duties

Snowflake enforces separation between policy creation and policy application. This is a security design — the person who creates a policy may not be the person who decides where it's applied.

PrivilegeWhat It AllowsTypical Role
CREATE MASKING POLICYCreate/replace masking policies in a schemaSecurity Admin / Policy Admin
APPLY MASKING POLICY (account-level)Set/unset masking policies on any columnData Steward
CREATE ROW ACCESS POLICYCreate/replace RAPs in a schemaSecurity Admin
APPLY ROW ACCESS POLICY (account-level)Add/drop RAPs on any tableData Steward
CREATE TAGCreate tags in a schemaGovernance Admin
APPLY TAG (account-level)Assign tags to any objectData Steward
-- Grant policy administration privileges
GRANT CREATE MASKING POLICY ON SCHEMA governance_db.policies TO ROLE security_admin;
GRANT APPLY MASKING POLICY ON ACCOUNT TO ROLE data_steward;

GRANT CREATE ROW ACCESS POLICY ON SCHEMA governance_db.policies TO ROLE security_admin;
GRANT APPLY ROW ACCESS POLICY ON ACCOUNT TO ROLE data_steward;

GRANT CREATE TAG ON SCHEMA governance_db.tags TO ROLE governance_admin;
GRANT APPLY TAG ON ACCOUNT TO ROLE data_steward;
EXAM TIP: APPLY privileges are account-level privileges, not schema or database level. You grant them ON ACCOUNT. This means once granted, the role can apply policies/tags anywhere.

6. Data Classification Workflow

End-to-End Classification Process
1
Detect: Run SYSTEM$CLASSIFY or EXTRACT_SEMANTIC_CATEGORIES on tables to identify sensitive columns automatically.
2
Review: Examine classification results (semantic_category, privacy_category, probability). Accept or override recommendations.
3
Apply Tags: Use ASSOCIATE_SEMANTIC_CATEGORY_TAGS to apply Snowflake system tags, or apply custom tags manually.
4
Attach Policies: Create masking/row access policies and attach them to tags (tag-based) or directly to columns.
5
Monitor: Use POLICY_REFERENCES, TAG_REFERENCES, and ACCESS_HISTORY to audit and verify coverage.
-- Complete workflow example:

-- 1. Detect
SELECT * FROM TABLE(
  EXTRACT_SEMANTIC_CATEGORIES('prod_db.public.customers')
);

-- 2. Review (examine output)
-- Column: email → semantic: EMAIL, privacy: IDENTIFIER, prob: 0.98
-- Column: age → semantic: AGE, privacy: QUASI_IDENTIFIER, prob: 0.85

-- 3. Apply system tags
CALL ASSOCIATE_SEMANTIC_CATEGORY_TAGS(
  'prod_db.public.customers',
  EXTRACT_SEMANTIC_CATEGORIES('prod_db.public.customers')
);

-- 4. Create tag-based masking policy
CREATE MASKING POLICY mask_identifiers AS (val VARCHAR) RETURNS VARCHAR ->
  CASE
    WHEN IS_ROLE_IN_SESSION('GOVERNANCE_ADMIN') THEN val
    ELSE '***MASKED***'
  END;

-- Attach to system tag
ALTER TAG SNOWFLAKE.CORE.PRIVACY_CATEGORY
  SET MASKING POLICY mask_identifiers;

-- 5. Verify
SELECT * FROM TABLE(INFORMATION_SCHEMA.POLICY_REFERENCES(
  POLICY_NAME => 'mask_identifiers'
));

7. External Tokenization

What is External Tokenization?

External tokenization replaces sensitive values with tokens using an external service (e.g., Protegrity, Voltage, Thales). Snowflake uses External Functions (via API integrations) combined with Secure UDFs to tokenize/detokenize data.

  • Tokenized data is stored in Snowflake (token replaces real value)
  • Detokenization requires calling the external service
  • Masking policy wraps the external function — only authorized roles can detokenize
  • Tokens are format-preserving (SSN token looks like an SSN)
-- External function for tokenization
CREATE EXTERNAL FUNCTION tokenize(val VARCHAR)
  RETURNS VARCHAR
  API_INTEGRATION = tokenization_api
  AS 'https://tokenize-service.example.com/tokenize';

CREATE EXTERNAL FUNCTION detokenize(val VARCHAR)
  RETURNS VARCHAR
  API_INTEGRATION = tokenization_api
  AS 'https://tokenize-service.example.com/detokenize';

-- Masking policy using external detokenization
CREATE MASKING POLICY token_policy AS (val VARCHAR) RETURNS VARCHAR ->
  CASE
    WHEN IS_ROLE_IN_SESSION('PII_ACCESS')
      THEN detokenize(val)  -- authorized users see real data
    ELSE val  -- everyone else sees the token (already tokenized at rest)
  END;

-- Apply to column containing tokenized data
ALTER TABLE customers ALTER COLUMN ssn_token SET MASKING POLICY token_policy;
Key Difference: With dynamic masking, real data is stored and masked at query time. With tokenization, tokens are stored at rest, and real data is only retrieved via the external service for authorized users. Tokenization provides stronger protection for data at rest.

9. Production Best Practices

Best Practices for Data Security Policies
  1. Use IS_ROLE_IN_SESSION() instead of CURRENT_ROLE() — respects hierarchy
  2. Use tag-based policies for scalability — avoid per-column policy assignment
  3. Centralize governance objects in a dedicated database (e.g., GOVERNANCE_DB)
  4. Use mapping tables for row access policies — allows dynamic changes without DDL
  5. Run SYSTEM$CLASSIFY regularly as new tables are created
  6. Monitor with POLICY_REFERENCES to ensure complete coverage
  7. Test policies by switching roles: USE ROLE analyst; SELECT * FROM table;
  8. Document policy intent using COMMENT on the policy object
  9. Separate creation from application (different roles for each)
  10. Performance: avoid subqueries in RAP that hit large mapping tables without proper indexing
  11. Use conditional logic in one policy rather than multiple policies (only 1 allowed per column)
  12. Audit regularly with ACCESS_HISTORY to verify policies work as intended
Common Mistakes to Avoid
  • Using CURRENT_ROLE() and expecting hierarchy to work (it won't!)
  • Trying to stack multiple masking policies on one column
  • Expecting tags to propagate from schema to tables automatically
  • Forgetting that masking uses SET and RAP uses ADD
  • Not granting APPLY privileges (creating policy is not enough)
  • Testing only with ACCOUNTADMIN (always test with the analyst role)
  • Masking a column then wondering why a JOIN stops working (hash pattern helps)
  • Ignoring RAP performance impact on large tables with complex subqueries
