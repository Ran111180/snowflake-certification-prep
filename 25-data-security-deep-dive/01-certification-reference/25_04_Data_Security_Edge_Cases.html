Data Security - Edge Cases & Exam Scenarios

Critical gotchas, tricky behaviors, and complex scenarios that appear on the certification exam.

Edge Case 1: Only ONE Masking Policy Per Column

The Rule

A column can have at most one masking policy applied at any time. You cannot layer multiple policies on the same column.

What About Tag-Based?

If a column has BOTH a direct policy and a tag-based policy, the direct policy wins. The tag-based policy is effectively ignored for that column.

If you try to SET a second masking policy on a column that already has one, you get an error. You must UNSET the first policy before applying a new one.
-- This FAILS if email already has a policy: ALTER TABLE t ALTER COLUMN email SET MASKING POLICY new_policy; -- Error: Column 'EMAIL' already has a masking policy -- Correct approach: force replace ALTER TABLE t ALTER COLUMN email SET MASKING POLICY new_policy FORCE; -- OR: unset then set ALTER TABLE t ALTER COLUMN email UNSET MASKING POLICY; ALTER TABLE t ALTER COLUMN email SET MASKING POLICY new_policy;

Edge Case 2: Only ONE Row Access Policy Per Table

The Rule

Each table or view can have at most one row access policy. To change it, drop the old one first.

You cannot combine multiple RAPs. If you need complex logic, put it all in one policy using AND/OR conditions or mapping tables.
-- This FAILS if table already has a RAP: ALTER TABLE t ADD ROW ACCESS POLICY rap2 ON (col); -- Error: Table already has a row access policy -- Must drop first: ALTER TABLE t DROP ROW ACCESS POLICY rap1; ALTER TABLE t ADD ROW ACCESS POLICY rap2 ON (col);

Edge Case 3: CURRENT_ROLE() vs IS_ROLE_IN_SESSION()

The Critical Difference

CURRENT_ROLE()

  • Returns the single active role name
  • Does NOT check inherited roles
  • String comparison only
  • If role is ANALYST and ANALYST inherits DATA_VIEWER, checking CURRENT_ROLE() = 'DATA_VIEWER' returns FALSE

IS_ROLE_IN_SESSION()

  • Returns TRUE/FALSE
  • Checks current role AND all inherited roles
  • Respects full role hierarchy
  • If role is ANALYST and ANALYST inherits DATA_VIEWER, IS_ROLE_IN_SESSION('DATA_VIEWER') returns TRUE
Using CURRENT_ROLE() in masking policies is the #1 source of "my policy doesn't work" bugs. When a user activates a parent role (e.g., SYSADMIN), CURRENT_ROLE() only matches 'SYSADMIN' - not any child roles. IS_ROLE_IN_SESSION() is almost always what you want.
-- BAD: Breaks when using parent roles CASE WHEN CURRENT_ROLE() = 'DATA_ADMIN' THEN val ... -- GOOD: Works with role hierarchy CASE WHEN IS_ROLE_IN_SESSION('DATA_ADMIN') THEN val ... -- Role hierarchy example: -- ACCOUNTADMIN → SYSADMIN → DATA_ADMIN → ANALYST -- If current role is SYSADMIN: -- CURRENT_ROLE() = 'SYSADMIN' ✓ -- IS_ROLE_IN_SESSION('SYSADMIN') = TRUE ✓ -- IS_ROLE_IN_SESSION('DATA_ADMIN') = TRUE ✓ (inherited) -- CURRENT_ROLE() = 'DATA_ADMIN' → FALSE ✗ (not current!)

Edge Case 4: Policy on VARIANT (Whole Column Only)

The Constraint

You cannot mask individual keys/paths within a VARIANT, OBJECT, or ARRAY column. The masking policy applies to the entire column.

If you need to mask specific fields inside a VARIANT (e.g., mask $.email but show $.name), you must restructure the data into separate columns, OR use a view that extracts and masks specific paths.
-- This works: mask entire VARIANT column CREATE MASKING POLICY variant_mask AS (val VARIANT) RETURNS VARIANT -> CASE WHEN IS_ROLE_IN_SESSION('DATA_ADMIN') THEN val ELSE NULL -- entire VARIANT becomes NULL END; -- Workaround: Use a secure view with selective extraction CREATE SECURE VIEW safe_data AS SELECT id, raw_json:"name"::VARCHAR AS name, -- visible CASE WHEN IS_ROLE_IN_SESSION('PII_ADMIN') THEN raw_json:"email"::VARCHAR ELSE '***' END AS email -- masked FROM raw_table;

Edge Case 5: Shared Data Policies

Provider vs Consumer

AspectBehavior
Policy ownershipProvider owns and controls all policies
Consumer overrideConsumer CANNOT override or remove provider policies
Role evaluationProvider's policy evaluates against CONSUMER's roles
Mapping tablesMust be in provider's account (consumer can't access provider tables)
IS_ROLE_IN_SESSION()Evaluates consumer's session roles
CURRENT_ROLE() in a shared data masking policy evaluates the CONSUMER's current role, not the provider's. The policy logic must anticipate consumer role names, or use a more flexible approach like mapping tables shared alongside the data.

Edge Case 7: Tag Propagation (Not Inherited)

Tags Are NOT Inherited

A tag on a database does NOT flow down to schemas, tables, or columns within it. Every object must be tagged explicitly.

ActionResult
Tag database as 'CONFIDENTIAL'Only database has the tag; tables/columns do NOT
Tag table as 'PII'Only the table object has tag; columns do NOT
Clone a tagged tableClone RETAINS the tag assignments
CTAS from a tagged tableNew table does NOT get tags
Tag lineage in viewsTags on base table columns are visible through TAG_REFERENCES on the view
Many people assume tagging a database = all contents are tagged. This is FALSE. You must tag each object/column individually or use SYSTEM$CLASSIFY with auto_tag for column-level classification.

10 Exam Scenarios

Scenario 1+

A company has role hierarchy: ACCOUNTADMIN > SYSADMIN > DATA_ADMIN > ANALYST. They create this masking policy:

CREATE MASKING POLICY ssn_mask AS (val VARCHAR) RETURNS VARCHAR -> CASE WHEN CURRENT_ROLE() = 'DATA_ADMIN' THEN val ELSE 'XXX-XX-XXXX' END;

Question: A user with SYSADMIN as their current role queries the table. Do they see unmasked SSN values?

NO - they see masked values. CURRENT_ROLE() returns 'SYSADMIN', which does NOT equal 'DATA_ADMIN'. Even though SYSADMIN inherits DATA_ADMIN, CURRENT_ROLE() does not check hierarchy. The fix is to use IS_ROLE_IN_SESSION('DATA_ADMIN').
Scenario 2+

A table has a masking policy applied directly to the EMAIL column. The same column also has a tag (pii_type = 'EMAIL') which has a DIFFERENT masking policy attached to it.

Question: Which masking policy is enforced?

The direct column policy wins. When both a direct masking policy and a tag-based masking policy apply to the same column, the direct policy takes precedence. The tag-based policy is effectively ignored for that column.
Scenario 3+

An analyst runs: SELECT COUNT(*) FROM sales WHERE region = 'EMEA';

The table has a row access policy that only shows US data to the ANALYST role.

Question: What does the query return?

Returns 0 (zero). The RAP filters out all EMEA rows before the WHERE clause is evaluated. The analyst only sees US rows, so COUNT(*) WHERE region='EMEA' returns 0. There is no error - the rows simply don't exist from the analyst's perspective.
Scenario 4+

A developer creates a CTAS:

CREATE TABLE new_customers AS SELECT * FROM customers;

The source table 'customers' has masking policies on email and ssn columns.

Question: Does new_customers have masking policies?

NO - the new table does NOT have masking policies. CTAS does not carry policy assignments. Furthermore, if the developer's role doesn't have access to unmasked data, the new table will contain MASKED values as actual data! Double danger: no policies AND potentially masked data stored permanently.
Scenario 5+

A table has BOTH a row access policy AND a masking policy on the salary column. An analyst queries the table.

Question: What order are they applied?

Row access policy FIRST, then masking policy. Order: (1) RAP filters which rows are visible, (2) Masking policy masks column values on the visible rows. The analyst only sees rows allowed by RAP, and within those rows, salary is masked according to the masking policy.
Scenario 6+

Provider shares a table with a masking policy. The consumer's ANALYST role queries it. The masking policy says:

CASE WHEN CURRENT_ROLE() = 'DATA_ADMIN' THEN val ELSE '***' END

Question: The consumer creates a role called DATA_ADMIN. Can they see unmasked data?

YES - they CAN see unmasked data! The policy evaluates CURRENT_ROLE() against the consumer's session. If the consumer creates a role named 'DATA_ADMIN' and uses it, the condition matches. This is a security risk - providers should use INVOKER_SHARE() or more secure patterns instead of role name matching for shared data.
Scenario 7+

A masking policy is applied to a column. The column contains some NULL values.

CREATE MASKING POLICY mask AS (val VARCHAR) RETURNS VARCHAR -> CASE WHEN IS_ROLE_IN_SESSION('ADMIN') THEN val ELSE 'HIDDEN' END;

Question: What do non-ADMIN users see for NULL values?

They see 'HIDDEN' (not NULL). NULL values go through the CASE statement like any other value. Since IS_ROLE_IN_SESSION('ADMIN') is FALSE, the ELSE branch returns 'HIDDEN'. To preserve NULLs: add WHEN val IS NULL THEN NULL before the ELSE.
Scenario 8+

A user queries a table using Time Travel: SELECT * FROM customers AT(OFFSET => -3600);

The masking policy was CHANGED 30 minutes ago (within the 1-hour offset). Previously it allowed ANALYST to see data; now it blocks ANALYST.

Question: Does the ANALYST role see unmasked historical data?

NO - the CURRENT policy applies to Time Travel data. Even though the data is from 1 hour ago when the old policy was in effect, Snowflake evaluates the CURRENT version of the masking policy against historical data. There is no "policy time travel."
Scenario 9+

A column has data type NUMBER(10,2). A masking policy is created:

CREATE MASKING POLICY num_mask AS (val NUMBER) RETURNS VARCHAR -> CASE WHEN IS_ROLE_IN_SESSION('FINANCE') THEN val::VARCHAR ELSE '***' END;

Question: Can this policy be applied to the NUMBER column?

NO - this will fail. The input type is NUMBER but the return type is VARCHAR. Input and output types MUST match. The correct approach: AS (val NUMBER) RETURNS NUMBER -> CASE WHEN ... THEN val ELSE NULL END; (return NULL or a sentinel number like -1).
Scenario 10+

You tag a database: ALTER DATABASE prod SET TAG sensitivity = 'HIGH';

Then you create a new table in that database.

Question: Does the new table inherit the 'sensitivity = HIGH' tag?

NO - tags do NOT inherit/propagate. The tag is only on the database object itself. New tables, existing tables, schemas, and columns within the database do NOT automatically receive the tag. Each must be tagged explicitly. This is one of the most commonly misunderstood behaviors.
